# เทมเพลตบรีฟการมอบหมายงาน

ต้นฉบับของรูปแบบชั้น B ([docs/07](../docs/07-delegation-brief.md)) ทุกครั้งที่มอบหมายงาน ให้คัดลอกเนื้อหาด้านล่างไปใส่ในข้อความคำขอแล้วกรอกให้ครบ สตริงหัวข้อเป็นเป้าหมายของการตรวจสอบด้วยเครื่อง ดังนั้นห้ามเปลี่ยนจากรูปแบบที่แต่ละบ้านกำหนดไว้ ([B-5](../docs/07-delegation-brief.md))

## เนื้อหาบรีฟ (B-1)

```markdown
## 実装仕様

<!-- Goal: 何を作る / 直すかを1〜3行で。担当 Issue: #番号 or URL（B-3: Issue が正本） -->
<!-- 触ってよい範囲: ファイル / ディレクトリの列挙（Issue のファイル予測と一致させる）。範囲外は触らない -->
<!-- 前積みの文脈: 必要な事実・パス・仕様・制約・環境の癖。委譲先に探索させない（B-4） -->
<!-- 納品形式: 出力先ファイルのパス・報告の分量・報告に含めるもの -->

## 実装チェック

<!-- 納品前に作業者自身が回す検証。機械判定できる形で書く -->
- [ ] テスト / lint green（実行コマンドと期待結果を明記）
- [ ] 追加・変更したテストと実行結果を報告に含める（T-3。前項が「緑になった」の確認・本項は「何を足したか」の目録。テスト追加なしは T-3 の閉じた列挙に従う理由を含める）
- [ ] 触ってよい範囲の外に diff がない
- [ ] （タスク固有の検証項目）

## レビュー基準

<!-- 後段のレビューが見る観点。作業者にも最初から見せる -->
- 正しさ: <このタスクで「正しい」とは何か>
- 境界: 宣言ファイル集合の内側に収まっているか
- 最悪の失敗形: <この変更で一番まずいのは◯◯が起きること（B-4: 名指しする）>
```

## ประเด็นสำคัญในการเขียน

- **เขียนโดยตั้งสมมติฐานว่าผู้รับมอบหมายอ่านประวัติการสนทนาของฝั่งเราไม่ได้** (fresh context) คำว่า "ตามแนวทางเมื่อกี้" หรือ "เรื่องนั้นน่ะ" ถือว่าไม่มีอยู่จริง
- **ต้องรักษาความเป็น blind สำหรับบรีฟที่ส่งไปยังที่นั่งรีวิวอิสระ** (B-4): ส่งบรีฟเดียวกันให้ทุกที่นั่ง โดยไม่ผสมข้อสังเกตจากที่นั่งอื่น การวิเคราะห์ล่วงหน้าของตัวเอง หรือข้อสรุปที่คาดหวังไว้เข้าไป
- **อย่าฝังเนื้อหายาวไว้ในข้อความคำขอโดยตรง**: สามารถวางเนื้อหาไว้ในไฟล์แล้วส่งเพียง "อ่าน <path> แล้วปฏิบัติตาม" ในข้อความคำขอแทนได้ เพราะบางสภาพแวดล้อมการทำงานอาจมีข้อจำกัดความยาวของ argument จนทำให้คำขอเงียบหายไปโดยไม่มีการแจ้งเตือน
- **การ retry มีจำกัด** ([L1-6](../docs/02-issue-loop.md)): อย่ามอบหมายซ้ำด้วยบรีฟเดิม ให้เพิ่มข้อสังเกตจากความล้มเหลวเข้าไปในบริบทที่เตรียมไว้ล่วงหน้าแล้วมอบหมายใหม่ หากยังไม่สำเร็จอีกจนหมดจำนวนครั้งที่กำหนด ให้หยุดพร้อมแนบหลักฐานประกอบ
