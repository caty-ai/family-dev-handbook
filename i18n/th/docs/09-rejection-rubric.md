# R ระดับการปฏิเสธ (Rejection Rubric) — ชั้นของสิ่งที่รับและสิ่งที่ปฏิเสธ

ในขณะที่ชั้น L (L2 / L1 / L0) เป็นสัญญาว่า "จะดำเนินการอย่างไร" และชั้น B เป็นสัญญาว่า "จะขอความช่วยเหลืออย่างไร" ชั้น R กำหนดสัญญาเรื่องเจตนาว่า**อะไรจะถูก merge และอะไรจะถูกปฏิเสธ** วิธีใช้มี 2 แบบ:

1. **สำหรับฝ่ายผู้สร้าง** — เพื่อให้การมีส่วนร่วม (รวมถึงข้อเสนอ งาน และ PR ที่มาจาก agent) สามารถเล็งเป้าหมายได้ตรงจุด
2. **สำหรับการตัดสินใจขั้นแรก** — เป็นแนวทางว่าเมื่อไรควรปิดโดยไม่ต้องรอการตัดสินใจของมนุษย์ และสิ่งที่สำคัญพอกันคือ "เมื่อไรไม่ควรปิด"

ระดับความเป็นข้อบังคับแตกต่างกันไปตามแต่ละข้อ: **R-1 / R-4 / R-5 / R-6 คือสัญญา**, **R-2 / R-3 คือรายการเกณฑ์สำหรับการตัดสินใจรับ** และการบังคับใช้การปฏิเสธที่อ้างอิง R-2 / R-3 จะต้องผ่านกฎวินัยเรื่องอำนาจของ R-1 เสมอ (การตัดสินคุณค่าเป็นสิทธิ์เฉพาะของ owner)

แต่ละกฎมี rule ID ที่คงที่ (`R-1`〜`R-6`) และข้อย่อยจะอ้างอิงด้วย ①②③… (รูปแบบเดียวกับ [E-6](06-epic-lane.md)①) ฝั่งสรุป ([docs/04](04-adoption.md)) จะอ้างอิง ID นี้ ท่าทีเมื่อไม่สามารถตรวจสอบได้ ดูที่ [docs/05](05-fail-posture.md)

## R-1 เหตุผล 3 ข้อสำหรับการปฏิเสธอัตโนมัติ — การตัดสินคุณค่าเป็นสิทธิ์เฉพาะของ owner

**ใช้กับข้อเสนอที่ถูกบันทึกไว้ (Issue, PR, ข้อเสนองานที่ถูกส่งเป็นบันทึก)** เท่านั้น สิ่งที่จะปฏิเสธได้โดยไม่ต้องมีการตัดสินใจของมนุษย์คือ**เฉพาะเหตุผล 3 ข้อที่ตัดสินได้อย่างชัดเจนด้วยกลไก**เท่านั้น แต่ละเหตุผลจะสมบูรณ์ก็ต่อเมื่อมีเงื่อนไขและหลักฐานประกอบ:

1. **มีอยู่แล้วใน main** (implemented on main) — ต้องชี้ไปยัง commit หรือบรรทัดที่แสดงว่าพฤติกรรมดังกล่าวมีอยู่ใน main ปัจจุบัน "มีสิ่งที่คล้ายกันในเชิงฟังก์ชัน" ไม่นับรวมในเหตุผลนี้ (นั่นคือการตัดสินคุณค่า = สิทธิ์เฉพาะของ owner)
2. **ไม่สามารถทำซ้ำได้** (cannot reproduce) — **จำกัดเฉพาะรายงานบั๊ก** ต้องมีบันทึกการพยายามทำซ้ำกับ main ปัจจุบัน (คำสั่ง / ขั้นตอน, ผลที่สังเกตได้, วันที่) ข้อมูลไม่เพียงพอไม่ใช่เหตุผลสำหรับการปฏิเสธ — ให้สอบถามและรอไว้ก่อน
3. **เนื้อหาไม่ปรากฏ** (incoherent) — จำกัดเฉพาะกรณีที่ไม่สามารถอ่านเนื้อหาที่มีสาระได้ เช่น ความขัดแย้ง ช่องว่าง สแปม ฯลฯ และ**เฉพาะเมื่อผ่านการสอบถาม 1 ครั้งแล้วก็ยังอ่านไม่ได้**เท่านั้น ข้อเสนอที่แค่อ่านยากไม่เข้าข่ายนี้

- การปฏิเสธด้วยการตัดสินคุณค่า เช่น "ไม่จำเป็น・ขัดกับนโยบาย・นอกขอบเขต" เป็น**สิทธิ์เฉพาะของ owner (มนุษย์)** agent ทำได้เพียงเสนอแนะพร้อมเหตุผลแล้วส่งขึ้นไปเท่านั้น (การปฏิเสธที่อ้างอิง R-2 / R-3 ก็เช่นกัน — ไม่รวมอยู่ในเหตุผล 3 ข้อ)
- **ถ้าลังเลใจ อย่าปิด** — "การปิด" คือการใช้อำนาจ หากตรวจสอบไม่ได้ ให้เอียงไปทางที่อำนาจลดลง (เปิดไว้แล้วส่งให้ owner) (ทิศทางเดียวกับ [FP-7](05-fail-posture.md)) หน้าที่ของการตัดสินใจขั้นแรกคืออ่านเจตนาการออกแบบและ**ไม่ปิดการมีส่วนร่วมที่ชอบธรรมโดยผิดพลาด**
- **การบันทึก**: การจบของข้อเสนอที่มี lane ตั้งขึ้นแล้ว (ประกาศ WIP แล้ว) ให้ใช้คำศัพท์ 5 คำของ [L1-4](02-issue-loop.md) **ข้อเสนอที่ถูกปฏิเสธก่อนที่ lane จะตั้งขึ้นไม่ใช้คำศัพท์ของ lane** ให้บันทึกเพียงเหตุผลการปิด (หนึ่งในเหตุผล 3 ข้อ + หลักฐานข้างต้น หรือลิงก์ไปยังคำตัดสินของ owner)
- **การเปิดใหม่ไม่สมมาตร**: การปิดด้วยเหตุผล 3 ข้อสามารถเปิดใหม่ได้โดยไม่ต้องได้รับอนุมัติจาก owner หากมีหลักฐานใหม่ปรากฏขึ้น (การเปิดใหม่เป็นทิศทางที่อำนาจลดลง)
- ข้อเสนอที่แตะรูปแบบทั้ง 4 ของ R-4 เป็นตัวอย่างทั่วไปที่การปิดอัตโนมัติด้วยเหตุผล 3 ข้อ**ไม่ปลอดภัย** — ต้องส่งให้มนุษย์
- การตัดสินใจปฏิเสธระหว่าง Epic กำลังดำเนินอยู่ ให้ส่งให้ owner **แบบ asynchronous โดยไม่หยุด lane** (ไม่เพิ่มจุดหยุดของ [E-3](06-epic-lane.md))

## R-2 การมีส่วนร่วมที่ยินดีต้อนรับ — 6 ข้อ

1. **แก้บั๊กจริง ให้ครอบคลุมทั้งคลาส** — ทำซ้ำอาการใน main ปัจจุบัน ชี้ไปยังบรรทัดที่ปรากฏ และแก้ไม่เฉพาะจุดที่รายงานแต่รวมถึง path การเรียกใช้ที่เป็นพี่น้องกันด้วย (คู่ตรงข้ามกับคำขวัญของ R-4)
2. **ขยายที่ปลาย รักษาที่แกน** — การมีส่วนร่วมที่ขยายส่วนปลาย (ฟังก์ชันของแต่ละผลิตภัณฑ์・แต่ละบ้าน) เป็นที่ยินดีต้อนรับ การควบคุมมุ่งไปที่แกน (โครงสร้างพื้นฐานร่วมของครอบครัว・จุดที่ทุกคนต้องแบกต้นทุนถาวร) เท่านั้น "footprint น้อยที่สุด" เป็นเรื่องของการเดินสายไปยังแกน ไม่ใช่เรื่องว่าผลิตภัณฑ์จะเติบโตได้หรือไม่
3. **การ refactor ที่ประกาศไว้ ยินดีต้อนรับแม้ diff จะใหญ่** — การตรวจสอบว่า "ทุกบรรทัดสามารถสืบย้อนไปยังคำขอได้" ใช้กับการเปลี่ยนแปลงฟังก์ชัน ส่วนคำขอเปลี่ยนแปลงที่ประกาศเป็น refactor นั้นคือการสกัดโดยตัวมันเอง (การแยกจุดร้อน = การลงทุนตาม [L2-6](01-milestone-loop.md)) **สิ่งที่ผ่อนปรนมีเพียงความสงสัยต่อขนาดของ diff เท่านั้น** — ชุดไฟล์ที่ประกาศ ([L0-2](03-git-protocol.md) default-deny) และการตรวจสอบ diff ตาม [L1-7](02-issue-loop.md)④ ไม่ผ่อนปรนแม้แต่น้อยแม้จะเป็น refactor (refactor คือการประกาศคาดการณ์ไฟล์ที่จะแตะอย่างกว้างขวางแล้วผ่าน ไม่ใช่การผ่านโดยละเว้นการประกาศ) การรัน refactor ขนาดกว้างแบบเดี่ยว ([L2-5](01-milestone-loop.md)) และขั้นตอนการ merge ([L0-7](03-git-protocol.md)) ก็ยังคงใช้เหมือนเดิม
4. **ขยาย ไม่ทำซ้ำ** — ก่อนเพิ่ม module・manager・hook ใหม่ ให้ตรวจสอบก่อนว่าเครื่องมือที่มีอยู่ใช้งานได้หรือไม่ (ตำแหน่งที่จะวางดูที่ R-5)
5. **test ต้องยืนยัน invariant** — ตรวจสอบว่า "ข้อมูลสองชุดควรสัมพันธ์กันอย่างไร" ไม่เขียน change-detection test ที่แช่แข็งค่าปัจจุบัน (รายการ・จำนวน・เวอร์ชันที่เขียนตรงๆ)
6. **ตรวจสอบ boundary・propagation・I/O ด้วย path จริง** — การเปลี่ยนแปลงที่แตะ resolution chain・การส่งผ่าน configuration・permission boundary・I/O ภายนอก ต้องแสดงหลักฐานแบบ E2E ที่รัน path จริง อย่าทำให้ green ที่มาจาก mock อย่างเดียวเป็นความสมบูรณ์ **ข้อนี้เป็นแนวทางการเลือกหลักฐาน ต้นฉบับของข้อกำหนด merge gate ยังคงเป็น [L1-7](02-issue-loop.md)** (ไม่เพิ่มข้อกำหนด)

## R-3 สิ่งที่ปฏิเสธแม้จะทำได้ดี — 7 ข้อ

สิ่งเหล่านี้ปฏิเสธด้วย**การตัดสินใจเชิงโครงสร้าง** ไม่ใช่มาตรฐานคุณภาพ แม้จะทำได้ดีเพียงใด เหตุผลของการปฏิเสธก็ไม่หายไป **การปฏิเสธที่อ้างอิงข้อนี้ไม่รวมอยู่ในเหตุผล 3 ข้อของ R-1 — การบังคับใช้เป็นสิทธิ์เฉพาะของ owner เสมอ** agent ทำได้เพียงชี้ข้อสงสัยที่เข้าข่ายแล้วส่งขึ้นไป:

1. **โครงสร้างพื้นฐานเชิงเก็งกำไร** — hook・callback・extension point ที่ไม่มีผู้ใช้ที่ชัดเจน หากมี use case จริงที่ระบุไว้ ก็ไม่ใช่การเก็งกำไร (แม้ผู้ใช้จะอยู่ใน repo อื่นก็ได้)
2. **การเพิ่ม environment variable สำหรับ configuration ที่ไม่ใช่ความลับ** — ที่เก็บความลับ (.env ฯลฯ) ใช้เฉพาะความลับ ส่วนการตั้งค่าพฤติกรรม (timeout・threshold・flag・การแสดงผล) ให้ไปที่ configuration file
3. **skill・hook・ระบบประจำที่สร้างใหม่ทั้งที่เครื่องมือที่มีอยู่เพียงพอแล้ว** — การสร้างใหม่ที่ไม่มีบันทึกการพิจารณาบันไดของ R-5 จากขั้นต่ำสุดก่อน จะถูกปฏิเสธ
4. **ทางลัดสำหรับการอ่านแบบขี้เกียจสำหรับสิ่งที่ควรอ่านทั้งหมด** — อย่าใส่ตัวเลือกแบ่งหน้า・ตัดตอนให้กับ loader ของเนื้อหาที่ agent ควรอ่านทั้งหมด (skill・prompt・คู่มือ) เพราะจะทำให้อ่านแค่หน้าแรกแล้วข้ามที่เหลือ
5. **"การแก้ไข" ที่ทำลายฟังก์ชันที่ควรถูกปกป้อง** — มาตรการบรรเทาที่ฆ่าจุดประสงค์ของฟังก์ชันคือมาตรการบรรเทาที่ผิด ก่อนจำกัดพฤติกรรม ให้อ่านเจตนาของ commit เดิม (`git log -p -S`)
6. **การเดินสายโดยไม่มีการพิสูจน์・telemetry ที่ไม่ใช่ความลับโดยไม่ได้รับอนุญาต** — code ที่ถูกเดินสายโดยไม่มีการพิสูจน์ E2E・branch ที่ไม่เคยถูกรันในเวลาทำงานจริง・telemetry ขาออก / การติด identifier ที่ไม่มี opt-in gate (**รวมถึงข้อมูลการใช้งานที่ไม่ใช่ความลับ**) การส่งข้อมูลความลับออกภายนอกไม่ใช่ขอบเขตของข้อนี้ **แต่เป็นไปตาม [E-5](06-epic-lane.md) และวินัยความลับของแต่ละบ้าน — ข้อนี้ไม่เปลี่ยนขอบเขตของรายการห้ามแบบปิดของ E-5**
7. **การผนวกเครื่องมือภายนอก・ผลิตภัณฑ์ของผู้อื่นเข้ามาใน core tree** — ภาระในการดูแลรักษาจะตกมาที่ฝั่งเราถาวร ให้วางไว้ใน wrapper・ที่เก็บที่แยกออกไป (เช่น: directory สำหรับกักเก็บ・repo แยกที่บริหารจากภายนอก — ตัวอย่างไม่ใช่ข้อบังคับ) และไม่นำเข้า core นี่คือการตัดสินใจเรื่องการเชื่อมต่อและการดูแลรักษา แม้คุณภาพจะสูงก็ปฏิเสธอยู่ดี

## R-4 การตรวจสอบสมมติฐาน — ก่อนจะเรียกว่าบั๊ก

คำขวัญ: **"ถ้าชี้บรรทัดที่บั๊กปรากฏไม่ได้ แสดงว่าสมมติฐานยังไม่ผ่านการตรวจสอบ"**

เหตุผลอันดับต้นๆ ที่การเปลี่ยนแปลงที่ทำได้ดีถูกปฏิเสธ ไม่ใช่เรื่องคุณภาพ แต่เป็นเพราะสร้างอยู่บน**สมมติฐานที่ผิด** หรือ**ปฏิบัติต่อการออกแบบที่ตั้งใจไว้ว่าเป็นข้อบกพร่อง** รูปแบบทั้ง 4 ต่อไปนี้ทำงานได้ทั้งสองทิศทาง — สอนตำแหน่งที่ควรพิจารณาอย่างละเอียดให้กับ review seat และสอนว่าเมื่อไรไม่ควรปิดให้กับการตัดสินใจขั้นแรก:

1. **เป็นการออกแบบที่ตั้งใจ ไม่ใช่ข้อบกพร่อง** — ข้อจำกัดที่ดูเหมือนการมองข้ามมักเป็นสิ่งที่ตั้งใจ ก่อนแก้ไข ให้ตั้งคำถามว่า "การแยกส่วนนี้เองไม่ใช่การออกแบบหรือ?" และอ่านเจตนาของ commit เดิม
2. **สมมติฐานไม่เป็นจริงเมื่อเทียบกับวิธีการทำงานจริง** — ก่อนยอมรับคำกล่าวอ้าง ให้ trace code จริง・การทำงานที่ runtime หากไม่สามารถแสดงได้ว่าการแก้ไขเปลี่ยนพฤติกรรมของบรรทัดใด แสดงว่ายังไม่ผ่านการตรวจสอบ
3. **การไม่มีอยู่เองคือสิ่งที่ค้ำจุนน้ำหนัก** — การเพิ่มชิ้นส่วนที่ดู "ขาดหายไปอย่างชัดเจน" อาจทำลายสิ่งที่การละเว้นนั้นกำลังปกป้องอยู่
4. **การทำเกินไป・การรื้อฟื้นนโยบายที่ผ่านพ้นไปแล้ว** — การขยายที่เกิน baseline ที่ตกลงกันไว้ หรือการรื้อฟื้นทิศทางที่ปิดไว้โดยตั้งใจ จะถูกปฏิเสธแม้จะใช้งานได้จริง ให้จำกัดการเปลี่ยนแปลงไว้ในส่วนแคบที่ตกลงกัน และเสนอส่วนที่เหลือเป็น follow-up

เนื้อหาหลัก: **ตรวจสอบทั้งคำกล่าวอ้างและเจตนากับ codebase จริง ก่อนเขียนโค้ด・ก่อน merge เสมอ** การทำซ้ำที่ยืนยันแล้ว + คำอธิบายระดับบรรทัด ชนะทฤษฎีที่ฟังดูสมเหตุสมผลได้เสมอ หากลังเลใจเรื่องเจตนา การถามย่อมถูกกว่าการเสนอการแก้ไขที่ขัดแย้งกับการออกแบบ

(ตัวอย่างจริงสามารถแทนที่ด้วยบันทึกอุบัติเหตุของแต่ละบ้านได้ — ตัวอย่างในเนื้อหาไม่ใช่ข้อบังคับ เมื่อมอบหมาย review ให้ สามารถนำรูปแบบทั้ง 4 นี้ไปวางไว้ล่วงหน้าเป็นมุมมองของ "การระบุรูปแบบความล้มเหลวที่เลวร้ายที่สุด" ตาม [B-4](07-delegation-brief.md))

## R-5 บันไดของตำแหน่งที่วาง — พื้นที่ผิวถาวรน้อยที่สุดที่ขั้นต่ำสุด

เมื่อสร้างความสามารถใหม่ ยิ่งขั้นล่างเท่าไร พื้นที่ผิวถาวร (ต้นทุนที่ทุกคนต้องจ่ายต่อเนื่อง) จะยิ่งเพิ่มขึ้น **เลือกขั้นที่หมายเลขน้อยที่สุดที่สามารถแก้ปัญหาได้อย่างถูกต้อง**:

1. **ขยาย code ที่มีอยู่แล้ว** — หากเป็นตัวแปรของสิ่งที่มีอยู่แล้ว พื้นที่ผิวใหม่จะเป็นศูนย์
2. **script / skill** — การดำเนินการที่แสดงได้ด้วย shell ไม่ประจำอยู่・ทำงานเฉพาะเมื่อถูกเรียก
3. **hook ที่มี conditional gate** — automation ที่ปรากฏเฉพาะเมื่อเงื่อนไขเบื้องต้นถูกตั้งค่าเท่านั้น
4. **เพิ่มฟังก์ชันเข้าไปใน repo ที่มีอยู่** — หากมีตำแหน่งที่วางอยู่แล้ว ให้วางที่นั่น
5. **แยกเป็น MCP server・repo อื่น** — หากเป็นความสามารถที่เป็นอิสระจริงๆ ให้อยู่นอก core
6. **repo ใหม่・ระบบประจำใหม่** — ทางเลือกสุดท้าย **ต้องได้รับอนุมัติจาก owner (มนุษย์)** หากเกิดกรณีเช่นนี้ระหว่าง Epic กำลังดำเนินอยู่ ให้**หยุดเป็น checkpoint พิเศษของ [E-3](06-epic-lane.md)** (ไม่เพิ่มลงในตารางหลักของ E-3)

- หากลังเลใจ ให้เลือกขั้นบน (พื้นที่ผิวน้อยที่สุด) "เพราะขั้นล่างง่ายกว่า" ไม่ใช่เหตุผล
- **เมื่อเลือกขั้นแล้ว ให้ตัดสิน exit trigger ของสิ่งที่จะวางไปพร้อมกัน** ([LC-1](08-lifecycle.md) — บันไดกำหนดตำแหน่งที่วาง LC-1 กำหนดวิธีออกไป ใช้คู่กัน)
- **ตัวที่ 3 ของประเภทเดียวกัน ให้มี common interface** — เมื่อ integration ประเภทเดียวกันรวมกันได้ 3 ตัว แทนที่จะใส่ทีละตัว ให้ออกแบบ common interface และห่อ implementation ที่มีอยู่เป็น provider ตัวแรก การออกแบบ interface เป็นการเปลี่ยน boundary จึงต้องผ่าน boundary PR ล่วงหน้าตาม [L2-2](01-milestone-loop.md)

## R-6 บังคับนโยบายด้วย check

**อย่าปล่อยให้นโยบายที่ห้ามฝ่าฝืนเป็นแค่ "คำขอร้อง"** กฎเชิงรับ (.gitignore・เอกสาร・คำสัญญาปากเปล่า) หยุดได้แค่ "ความประมาทเผลอ" เท่านั้น — นโยบายที่ต้องการบังคับใช้ ให้ยกระดับเป็น check ที่จะขึ้นสีแดงเมื่อถูกฝ่าฝืน

- **จุดกระตุ้นการยกระดับ**: เมื่อนโยบายเดียวกันถูกฝ่าฝืน 2 ครั้ง ให้เปิด Issue เพื่อทำเป็น check **บันทึกการฝ่าฝืนให้เก็บไว้ใน Issue หรือบันทึกอุบัติเหตุของแต่ละบ้าน และเปิดขึ้นเมื่อบันทึกครั้งที่ 2** (ทำให้การนับสามารถตรวจสอบย้อนหลังได้)
- check ต้อง**ตรวจจับจากเนื้อหาจริง** (match ด้วยเนื้อหา・pattern ที่แท้จริง ไม่ใช่ชื่อ directory หรือการสะกดนามสกุลไฟล์ — มีตัวอย่างจริงที่หลุดรอดไปได้เพราะสะกดผิดในที่มา)
- ท่าทีของ check ให้สอดคล้องกับข้อบังคับที่มีอยู่: **gate ที่หยุด merge เป็น fail-closed** (ทิศทางเดียวกับ [FP-3](05-fail-posture.md)), **ท่อสำหรับ report・synthesis・notification เป็น fail-open** ([FP-4](05-fail-posture.md)) check ไม่ย้ายไฟล์ ([LC-5](08-lifecycle.md) — ตรวจจับแล้วหยุดเท่านั้น・ไม่ซ่อมอัตโนมัติหรือ退蔵อัตโนมัติ)
- check ประเภทการอนุมัติ (เช่น label ของมนุษย์) ต้อง**ตรวจสอบการมีอยู่จริงของการอนุมัติ** — อย่าผ่านแค่เพราะมี text หรือ label อยู่ (ทิศทางเดียวกับ [FP-8](05-fail-posture.md)) การตรวจสอบการอนุมัติอาจมีข้อจำกัด (เช่น environment ที่ identity ใช้ร่วมกัน) — ในกรณีนั้น ให้ระบุข้อจำกัดไว้ในคำอธิบายของ check อย่างชัดเจน และอย่าแสร้งทำเป็นว่า "ตรวจสอบแล้ว" ([FP-5](05-fail-posture.md))
- ต้นฉบับของ type อยู่ที่ `templates/ci/` ของ repo นี้
