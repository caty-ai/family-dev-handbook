# R เกณฑ์การปฏิเสธ — ชั้นที่กำหนดว่าจะรับอะไร ปฏิเสธอะไร

ในขณะที่ชั้น L (L2 / L1 / L0) เป็นสัญญาว่า "จะดำเนินการอย่างไร" และชั้น B เป็นสัญญาว่า "จะขอร้องอย่างไร" ชั้น R จะกำหนดสัญญาแห่งเจตนาว่า **อะไรจะถูก merge และอะไรจะถูกปฏิเสธ** วิธีใช้มี 2 แบบ:

1. **สำหรับฝ่ายที่สร้าง** — เพื่อให้ contribution (รวมถึงข้อเสนอ งาน และ PR ที่มาจาก agent) สามารถเล็งเป้าได้ตรงจุด
2. **สำหรับการตัดสินขั้นต้น** — เป็นแนวทางว่าเมื่อไหร่ที่สามารถปิดได้โดยไม่ต้องมีการตัดสินใจของมนุษย์ และสิ่งที่สำคัญพอกันคือ "เมื่อไหร่ที่ไม่ควรปิด"

ความเข้มงวดของกฎแต่ละข้อแตกต่างกัน: **R-1 / R-4 / R-5 / R-6 คือสัญญา**, **R-2 / R-3 คือรายการเกณฑ์สำหรับการตัดสินใจรับ** และการบังคับใช้การปฏิเสธที่อ้างอิง R-2 / R-3 จะต้องผ่านวินัยเรื่องอำนาจของ R-1 เสมอ (การตัดสินใจเชิงคุณค่าเป็นสิทธิ์เฉพาะของ owner)

แต่ละกฎมี rule ID ที่มั่นคง (`R-1`〜`R-6`) และข้ออ้างอิงจะใช้ ①②③… (รูปแบบเดียวกับ [E-6](06-epic-lane.md)①) ฝั่งสรุป ([docs/04](04-adoption.md)) จะอ้างอิง ID เหล่านี้ ท่าทีเมื่อไม่สามารถตรวจสอบได้ ดูที่ [docs/05](05-fail-posture.md)

## R-1 3 เหตุผลสำหรับการปฏิเสธอัตโนมัติ — การตัดสินใจเชิงคุณค่าเป็นสิทธิ์เฉพาะของ owner

**ใช้กับข้อเสนอที่ถูกบันทึกไว้** (Issue, PR, ข้อเสนองานที่ยื่นเป็นบันทึก) การจะปฏิเสธสิ่งเหล่านี้โดยไม่ต้องมีการตัดสินใจของมนุษย์ทำได้ **เฉพาะ 3 เหตุผลที่ตัดสินได้ด้วยกลไกเท่านั้น** แต่ละเหตุผลจะสมบูรณ์ก็ต่อเมื่อมีเงื่อนไขและหลักฐานประกอบ:

1. **มีอยู่ใน main แล้ว** (implemented on main) — ต้องชี้ commit หรือบรรทัดที่แสดงว่าพฤติกรรมดังกล่าวมีอยู่ใน main ปัจจุบัน "มีสิ่งที่คล้ายกันในเชิงฟังก์ชัน" ไม่นับรวมในเหตุผลนี้ (นั่นคือการตัดสินใจเชิงคุณค่า = สิทธิ์เฉพาะของ owner)
2. **ไม่สามารถทำซ้ำได้** (cannot reproduce) — **จำกัดเฉพาะรายงานบั๊ก** ต้องมีบันทึกความพยายามในการทำซ้ำกับ main ปัจจุบัน (คำสั่ง/ขั้นตอน ผลที่สังเกตได้ วันที่) ข้อมูลไม่เพียงพอไม่ใช่เหตุผลสำหรับการปฏิเสธ — ให้สอบถามเพิ่มเติมและ hold ไว้
3. **ไม่มีเนื้อหาสาระ** (incoherent) — จำกัดเฉพาะกรณีที่อ่านไม่ออกว่ามีข้อเสนอที่เป็นสาระ เช่น ขัดแย้งในตัวเอง ว่างเปล่า สแปม เป็นต้น และ **เฉพาะเมื่อสอบถาม 1 ครั้งแล้วยังอ่านไม่ออก** เท่านั้น ข้อเสนอที่แค่อ่านยากไม่เข้าข่ายนี้

- **การปฏิเสธด้วยการตัดสินใจเชิงคุณค่า** เช่น "ไม่จำเป็น ขัดกับนโยบาย นอกขอบเขต" เป็น**สิทธิ์เฉพาะของ owner (มนุษย์)** agent ทำได้แค่เสนอพร้อมคำแนะนำและเหตุผลขึ้นไป (การปฏิเสธที่อ้างอิง R-2 / R-3 ก็เช่นกัน — ไม่รวมอยู่ใน 3 เหตุผล)
- **ถ้าลังเลอย่าปิด** — "การปิด" คือการใช้อำนาจ หากไม่สามารถตรวจสอบได้ให้เอนไปทางที่อำนาจหดตัวลง (เปิดค้างไว้แล้วส่งให้ owner) (ทิศทางเดียวกับ [FP-7](05-fail-posture.md)) หน้าที่ของการตัดสินขั้นต้นคือการอ่านเจตนาการออกแบบและ **ไม่ปิดข้อเสนอที่ชอบธรรมโดยผิดพลาด**
- **การบันทึก**: จุดจบของข้อเสนอที่มี lane ตั้งขึ้นแล้ว (ประกาศ WIP แล้ว) จะใช้คำศัพท์ 5 คำของ [L1-4](02-issue-loop.md) **ข้อเสนอที่ถูกปฏิเสธก่อนที่ lane จะถูกตั้งขึ้นไม่ใช้คำศัพท์ของ lane** ให้บันทึกเพียงเหตุผลในการปิด (หนึ่งใน 3 เหตุผลข้างต้นพร้อมหลักฐาน หรือลิงก์ไปยังคำตัดสินของ owner)
- **การเปิดใหม่ไม่สมมาตร**: การปิดด้วย 3 เหตุผลนี้ สามารถเปิดใหม่ได้โดยไม่ต้องรออนุมัติจาก owner หากมีหลักฐานใหม่ปรากฏ (เปิดใหม่คือทิศทางที่อำนาจหดตัวลง)
- ข้อเสนอที่แตะ 4 รูปแบบของ R-4 เป็นตัวอย่างทั่วไปที่การปิดอัตโนมัติด้วย 3 เหตุผล**ไม่ปลอดภัย** — ต้องส่งให้มนุษย์
- การตัดสินใจปฏิเสธระหว่างที่ Epic กำลังดำเนินอยู่ ให้ส่งต่อ owner **แบบ asynchronous โดยไม่หยุด lane** (ไม่เพิ่มจุดหยุดของ [E-3](06-epic-lane.md))

## R-2 Contribution ที่ต้อนรับ — 6 ข้อ

1. **แก้บั๊กที่เกิดขึ้นจริง ทั้งคลาส** — ทำซ้ำอาการใน main ปัจจุบัน ชี้บรรทัดที่ปรากฏ และแก้ไม่ใช่แค่จุดที่รายงานมาจุดเดียว แต่รวมถึง call path พี่น้องด้วย (คู่ตรงข้ามกับคำขวัญของ R-4)
2. **ปลาย (edge) ขยายได้ แกนกลาง (core) รักษาไว้** — contribution ที่ขยายปลาย (ฟังก์ชันเฉพาะของแต่ละผลิตภัณฑ์/แต่ละบ้าน) ได้รับการต้อนรับ การควบคุมมุ่งไปที่แกนกลาง (โครงสร้างพื้นฐานที่ทุกคนใช้ร่วมกัน ที่ซึ่งทุกคนต้องจ่ายต้นทุนถาวร) เท่านั้น "footprint น้อยที่สุด" เป็นเรื่องของการเดินสายไปยังแกนกลาง ไม่ใช่เรื่องว่าผลิตภัณฑ์จะเติบโตได้หรือไม่
3. **Refactor ที่ประกาศไว้ต้อนรับแม้ diff จะใหญ่** — การตรวจสอบว่า "ทุกบรรทัดสามารถสืบย้อนไปยังคำขอได้" ใช้กับการเปลี่ยนแปลงฟังก์ชัน ส่วนคำขอเปลี่ยนแปลงที่ประกาศเป็น refactor คือการสกัดโดยตรง (การแบ่ง hotspot = การลงทุนของ [L2-6](01-milestone-loop.md)) **สิ่งที่ผ่อนคลายมีเพียงความสงสัยต่อขนาดของ diff เท่านั้น** — ชุดไฟล์ที่ประกาศ ([L0-2](03-git-protocol.md) default-deny) และการตรวจสอบ diff ของ [L1-7](02-issue-loop.md)④ ไม่ผ่อนคลายแม้แต่กับ refactor (refactor ผ่านได้เพราะประกาศการคาดการณ์ไฟล์ที่จะแตะอย่างกว้าง ไม่ใช่เพราะละเว้นการประกาศ) การรันเดี่ยวสำหรับ refactor แบบกว้าง ([L2-5](01-milestone-loop.md)) และขั้นตอน merge ([L0-7](03-git-protocol.md)) ก็ใช้ตามเดิม
4. **ขยาย ไม่ทำซ้ำ** — ก่อนจะเพิ่ม module, manager, hook ใหม่ ให้ตรวจสอบก่อนว่าเครื่องมือที่มีอยู่ใช้ไม่ได้จริงหรือไม่ (ที่วางเครื่องมือดู R-5)
5. **Test ยืนยัน invariant** — ตรวจสอบว่า "ข้อมูล 2 ชุดควรมีความสัมพันธ์กันอย่างไร" และไม่เขียน change detection test ที่ตรึงค่าปัจจุบัน (list, จำนวน, version ที่เขียนตรงๆ)
6. **Boundary, propagation, I/O ต้องตรวจสอบผ่าน path จริง** — การเปลี่ยนแปลงที่แตะ resolution chain, การส่งต่อ config, permission boundary, I/O ภายนอก ต้องมีหลักฐาน E2E ที่รัน path จริง อย่าทำให้ green ที่เป็น mock อย่างเดียวกลายเป็นความสมบูรณ์ **ข้อนี้เป็นแนวทางในการเลือกหลักฐาน ส่วนต้นฉบับของข้อกำหนด merge gate ยังคงเป็น [L1-7](02-issue-loop.md)** (ไม่เพิ่มข้อกำหนด)

## R-3 สิ่งที่ปฏิเสธแม้จะทำได้ดี — 7 ข้อ

นี่คือ**การตัดสินใจเชิงโครงสร้าง** ไม่ใช่มาตรฐานคุณภาพ แม้จะทำได้ดี เหตุผลในการปฏิเสธก็ไม่หายไป **การปฏิเสธที่อ้างอิงข้อนี้ไม่รวมอยู่ใน 3 เหตุผลของ R-1 — การบังคับใช้เป็นสิทธิ์เฉพาะของ owner เสมอ** agent ทำได้แค่ชี้ข้อสงสัยที่เข้าข่ายและส่งขึ้นไป:

1. **โครงสร้างพื้นฐานเชิงเก็งกำไร** — hook, callback, extension point ที่ไม่มีผู้ใช้จริงที่ระบุได้ ถ้ามี use case จริงที่ระบุแล้ว ก็ไม่ใช่การเก็งกำไร (แม้ผู้ใช้จะอยู่ใน repo อื่น)
2. **การเพิ่ม environment variable สำหรับ config ที่ไม่ใช่ความลับ** — ที่เก็บความลับ (.env ฯลฯ) สำหรับความลับเท่านั้น ส่วน config พฤติกรรม (timeout, threshold, flag, การแสดงผล) ให้ไปที่ config file
3. **skill, hook, ระบบประจำใหม่ที่สร้างขึ้นทั้งที่เครื่องมือเดิมเพียงพอแล้ว** — สิ่งที่สร้างใหม่โดยไม่มีบันทึกว่าพิจารณาบันไดของ R-5 จากขั้นที่เล็กที่สุดแล้ว จะถูกปฏิเสธ
4. **ทางลัดสำหรับการอ่านแบบขี้เกียจสำหรับสิ่งที่ควรอ่านทั้งหมด** — อย่าใส่ตัวเลือกแบ่งหน้า/ตัดตอนใน loader ของเนื้อหาที่ agent ควรอ่านทั้งหมด (skill, prompt, คู่มือ) เพราะจะทำให้อ่านแค่หน้าแรกแล้วข้ามที่เหลือ
5. **"การแก้ไข" ที่ทำลายฟังก์ชันที่ควรจะปกป้อง** — มาตรการบรรเทาที่ฆ่าจุดประสงค์ของฟังก์ชันคือมาตรการบรรเทาที่ผิด ก่อนจำกัดพฤติกรรม ให้อ่านเจตนาของ commit เดิม (`git log -p -S`)
6. **การเดินสายโดยไม่มีการพิสูจน์ / telemetry ที่ไม่ใช่ความลับโดยไม่ได้รับอนุญาต** — โค้ดที่เดินสายโดยไม่มีการพิสูจน์ E2E, branch ที่ไม่เคยถูกรันขณะทำงานจริง, telemetry ขาออก / การให้ identifier ที่ไม่มี opt-in gate (**รวมถึงข้อมูลการใช้งานที่ไม่ใช่ความลับ**) การส่งข้อมูลความลับออกภายนอกไม่ใช่หัวข้อของข้อนี้ แต่**เป็นไปตาม [E-5](06-epic-lane.md) และวินัยความลับของแต่ละบ้าน — ข้อนี้ไม่เปลี่ยนขอบเขตของรายการห้ามที่ปิดของ E-5**
7. **การผนวกเครื่องมือภายนอก/ผลิตภัณฑ์ของผู้อื่นเข้า core tree** — ภาระการดูแลรักษาจะตกมาที่ฝั่งนี้ถาวร ให้วางใน wrapper หรือที่เก็บที่แยกไว้ (เช่น directory แยกสำหรับการอพยพ, repo แยกที่จัดการโดยภายนอก — ตัวอย่างไม่ใช่บรรทัดฐาน) ไม่นำเข้า core นี่คือการตัดสินใจเรื่อง coupling และการดูแลรักษา แม้คุณภาพจะสูงก็ปิดคือปิด

## R-4 การตรวจสอบสมมติฐาน — ก่อนจะเรียกว่าบั๊ก

คำขวัญ: **"ถ้าชี้บรรทัดที่บั๊กปรากฏไม่ได้ แสดงว่าสมมติฐานยังไม่ได้ตรวจสอบ"**

เหตุผลอันดับต้นๆ ที่การเปลี่ยนแปลงที่ทำได้ดีถูกปฏิเสธไม่ใช่เรื่องคุณภาพ แต่เป็นเพราะสร้างอยู่บน**สมมติฐานที่ผิด** หรือ**เข้าใจผิดว่าการออกแบบที่ตั้งใจไว้เป็นข้อบกพร่อง** 4 รูปแบบต่อไปนี้ทำงานได้ทั้ง 2 ทิศทาง — สอนที่นั่ง review ว่า "ตรวจสอบตรงไหนอย่างละเอียด" และสอนการตัดสินขั้นต้นว่า "เมื่อไหร่ที่ไม่ควรปิด":

1. **เป็นการออกแบบที่ตั้งใจ ไม่ใช่ข้อบกพร่อง** — ข้อจำกัดที่ดูเหมือนการมองข้ามมักเป็นความตั้งใจ ก่อนจะแก้ไข ให้ถามว่า "การแยกส่วนนั้นเองคือการออกแบบหรือไม่" และอ่านเจตนาของ commit เดิม
2. **สมมติฐานไม่เป็นจริงเมื่อเทียบกับการทำงานจริง** — ก่อนยอมรับคำอ้าง ให้ trace โค้ดจริงและการทำงานขณะรันจริง ถ้าอธิบายไม่ได้ว่าการแก้ไขจะเปลี่ยนพฤติกรรมของบรรทัดไหน แสดงว่ายังไม่ได้ตรวจสอบ
3. **การขาดหายไปเคยรองรับน้ำหนักอยู่** — การเพิ่มชิ้นส่วนที่ "เห็นได้ชัดว่าขาด" อาจทำลายสิ่งที่การละเว้นนั้นเคยปกป้องไว้
4. **การฟื้นคืนนโยบายที่เกินเลย/ผ่านไปแล้ว** — การขยายที่เกินกว่าฐานที่ตกลงกันไว้ หรือการรื้อฟื้นทิศทางที่ปิดไปแล้วโดยตั้งใจ จะถูกปฏิเสธแม้จะทำงานได้ ให้จำกัดการเปลี่ยนแปลงไว้ในส่วนแคบที่ตกลงกัน ส่วนที่เหลือให้เสนอเป็น follow-up

แนวคิดหลัก: **ตรวจสอบทั้งคำอ้างและเจตนากับ codebase จริง ก่อนเขียนและก่อน merge** การทำซ้ำที่ยืนยันแล้ว + คำอธิบายระดับบรรทัด ชนะเหตุผลที่ฟังดูสมเหตุสมผลได้เสมอ ถ้าลังเลเรื่องเจตนา การถามจะถูกกว่าการยื่นการแก้ไขที่ขัดแย้งกับการออกแบบ

(ตัวอย่างจริงสามารถแทนที่ด้วยบันทึกอุบัติเหตุของแต่ละบ้านได้ — ตัวอย่างในเนื้อหาไม่ใช่บรรทัดฐาน เมื่อมอบหมาย review สามารถนำ 4 รูปแบบนี้มาใช้เป็นมุมมอง "การระบุชื่อรูปแบบความล้มเหลวที่เลวร้ายที่สุด" ของ [B-4](07-delegation-brief.md) ล่วงหน้าได้)

## R-5 บันไดของที่วาง — พื้นที่ผิวถาวรน้อยที่สุดในขั้นที่เล็กที่สุด

เมื่อสร้างความสามารถใหม่ ยิ่งขั้นล่างยิ่งเพิ่มพื้นที่ผิวถาวร (ต้นทุนที่ทุกคนต้องจ่ายต่อเนื่อง) **ให้เลือกขั้นที่มีหมายเลขน้อยที่สุดที่แก้ปัญหาได้ถูกต้อง**:

1. **ขยายโค้ดที่มีอยู่** — ถ้าเป็นตัวแปรของสิ่งที่มีอยู่แล้ว พื้นที่ผิวใหม่จะเป็นศูนย์
2. **Script / skill** — การดำเนินการที่แสดงออกได้ด้วย shell ไม่ทำงานประจำ ทำงานเฉพาะเมื่อถูกเรียก
3. **Hook ที่มี conditional gate** — automation ที่ปรากฏเฉพาะเมื่อเงื่อนไขที่ตั้งไว้เป็นจริง
4. **เพิ่มฟังก์ชันใน repo ที่มีอยู่** — ถ้ามีที่วางอยู่แล้ว ให้ไปที่นั่น
5. **แยกเป็น MCP server หรือ repo อื่น** — ถ้าเป็นความสามารถที่เป็นอิสระจริงๆ ให้แยกออกจาก core
6. **Repo ใหม่ / ระบบประจำใหม่** — ทางเลือกสุดท้าย **ต้องได้รับการอนุมัติจาก owner (มนุษย์)** หากเกิดกรณีนี้ระหว่างที่ Epic กำลังดำเนินอยู่ ให้**หยุดเป็นจุดตรวจสอบชั่วคราวของ [E-3](06-epic-lane.md)** (ไม่เพิ่มลงในตารางหลักของ E-3)

- ถ้าลังเลให้เลือกขั้นที่สูงกว่า (พื้นที่ผิวน้อยที่สุด) "เพราะขั้นล่างง่ายกว่า" ไม่ใช่เหตุผล
- **เมื่อเลือกขั้นแล้ว ให้กำหนด trigger การถอนตัวของสิ่งที่จะวางไปพร้อมกัน** ([LC-1](08-lifecycle.md) — บันไดกำหนดที่วาง ส่วน LC-1 กำหนดวิธีออก ใช้คู่กัน)
- **ประเภทเดียวกันครบ 3 ชิ้นให้รวม interface** — เมื่อ integration ประเภทเดียวกันรวมกันได้ 3 ชิ้น อย่าใส่ทีละชิ้น แต่ให้ออกแบบ common interface และห่อ implementation ที่มีอยู่เป็น provider แรก การออกแบบ interface ร่วมคือการเปลี่ยนแปลง boundary จึงต้องผ่านการนำหน้าด้วย boundary PR ของ [L2-2](01-milestone-loop.md)

## R-6 บังคับใช้นโยบายด้วย check

**อย่าปล่อยให้นโยบายที่ห้ามละเมิดเป็นเพียง "การขอร้อง"** กฎแบบ passive (.gitignore, เอกสาร, คำมั่นสัญญาปากเปล่า) หยุดได้แค่ "ความประมาท" — นโยบายที่ต้องการบังคับใช้จริงต้องยกระดับเป็น check ที่ขึ้นแดงเมื่อถูกละเมิด

- **Trigger การยกระดับ**: เมื่อนโยบายเดียวกันถูกละเมิด 2 ครั้ง ให้เปิด Issue เพื่อทำเป็น check **บันทึกการละเมิดให้เก็บไว้ใน Issue หรือบันทึกอุบัติเหตุของแต่ละบ้าน และเปิด Issue เมื่อบันทึกครั้งที่ 2** (ทำให้การนับสามารถตรวจสอบย้อนหลังได้)
- check ต้อง**ตรวจจับที่เนื้อหาจริง** (จับคู่ด้วยเนื้อหา/pattern ที่แท้จริง ไม่ใช่ชื่อ directory หรือการสะกดนามสกุลไฟล์ — มีตัวอย่างจริงที่หลุดรอดไปได้ด้วยการสะกดผิดอยู่ในที่มา)
- ท่าทีของ check ให้สอดคล้องกับข้อกำหนดเดิม: **gate ที่หยุด merge เป็น fail-closed** (ทิศทางเดียวกับ [FP-3](05-fail-posture.md)) **ท่อส่งสำหรับรายงาน/สังเคราะห์/แจ้งเตือนเป็น fail-open** ([FP-4](05-fail-posture.md)) check ไม่ขยับไฟล์ ([LC-5](08-lifecycle.md) — แค่ตรวจจับแล้วหยุด ไม่ซ่อมหรือถอนตัวอัตโนมัติ)
- check ประเภทอนุมัติ (เช่น label ของมนุษย์) ต้อง**ตรวจสอบการมีอยู่จริงของการอนุมัติ** — อย่าปล่อยผ่านแค่เพราะมีข้อความหรือ label อยู่ (ทิศทางเดียวกับ [FP-8](05-fail-posture.md)) การตรวจสอบการอนุมัติอาจมีข้อจำกัด (เช่น สภาพแวดล้อมที่ใช้ identity ร่วมกัน) — ในกรณีนั้นให้ระบุข้อจำกัดไว้ในคำอธิบายของ check อย่างชัดเจน อย่าแสร้งทำเป็นว่า "ตรวจสอบแล้ว" ([FP-5](05-fail-posture.md))
- ต้นฉบับของ type คือ [templates/ci/](../templates/ci/) ใน repo นี้
