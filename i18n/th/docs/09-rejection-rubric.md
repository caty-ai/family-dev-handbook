# R กฎการปฏิเสธ — ชั้นที่กำหนดว่าจะรับอะไรและปฏิเสธอะไร

หากชั้น L (L2 / L1 / L0) เป็นสัญญาว่า "จะดำเนินการอย่างไร" และชั้น B เป็นสัญญาว่า "จะร้องขออย่างไร" ชั้น R จะกำหนดสัญญาแห่งเจตนาว่า **อะไรจะถูก merge และอะไรจะถูกปฏิเสธ** วิธีใช้มี 2 แบบ:

1. **สำหรับฝ่ายที่สร้าง** — เพื่อให้ contribution (รวมถึงข้อเสนอ งาน และ PR ที่มาจาก agent) เล็งเป้าได้ตรงจุด
2. **สำหรับการตัดสินขั้นต้น** — เป็นแนวทางว่าเมื่อไหร่ที่สามารถปิดได้โดยไม่ต้องอาศัยการตัดสินใจของมนุษย์ และที่สำคัญไม่แพ้กันคือ "เมื่อไหร่ที่ห้ามปิด"

ความเข้มงวดของแต่ละข้อแตกต่างกัน: **R-1 / R-4 / R-5 / R-6 คือสัญญา**, **R-2 / R-3 คือรายการเกณฑ์สำหรับการตัดสินใจรับ** และการบังคับใช้การปฏิเสธที่อ้างอิง R-2 / R-3 จะต้องผ่านระเบียบเรื่องอำนาจของ R-1 เสมอ (การตัดสินคุณค่าเป็นอำนาจของ owner โดยเฉพาะ)

แต่ละกฎมี rule ID ที่คงที่ (`R-1`〜`R-6`) และข้อย่อยจะอ้างอิงด้วย ①②③… (รูปแบบเดียวกับ [E-6](06-epic-lane.md)①) ฝั่งสรุป ([docs/04](04-adoption.md)) จะอ้างอิง ID เหล่านี้ ท่าทีเมื่อไม่สามารถตรวจสอบได้ ดูที่ [docs/05](05-fail-posture.md)

ที่มา: บทนี้เป็นการดัดแปลงจากส่วน "Contribution Rubric" ใน AGENTS.md ของ NousResearch/hermes-agent (MIT) วันที่ดึงข้อมูล ประเภทที่มา และเนื้อหาสัญญาอนุญาตฉบับเต็มรวมไว้ที่ [templates/ci/NOTICE.md](../../../templates/ci/NOTICE.md)

## R-1 3 เหตุผลของการปฏิเสธอัตโนมัติ — การตัดสินคุณค่าเป็นอำนาจของ owner โดยเฉพาะ

**ใช้กับข้อเสนอที่ถูกบันทึกไว้ (Issue, PR, ข้อเสนองานที่ยื่นเป็นบันทึก)** สิ่งที่สามารถปฏิเสธได้โดยไม่ต้องอาศัยการตัดสินใจของมนุษย์คือ **3 เหตุผลที่ตัดสินได้เชิงกลไกเท่านั้น** แต่ละเหตุผลจะสมบูรณ์ก็ต่อเมื่อมีเงื่อนไขและหลักฐานประกอบ:

1. **มีอยู่แล้วใน main** (implemented on main) — ต้องชี้ไปยัง commit หรือบรรทัดที่แสดงว่าพฤติกรรมดังกล่าวมีอยู่ใน main ปัจจุบันแล้ว "มีสิ่งที่คล้ายกันในเชิงฟังก์ชัน" ไม่นับรวมในเหตุผลนี้ (นั่นคือการตัดสินคุณค่า = อำนาจของ owner)
2. **ไม่สามารถทำซ้ำได้** (cannot reproduce) — **จำกัดเฉพาะรายงานบั๊กเท่านั้น** ต้องเก็บบันทึกความพยายามทำซ้ำกับ main ปัจจุบัน (คำสั่ง/ขั้นตอน ผลที่สังเกตได้ วันที่) ข้อมูลไม่เพียงพอไม่ใช่เหตุผลของการปฏิเสธ — ให้สอบถามและพักไว้แทน
3. **เนื้อหาไม่มีอยู่จริง** (incoherent) — จำกัดเฉพาะกรณีที่อ่านไม่ออกว่ามีข้อความที่มีเนื้อหาจริงหรือไม่ เช่น ขัดแย้งในตัวเอง ว่างเปล่า สแปม และเป็นเช่นนั้น **แม้หลังจากสอบถามไปแล้ว 1 ครั้ง** ก็ยังอ่านไม่ออก ข้อเสนอที่แค่อ่านยากไม่นับรวม

- การปฏิเสธด้วยการตัดสินคุณค่า เช่น "ไม่จำเป็น ขัดกับนโยบาย นอกขอบเขต" เป็น **อำนาจของ owner (มนุษย์) โดยเฉพาะ** Agent ทำได้เพียงเสนอคำแนะนำพร้อมเหตุผลขึ้นไปให้พิจารณา (การปฏิเสธที่อ้างอิง R-2 / R-3 ก็เช่นเดียวกัน — ไม่นับรวมใน 3 เหตุผลนี้)
- **หากลังเลอย่าปิด** — "การปิด" คือการใช้อำนาจ หากตรวจสอบไม่ได้ให้เอียงไปทางที่อำนาจลดลง (เปิดค้างไว้แล้วส่งให้ owner) (ทิศทางเดียวกับ [FP-7](05-fail-posture.md)) งานของการตัดสินขั้นต้นคืออ่านเจตนาการออกแบบและ**ไม่ปิด contribution ที่ถูกต้องโดยผิดพลาด**
- **การบันทึก**: การจบของข้อเสนอที่มี lane ตั้งขึ้นแล้ว (ประกาศ WIP แล้ว) ใช้คำศัพท์ 5 คำของ [L1-4](02-issue-loop.md) **สำหรับข้อเสนอที่ถูกปฏิเสธก่อนที่ lane จะถูกตั้งขึ้น ไม่ใช้คำศัพท์ของ lane** ให้บันทึกเพียงเหตุผลการปิด (หนึ่งใน 3 เหตุผลพร้อมหลักฐานข้างต้น หรือลิงก์ไปยังคำตัดสินของ owner)
- **การเปิดใหม่ไม่สมมาตร**: การปิดด้วย 3 เหตุผลนี้ สามารถเปิดใหม่ได้โดยไม่ต้องขออนุมัติจาก owner หากมีหลักฐานใหม่เกิดขึ้น (การเปิดใหม่คือทิศทางที่อำนาจลดลง)
- ข้อเสนอที่แตะ 4 รูปแบบของ R-4 เป็นตัวอย่างทั่วไปที่การปิดอัตโนมัติด้วย 3 เหตุผล**ไม่ปลอดภัย** — ให้ส่งต่อมนุษย์
- การตัดสินการปฏิเสธระหว่าง Epic กำลังดำเนินอยู่ ให้ส่งต่อ owner **แบบ asynchronous โดยไม่หยุด lane** (ไม่เพิ่มจุดหยุดของ [E-3](06-epic-lane.md))

## R-2 Contribution ที่ยินดีต้อนรับ — 6 ข้อ

1. **แก้บั๊กจริง ทั้ง class** — ทำซ้ำอาการกับ main ปัจจุบันได้ ชี้บรรทัดที่ปรากฏอาการ และแก้ไม่เพียงจุดที่รายงานมา แต่รวมถึง call path พี่น้องด้วย (คู่กับคำขวัญของ R-4)
2. **ขยายที่ปลาย รักษาที่แกน** — contribution ที่ขยายส่วนปลาย (ฟังก์ชันเฉพาะของแต่ละผลิตภัณฑ์/แต่ละบ้าน) เป็นที่ยินดีต้อนรับ การควบคุมมุ่งไปที่แกน (โครงสร้างพื้นฐานที่แชร์กันในครอบครัว สถานที่ที่ทุกคนต้องจ่ายต้นทุนถาวร) เท่านั้น "footprint น้อยที่สุด" เป็นเรื่องของการเดินสายไปยังแกน ไม่ใช่เรื่องว่าผลิตภัณฑ์จะเติบโตได้หรือไม่
3. **การ refactor ที่ประกาศไว้ยินดีต้อนรับแม้ diff จะใหญ่** — การตรวจสอบว่า "ทุกบรรทัดสามารถสืบย้อนไปยังคำร้องขอได้" ใช้กับการเปลี่ยนแปลงฟังก์ชัน ส่วนคำร้องขอการเปลี่ยนแปลงที่ประกาศเป็น refactor คือตัวการสกัดเอง (การแยก hotspot = การลงทุนตาม [L2-6](01-milestone-loop.md)) **สิ่งที่ผ่อนปรนมีเพียงความสงสัยต่อขนาดของ diff เท่านั้น** — ชุดไฟล์ที่ประกาศ (default-deny ของ [L0-2](03-git-protocol.md)) และการตรวจสอบ diff ของ [L1-7](02-issue-loop.md)④ ไม่ผ่อนปรนแม้แต่กับ refactor (refactor จะผ่านได้ด้วยการประกาศการคาดการณ์ไฟล์ที่จะแตะอย่างกว้างขวาง ไม่ใช่ผ่านโดยละเว้นการประกาศ) การดำเนินการ refactor ขอบเขตกว้างแบบเดี่ยว ([L2-5](01-milestone-loop.md)) และขั้นตอนการ merge ([L0-7](03-git-protocol.md)) ก็ยังคงใช้เหมือนเดิม
4. **ขยายแทนการทำซ้ำ** — ก่อนเพิ่ม module, manager, hook ใหม่ ให้ตรวจสอบก่อนว่าเครื่องมือที่มีอยู่ใช้งานได้หรือไม่ (ที่วางเลือกดูที่ R-5)
5. **Test ต้องยืนยัน invariant** — ตรวจสอบว่า "ข้อมูล 2 ตัวควรมีความสัมพันธ์กันอย่างไร" และอย่าเขียน change-detection test ที่ตรึงค่าปัจจุบัน (รายการ, จำนวน, เวอร์ชันที่เขียนตรงๆ)
6. **ตรวจสอบขอบเขต, การส่งต่อ, I/O ด้วย path จริง** — การเปลี่ยนแปลงที่แตะ resolution chain, การส่งต่อ configuration, ขอบเขตสิทธิ์, I/O ภายนอก ต้องแสดงหลักฐาน E2E ที่รัน path จริง อย่าให้ green ที่มีแค่ mock เป็นสิ่งสมบูรณ์ **ข้อนี้เป็นแนวทางในการเลือกหลักฐาน ส่วนต้นฉบับของข้อกำหนด merge gate ยังคงเป็น [L1-7](02-issue-loop.md)** (ไม่เพิ่มข้อกำหนด)

## R-3 สิ่งที่แม้ทำได้ดีก็ยังปฏิเสธ — 7 ข้อ

สิ่งที่ปฏิเสธด้วย**การตัดสินเชิงโครงสร้าง** ไม่ใช่มาตรฐานคุณภาพ แม้จะทำได้ดี เหตุผลของการปฏิเสธก็ไม่หายไป **การปฏิเสธที่อ้างอิงข้อนี้ไม่นับรวมใน 3 เหตุผลของ R-1 — การบังคับใช้เป็นอำนาจของ owner เสมอ** และ Agent ทำได้เพียงชี้ข้อสงสัยที่เกี่ยวข้องขึ้นไปให้พิจารณา:

1. **โครงสร้างพื้นฐานเชิงคาดเดา** — hook, callback, extension point ที่ไม่มีผู้ใช้ที่ชัดเจน หากมี use case จริงที่ระบุไว้ ก็ไม่ถือว่าเป็นการคาดเดา (แม้ผู้ใช้จะอยู่ใน repo อื่นก็ได้)
2. **การเพิ่ม environment variable สำหรับ configuration ที่ไม่ใช่ความลับ** — ที่เก็บความลับ (.env ฯลฯ) มีไว้สำหรับความลับเท่านั้น การตั้งค่าพฤติกรรม (timeout, threshold, flag, การแสดงผล) ควรอยู่ใน configuration file
3. **skill, hook, ระบบประจำการใหม่ที่ถูกสร้างขึ้นทั้งที่เครื่องมือเดิมเพียงพอ** — การสร้างใหม่ที่ไม่มีบันทึกการพิจารณาจากขั้นน้อยที่สุดของบันได R-5 จะถูกปฏิเสธ
4. **ทางลัดสำหรับการอ่านแบบขี้เกียจต่อสิ่งที่ควรอ่านทั้งหมด** — อย่าเพิ่ม option แบ่งหน้าหรือตัดตอนให้กับ loader ของเนื้อหาที่ agent ควรอ่านทั้งหมด (skill, prompt, คู่มือ) เพราะจะทำให้อ่านแค่หน้าแรกแล้วข้ามที่เหลือ
5. **"การแก้ไข" ที่ทำลายฟังก์ชันที่ควรปกป้องไว้** — มาตรการบรรเทาที่ฆ่าจุดประสงค์ของฟังก์ชันคือมาตรการบรรเทาที่ผิด ก่อนจำกัดพฤติกรรม ให้อ่านเจตนาของ commit เดิม (`git log -p -S`)
6. **การเดินสายโดยไม่มีการพิสูจน์, telemetry ที่ไม่ใช่ความลับโดยไม่ได้รับอนุญาต** — code ที่ถูกเดินสายโดยไม่มีการพิสูจน์ E2E, branch ที่ไม่เคยถูกรันในเวลาทำงานจริงเลย, telemetry/การผูก identifier ที่ส่งออกภายนอกโดยไม่มี gate แบบ opt-in (**รวมถึงข้อมูลการใช้งานที่ไม่ใช่ความลับ**) การส่งข้อมูลลับออกภายนอกไม่ใช่เป้าหมายของข้อนี้ **แต่เป็นไปตาม [E-5](06-epic-lane.md) และระเบียบความลับของแต่ละบ้าน — ข้อนี้ไม่เปลี่ยนขอบเขตของรายการห้ามแบบปิดใน E-5**
7. **การผนวกเครื่องมือภายนอกหรือผลิตภัณฑ์ของผู้อื่นเข้าใน core tree** — ภาระการดูแลรักษาจะตกมาที่ฝั่งนี้อย่างถาวร ให้วางไว้ใน wrapper หรือที่เก็บแยกต่างหาก (เช่น directory แยกสำหรับการกักกัน, repo แยกที่บริหารจัดการภายนอก — ตัวอย่างนี้ไม่ใช่ข้อกำหนด) และไม่นำเข้า core นี่คือการตัดสินเรื่องการผูกติดและการดูแลรักษา แม้คุณภาพจะสูง การปิดก็ยังคงเป็นการปิด

## R-4 การตรวจสอบสมมติฐาน — ก่อนจะเรียกว่าบั๊ก

คำขวัญ: **"ถ้าชี้บรรทัดที่บั๊กปรากฏไม่ได้ แสดงว่าสมมติฐานยังไม่ได้รับการตรวจสอบ"**

เหตุผลอันดับต้นๆ ที่การเปลี่ยนแปลงที่ทำได้ดีถูกปฏิเสธ ไม่ใช่เรื่องคุณภาพ แต่เป็นเพราะมันสร้างขึ้นบน**สมมติฐานที่ผิด** หรือ**ตีความการออกแบบที่ตั้งใจว่าเป็นข้อบกพร่อง** 4 รูปแบบต่อไปนี้ทำงานได้ทั้งสองทิศทาง — สอนที่นั่งรีวิวว่า "ควรพิจารณาส่วนไหนอย่างละเอียด" และสอนการตัดสินขั้นต้นว่า "เมื่อไหร่ที่ห้ามปิด":

1. **เป็นการออกแบบที่ตั้งใจ ไม่ใช่ข้อบกพร่อง** — ข้อจำกัดที่ดูเหมือนถูกมองข้ามมักเป็นสิ่งที่ตั้งใจไว้ ก่อนแก้ไข ให้ตั้งคำถามว่า "การแยกส่วนนี้ไม่ใช่การออกแบบหรือ?" และอ่านเจตนาของ commit เดิม
2. **สมมติฐานไม่สอดคล้องกับการทำงานจริง** — ก่อนยอมรับข้อโต้แย้ง ให้ trace โค้ดจริงและการทำงานขณะรันจริง หากแสดงไม่ได้ว่าการแก้ไขจะเปลี่ยนพฤติกรรมของบรรทัดไหน แสดงว่ายังไม่ได้ตรวจสอบ
3. **สิ่งที่ไม่มีอยู่กำลังรับน้ำหนักอยู่** — การเพิ่มชิ้นส่วนที่ "ดูเหมือนขาดหายไปอย่างชัดเจน" บางครั้งอาจทำลายสิ่งที่การละเว้นนั้นกำลังปกป้องอยู่
4. **การฟื้นคืนนโยบายที่เกินเลยหรือถูกผ่านไปแล้ว** — การขยายที่เกินกว่า base ที่ตกลงกันไว้แล้ว หรือการรื้อฟื้นทิศทางที่ปิดไปโดยตั้งใจ จะถูกปฏิเสธแม้จะใช้งานได้ ให้จำกัดการเปลี่ยนแปลงไว้เฉพาะส่วนแคบที่ตกลงกัน และเสนอส่วนที่เหลือเป็น follow-up

หลักการพื้นฐาน: **ตรวจสอบทั้งข้อกล่าวอ้างและเจตนากับ codebase จริง ก่อนเขียนโค้ดและก่อน merge** การทำซ้ำที่ยืนยันแล้วบวกกับคำอธิบายระดับบรรทัด ชนะเหตุผลที่ฟังดูสมเหตุสมผลได้เสมอ หากลังเลใจเรื่องเจตนา การถามย่อมถูกกว่าการยื่นการแก้ไขที่ขัดแย้งกับการออกแบบ

(ตัวอย่างจริงสามารถแทนที่ด้วยบันทึกอุบัติเหตุของแต่ละบ้านได้ — ตัวอย่างในเนื้อหาไม่ใช่ข้อกำหนด เมื่อมอบหมายการรีวิว สามารถนำ 4 รูปแบบนี้ไปใช้เป็นมุมมอง "การชี้ชื่อรูปแบบความล้มเหลวที่เลวร้ายที่สุด" ของ [B-4](07-delegation-brief.md) ได้ล่วงหน้า)

## R-5 บันไดของที่วาง — พื้นที่ผิวถาวรน้อยที่สุดในขั้นที่เล็กที่สุด

เมื่อสร้างความสามารถใหม่ ยิ่งขั้นล่างยิ่งเพิ่มพื้นที่ผิวถาวร (ต้นทุนที่ทุกคนต้องจ่ายต่อเนื่อง) **เลือกขั้นที่มีหมายเลขน้อยที่สุดที่สามารถแก้ปัญหาได้อย่างถูกต้อง**:

1. **การขยายโค้ดที่มีอยู่** — หากเป็นตัวแปรของสิ่งที่มีอยู่แล้ว พื้นที่ผิวใหม่จะเป็นศูนย์
2. **Script / skill** — การดำเนินการที่แสดงออกได้ด้วย shell ไม่ประจำการ ทำงานเฉพาะเมื่อถูกเรียก
3. **Hook ที่มี conditional gate** — automation ที่ปรากฏเฉพาะเมื่อเงื่อนไขที่ตั้งไว้ถูกเติมเต็ม
4. **การเพิ่มฟังก์ชันใน repo ที่มีอยู่** — หากมีที่วางอยู่แล้ว ให้ใส่ไว้ที่นั่น
5. **แยกเป็น MCP server หรือ repo แยก** — หากเป็นความสามารถที่แยกอิสระจริงๆ ให้แยกออกไปนอก core
6. **Repo ใหม่ / ระบบประจำการใหม่** — วิธีสุดท้าย **ต้องได้รับการอนุมัติจาก owner (มนุษย์)** หากเกิดกรณีนี้ระหว่าง Epic กำลังดำเนินอยู่ ให้**หยุดเป็น checkpoint ชั่วคราวของ [E-3](06-epic-lane.md)** (ไม่เพิ่มลงในตารางหลักของ E-3)

- หากลังเลใจ ให้เลือกขั้นบน (พื้นที่ผิวน้อยที่สุด) "เพราะขั้นล่างง่ายกว่า" ไม่ใช่เหตุผล
- **เมื่อเลือกขั้นแล้ว ให้ตัดสินใจ retirement trigger ของสิ่งที่วางไปพร้อมกัน** ([LC-1](08-lifecycle.md) — บันไดกำหนดที่วาง ส่วน LC-1 กำหนดวิธีออก ใช้คู่กัน)
- **ชิ้นที่ 3 ของประเภทเดียวกัน = ทางเข้าร่วม** — เมื่อการรวมของหมวดเดียวกันสะสมครบ 3 ชิ้น แทนที่จะใส่ทีละชิ้น ให้ออกแบบ interface ร่วม และห่อการ implement ที่มีอยู่เป็น provider แรก การออกแบบทางเข้าร่วมเป็นการเปลี่ยนแปลงขอบเขต จึงอยู่ภายใต้การนำหน้าด้วย boundary PR ของ [L2-2](01-milestone-loop.md)

## R-6 บังคับใช้นโยบายด้วย check

**อย่าปล่อยให้นโยบายที่ห้ามละเมิดเป็นเพียง "การขอร้อง"** กฎแบบ passive (.gitignore, เอกสาร, คำสัญญาปากเปล่า) หยุดได้แค่ "ความประมาทเลินเล่อ" — นโยบายที่ต้องการบังคับใช้ ควรยกระดับเป็น check ที่จะขึ้นสีแดงเมื่อถูกละเมิด

- **จุดยกระดับ**: เมื่อนโยบายเดียวกันถูกละเมิด 2 ครั้ง ให้เปิด Issue สำหรับการทำเป็น check **บันทึกการละเมิดให้เก็บไว้ใน Issue หรือบันทึกอุบัติเหตุของแต่ละบ้าน และเปิด Issue เมื่อบันทึกครั้งที่ 2** (ทำให้การนับสามารถตรวจสอบย้อนหลังได้)
- check ต้อง**ตรวจจับด้วยเนื้อหาจริง** (ให้ match ด้วยสาระของเนื้อหา/pattern ไม่ใช่ชื่อ directory หรือนามสกุลไฟล์ — มีตัวอย่างจริงในที่มาที่หลุดรอดไปได้ด้วยการสะกดผิด)
- ท่าทีของ check ให้สอดคล้องกับข้อกำหนดที่มีอยู่: **gate ที่หยุด merge เป็น fail-closed** (ทิศทางเดียวกับ [FP-3](05-fail-posture.md)) **ระบบท่อสำหรับการรายงาน/การรวม/การแจ้งเตือนเป็น fail-open** ([FP-4](05-fail-posture.md)) check ไม่ขยับไฟล์ ([LC-5](08-lifecycle.md) — แค่ตรวจจับและหยุด ไม่ซ่อมแซมหรือ retire อัตโนมัติ)
- check ประเภทการอนุมัติ (label ของมนุษย์ ฯลฯ) ต้อง**ตรวจสอบว่าการอนุมัตินั้นมีอยู่จริง** — อย่าปล่อยผ่านแค่เพราะมีข้อความหรือ label อยู่ (ทิศทางเดียวกับ [FP-8](05-fail-posture.md)) การตรวจสอบการอนุมัติอาจมีข้อจำกัด (เช่น สภาพแวดล้อมที่แชร์ identity) — ในกรณีนั้น ให้ระบุข้อจำกัดไว้ในคำอธิบายของ check อย่างชัดเจน อย่าแสร้งทำเป็นว่า "ตรวจสอบแล้ว" ([FP-5](05-fail-posture.md))
- ต้นฉบับของประเภทอยู่ที่ [templates/ci/](../../../templates/ci/) ของ repo นี้
