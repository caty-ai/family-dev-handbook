# R Rubric สำหรับการปฏิเสธ — ชั้นที่กำหนดว่ารับอะไร และปฏิเสธอะไร

ในขณะที่ชั้น L (L2 / L1 / L0) เป็นสัญญาว่า "จะดำเนินการอย่างไร" และชั้น B เป็นสัญญาว่า "จะขอความช่วยเหลืออย่างไร" ชั้น R กำหนดสัญญาของเจตนาว่า**อะไรจะถูก merge และอะไรจะถูกปฏิเสธ** วิธีใช้มี 2 แบบ:

1. **สำหรับฝ่ายที่สร้าง** — เพื่อให้การมีส่วนร่วม (รวมถึงข้อเสนอ งาน PR ที่เกิดจาก agent) สามารถเล็งเป้าหมายได้ตรงจุด
2. **สำหรับการตัดสินขั้นต้น** — เป็นแนวทางว่าเมื่อไหร่ที่สามารถปิดได้โดยไม่ต้องใช้วิจารณญาณของมนุษย์ และที่สำคัญพอกันคือ "เมื่อไหร่ที่ไม่ควรปิด"

ระดับความบังคับแตกต่างกันไปตามแต่ละข้อ: **R-1 / R-4 / R-5 / R-6 คือสัญญา** ส่วน **R-2 / R-3 คือรายการเกณฑ์สำหรับการตัดสินใจรับ** และการบังคับใช้การปฏิเสธที่อ้างอิง R-2 / R-3 จะต้องผ่านวินัยด้านอำนาจของ R-1 เสมอ (การตัดสินใจเชิงคุณค่าเป็นสิทธิ์เฉพาะของเจ้าของ)

แต่ละกฎมี rule ID ที่คงที่ (`R-1`〜`R-6`) กำกับไว้ และแต่ละข้อย่อยจะอ้างอิงด้วย ①②③… (รูปแบบเดียวกับ [E-6](06-epic-lane.md)①) ฝั่งสรุป ([docs/04](04-adoption.md)) จะอ้างอิง ID นี้ ท่าทีเมื่อไม่สามารถตรวจสอบได้ ดูที่ [docs/05](05-fail-posture.md)

## R-1 เหตุผล 3 ข้อสำหรับการปฏิเสธอัตโนมัติ — การตัดสินใจเชิงคุณค่าเป็นสิทธิ์เฉพาะของเจ้าของ

**สิ่งที่ใช้ได้คือข้อเสนอที่ถูกบันทึกไว้ (Issue, PR, ข้อเสนองานที่ยื่นเป็นบันทึก)** สิ่งที่สามารถปฏิเสธได้โดยไม่ต้องใช้วิจารณญาณของมนุษย์มีเพียง **3 เหตุผลที่ตัดสินได้อย่างชัดเจนด้วยกลไก** เท่านั้น แต่ละเหตุผลจะสมบูรณ์ก็ต่อเมื่อมีเงื่อนไขที่เป็นจริงและหลักฐานประกอบ:

1. **มีอยู่แล้วใน main** (implemented on main) — ต้องชี้ได้ว่าพฤติกรรมที่เกี่ยวข้องมีอยู่ใน main ปัจจุบันแล้ว โดยระบุ commit หรือบรรทัด "มีสิ่งที่คล้ายกันในเชิงฟังก์ชัน" ไม่นับรวมในเหตุผลนี้ (นั่นคือการตัดสินใจเชิงคุณค่า = สิทธิ์เฉพาะของเจ้าของ)
2. **ไม่สามารถทำซ้ำได้** (cannot reproduce) — **จำกัดเฉพาะรายงานบั๊กเท่านั้น** ต้องเก็บบันทึกการพยายามทำซ้ำกับ main ปัจจุบัน (คำสั่ง / ขั้นตอน ผลที่สังเกตได้ วันที่) การขาดข้อมูลไม่ใช่เหตุผลของการปฏิเสธ — ให้สอบถามและพักไว้ก่อน
3. **ไม่มีเนื้อหาที่อ่านได้** (incoherent) — จำกัดเฉพาะกรณีที่ขัดแย้งในตัวเอง ว่างเปล่า สแปม ฯลฯ ซึ่งอ่านไม่ออกว่ามีข้อเสนอที่เป็นสาระสำคัญอยู่ **หลังจากสอบถาม 1 ครั้งแล้วยังอ่านไม่ออก** เท่านั้น ข้อเสนอที่แค่อ่านยากไม่นับรวม

- **การปฏิเสธด้วยการตัดสินใจเชิงคุณค่า** เช่น "ไม่จำเป็น・ขัดกับนโยบาย・นอกขอบเขต" เป็น**สิทธิ์เฉพาะของเจ้าของ (มนุษย์)** agent ทำได้แค่เสนอพร้อมคำแนะนำและเหตุผลขึ้นไปให้พิจารณา (การปฏิเสธที่อ้างอิง R-2 / R-3 ก็เช่นกัน — ไม่รวมอยู่ใน 3 เหตุผลนี้)
- **ถ้าไม่แน่ใจ อย่าปิด** — "การปิด" คือการใช้อำนาจ หากตรวจสอบไม่ได้ ให้เอียงไปในทิศทางที่อำนาจแคบลง (เปิดค้างไว้ให้เจ้าของ) (ทิศทางเดียวกับ [FP-7](05-fail-posture.md)) หน้าที่ของการตัดสินขั้นต้นคือการอ่านเจตนาการออกแบบและ**ไม่ปิดข้อเสนอที่ถูกต้องโดยผิดพลาด**
- **การบันทึก**: การปิดข้อเสนอที่มี lane ตั้งขึ้นแล้ว (ประกาศ WIP แล้ว) ให้ใช้คำศัพท์ 5 คำของ [L1-4](02-issue-loop.md) **ข้อเสนอที่ถูกปฏิเสธก่อนที่ lane จะตั้งขึ้น ไม่ใช้คำศัพท์ของ lane** ให้บันทึกเพียงเหตุผลการปิด (ข้อใดข้อหนึ่งใน 3 เหตุผล พร้อมหลักฐานข้างต้น หรือลิงก์ไปยังคำวินิจฉัยของเจ้าของ)
- **การเปิดใหม่ไม่สมมาตร**: การปิดด้วย 3 เหตุผลนี้ สามารถเปิดใหม่ได้โดยไม่ต้องขออนุมัติจากเจ้าของหากมีหลักฐานใหม่ปรากฏขึ้น (การเปิดใหม่คือทิศทางที่อำนาจแคบลง)
- ข้อเสนอที่เข้าข่าย 4 รูปแบบของ R-4 เป็นตัวอย่างทั่วไปที่การปิดอัตโนมัติด้วย 3 เหตุผล**ไม่ปลอดภัย** — ให้ส่งต่อมนุษย์
- การตัดสินใจปฏิเสธระหว่างที่ Epic กำลังดำเนินอยู่ ให้ส่งต่อเจ้าของแบบ**อะซิงโครนัสโดยไม่หยุด lane** (ไม่เพิ่มจุดหยุดของ [E-3](06-epic-lane.md))

## R-2 การมีส่วนร่วมที่ยินดีต้อนรับ — 6 ข้อ

1. **แก้บั๊กจริง ให้ครอบคลุมทั้งคลาส** — ทำซ้ำอาการใน main ปัจจุบันได้ ชี้บรรทัดที่ปรากฏได้ และแก้ไม่ใช่แค่จุดที่รายงานเพียงจุดเดียว แต่รวมถึงเส้นทางการเรียกที่เป็นพี่น้องกันด้วย (คู่กับคำขวัญของ R-4)
2. **ขยายที่ปลาย・รักษาที่แกนกลาง** — การมีส่วนร่วมที่ขยายปลาย (ฟีเจอร์ของแต่ละผลิตภัณฑ์・แต่ละบ้าน) เป็นที่ยินดีต้อนรับ การควบคุมมุ่งไปที่แกนกลาง (โครงสร้างพื้นฐานที่ครอบครัวใช้ร่วมกัน・ที่ที่ทุกคนต้องจ่ายต้นทุนถาวร) เท่านั้น "footprint น้อยที่สุด" เป็นเรื่องของสายไฟที่ไปแกนกลาง ไม่ใช่เรื่องว่าผลิตภัณฑ์เติบโตได้หรือไม่
3. **การ refactor ที่ประกาศไว้ ยินดีต้อนรับแม้ diff จะใหญ่** — การตรวจสอบว่า "ทุกบรรทัดต้องสืบย้อนไปยังคำขอได้" นั้นใช้กับการเปลี่ยนแปลงฟังก์ชัน ส่วนคำขอการเปลี่ยนแปลงที่ประกาศว่าเป็น refactor คือตัวการสกัดเอง (การแบ่ง hotspot = การลงทุนของ [L2-6](01-milestone-loop.md)) **สิ่งที่ผ่อนปรนมีเพียงข้อสงสัยเกี่ยวกับขนาดของ diff เท่านั้น** — ชุดไฟล์ที่ประกาศ ([L0-2](03-git-protocol.md) default-deny) และการตรวจสอบ diff ของ [L1-7](02-issue-loop.md)④ ไม่ผ่อนปรนแม้จะเป็น refactor (refactor ต้องประกาศชุดไฟล์ที่คาดว่าจะแตะกว้างๆ เพื่อให้ผ่าน ไม่ใช่ผ่านโดยละเว้นการประกาศ) การรัน refactor แบบกว้างเพียงลำพัง ([L2-5](01-milestone-loop.md)) และขั้นตอนการ merge ([L0-7](03-git-protocol.md)) ก็ยังคงใช้เหมือนเดิม
4. **ขยายไม่ใช่ทำซ้ำ** — ก่อนเพิ่ม module・manager・hook ใหม่ ให้ตรวจสอบก่อนว่าเครื่องมือที่มีอยู่แล้วใช้ไม่ได้จริงหรือไม่ (ที่วางเลือกดูที่ R-5)
5. **test ต้องยืนยัน invariant** — ตรวจสอบว่า "ข้อมูล 2 ชุดควรมีความสัมพันธ์กันอย่างไร" และไม่เขียน test ตรวจจับการเปลี่ยนแปลงที่ตรึงค่าปัจจุบัน (รายการ・จำนวน・เวอร์ชันที่เขียนตรงๆ)
6. **ตรวจสอบขอบเขต การส่งต่อ I/O ด้วยเส้นทางจริง** — การเปลี่ยนแปลงที่แตะ resolution chain・การส่งต่อ config・ขอบเขตสิทธิ์・I/O ภายนอก ต้องแสดงหลักฐาน E2E ที่รันเส้นทางจริง อย่าทำให้ green ที่มีแต่ mock กลายเป็นงานเสร็จสมบูรณ์ **ข้อนี้เป็นแนวทางในการเลือกหลักฐาน ส่วนข้อกำหนดของ merge gate ยังคงอยู่ที่ [L1-7](02-issue-loop.md) เป็นตัวจริงเหมือนเดิม** (ไม่ได้เพิ่มข้อกำหนด)

## R-3 สิ่งที่ปฏิเสธแม้จะทำได้ดี — 7 ข้อ

ไม่ใช่มาตรฐานด้านคุณภาพ แต่เป็น**การตัดสินเชิงโครงสร้าง**ที่ปฏิเสธ แม้ทำได้ดี เหตุผลของการปฏิเสธก็ไม่ได้หายไป **การปฏิเสธที่อ้างอิงข้อนี้ไม่นับรวมใน 3 เหตุผลของ R-1 — การบังคับใช้เป็นสิทธิ์เฉพาะของเจ้าของเสมอ** agent ทำได้แค่ชี้ข้อสงสัยที่เข้าข่ายและส่งขึ้นไปให้พิจารณา:

1. **โครงสร้างพื้นฐานเชิงคาดเดา** — hook・callback・extension point ที่ไม่มีผู้ใช้จริงที่ระบุได้ ถ้ามี use case จริงที่ระบุไว้ ก็ไม่นับเป็นการคาดเดา (แม้ผู้ใช้จะอยู่ใน repo อื่น)
2. **การเพิ่ม environment variable สำหรับ config ที่ไม่ใช่ความลับ** — ที่เก็บความลับ (.env ฯลฯ) เป็นของความลับเท่านั้น การตั้งค่าพฤติกรรม (timeout・threshold・flag・การแสดงผล) ควรอยู่ใน config file
3. **skill・hook・ระบบประจำที่ใหม่ ทั้งที่เครื่องมือที่มีอยู่แล้วเพียงพอ** — สิ่งที่สร้างใหม่โดยไม่มีบันทึกการพิจารณาลำดับขั้นต่ำสุดของ R-5 จะถูกปฏิเสธ
4. **ทางลัดสำหรับการอ่านแบบขี้เกียจในสิ่งที่ควรอ่านทั้งหมด** — อย่าใส่ตัวเลือกแบ่งหน้าหรือสรุปย่อในตัวโหลดเนื้อหาที่ agent ควรอ่านให้ครบ (skill・prompt・คู่มือ) เพราะจะทำให้อ่านแค่หน้าแรกแล้วข้ามที่เหลือ
5. **"การแก้ไข" ที่ทำลายฟังก์ชันที่ควรจะปกป้อง** — มาตรการผ่อนปรนที่ฆ่าจุดประสงค์ของฟังก์ชันคือมาตรการผ่อนปรนที่ผิด ก่อนจำกัดพฤติกรรม ให้อ่านเจตนาของ commit เดิม (`git log -p -S`)
6. **การเดินสายโดยไม่มีการพิสูจน์・telemetry ที่ไม่ใช่ความลับโดยไม่ได้รับอนุญาต** — โค้ดที่เดินสายโดยไม่มีหลักฐาน E2E・branch ที่ไม่เคยถูกรันในระหว่างการทำงานจริง・telemetry ภายนอก / การติดตั้ง identifier โดยไม่มี opt-in gate (**รวมถึงข้อมูลการใช้งานที่ไม่ใช่ความลับ**) การส่งข้อมูลความลับออกภายนอกไม่ใช่หัวข้อของข้อนี้ **แต่เป็นไปตาม [E-5](06-epic-lane.md) และวินัยความลับของแต่ละบ้าน — ข้อนี้ไม่เปลี่ยนขอบเขตของรายการห้ามแบบปิดของ E-5**
7. **การอุ้มเครื่องมือภายนอก・ผลิตภัณฑ์ของผู้อื่นเข้ามาไว้ใน core tree** — ภาระการบำรุงรักษาจะตกมาที่ฝั่งนี้อย่างถาวร ให้วางไว้ใน wrapper・ที่เก็บที่แยกออกไป (เช่น: directory แยกสำหรับพักไว้・repo แยกที่บริหารจัดการภายนอก — ตัวอย่างไม่ใช่ข้อบังคับ) และไม่นำเข้า core นี่เป็นการตัดสินใจเรื่อง coupling และการบำรุงรักษา แม้คุณภาพจะสูงก็ยังคงปิด

## R-4 การตรวจสอบสมมติฐาน — ก่อนจะเรียกว่าบั๊ก

คำขวัญ: **"ถ้าชี้บรรทัดที่บั๊กปรากฏไม่ได้ แสดงว่าสมมติฐานยังไม่ผ่านการตรวจสอบ"**

เหตุผลอันดับต้นๆ ที่การเปลี่ยนแปลงที่ทำได้ดีถูกปฏิเสธ ไม่ใช่เรื่องคุณภาพ แต่เพราะ**สร้างอยู่บนสมมติฐานที่ผิด** หรือ**ปฏิบัติต่อการออกแบบที่ตั้งใจไว้ว่าเป็นข้อบกพร่อง** 4 รูปแบบต่อไปนี้ทำงานได้ทั้ง 2 ทิศทาง — บอกกับที่นั่งของ reviewer ว่า "ควรตรวจสอบตรงไหน" และบอกกับการตัดสินขั้นต้นว่า "เมื่อไหร่ที่ไม่ควรปิด":

1. **การออกแบบที่ตั้งใจ ไม่ใช่ข้อบกพร่อง** — ข้อจำกัดที่ดูเหมือนการมองข้าม มักเป็นสิ่งที่ตั้งใจไว้ ก่อนแก้ไข ให้ตั้งคำถามว่า "การแยกส่วนนี้เองคือการออกแบบหรือไม่?" และอ่านเจตนาของ commit เดิม
2. **สมมติฐานที่ไม่เป็นจริงเมื่อเทียบกับพฤติกรรมจริง** — ก่อนยอมรับข้อโต้แย้ง ให้ตาม trace โค้ดจริง・พฤติกรรมขณะทำงานจริง หากไม่สามารถแสดงได้ว่าการแก้ไขเปลี่ยนพฤติกรรมของบรรทัดใด แสดงว่ายังไม่ผ่านการตรวจสอบ
3. **การไม่มีอยู่กำลังรับน้ำหนักอยู่** — การเพิ่มชิ้นส่วนที่ดูเหมือน "หายไปอย่างชัดเจน" บางครั้งทำลายสิ่งที่การละเว้นนั้นกำลังปกป้องอยู่
4. **การทำเกินความจำเป็น・การรื้อฟื้นนโยบายที่เลยผ่านไปแล้ว** — การขยายที่เกินกว่าฐานที่ตกลงกันไว้ หรือการรื้อฟื้นทิศทางที่ปิดไปแล้วโดยตั้งใจ จะถูกปฏิเสธแม้จะใช้งานได้ ให้จำกัดการเปลี่ยนแปลงไว้เฉพาะส่วนแคบๆ ที่ตกลงกันไว้ และเสนอส่วนที่เหลือเป็น follow-up

แก่นสำคัญ: **ตรวจสอบทั้งข้อโต้แย้งและเจตนาเทียบกับ codebase ก่อนเขียนโค้ด・ก่อน merge เสมอ** การทำซ้ำที่ยืนยันได้แล้ว + คำอธิบายระดับบรรทัด ชนะเหตุผลที่ฟังดูสมเหตุสมผลได้เสมอ หากไม่แน่ใจในเจตนา ถามดีกว่าเสนอการแก้ไขที่ขัดกับการออกแบบ

（ตัวอย่างจริงสามารถแทนที่ด้วยบันทึกอุบัติเหตุของแต่ละบ้านได้ — ตัวอย่างในเนื้อหาไม่ใช่ข้อบังคับ เมื่อมอบหมายการ review สามารถนำ 4 รูปแบบนี้มาใช้เป็นมุมมองของ "การระบุรูปแบบความล้มเหลวที่เลวร้ายที่สุด" ใน [B-4](07-delegation-brief.md) ล่วงหน้าได้）

## R-5 ลำดับขั้นของที่วาง — พื้นที่ผิวถาวรให้น้อยที่สุดในขั้นที่ต่ำที่สุด

เมื่อสร้างความสามารถใหม่ ยิ่งขั้นล่างเท่าไหร่ พื้นที่ผิวถาวร (ต้นทุนที่ทุกคนต้องจ่ายต่อเนื่อง) ยิ่งเพิ่มขึ้น **ให้เลือกขั้นที่มีเลขน้อยที่สุดที่สามารถแก้ปัญหาได้อย่างถูกต้อง**:

1. **การขยายโค้ดที่มีอยู่แล้ว** — หากเป็นตัวแปรของสิ่งที่มีอยู่แล้ว พื้นที่ผิวใหม่จะเป็นศูนย์
2. **script / skill** — การดำเนินการที่แสดงออกได้ด้วย shell ไม่ประจำอยู่・ทำงานเฉพาะเมื่อถูกเรียก
3. **hook แบบมีเงื่อนไข** — automation ที่ปรากฏเฉพาะเมื่อเงื่อนไขที่ตั้งไว้ล่วงหน้าถูกตั้งค่า
4. **การเพิ่มฟีเจอร์ใน repo ที่มีอยู่แล้ว** — หากมีที่วางอยู่แล้ว ให้ไปที่นั่น
5. **การแยกเป็น MCP server・repo แยก** — หากเป็นความสามารถที่แยกออกมาจริงๆ ให้แยกออกจาก core
6. **repo ใหม่・ระบบประจำใหม่** — ทางเลือกสุดท้าย **ต้องได้รับการอนุมัติจากเจ้าของ (มนุษย์)** หากเข้าข่ายนี้ระหว่างที่ Epic กำลังดำเนินอยู่ ให้**หยุดเป็น checkpoint ชั่วคราวของ [E-3](06-epic-lane.md)** (ไม่เพิ่มลงในตารางฝั่งของ E-3)

- หากไม่แน่ใจ ให้เลือกขั้นที่สูงกว่า (พื้นที่ผิวน้อยที่สุด) "เพราะขั้นล่างง่ายกว่า" ไม่ใช่เหตุผล
- **เมื่อเลือกขั้นแล้ว ให้ตัดสินใจ retirement trigger ของสิ่งที่วางไปพร้อมกัน** ([LC-1](08-lifecycle.md) — ลำดับขั้นกำหนดที่วาง LC-1 กำหนดวิธีออกจากที่นั้น ใช้คู่กัน)
- **ชิ้นที่ 3 ในหมวดเดียวกัน = ทางเข้าร่วม** — เมื่อการรวมระบบในหมวดหมู่เดียวกันสะสมครบ 3 ชิ้น ให้ออกแบบ interface ร่วมแทนการใส่ทีละชิ้น และห่อ implementation ที่มีอยู่แล้วเป็น provider ตัวแรก การออกแบบทางเข้าร่วมเป็นการเปลี่ยนแปลงขอบเขต จึงต้องผ่านการทำ boundary PR ล่วงหน้าตาม [L2-2](01-milestone-loop.md)

## R-6 บังคับใช้นโยบายด้วย check

**อย่าปล่อยให้นโยบายที่ห้ามละเมิดเป็นแค่ "การขอร้อง"** กฎเชิงรับ (.gitignore・เอกสาร・คำมั่นสัญญาปากเปล่า) หยุดได้แค่ "ความประมาท" เท่านั้น — นโยบายที่ต้องการบังคับใช้จริง ให้ยกระดับเป็น check ที่จะแสดงสีแดงเมื่อถูกละเมิด

- **จุดกระตุ้นการยกระดับ**: เมื่อนโยบายเดียวกันถูกละเมิด 2 ครั้ง ให้เปิด Issue เพื่อทำเป็น check **บันทึกการละเมิดให้เก็บไว้ใน Issue หรือบันทึกอุบัติเหตุของแต่ละบ้าน และเปิด Issue เมื่อบันทึกครั้งที่ 2** (ให้สามารถตรวจสอบการนับย้อนหลังได้)
- check ต้องตรวจจับด้วย**เนื้อหาจริง** (จับคู่ด้วยเนื้อหา・pattern ที่แท้จริง ไม่ใช่ชื่อ directory หรือการสะกดนามสกุลไฟล์ — มีตัวอย่างจริงที่หลุดรอดจากการสะกดผิดอยู่ในที่มา)
- ท่าทีของ check ให้สอดคล้องกับข้อบังคับที่มีอยู่แล้ว: **gate ที่หยุด merge ให้เป็น fail-closed** (ทิศทางของ [FP-3](05-fail-posture.md))、**สายท่อของรายงาน・การรวม・การแจ้งเตือน ให้เป็น fail-open** ([FP-4](05-fail-posture.md)) check ไม่ย้ายไฟล์ ([LC-5](08-lifecycle.md) — แค่ตรวจจับแล้วหยุด・ไม่ซ่อมอัตโนมัติหรือ retire อัตโนมัติ)
- check ประเภทการอนุมัติ (label ของมนุษย์ ฯลฯ) ต้อง**ตรวจสอบการมีอยู่จริงของการอนุมัติ** — อย่าปล่อยผ่านแค่เพราะมีข้อความหรือ label อยู่ (ทิศทางของ [FP-8](05-fail-posture.md)) การตรวจสอบการอนุมัติอาจมีข้อจำกัด (เช่น สภาพแวดล้อมที่ใช้ identity ร่วมกัน) — ในกรณีนั้น ให้ระบุข้อจำกัดไว้ในคำอธิบายของ check อย่างชัดเจน และอย่าทำเป็นว่า "ตรวจสอบแล้ว" ([FP-5](05-fail-posture.md))
- ต้นแบบที่เป็นทางการอยู่ที่ `templates/ci/` ของ repo นี้ (จัดเตรียมไว้ใน #18)
