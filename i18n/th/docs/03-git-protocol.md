# L0 กฎวินัย git — ชั้นที่ป้องกันการชนกันทางกายภาพ

กฎวินัยที่ตั้งอยู่บนสมมติฐานว่า**หลายเซสชัน / หลายเอเจนต์จะแตะ repo เดียวกันพร้อมกัน** (ตกลงกันเมื่อ 2026-07-03 · ทำเป็นสัญญาเมื่อ 2026-07-21)
แต่ละกฎมี rule ID ที่คงที่ (`L0-1` ถึง `L0-9`) กำกับไว้ ฝั่งสรุป ([docs/04](04-adoption.md)) จะอ้างอิง ID นี้ ส่วนท่าทีเมื่อตรวจสอบไม่ได้ ดูที่ [docs/05](05-fail-posture.md)

## L0-1 ตรวจสอบความซ้ำซ้อนก่อนเริ่มงาน + ประกาศ WIP (Issue = soft lock)

```bash
gh issue list --state open
gh pr list --state open
```

ตรวจสอบความซ้ำซ้อนด้วยคำสั่งข้างต้นก่อน แล้วจึงเขียนคอมเมนต์ WIP ลงใน Issue ที่รับผิดชอบ ([เทมเพลต](../templates/issue-template.md))

การประกาศ WIP จะมีผลเป็น soft lock ก็ต่อเมื่อ**มีฟิลด์บังคับครบทั้ง 4 ฟิลด์เท่านั้น**:
`agent / date / Files to touch / Branch`

WIP ที่ขาดฟิลด์ใดฟิลด์หนึ่งถือเป็น lock ที่ไม่มีผล — ให้ถือว่า scope ไม่ชัดเจน และงานใดที่เกี่ยวข้องกับเลนนั้นต้องทำแบบเรียงลำดับ (serial) ([FP-7](05-fail-posture.md)) เซสชันอื่นจะไม่เริ่มงานที่ทับซ้อนกับชุดไฟล์ของ WIP ที่มีผลอยู่

## L0-2 ความหมายของ path ที่ประกาศ — ไม่แตะสิ่งที่ไม่ได้ประกาศ (default-deny)

- path เป็นแบบ**สัมพัทธ์กับ root ของ repo** ชื่อไฟล์หมายถึงไฟล์นั้นไฟล์เดียว ไดเรกทอรีที่มี slash ปิดท้ายจะครอบคลุมทุกอย่างข้างใน
- ห้ามใช้ glob และการปฏิเสธ (exclude ด้วย `!`)
- เลนที่ประกาศ `Files to touch: UNKNOWN` **ใช้ได้เฉพาะแบบเรียงลำดับ (serial) เท่านั้น** (ห้ามทำพร้อมกัน)
- **ไฟล์ที่ไม่ได้ประกาศถือว่าอยู่นอก scope** (default-deny) หากจำเป็นต้องแตะไฟล์นั้น ให้ประกาศ WIP ใหม่*ก่อน*การเขียนครั้งแรกที่อยู่นอก scope และทำการตรวจสอบการทับซ้อนกับฝ่ายที่ทำงานพร้อมกัน ([L2-4](01-milestone-loop.md)) ใหม่อีกครั้ง
- **ชุดไฟล์ที่มีผลจริง**ให้นับรวมทั้งสอง path ของการ rename · การลบ · lockfile · ไฟล์ที่ถูก generate ด้วย (ทั้งตอนประกาศและตอนตรวจสอบการทับซ้อน)
- **อ่านซ้ำแบบ optimistic** — ก่อนการเขียนครั้งแรกในเลนนั้น ให้อ่าน WIP ที่มีผลอยู่ทั้งหมดซ้ำอีกครั้ง หากมีการเปลี่ยนแปลง (WIP เพิ่ม/ลด · เนื้อหาการประกาศเปลี่ยน · ประกาศใหม่) หลังจากตัดสินใจ GO แล้ว ให้ทำการตรวจสอบการทับซ้อนใหม่

## L0-3 การหมดอายุของ lock และการส่งต่องาน (stale = 72h / TAKEOVER)

lock จะหมดอายุเมื่อ: branch ถูก merge / ลบแล้ว · stale · มีคอมเมนต์ `RELEASE` · มีคอมเมนต์ `HANDED-OFF`
`RELEASE` / `HANDED-OFF` เป็น**คอมเมนต์เกี่ยวกับ lifecycle ของ lock** ไม่ใช่ lane state ตาม L1-4 (รูปแบบดูที่[เทมเพลต](../templates/issue-template.md)) **มีเพียงเจ้าของ lock (agent ของ WIP นั้น) เท่านั้นที่โพสต์ได้** — หากคนอื่นโพสต์ถือว่าไม่มีผล และช่องทางเดียวที่คนอื่นจะปลด lock ได้คือผ่าน stale + TAKEOVER เท่านั้น

- **stale = ไม่มีการประกาศ/อัปเดตนาน 72 ชั่วโมง** (วัดจาก timestamp ของคอมเมนต์ใน GitHub — การอัปเดตทำได้แค่เขียนคอมเมนต์ใหม่ก็เพียงพอ อย่าเพิ่มช่อง timestamp เฉพาะทางสำหรับวัด staleness: อย่าซ้ำซ้อนกับ metadata ของแพลตฟอร์ม ส่วนฟิลด์ `date` ในตัวการประกาศ WIP ยังคงบังคับตาม L0-1 เหมือนเดิม) เลนที่คาดว่าจะเงียบไปนานสามารถระบุช่วงเวลาที่ยาวขึ้นได้**พร้อมเหตุผล**ตั้งแต่ตอนประกาศ WIP (ถือเป็นข้อยกเว้น ไม่ใช่ค่าเริ่มต้น การขยายเวลาในภายหลังต้องทำให้เห็นชัดด้วยการเขียนคอมเมนต์ใหม่)
- **stale ⇒ เจ้าของไม่ชัดเจน ⇒ ห้ามถือว่าว่างเปล่าโดยไม่บอกกล่าว** ขั้นตอนการรับช่วงเลนที่ stale: checklist การกลับมาเริ่มงานตาม L0-9 + **คอมเมนต์ `TAKEOVER`** ที่อ้างอิง WIP ที่ stale + ประกาศ WIP ใหม่
- การปรับตัวเลข 72 ชั่วโมงให้ทำ**เฉพาะผ่าน PR ของ handbook ฉบับนี้เท่านั้น** โดยอ้างอิงข้อมูลการดำเนินงานจริง (weekly probe) (ห้ามเปลี่ยนเองภายในเลน) สิ่งที่ปรับไม่ได้คือ invariant ที่ว่า "ห้ามปล่อยให้ stale เป็นอิสระโดยไม่บอกกล่าว"

HOLD **ไม่ใช่**เหตุให้ lock หมดอายุ (ไม่ใช่สถานะจบ — [L1-5](02-issue-loop.md)) คอมเมนต์ HOLD ต้องระบุ**การจัดการ lock**ให้ชัดเจนเสมอ (คงไว้จนถึง review-by หรือปล่อย) — HOLD ที่ไม่พูดถึง lock ถือว่าไม่มีผล

## L0-4 1 เซสชัน = 1 Issue = 1 branch = 1 worktree

**มีผู้เขียนที่ทำงานอยู่ได้เพียงหนึ่งเดียว**ต่อ 1 เลน / 1 worktree ห้ามทำงานบน checkout ที่ใช้ร่วมกัน:

```bash
git worktree add ../<repo>-wt/<issue> -b fix/<issue>-<slug> origin/main
```

## L0-5 main สำหรับ merge เท่านั้น

ห้าม push ตรงเข้า main ทุกอย่างต้องผ่าน PR

## L0-6 ใส่รายการไฟล์ที่แตะ + ตรวจสอบ diff ใน PR body

ให้ผู้รีวิวเห็นส่วนต่าง (ไฟล์ที่เพิ่ม/ลดลงจากที่ประกาศไว้) ระหว่าง WIP ที่ประกาศไว้กับของจริง
ตอน merge ให้เทียบชุดไฟล์ที่ประกาศกับ `git diff --stat` — **ไฟล์ที่อยู่ใน diff แต่ไม่อยู่ในรายการถือเป็น blocking** (ส่วนหนึ่งของ evidence gate การจบงานตาม [L1-7](02-issue-loop.md))

## L0-7 merge ทีละ PR

```
git fetch → rebase origin/main → ตรวจสอบซ้ำ (typecheck / tests) → merge
```

หลัง merge ให้ rebase branch อื่นที่ยังเปิดอยู่โดยเร็ว ห้าม merge สองอันพร้อมกัน
**เมื่อ PR ที่อยู่ติดกันถูก merge แล้ว PR ที่รอคิวอยู่มีหน้าที่ต้อง rebase + ตรวจสอบซ้ำ (รัน typecheck / tests ใหม่)** — แค่ rebase ผ่านอย่างเดียวไม่ถือว่าทำหน้าที่นี้เสร็จ

## L0-8 branch ควรมีขนาดเล็กและอายุสั้น

branch ที่มีอายุนานจะกลายเป็น rebase hell PR ที่ค้าง merge ต้องระบุสถานะด้วย **คอมเมนต์ HOLD** (ฟิลด์บังคับดูที่ [L1-5](02-issue-loop.md)) และห้ามปล่อยทิ้งไว้เงียบๆ

## L0-9 checklist การเริ่มต้นใหม่ — ก่อนการเขียนครั้งแรกของเลนที่กลับมาเริ่มงาน/ส่งต่องาน

เลนที่กลับมาเริ่มงาน / ส่งต่องาน / TAKEOVER ต้องโพสต์ผลการตรวจสอบ 4 ข้อต่อไปนี้เป็นคอมเมนต์เดียวใน Issue **ก่อนการเขียนครั้งแรก** ([เทมเพลต](../templates/issue-template.md)):

1. **Lock** — เป็นของตัวเองหรือไม่ หรือหมดอายุแล้วตาม L0-3 หรือไม่
2. **ขอบเขตไฟล์** — ชุดไฟล์ที่ประกาศไว้ยังถูกต้องเมื่อเทียบกับ origin/main ปัจจุบัน**และ**ไม่ทับซ้อนกับ WIP/PR ที่มีผลอยู่ทั้งหมด ณ ขณะนี้หรือไม่ (รัน `gh issue list` + `gh pr list --state open` ใหม่ ข้อนี้รวม query สองอย่างเข้าเป็น gate เดียวคือ "scope ที่ประกาศไว้ของตัวเองยังมีผลอยู่หรือไม่?")
3. **branch** — fetch / rebase ผ่านโดยไม่มีปัญหาหรือไม่ (ถ้าล้าหลัง · ก่อน merge ให้ rebase)
4. **Done when** — เปลี่ยนไปจากตอน handoff หรือไม่

หากพบความไม่สอดคล้อง: ให้เลือกอย่างใดอย่างหนึ่งระหว่าง แก้ไข / handoff · TAKEOVER / เปลี่ยนเป็นแบบเรียงลำดับ (serial) **ห้ามทำงานต่อบน lock ที่มีผลอยู่ของเอเจนต์อื่นโดยไม่บอกกล่าว**
checklist **ตายตัวที่ 4 ข้อนี้เท่านั้น** ตัวคอมเมนต์ที่โพสต์เองคือผลงานที่ตรวจสอบได้ (auditable) ห้ามเพิ่มข้อ (checklist fatigue คือ failure mode ที่ถูกระบุไว้ชัดเจน)

## เมื่อเกิดอุบัติเหตุ

- เกิด conflict → อย่าตกใจ แก้ไขด้วย rebase หากการแก้ไขมีขนาดใหญ่ขึ้นเรื่อยๆ ให้คอมเมนต์แจ้งข้อเท็จจริงนี้ใน Issue แล้วเปลี่ยนเป็นแบบเรียงลำดับ (serial)
- จำเป็นต้องแตะไฟล์ที่ไม่ได้ประกาศไว้ → ประกาศ WIP ใหม่**ก่อนเขียน** แล้วทำการตรวจสอบการทับซ้อนใหม่ (L0-2)
- push เข้า main โดยพลาด → ย้อนกลับด้วย revert commit และบันทึกเหตุการณ์ไว้ใน Issue
