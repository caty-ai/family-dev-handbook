# L0 วินัย Git — ชั้นป้องกันการชนกันทางกายภาพ

วินัยที่ตั้งอยู่บนสมมติฐานว่า**หลาย session / หลาย agent จะแตะ repo เดียวกันพร้อมกัน** (ตกลงกันเมื่อ 2026-07-03 และทำเป็นข้อสัญญาเมื่อ 2026-07-21)
แต่ละกฎมี rule ID ที่คงที่ (`L0-1` ถึง `L0-9`) ฝั่งสรุป ([docs/04](04-adoption.md)) จะอ้างอิง ID เหล่านี้ ท่าทีเมื่อไม่สามารถตรวจสอบได้ ดูที่ [docs/05](05-fail-posture.md)

## L0-1 ตรวจสอบความซ้ำซ้อนก่อนเริ่มงาน + ประกาศ WIP (Issue = soft lock)

```bash
gh issue list --state open
gh pr list --state open
```

ตรวจสอบความซ้ำซ้อนด้วยคำสั่งนี้ก่อน แล้วเขียนคอมเมนต์ WIP ใน Issue ที่รับผิดชอบ ([template](../templates/issue-template.md))

การประกาศ WIP จะมีผลเป็น soft lock **ก็ต่อเมื่อมีครบ 4 ฟิลด์ที่จำเป็น** เท่านั้น:
`agent / date / Files to touch / Branch`

WIP ที่ขาดฟิลด์ใดฟิลด์หนึ่งถือว่าไม่มีผลเป็น lock — ให้ถือว่า scope ไม่ชัดเจน และงานที่เกี่ยวข้องกับ lane นั้นให้ทำแบบ serial ([FP-7](05-fail-posture.md)) session อื่นจะไม่เริ่มงานที่ทับซ้อนกับชุดไฟล์ของ WIP ที่มีผลบังคับใช้

## L0-2 ความหมายของ path ที่ประกาศ — ไม่แตะสิ่งที่ไม่ได้ประกาศ (default-deny)

- path เป็นแบบ **สัมพัทธ์กับ root ของ repo** ชื่อไฟล์จะระบุเฉพาะไฟล์นั้น ส่วน directory ที่มี slash ต่อท้ายจะครอบคลุมทุกอย่างข้างใต้
- ห้ามใช้ glob และการยกเว้น (`!` exclude)
- lane ที่ประกาศ `Files to touch: UNKNOWN` จะต้อง**ทำแบบ serial เท่านั้น** (ห้าม parallel)
- **ไฟล์ที่ไม่ได้ประกาศถือว่าอยู่นอก scope** (default-deny) หากจำเป็นต้องแตะไฟล์นั้น ให้ประกาศ WIP ใหม่*ก่อน*การเขียนครั้งแรกนอก scope และทำการตรวจสอบการทับซ้อนกับฝ่ายที่ทำงานคู่ขนานใหม่ ([L2-4](01-milestone-loop.md))
- **ชุดไฟล์ที่มีผลจริง** ให้นับทั้งสอง path ของการ rename, การลบ, lockfile, และไฟล์ที่ถูก generate ด้วย (นับทั้งตอนประกาศและตอนตรวจสอบการทับซ้อน)
- **การอ่านซ้ำแบบ optimistic** — ก่อนการเขียนครั้งแรกใน lane ให้อ่าน WIP ที่ active อยู่ทั้งหมดซ้ำ หากมีการเปลี่ยนแปลง (WIP เพิ่ม/ลด, เนื้อหาการประกาศเปลี่ยน, ประกาศใหม่) หลังจากตัดสิน GO ให้ตรวจสอบการทับซ้อนใหม่

## L0-3 การหมดอายุและการส่งต่อของ lock (stale = 72h / TAKEOVER)

lock จะหมดอายุเมื่อ: branch ถูก merge / ลบ, stale, มีคอมเมนต์ `RELEASE`, หรือคอมเมนต์ `HANDED-OFF`
`RELEASE` / `HANDED-OFF` เป็น**คอมเมนต์เกี่ยวกับ lifecycle ของ lock** ไม่ใช่ lane state ตาม L1-4 (รูปแบบดูที่ [template](../templates/issue-template.md)) **ผู้ที่ออกคอมเมนต์ได้มีเพียงเจ้าของ lock (agent ของ WIP)** — การออกโดยผู้อื่นถือว่าไม่มีผล วิธีเดียวที่ผู้อื่นจะปลด lock ได้คือผ่าน stale + TAKEOVER

- **stale = ไม่มีการประกาศ/อัปเดตเกิน 72 ชั่วโมง** (วัดจาก timestamp ของคอมเมนต์ GitHub — การอัปเดตทำได้แค่เขียนคอมเมนต์ใหม่ก็พอ อย่าเพิ่มช่อง timestamp เฉพาะสำหรับวัด staleness: อย่าซ้ำซ้อนกับ metadata ของ platform ฟิลด์ `date` ในตัว WIP declaration ยังคงจำเป็นตาม L0-1 เหมือนเดิม) lane ที่คาดว่าจะเงียบไปนาน สามารถระบุหน้าต่างเวลาที่ยาวได้**พร้อมเหตุผล**ตอนประกาศ WIP (เป็นข้อยกเว้น ไม่ใช่ค่าเริ่มต้น การขยายเวลาภายหลังต้องทำให้เห็นชัดเจนในรูปคอมเมนต์ใหม่)
- **stale ⇒ เจ้าของไม่ชัดเจน ⇒ ห้ามถือว่าว่างโดยไม่บอกกล่าว** ขั้นตอนการรับช่วง lane ที่ stale: checklist การ resume ตาม L0-9 + **คอมเมนต์ `TAKEOVER`** ที่อ้างอิง WIP ที่ stale + ประกาศ WIP ใหม่
- การปรับตัวเลข 72 ชั่วโมงต้องอิงข้อมูลการใช้งานจริง (probe รายสัปดาห์) และทำได้**เฉพาะผ่าน PR ของ handbook นี้เท่านั้น** (ห้ามเปลี่ยนเองภายใน lane) สิ่งที่ปรับไม่ได้คือ invariant ที่ว่า "ห้ามปล่อยให้ stale เป็นอิสระโดยไม่บอกกล่าว"

HOLD **ไม่ใช่**เหตุที่ทำให้ lock หมดอายุ (non-terminal — [L1-5](02-issue-loop.md)) คอมเมนต์ HOLD ต้องระบุการจัดการ lock ให้ชัดเจน (คงไว้จนถึง review-by หรือปล่อย) — HOLD ที่ไม่พูดถึง lock ถือว่าไม่มีผล

## L0-4 1 session = 1 Issue = 1 branch = 1 worktree

**ผู้เขียนที่ active ได้มีเพียง 1 คน**ต่อ 1 lane / 1 worktree ห้ามทำงานใน shared checkout:

```bash
git worktree add ../<repo>-wt/<issue> -b fix/<issue>-<slug> origin/main
```

## L0-5 main ใช้สำหรับ merge เท่านั้น

ห้าม push ตรงเข้า main ทั้งหมดต้องผ่าน PR

## L0-6 ใส่รายการไฟล์ที่แตะ + diff ตรวจสอบไว้ใน PR body

ให้ผู้รีวิวเห็นความต่างจากที่ประกาศ WIP (ไฟล์ที่เพิ่มขึ้น/ลดลงจากที่ประกาศไว้)
ตอน merge ให้เทียบชุดไฟล์ที่ประกาศกับ `git diff --stat` — **ไฟล์ที่อยู่ใน diff แต่ไม่อยู่ในรายการถือว่า blocking** (ส่วนหนึ่งของ completion evidence gate ตาม [L1-7](02-issue-loop.md))

## L0-7 merge ทีละอันเท่านั้น

```
git fetch → rebase origin/main → 再検証（typecheck / tests）→ merge
```

หลัง merge เสร็จ ให้ rebase branch ที่ยังเปิดอยู่โดยเร็ว ห้าม merge สองอันพร้อมกัน
**เมื่อ PR ที่อยู่ติดกันถูก merge ไปแล้ว PR ที่รอคิวอยู่มีหน้าที่ต้อง rebase + ตรวจสอบซ้ำ (รัน typecheck / tests ใหม่)** — แค่ rebase ผ่านไม่ถือว่าทำหน้าที่ครบแล้ว

สคริปต์ / automation ที่แตะ git ต้อง**ระบุ identity / config อย่างชัดเจนผ่าน env ทุกครั้ง และไม่อ่าน・ไม่เขียนสถานะ git ของผู้ใช้** (ไม่พึ่งพา global / local config・index จริง・HEAD หากจำเป็นให้ใช้ temporary index) นี่คือการสรุปเชิงโครงสร้างของอุบัติเหตุ API merge ที่ถูกบันทึกในนามบัญชีที่รันงาน

## L0-8 branch ให้เล็กและอายุสั้น

branch ที่มีอายุยืนจะกลายเป็น rebase hell PR ที่จะ hold การ merge ไว้ต้องระบุสถานะให้ชัดด้วย **คอมเมนต์ HOLD** (ฟิลด์ที่จำเป็นดูที่ [L1-5](02-issue-loop.md)) ห้ามปล่อยทิ้งไว้เงียบๆ

## L0-9 checklist การ resume — ก่อนการเขียนครั้งแรกของ lane ที่ resume/ส่งต่อ

lane ที่ resume / ส่งต่อ / TAKEOVER ต้องโพสต์ผลการตรวจสอบ 4 ข้อต่อไปนี้เป็นคอมเมนต์เดียวใน Issue **ก่อนการเขียนครั้งแรก** ([template](../templates/issue-template.md)):

1. **Lock** — เป็นของตัวเองหรือไม่ หรือหมดอายุตาม L0-3 หรือไม่
2. **File scope** — ชุดไฟล์ที่ประกาศไว้ยังตรงกับ origin/main ปัจจุบันหรือไม่ **และ**ไม่ทับซ้อนกับ WIP/PR ที่ active อยู่ทั้งหมดในปัจจุบันหรือไม่ (รัน `gh issue list` + `gh pr list --state open` ใหม่ ข้อนี้รวมสองการตรวจสอบเข้าเป็น gate เดียวคือ "scope ที่ประกาศไว้ของตัวเองยังใช้ได้อยู่หรือไม่?")
3. **Branch** — fetch / rebase ผ่านโดยไม่มีปัญหาหรือไม่ (ถ้าล้าหลัง/ก่อน merge ให้ rebase)
4. **Done when** — เปลี่ยนไปจากตอน handoff หรือไม่

ถ้าพบความไม่ตรงกัน: ให้เลือกทำอย่างใดอย่างหนึ่งระหว่าง แก้ไข / handoff・TAKEOVER / เปลี่ยนเป็น serial **ห้ามดำเนินงานต่อโดยเงียบๆ บน lock ที่ยัง active ของ agent อื่น**
checklist นี้**ตายตัวที่ 4 ข้อนี้เท่านั้น** ตัวคอมเมนต์ที่โพสต์คือผลงานที่ตรวจสอบได้ในตัวเอง อย่าเพิ่มข้อ (checklist fatigue ถูกระบุว่าเป็น failure mode ที่พบได้)

## หากเกิดอุบัติเหตุ

- เกิด conflict → อย่าตื่นตระหนก แก้ด้วย rebase หากการแก้ไขบานปลาย ให้คอมเมนต์แจ้งข้อเท็จจริงนี้ใน Issue แล้วเปลี่ยนเป็น serial
- จำเป็นต้องแตะไฟล์ที่ไม่ได้ประกาศไว้ → **ก่อนเขียน** ให้ประกาศ WIP ใหม่และตรวจสอบการทับซ้อนอีกครั้ง (L0-2)
- push เข้า main ผิดพลาด → ย้อนกลับด้วย revert commit และบันทึกรายละเอียดไว้ใน Issue
