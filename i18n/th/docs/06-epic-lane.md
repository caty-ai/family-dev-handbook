# ชั้น Epic Lane — รวมการยืนยันของมนุษย์ให้อยู่ในระดับหน่วย Epic

เมื่องานขนาดใหญ่ต้องให้เจ้าของงาน (มนุษย์) ยืนยันทีละ Issue มนุษย์จะกลายเป็นคอขวด ชั้นนี้จะรวมการยืนยันของมนุษย์ให้อยู่แค่ 3 จุดเท่านั้น คือ ทางเข้าของ Epic (kickoff) จุดหยุดที่ตกลงกันไว้ล่วงหน้า และทางออก (การยืนยันการรวมระบบ) โดย**ไม่ลดหย่อน**เกตระหว่างเอเจนต์ (cross review, evidence, declared scope) แม้แต่น้อย
แต่ละกฎมี rule ID ที่คงที่ (`E-1`〜`E-10`) กำกับไว้ ฝั่งสรุป ([docs/04](04-adoption.md)) จะอ้างอิง ID เหล่านี้ ข้อกำหนดเรื่องที่นั่ง review ดูที่ [L1-9〜L1-11](02-issue-loop.md) ท่าทีเมื่อไม่สามารถตรวจสอบได้ดูที่ [docs/05](05-fail-posture.md) (โดยเฉพาะ FP-9)

## นิยามพื้นที่ความเสี่ยงสูง (นิยามเดียวที่ E-3 และ L1-11 อ้างอิงร่วมกัน)

งานที่แตะต้องสิ่งต่อไปนี้เรียกว่า**พื้นที่ความเสี่ยงสูง**:

**การเปิดเผยต่อสาธารณะ/การส่งถึงบุคคลภายนอก / การเรียกเก็บเงิน・การใช้จ่าย / การดำเนินการที่ย้อนกลับไม่ได้ (การลบข้อมูล・migration・การเขียนทับประวัติที่ใช้ร่วมกัน) / ขอบเขตของสิทธิ์・การยืนยันตัวตน・secret / เกตก่อนเปิดตัวสู่สาธารณะ**

การตอบสนองต่อพื้นที่ความเสี่ยงสูงมี 2 อย่าง: หยุดเป็น human checkpoint เสมอ (E-3)・เพิ่มที่นั่ง review เป็น 5 ที่นั่ง ([L1-11](02-issue-loop.md)) ไม่ต้องแยกเก็บรายการทั้งสองไว้คนละที่ — ต้นฉบับที่แท้จริงคือจุดนี้จุดเดียว **นิยามนี้ใช้กับทุกที่ ไม่จำกัดเฉพาะ Epic lane** (การตัดสินจำนวนที่นั่งของ L1-11 อ้างอิงนิยามนี้ในทุกขนาดงาน・ทุก lane — แม้แต่โครงการที่ไม่ได้ใช้ Epic lane ก็ควรอ่านหัวข้อนี้)

## E-1 เกณฑ์การขึ้นเป็น Epic และเงื่อนไขการก่อตั้ง

- การตัดสินความหนักของงานใช้ [L2-1](01-milestone-loop.md) ตามเดิม (ไม่คิดเกณฑ์ตัดสินใหม่) หัวข้อนี้เป็นเพียงการประกาศทางเข้าว่า "งานที่ L2-1 ตัดสินว่าเข้าเกณฑ์ EPIC Issue จะใช้การดำเนินงานในชั้นนี้"
- **Epic จะก่อตั้งขึ้นเมื่อได้รับการอนุมัติ kickoff จากเจ้าของงาน (มนุษย์)** — สิ่งที่ต้องอนุมัติคือเนื้อหา EPIC Issue (รวมตาราง checkpoint ของ E-3・[เทมเพลต](../templates/epic-template.md)) การอนุมัติทำผ่านคอมเมนต์ของเจ้าของงานใน EPIC Issue และคอมเมนต์นั้นคือหลักฐานการก่อตั้ง
- Epic ก่อนได้รับการอนุมัติยังไม่ใช่ Epic: ทั้ง integration branch ของ E-4 และสิทธิ์อิสระของ E-5 จะ**ยังไม่เกิดขึ้น** (ยังคงเป็นการดำเนินงาน Issue ปกติ — [FP-9](05-fail-posture.md)) อย่าให้ความสัมพันธ์ระหว่าง การเป็น Epic ＝ การได้รับสิทธิ์อิสระ ＝ การตัดสินใจอย่างชัดเจนของมนุษย์ พังลง

## E-2 การแยกแกน — Epic แกนฟีเจอร์ × child Issue แกนโมดูล

- **Epic ＝ แกนฟีเจอร์** (เขียนคุณค่าด้วยภาษามนุษย์ เช่น "ทำให้การตอบรับสายเร็วขึ้น") **child Issue ＝ แกนโมดูล** (1 child Issue ＝ 1 โมดูล หรือ 1 repo แยกเป็น child ฝั่ง gateway・child ฝั่งแอป)
- Epic ที่แตะ interface ของขอบเขตโมดูล ให้ **นำ child Issue สำหรับ freeze สัญญา (contract) ขึ้นก่อนเป็นลำดับที่ 0** (การประยุกต์ใช้ [L2-2](01-milestone-loop.md) ภายใน Epic ให้ยืนยัน schema API・protocol และสัญญาที่ทั้งสองฝั่งแตะร่วมกันด้วยเพียงหนึ่งฉบับก่อนเป็นอันดับแรก)
- **จนกว่าลำดับที่ 0 จะถูก merge เข้า epic branch การเริ่มลงมือ implement ของ child Issue อื่นจะทำไม่ได้** (ช่วง serial ภายใน Epic — แนวคิดเดียวกับ "หยุดการทำงานคู่ขนานใหม่จนกว่า boundary PR จะ merge" ของ L2-2) หลัง merge ลำดับที่ 0 แล้ว child branch ทั้งหมดต้อง rebase ก่อนดำเนินการ implement ต่อ
- หลัง freeze สัญญาแล้ว child Issue ที่มีชุดไฟล์ที่ประกาศไว้ไม่ทับซ้อนกันสามารถทำคู่ขนานได้ (ใช้ตาม [L2-4](01-milestone-loop.md) ได้เลย)
- Epic ที่ข้าม repo ให้วาง child Issue ไว้ในแต่ละ repo โดยมี EPIC Issue เป็น hub ความสัมพันธ์ระหว่าง child Issue ให้ประกาศด้วยลิงก์ `Blocked-by` / ลิงก์ผู้สืบทอด (รับเอาข้อ 6a ของ[ภาคผนวก docs/05](05-fail-posture.md)・รายการค้าง **รับเฉพาะส่วนภาระการประกาศเท่านั้น** — ส่วน "ไม่ปิดเป็น MERGED จนกว่าจะถึงจุดสิ้นสุด" (6b) ยังคงเป็นรายการค้างอยู่ child Issue สามารถปิดเป็น MERGED ตามปกติเมื่อถึงจุดสิ้นสุดของตัวเองได้)

## E-3 ตาราง Human Checkpoint

**ส่วนที่จำเป็น**ของ EPIC Issue ([เทมเพลต](../templates/epic-template.md)) แต่ละแถว ＝ "หยุดตรงไหน / แสดงอะไร / ทำไมต้องให้มนุษย์ตัดสิน"

- เจ้าของงานอนุมัติตารางตอน kickoff (เหตุการณ์เดียวกับ E-1) → หลังจากนั้น**หยุดเฉพาะจุดที่มีอยู่ในตาราง**เท่านั้น นอกนั้นให้ทำงานต่อไปจนจบ
- **ทริกเกอร์ที่จำเป็นต้องมีในตาราง**: **พื้นที่ความเสี่ยงสูงทุกรายการ**ที่กล่าวไว้ตอนต้น＋**การเบี่ยงเบนระดับสัญญา (contract)** การตัดสินว่าเป็นระดับสัญญาหรือไม่ใช้การตรวจสอบ 3 ข้ออย่างเป็นกลไก: "แตะต้อง **ผลงานที่ freeze ไว้ในลำดับที่ 0 ของ E-2・Done when ของ EPIC Issue・คำอธิบาย external interface** ข้อใดข้อหนึ่งหรือไม่" สำหรับ Epic ที่ไม่มีลำดับที่ 0 ให้ถือว่า Done when และคำอธิบาย external IF เป็นผลงานที่ freeze ไว้ — อย่าให้การตัดสินเกตเกิดจากเซตว่างเปล่า ([FP-6](05-fail-posture.md))
- **การอนุมัติผ่าน checkpoint ทำโดยคอมเมนต์ที่ชัดเจนของเจ้าของงาน** (รูปแบบเดียวกับการอนุมัติ kickoff ของ E-1・ให้เก็บ URL ของคอมเมนต์อนุมัติไว้ในช่องสถานะของเทมเพลต) การเปลี่ยนแปลงเฉพาะช่องสถานะของตารางไม่ถือเป็นการอนุมัติ ([FP-8](05-fail-posture.md))
- **การเบี่ยงเบนของการตัดสินใจ implement ภายในจะไม่หยุด**: การเปลี่ยนแปลงการออกแบบที่ไม่กระทบสัญญา・external IF・Done when ให้บันทึกลง Epic log (E-7) โดยไม่ต้องหยุด แล้วรีวิวรวมทีเดียวตอน integration review ถ้าทำให้จุดนี้เป็นเป้าหมายการหยุด การยืนยันของมนุษย์แบบต่อ Issue จะกลับมา และวัตถุประสงค์ของชั้นนี้จะพังลงด้วยความขัดแย้งในตัวเอง
- เมื่อเกิด "เรื่องที่ต้องให้มนุษย์ตัดสิน" ที่ไม่ได้คาดการณ์ไว้ ให้**หยุดในฐานะ checkpoint ชั่วคราว** (fail-closed)
- **การแก้ไขตารางเป็นแบบไม่สมมาตร**: การ**เพิ่ม**แถวเอเจนต์ตัดสินใจเองได้・มีผลทันที การ**ลบ・ผ่อนปรน・ทำให้มีเงื่อนไข**ของแถว ให้ถือเป็นการบันทึกแทนที่ตาม [L1-8](02-issue-loop.md) และ**ตารางเดิมยังคงมีผลจนกว่าจะมีคอมเมนต์อนุมัติที่ชัดเจนจากเจ้าของงาน** ([FP-8](05-fail-posture.md) — การแก้ไขเนื้อหาด้วยตัวเองไม่ก่อให้เกิดการอนุมัติ) การตัดสินให้ดูที่**ผลกระทบ**ไม่ใช่รูปแบบ: แม้จะอยู่ในรูปแบบการเพิ่ม แต่ถ้าเนื้อหาทำให้ขอบเขตการใช้งานของแถวเดิมแคบลง (เช่น การเพิ่มแถวที่ระบุว่า "child #5 เป็นต้นไปไม่ต้องหยุดตามแถวนี้") ให้ถือเป็นการผ่อนปรน และไม่มีผลจนกว่าเจ้าของงานจะอนุมัติใหม่ (tighten-only — ทิศทางเดียวกับ [docs/04](04-adoption.md))
- Epic ที่**ไม่มีตาราง・ขาดแถวทริกเกอร์ที่จำเป็น・รูปแบบไม่ถูกต้อง・ยังไม่ได้รับอนุมัติ**ถือว่ายังไม่ได้เริ่มเป็น Epic (E-1) หากในสถานะนี้จำเป็นต้องตัดสิน checkpoint ให้**หยุดและ escalate ไปยังมนุษย์** ([FP-9](05-fail-posture.md)) หากตารางกลายเป็นไม่ถูกต้องระหว่าง**การทำงานของ Epic** ก็ให้หยุดด้วยท่าทีเดียวกัน แต่ให้**คงโครงสร้าง (topology) ไว้** — สิ่งที่หยุดคือสิทธิ์อิสระของ E-5 และการผ่าน checkpoint ไม่ใช่การนำ child lane กลับไปเป็นการดำเนินงาน Issue ปกติที่ไปตรง main (นั่นจะกลายเป็นการเลี่ยง integration gate ของ E-6③)

## E-4 Epic integration branch และ topology

- สร้าง branch `epic/<หมายเลข EPIC Issue>`＋worktree เฉพาะสำหรับ**การรวมระบบ** การ merge เข้า main ตามค่าเริ่มต้นคือ **1 ครั้งตอน Epic เสร็จสมบูรณ์** (L0-5 / [L0-7](03-git-protocol.md) ใช้กับ epic→main ได้เลย)
- **การกำหนดผู้เขียน** (ให้สอดคล้องกับ [L0-4](03-git-protocol.md)):
  - child lane ยังคงเป็น **1 child Issue ＝ 1 branch ＝ 1 worktree** เหมือนเดิม ทำงานใน worktree ของตัวเอง และประกาศ WIP (4 ช่องของ [L0-1](03-git-protocol.md)) ใน child Issue ของตัวเอง **child branch จะแยก (branch) มาจาก epic branch** (ตัวอย่างคำสั่งใน [L0-4](03-git-protocol.md) ที่ระบุ `origin/main` เป็นค่าเริ่มต้นของ lane นอก Epic — ภายใน Epic ให้อ่านแทนด้วย `epic/<หมายเลข>` ถ้าแยกจาก main ความแตกต่างกับ main จะปนเข้าไปทั้งหมดใน child→epic PR และทำให้การตรวจสอบ diff ของ E-6② พังลง)
  - epic worktree ใช้**เฉพาะ**งานรวมระบบ (merge・แก้ conflict・การรับ main เข้ามา) เท่านั้น และผู้เขียนคือ **เฉพาะ 1 คนที่ประกาศ WIP ใน EPIC Issue** (Files to touch คือเป้าหมายของงานรวมระบบเท่านั้น) child lane จะไม่ทำงานใน epic worktree
  - การตัดสินการทับซ้อนทำที่ 2 ชั้น: (a) ระหว่าง child ภายใน Epic เดียวกัน (ใช้ L2-4 โดยอนุโลม) (b) กับ lane นอก Epic (E-10) เกณฑ์ของ default-deny ([L0-2](03-git-protocol.md)) คือ**ชุดไฟล์ที่ประกาศของ child Issue**
- **วิธี merge จาก child→epic ให้ตายตัวเป็น "PR ที่ตั้ง base เป็น epic branch"** (การตรวจสอบ diff และบันทึก review จะเหลืออยู่บน GitHub) merge ทีละหนึ่ง・เมื่อ child ที่อยู่ติดกันถูก merge เข้า epic แล้ว child ที่รออยู่ในคิวมีหน้าที่ต้อง rebase＋ตรวจสอบใหม่ (ใช้ L0-7 โดยอนุโลม)
- **การรับ main เข้ามาเป็นระยะ**: เมื่อ lane นอก Epic ถูก merge เข้า main แล้ว epic branch ต้องรับ main เข้ามาและตรวจสอบใหม่โดยเร็ว (เวอร์ชัน epic ของภาระ rebase ตาม L0-7 การรับเข้ามาทำโดยผู้เขียนของ epic worktree) การรับมือกับปัญหา rebase ของ branch ที่มีอายุยาว ([L0-8](03-git-protocol.md)) แก้ด้วยการรับเข้ามาเป็นระยะนี้และเวลาจำกัดของ E-8
- **การ merge กลางทาง (การ merge epic→main ระหว่างทาง) เป็นข้อยกเว้น** และจะได้รับอนุญาตเฉพาะเมื่อ: ①ระบุไว้ล่วงหน้าเป็น checkpoint ของ E-3 ②กำหนดให้ผ่าน integration gate ของ E-6③ (fully [L1-7](02-issue-loop.md)) ในแต่ละครั้ง หากไม่เข้าเงื่อนไขทั้งสองข้อนี้ การ merge ระหว่างทางถือว่าละเมิด E-4

## E-5 สิทธิ์อิสระในแซนด์บอกซ์

หลังจาก Epic ก่อตั้งแล้ว (E-1) ภายใน worktree/child branch ของ child lane มีอิสระภายในขอบเขตที่ประกาศไว้: หน่วยของ commit・การทำใหม่・refactor・การดำเนินการของ child branch・การเขียนทับ**ประวัติของ branch ตัวเองที่ยังไม่ merge** (รวมถึง force-push)

**"branch ตัวเอง" ＝ ประวัติของ child Issue branch ของตัวเองที่ยังไม่ถูก merge เข้า epic** นอกเหนือจากนี้ไม่ถือเป็น branch ตัวเอง

**สิ่งต้องห้ามที่ไม่เปลี่ยนแปลง** (รายการนี้คือขอบเขตของอิสระ เวลาสรุปห้ามพูดให้อ่อนลงเช่น "อิสระยกเว้นการกระทำที่เป็นการทำลาย"):

1. push ตรงเข้า main ([L0-5](03-git-protocol.md))
2. เขียนนอกขอบเขตที่ประกาศไว้ ([L0-2](03-git-protocol.md) default-deny — เกณฑ์คือชุดไฟล์ที่ประกาศของ child Issue)
3. ลบ・แก้ไข lane อื่น・worktree อื่น
4. **การเขียนทับประวัติของ epic integration branch (force-push・reset)** — epic เทียบเท่ากับ main ภายใน Epic นั้นๆ หากต้องการแทนที่เนื้อหาที่ merge เข้า epic แล้ว ให้ใช้การบันทึกแทนที่＋review ใหม่ตาม [L1-8](02-issue-loop.md) (ห้าม merge ใหม่แบบเงียบๆ)
5. การส่งข้อมูลลับออกภายนอก
6. การดำเนินการเรื่อง E-3 checkpoint โดยไม่ได้รับอนุมัติ

## E-6 Review นาฬิกาทราย — 3 จุด หน่วยต่างกัน

ความหลากหลาย (heterogeneity) ของที่นั่ง review และนิยามจำนวนที่นั่งดูที่ [L1-10 / L1-11](02-issue-loop.md)

1. **Design review ＝ 1 ครั้งต่อ Epic (ก่อนเริ่ม implement — ทำได้ตั้งแต่หลังตั้ง EPIC Issue อย่างช้าที่สุดก่อนเริ่ม implement ของ child Issue แรก นาฬิกาเดียวกับ [L1-9](02-issue-loop.md))**: ระบบใช้ L/H (3 ที่นั่งต่างชนิดกัน) **เฉพาะ Epic ที่มีพื้นที่ความเสี่ยงสูงเท่านั้นที่ใช้ 5 ที่นั่ง** (L1-11) ไม่ให้ child Issue ต้องประชุม design review เต็มรูปแบบซ้ำอีก
2. **Implementation review ＝ ทุกครั้งต่อ child Issue (light gate ของ child→epic)**: จำนวนที่นั่งอ้างอิงตาราง [L1-11](02-issue-loop.md) จาก**ความหนักของ child Issue นั้นเอง** (ไม่ตัดสินจากความหนักของ Epic — ถ้าใส่ review หนักให้ทุก child ความเร็วจะตาย) **แต่ถ้า child Issue แตะพื้นที่ความเสี่ยงสูง (นิยามตอนต้น) ให้ใช้ 5 ที่นั่งของ L1-11 เป็นหลัก ลดจำนวนที่นั่งไม่ได้** **สิ่งที่ลดได้มีแค่จำนวนที่นั่งและรูปแบบการบันทึก ไม่ลดการมีอยู่ของหลักฐาน** สิ่งที่ต้องบันทึกใน child→epic PR: **ผลลัพธ์สุดท้ายของ test green แบบ inline excerpt / cross review ต่างชนิด ([L1-3](02-issue-loop.md)・รวม identity check) / candidate commit SHA / การตรวจสอบชุดไฟล์ที่ประกาศ vs `git diff --stat` ([L0-6](03-git-protocol.md) — ไฟล์ที่มีใน diff แต่ไม่มีในที่ประกาศคือ blocking)** candidate SHA ต้อง**ตรงกับ PR head ณ เวลา merge** — ถ้าเปลี่ยนหลัง review ต้อง review ใหม่ (ใช้ [L1-8](02-issue-loop.md) โดยอนุโลม สิทธิ์อิสระ force-push ของ E-5 **ไม่รวมการแทนที่ SHA ที่ review แล้ว**) สิ่งที่ละไว้ได้มีแค่รูปแบบตารางเทียบกับ Done when (เขียนเป็นข้อความสรุปประเด็นก็ได้ แต่ยังต้องรักษาหลักการของ L1-7 ที่ว่า "อ่านผลลัพธ์สุดท้ายได้จากตัวบันทึกเอง" — หลักฐานที่มีแค่ลิงก์ถือว่าไม่เข้าเกณฑ์)
3. **Integration review ＝ 1 ครั้งต่อ epic→main**: สำหรับ diff รวมทั้งหมดใช้**ระบบตามความหนักของ Epic＋บันทึกความสมบูรณ์ตาม [L1-7](02-issue-loop.md) แบบเต็ม** การยืนยันครั้งสุดท้ายของเจ้าของงานก็อยู่ตรงนี้ (E-7)

## E-7 Epic log และ digest

- ทุกครั้งที่ child Issue ถึงจุดสิ้นสุด ให้คอมเมนต์ 1 รายการใน EPIC Issue: **ทำอะไรสำเร็จ / หลักฐาน (ลิงก์ไปยัง child→epic PR＋ประเด็นสำคัญ) / สิ่งที่ยังไม่บรรลุ Done when・ข้อประนีประนอม (ถ้าไม่มีให้ระบุชัดว่า "ไม่มี") / ขั้นตอนถัดไป** ห้ามละการระบุสิ่งที่ยังไม่บรรลุ・ข้อประนีประนอม — เพื่อป้องกันไม่ให้ digest กลายเป็นสรุปที่สวยหรูเกินจริง
- การยืนยันครั้งสุดท้ายของเจ้าของงานทำผ่าน **digest ของ log＋diff รวม＋การตรวจสอบผลงานที่ใช้งานได้จริง** (ถ้าเป็นสิ่งที่รันได้ให้ทำเดโม ถ้าเป็น docs ให้ render・ตรวจสอบลิงก์ที่เสีย)
- ขอบเขตที่ได้รับอนุมัติแล้วใน checkpoint ของ E-3 ในการยืนยันครั้งสุดท้ายให้แสดง**เฉพาะส่วนต่างจากจุดที่อนุมัติ**เท่านั้น (ให้การอนุมัติ checkpoint มีผลสะสม ไม่ย้ายปริมาณการยืนยันของมนุษย์ทั้งหมดไปไว้ตอนท้ายทีเดียว)

## E-8 เวลาจำกัด — อ่านแยกนาฬิกา 2 เรือน

- **อายุของ branch (เป้าหมายบังคับใช้)**: epic branch ควรเข้า main ภายใน **1〜2 สัปดาห์** (จุดเริ่มต้น ＝ วันที่ของคอมเมนต์อนุมัติ kickoff ของ E-1) หากคาดว่าจะเกินเวลา ให้แบ่ง Epic หรือกำหนด checkpoint สำหรับการ merge กลางทาง (ขั้นตอนข้อยกเว้นของ E-4) การปรับตัวเลขนี้ทำได้เฉพาะผ่าน PR ของ handbook เท่านั้น (จัดการเหมือนกับ 72h ของ [L0-3](03-git-protocol.md)) ขนาด "ประมาณ child Issue กี่ฉบับ" เป็นเพียงแนวทางคร่าวๆ (ไม่ใช่ข้อบังคับ)
- **staleness (นาฬิกาของ lock)**: [L0-3](03-git-protocol.md) ใช้กับ WIP ของ EPIC Issue เช่นเดียวกัน (ค่าเริ่มต้น 72 ชม.) เนื่องจาก Epic อาจมีความเงียบยาวนานตามแผน ให้ใช้**เส้นทางประกาศข้อยกเว้น**ของ L0-3 ตามความจำเป็น (ระบุหน้าต่างเวลาที่ยาวขึ้นพร้อมเหตุผลในการประกาศ WIP) "1〜2 สัปดาห์" คือ อายุของ branch **ไม่ใช่** หน้าต่าง staleness — หมายความว่าทั้งสองอย่าง: อย่าถือว่า epic ที่เงียบไป 5 วันเป็น stale เพียงเพราะยังอยู่ในอายุของมัน และในทางกลับกัน epic ที่ไม่ได้ประกาศหน้าต่างและเกิน 72 ชม. ก็ถือว่า stale ตามปกติ

## E-9 จุดสิ้นสุดของ Epic — เสร็จสมบูรณ์・ยุติ・ส่งต่อ

- คำศัพท์ 5 คำของสถานะ lane ตาม [L1-4](02-issue-loop.md) (WIP / HOLD / MERGED / SUPERSEDED / ABANDONED) ใช้กับสถานะ lane ของ EPIC Issue เช่นกัน
- **เสร็จสมบูรณ์** ＝ สถานะที่ epic→main ผ่าน E-6③ และถูก merge แล้ว・child Issue ทั้งหมดถึงจุดสิ้นสุด・epic branch・worktree ถูกล้างข้อมูลแล้ว
- **การยุติ・ยกเลิก (ABANDONED / SUPERSEDED)** อย่าจบเพียงแค่ประกาศ ต้องระบุใน endpoint comment เสมอ: ①**การจัดการ epic branch** — ยกเลิก (ลบ) หรือ **PR กู้คืน**ส่วนที่มีคุณค่า (การ merge บางส่วนของ epic→main ให้ผ่าน integration gate ของ E-6③ — อย่าลดหย่อนแม้จะเป็นการกู้คืน) ②**การสรุปสถานะของ child Issue** ทั้งที่ merge แล้วและยังไม่ merge (SUPERSEDED / ABANDONED / แยกเป็น Issue อิสระ) ③การล้าง worktree แต่**ห้ามให้ฝั่ง epic ยุติ child lane ที่มี WIP lock ที่ยังมีชีวิตอยู่แต่เพียงฝ่ายเดียว** — การสรุปสถานะให้ทำผ่านการแจ้งเจ้าของ lock＋การประกาศยุติของเจ้าของ lock เอง หรือผ่าน TAKEOVER หลังจากกลายเป็น stale ([L0-3](03-git-protocol.md)) เท่านั้น
- **การส่งต่อ**: การรับช่วงต่อ epic lane ทำผ่าน **TAKEOVER ที่ EPIC Issue** ([L0-3](03-git-protocol.md))＋checklist สำหรับเริ่มใหม่ ([L0-9](03-git-protocol.md)) ถ้ามี child lane ที่ยังมีชีวิตอยู่ ผู้รับช่วงต้องอ่าน WIP กลุ่ม child ใหม่ก่อน และห้ามทำงานรวมระบบทับ lock ที่ยังมีชีวิตอยู่ (เวอร์ชัน epic ของการอ่านซ้ำแบบ optimistic ของ L0-2)

## E-10 การทำงานคู่ขนานของหลาย Epic

- **ชุดที่ประกาศจริงของ Epic ＝ union ของชุดไฟล์ที่ประกาศของ child Issue ∪ ชุดที่ประกาศ WIP ของ EPIC Issue** (ให้รวมเป้าหมายงานรวมระบบของ epic worktree — E-4 — เข้าในการตัดสินการทับซ้อนด้วย ให้รวบรวมบันทึกไว้ในเนื้อหา EPIC Issue・อัปเดตตามจำนวน child ที่เพิ่มขึ้นลดลง)
- การตัดสิน GO สำหรับการทำงานคู่ขนานระหว่าง Epic ด้วยกัน・ระหว่าง Epic กับ lane เดี่ยว ให้ใช้ [L2-4](01-milestone-loop.md) โดยอนุโลมกับชุดที่ประกาศจริงนี้ (GO เฉพาะเมื่อไม่ทับซ้อนกัน・ถ้าตรวจสอบไม่ได้ให้ทำแบบ serial — [FP-1](05-fail-posture.md))
- Epic ที่แตะพื้นที่กว้างของ repo ให้**ทำงานเดี่ยว**ตาม [L2-5](01-milestone-loop.md)
- การ merge epic→main ทำทีละหนึ่งตาม [L0-7](03-git-protocol.md) เมื่อ Epic ที่อยู่ติดกัน (หรือ lane เดี่ยว) ถูก merge เข้า main แล้ว Epic ที่กำลังทำงานอยู่มีหน้าที่ต้องรับ main เข้ามาและตรวจสอบใหม่ (การรับเข้ามาเป็นระยะของ E-4)
