# B บรีฟการมอบหมายงาน — ชั้นที่ทำให้การมอบหมายงานหนึ่งครั้งกลายเป็นสัญญา

ในขณะที่ชั้น L (L2 / L1 / L0) เป็นสัญญาระหว่างเลน (lane) กับคน ชั้น B กำหนด**สัญญาของข้อความคำขอ เมื่อเอเจนต์ส่งงานให้ซับเอเจนต์ (implementation worker, ที่นั่งรีวิว, เอเจนต์ CLI อื่น) ในครั้งเดียว** แต่ละกฎมี rule ID ที่คงที่ (`B-1`ถึง`B-5`) กำกับไว้ ฝั่งสรุป ([docs/04](04-adoption.md)) จะอ้างอิง ID นี้ ต้นฉบับของรูปแบบคือ [templates/brief-template.md](../templates/brief-template.md) ท่าทีเมื่อไม่สามารถตรวจสอบได้ดูที่ [docs/05](05-fail-posture.md)

ที่มา: การส่งต่องานระหว่างเลนได้รับการปกป้องด้วย Issue ในฐานะ SoT ([L1-1](02-issue-loop.md)) แต่**คุณภาพของการมอบหมายงานแต่ละครั้งไม่สามารถรักษาไว้ได้ด้วยระเบียบวินัยของเลนเพียงอย่างเดียว** ฝ่ายที่รับมอบหมายไม่มีประวัติการสนทนาของเรา (fresh context) สิ่งที่ไม่ได้เขียนไว้ในข้อความคำขอก็เหมือนกับไม่มีอยู่จริง การทำให้ข้อความคำขอเองกลายเป็นสัญญาเล็กๆ นี่คือสิ่งที่ชั้น B ทำ

## B-1 โครงสร้างบรีฟ 3 ชั้นที่จำเป็น

ข้อความคำขอสำหรับการมอบหมายงานที่มีเนื้อหาจริง (ที่เกี่ยวข้องกับการ implement / แก้ไข / สร้างโค้ดหรือเอกสาร) ต้องมี 3 ส่วนต่อไปนี้เสมอ:

1. **ข้อกำหนดการ implement (Goal)** — เป้าหมาย ข้อจำกัด บริบทที่วางไว้ล่วงหน้า ขอบเขตที่แตะต้องได้
2. **การตรวจสอบการ implement (Self-verification)** — รายการตรวจสอบที่ผู้ปฏิบัติงานรันด้วยตัวเองก่อนส่งมอบ
3. **เกณฑ์การรีวิว (Reviewer criteria)** — มุมมองที่การรีวิวขั้นถัดไปจะพิจารณา

เหตุผล: ถ้าส่งแค่ข้อกำหนดอย่างเดียว คำว่า "เสร็จแล้ว" จะกลายเป็นสิ่งที่ตรวจสอบไม่ได้ การส่งมอบว่าอะไรคือความสมบูรณ์ (self-verification) และควรสงสัยตรวจดูอะไรบ้าง (มุมมองการรีวิว) **ตั้งแต่ตอนมอบหมายงาน** ทำให้สามารถตัดสินผลงานด้วยหลักฐานแทนที่จะเป็นคำกล่าวอ้าง (ทิศทางเดียวกับ [L1-7](02-issue-loop.md))

## B-2 เงื่อนไขการใช้ — ถ้าลังเลให้ใส่

- **จำเป็น**: การมอบหมายงานที่เกี่ยวข้องกับการ implement / แก้ไข / สร้าง แม้ขนาด S ถ้าผลงานจะยังคงอยู่ใน repository ก็ต้องใส่
- **ยกเว้น**: การค้นหา / สืบค้นข้อมูลแบบอ่านอย่างเดียว / คำถามสั้นๆ (ที่ผลลัพธ์ถูกใช้แล้วทิ้งไปในทันที)
- ถ้าลังเลให้ใส่ (เลือกฝั่งที่หนักกว่า — ท่าทีเดียวกับการตัดสินความหนักของ [L2-1](01-milestone-loop.md))

## B-3 Issue คือต้นฉบับ — บรีฟเป็นสิ่งที่ได้มาจากมัน

- Goal / เงื่อนไขความสำเร็จ / ขอบเขตที่แตะต้องได้ ของบรีฟ ได้มาจาก **Why / Done when / รายการไฟล์ที่คาดว่าจะแตะ** ของ Issue ที่รับผิดชอบ ([L1-2](02-issue-loop.md))
- ถ้าบรีฟกับ Issue ขัดแย้งกัน **ให้ยึด Issue เป็นหลัก** ผู้ที่สังเกตเห็นความขัดแย้งต้องแก้ไข Issue ก่อนแล้วจึงมอบหมายงาน — ห้ามปล่อยให้เบี่ยงเบนไปโดยเงียบๆ (ทิศทางเดียวกับ [L1-8](02-issue-loop.md))
- การที่บรีฟหลายฉบับเกิดจาก Issue เดียวกันถือเป็นเรื่องปกติ (บรีฟแยกกันสำหรับรอบ implement, รอบแก้ไข, ที่นั่งรีวิว)

## B-4 วางบริบทล่วงหน้า — ไม่ให้ต้องสำรวจเอง

- ข้อเท็จจริงที่ฝ่ายรับมอบหมายต้องใช้ (path, ข้อกำหนด, ข้อจำกัด, ข้อห้าม, ลักษณะเฉพาะของสภาพแวดล้อม) ให้**วางไว้ล่วงหน้า**ในบรีฟ ไม่ฝากให้ฝ่ายรับมอบหมายไปสำรวจเอง
- เหตุผล: การสำรวจให้ผลลัพธ์ที่แกว่งไปตามแต่ละฝ่ายที่รับมอบหมาย ในที่นั่งแบบ read-only หรือสภาพแวดล้อม sandbox บางครั้งไม่สามารถสำรวจได้เลยด้วยซ้ำ การวางไว้ล่วงหน้าเป็นวิธีเดียวที่ทำให้คุณภาพเท่ากันได้ ไม่ว่าจะเป็น fresh context หรือ read-only
- เมื่อมอบหมายงานรีวิว ให้**ระบุรูปแบบความล้มเหลวที่แย่ที่สุดอย่างเจาะจง** (เช่น "สิ่งที่แย่ที่สุดจากการเปลี่ยนแปลงนี้คือการที่ ◯◯ เกิดขึ้น") ซึ่งจะทำให้เป้าหมายการตรวจจับชัดเจนกว่าการบอกแค่ "หาบั๊ก"
- ในการมอบหมายที่ต้องการความเป็นกลาง (blind) (ที่นั่งรีวิวอิสระ) **ห้ามผสม**ข้อสังเกตจากที่นั่งอื่นหรือการวิเคราะห์ล่วงหน้าของตัวเองเข้าไป สิ่งที่วางไว้ล่วงหน้าคือข้อเท็จจริง ไม่ใช่ข้อสรุป

## B-5 รักษารูปแบบให้ตรวจสอบได้ด้วยเครื่อง

- ทั้ง 3 ส่วนต้องรักษารูปแบบที่**ตรวจสอบได้ด้วยเครื่องจากข้อความหัวข้อที่ตายตัว** (ไม่ปล่อยให้กลายเป็นข้อความอิสระ) ข้อความหัวข้อแต่ละบ้านสามารถแปลเป็นภาษาท้องถิ่นได้ แต่เมื่อกำหนดแล้วต้องตายตัว
- แนะนำให้ฝั่งเครื่องมือมอบหมายงานติดตั้งการตรวจสอบ (เช่น hook) ที่บล็อกก่อนเริ่มงานหากมีส่วนที่ขาดหายไป การ implement การตรวจสอบอยู่นอกขอบเขตของ handbook นี้ (เป็นเรื่องของชั้นเครื่องมือของแต่ละบ้าน)
- **แม้ในสภาพแวดล้อมที่ไม่มีการตรวจสอบ B-1 ถึง B-4 ก็ยังมีผลในฐานะสัญญา** — fail-open ไม่ได้หมายความว่า "ไม่จำเป็นต้องมีรูปแบบ" (ทิศทางเดียวกับ [docs/05](05-fail-posture.md))
