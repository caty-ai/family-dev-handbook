# T เกณฑ์เทสต์ & CI — ชั้นที่สะสมหลักฐานความถูกต้องไว้ที่เครื่อง

ในขณะที่ชั้น L (L2 / L1 / L0) เป็นสัญญาว่า "จะดำเนินงานอย่างไร" และชั้น R เป็นสัญญาว่า "รับอะไร" ชั้น T กำหนด**ขั้นต่ำสุดที่รีโปจะพิสูจน์ความถูกต้องของตัวเองต่อเนื่องด้วยเทสต์และ CI — การจัดเตรียมเบื้องต้น การสะสม regression test การเชื่อมเข้ากับรูปแบบการมอบหมายงาน การไม่ merge ขณะยังแดง การปิดงาน release ด้วยแท็ก สัญญาเอาต์พุตเทสต์ และความซื่อตรงของแบดจ์กับตัวเลข** แต่ละกฎมี rule ID ที่คงที่ (`T-1`ถึง`T-7`) กำกับไว้ และแต่ละข้อระบุขอบเขตการใช้ไว้ใน〔 〕 ฝั่งสรุป ([docs/04](04-adoption.md)) จะอ้างอิง ID เหล่านี้ หลักการทั่วไปของการบังคับใช้ gate ในฐานะ check คือ [R-6](09-rejection-rubric.md) ท่าทีเมื่อไม่สามารถตรวจสอบได้ดูที่ [docs/05](05-fail-posture.md)

ที่มา: ความน่าเชื่อถือของรีโปสาธารณะถูกตัดสินจากภายนอกทันทีด้วย "มีเทสต์หรือไม่・CI เขียวหรือไม่" ประตูหลักฐานสำหรับ merge ([L1-7](02-issue-loop.md)) และการบังคับใช้ check ([R-6](09-rejection-rubric.md)) มีแนวคิดอยู่แล้ว แต่**ยังไม่มีชั้นที่บังคับการจัดเตรียมเบื้องต้นและการสะสมของเทสต์กับ CI** การสะสมเทสต์ไม่ใช่ฟังก์ชันของ CI แต่สร้างได้ด้วยกฎการปฏิบัติงานเท่านั้น ในขณะที่การนำโปรโตคอลนี้ไปปฏิบัติจริงผ่านบรีฟการมอบหมาย ([ชั้น B](07-delegation-brief.md)) ดังนั้นเมื่อฝังไว้ในรูปแบบก็จะทำให้บังคับใช้ได้จริง

## T-1 การจัดเตรียมเบื้องต้น — ตั้งโครงไว้ก่อน〔รีโปใหม่ที่มีโค้ด = MUST / รีโปเดิม = เลนถัดไปที่แตะโค้ด / รีโปที่ไม่มีโค้ด = N/A พร้อมเหตุผล〕

**รีโปที่มีโค้ดต้องจัดเตรียมเทสต์รันเนอร์และ CI workflow ตั้งแต่ตอนสร้าง สิ่งที่ gate ต้องมีคือ test ส่วนภาษาที่มีการตรวจสอบชนิดข้อมูลก็ต้องมี typecheck อยู่ใน gate เดียวกันด้วย แม้เทสต์จะยังมี 0 ตัวก็ต้องตั้งโครงไว้ก่อน**

เหตุผล: การนำเข้ามาทีหลังจะทำให้ "รีโปที่ไม่มีวัฒนธรรมเทสต์" กลายเป็นเรื่องสำเร็จรูปไปแล้ว ขอเพียงมีโครงอยู่ เทสต์ต่อจากนี้ก็จะถูกสะสมขึ้นเองโดย T-2 / T-3 รูปแบบของ CI ที่ใช้เป็นค่าเริ่มต้นคือ [templates/ci/](../templates/ci/README.md) (ใช้ workflow ของตัวเองก็ยังเข้าเงื่อนไขได้) CI ที่จัดเตรียมแล้วให้ลงทะเบียนไว้ใน required status checks เพื่อยืนยันด้วยเครื่อง (ขั้นตอน 5-6 ใน templates/ci ในสภาพแวดล้อมที่ตั้ง branch protection ไม่ได้ ให้รักษาไว้ด้วยการปฏิบัติงานแทน)

การย้อนไปใช้กับรีโปเดิมเป็นแบบ **opportunistic** — ให้จัดเตรียม T-1 ไปพร้อมกันในเลนถัดไปที่แตะโค้ด โดยเพิ่ม 1 บรรทัดใน Issue นั้น ไม่ตั้งเลนสำรวจสำหรับจัดเตรียมโดยเฉพาะ (ไม่จ่ายงานล่วงหน้าให้กับรีโปที่ไม่ได้ใช้งาน — [หลักการเรียบง่าย](why-simple-systems.md))

**รีโปที่ไม่มีโค้ด** ซึ่งมีแต่เอกสาร・วัสดุ・การตั้งค่า **ให้เขียน N/A พร้อมเหตุผล** (คำศัพท์เดียวกับ [L1-7](02-issue-loop.md)) — เขียนเหตุผลไว้ 1 บรรทัดใน Issue ตอนสร้าง อย่าเติมโครงด้วยเทสต์หลอกที่ไม่มีเนื้อหา (อย่าสร้าง "เป้าหมาย 0 รายการแล้วเขียว" ขึ้นเอง — กับดักที่อยู่ใน [templates/ci/](../templates/ci/README.md))

## T-2 ค่าเริ่มต้นของ regression test〔PR แก้บั๊กขนาด M / L / H โดย Issue ลูกใน Epic ให้ตัดสินตามความหนักของ Issue ลูก〕

**PR แก้บั๊กขนาด M / L / H (ตามเกณฑ์แยกขนาดของ [L2-1](01-milestone-loop.md) Issue ลูกใน Epic ให้ตัดสินตามความหนักของ Issue ลูกเช่นเดียวกับ [E-6](06-epic-lane.md)) ให้แนบเทสต์สร้างซ้ำของบั๊กนั้น (fix ก่อนแดง・fix แล้วเขียว) เป็นค่าเริ่มต้น**

ขนาด S (typo・จุดเดียว 1 ไฟล์ระดับนี้) ได้รับการยกเว้น การประเมินขนาดต่ำกว่าจริงเพื่อหวังยกเว้นถูกกันไว้ด้วย "เมื่อไม่แน่ใจให้ปัดไปทางหนักกว่า" ของฝั่งตัดสินขนาด (L2-1) ข้อบังคับเรื่องเทสต์สำหรับการเพิ่มฟีเจอร์ไม่อยู่ในขอบเขตของข้อนี้ — [T-3](#t-3) และ Done when ของแต่ละ Issue เป็นผู้รับผิดชอบแทน

เหตุผลกรณีที่แนบไม่ได้ ให้เขียนเป็น**โครงสร้าง 2 ชั้น**:

1. **3 ประเภทที่กำหนดไว้แล้ว** (รายการปิด — ตัดสินได้ด้วยเครื่อง):
   - **ขึ้นอยู่กับสภาพแวดล้อม** — เกิดซ้ำได้เฉพาะบนเครื่องจริง・อุปกรณ์จริง・OS เฉพาะเท่านั้น
   - **ขึ้นอยู่กับบริการภายนอก** — ต้องการการตอบสนองจริงของ API ภายนอก・ระบบภายนอก
   - **ต้นทุนการสร้างซ้ำสูงเกินไป** — ต้นทุนการสร้างไม่คุ้มกับคุณค่าของการแก้ไข (เฉพาะกรณีที่ owner ยอมรับเท่านั้น)
2. **กรณีที่ไม่เข้า 3 ประเภทข้างต้นเป็นอำนาจของ owner โดยเฉพาะ** — บันทึกข้อเท็จจริงและเหตุผลของการตัดสินโดย owner ไว้ 1 บรรทัดใน PR เหตุผลแบบเขียนอิสระใช้ได้เฉพาะกรณีที่เป็นการตัดสินโดย owner เท่านั้น

เหตุผลที่ทำเป็นรายการปิด: เพื่อป้องกันไม่ให้ "เหตุผลที่เขียนไม่ได้" แบบเขียนอิสระ เพิ่มจำนวนขึ้นอย่างไม่มีที่สิ้นสุดในฐานะข้ออ้าง

## T-3 การเชื่อมกับบรีฟ — ฝังการสะสมไว้ในรูปแบบ〔การมอบหมายที่มีการเปลี่ยนแปลงโค้ด = ในบรรดาที่ใช้ B-1 เฉพาะส่วนที่เปลี่ยนแปลงโค้ดของรีโป〕

**"การตรวจสอบการ implement (Self-verification)" ของบรีฟการมอบหมายที่มีการเปลี่ยนแปลงโค้ด ให้รวม "เทสต์ที่เพิ่ม/แก้ไข พร้อมผลการรัน" ไว้เป็นหัวข้อมาตรฐาน** (ต้นฉบับของรูปแบบ: [templates/brief-template.md](../templates/brief-template.md))

การมอบหมายที่ไม่ได้เพิ่มเทสต์ ให้รวม "ไม่ได้เพิ่ม + เหตุผล" ไว้ในรายงานส่งมอบ เหตุผลให้เขียนเป็น**รายการปิด**:

1. **เข้าเงื่อนไขการยกเว้นของ T-2** (ขนาด S) — เขียนไว้ 1 บรรทัดก็เพียงพอ
2. **การเปลี่ยนแปลงไม่มีเป้าหมายให้เทสต์** (เฉพาะการตั้งค่า・การประกาศ เป็นต้น)
3. **เทสต์ที่มีอยู่แล้วครอบคลุมการเปลี่ยนแปลงนี้อยู่แล้ว** — ต้องระบุเทสต์นั้นได้
4. **เข้าประเภทใดประเภทหนึ่งของ T-2** (ขึ้นอยู่กับสภาพแวดล้อม / ขึ้นอยู่กับบริการภายนอก / ต้นทุนการสร้างซ้ำสูงเกินไป = owner อนุมัติ)
5. **เข้าเงื่อนไขชั้นที่ 2 ของ owner ใน T-2** — ต้องระบุบันทึกการตัดสินนั้นได้

เหตุผล: การสะสมเทสต์จะเป็นไปโดยอัตโนมัติก็ต่อเมื่อฝังไว้ในรูปแบบของการมอบหมายเท่านั้น ฝ่ายรับมอบหมายมี fresh context ดังนั้นสิ่งที่ไม่ได้เขียนไว้ในบรีฟก็เท่ากับไม่มีอยู่จริง (ทิศทางเดียวกับ [B-4](07-delegation-brief.md))

## T-4 fail-closed merge — ห้าม merge ขณะยังแดง〔ทุกรีโป = MUST〕

**ห้าม merge ขณะ CI ยังแดง** ข้อนี้กำหนด**ข้อยกเว้นที่บัญญัติไว้เพียงข้อเดียว**ต่อ "ผ่านทั้งเทสต์และ lint" ในหัวข้อ "นิยามของความเสร็จสมบูรณ์" ของ [docs/02](02-issue-loop.md) และสถานะ CI ให้ระบุไว้ในบันทึกการเสร็จสิ้น (L1-7)

ข้อยกเว้นมีเพียงข้อเดียวเท่านั้นคือ **สีแดงที่รู้อยู่แล้วและไม่เกี่ยวข้องกับ PR นี้** (เช่น สีแดงจากบั๊กที่มีอยู่แล้วในฝั่ง main) เงื่อนไขความสำเร็จคือ**ต้องครบทุกข้อ**:

1. **การพิสูจน์ความไม่เกี่ยวข้อง** — แนบบันทึกที่ยืนยันว่าสีแดงเดียวกันเกิดซ้ำบน base (สถานะที่ไม่มีการเปลี่ยนแปลงของ PR นี้) ไว้แบบ inline ในบันทึกการเสร็จสิ้น (หลักฐาน ไม่ใช่คำกล่าวอ้าง — L1-7②)
2. **การผูก identity ของสีแดง** — เขียนชื่อ check ที่ล้มเหลว + ตัวระบุ workflow run + วันที่สังเกต ให้สอดคล้องกับ candidate SHA
3. **การอ้างอิงถึง Issue ที่เกี่ยวข้อง** — หากไม่มี Issue ที่อ้างอิงได้ ให้สร้างขึ้นก่อน Issue ต้องมีทริกเกอร์การออก ([LC-1](08-lifecycle.md)・กำหนดเวลา หรือเงื่อนไขความสำเร็จ) เสมอ และเมื่อทริกเกอร์หมดอายุ ข้อยกเว้นนี้ก็หมดอายุตามไปด้วย
4. **การตรวจสอบการมีอยู่จริงของการตัดสินโดย owner** — ต้องเหลือร่องรอยในรูปแบบที่**บุคคลที่สามยืนยันการมีอยู่จริงได้** เช่น คอมเมนต์ใน PR จากบัญชีของ owner เอง การเขียนไว้แค่ในเนื้อหาบันทึกการเสร็จสิ้นเพียงอย่างเดียวไม่ถือว่าข้อยกเว้นสำเร็จ ([FP-8](05-fail-posture.md) / [R-6](09-rejection-rubric.md))

การเขียนขอบเขตให้ชัดเจน:

- **สีแดงที่เกิดขึ้นเป็นครั้งคราว (flaky) ไม่นับรวมอยู่ใน "รู้อยู่แล้วและไม่เกี่ยวข้อง"** — หากต้องการรวมด้วย owner ต้องตัดสินและบันทึกทุกครั้ง นอกเหนือจาก 4 เงื่อนไขข้างต้น
- **ห้ามเขียนสถานะที่ไม่มี CI ว่าเป็น green** — เลนที่แตะโค้ดในรีโปที่ยังไม่จัดเตรียม CI ห้าม merge จนกว่าจะเข้าเงื่อนไข T-1 ในเลนเดียวกัน (กรณีแก้ไขฉุกเฉินที่ไม่ทันการณ์ owner สามารถผ่อนปรนได้ด้วยการตัดสินโดยตรง โดยต้องเหลือ Issue สำหรับจัดเตรียม T-1 พร้อมทริกเกอร์การออกตาม LC-1 ไว้ด้วย และการตัดสินนี้ต้องบันทึกในรูปแบบที่ตรวจสอบการมีอยู่จริงได้เช่นเดียวกับเงื่อนไขข้อ 4)
- **`CI: N/A` ใช้ได้เฉพาะกรณีที่ CI ไม่ตรวจสอบการเปลี่ยนแปลงนั้น** (เหตุผล = เขียนหลักฐานว่าเป็นสิ่งที่อยู่นอกขอบเขตการตรวจสอบ) การเปลี่ยนแปลงที่ CI ทำงาน แม้จะไม่ใช่โค้ดก็ห้ามใช้ N/A
- ในรีโปที่ตั้ง required status checks ไว้ ห้ามใช้สิทธิ์ข้อยกเว้นด้วยการ**ปลด required ออก** — ให้บันทึกไว้เป็นการดำเนินการที่ owner ทำอย่างชัดแจ้ง

สีแดงที่ไม่มีการอ้างอิง・ข้อยกเว้นที่ตรวจสอบไม่ได้ ไม่ถือว่าเป็นข้อยกเว้น (fail-open ไม่ได้แปลว่า "ผ่าน" — [docs/05](05-fail-posture.md))

## T-5 ค่าเริ่มต้นของ release — ปิดงาน release ด้วยแท็ก〔merge ที่มีการเปลี่ยนแปลงระดับ release = MUST / นอกเหนือจากนั้น = N/A พร้อมเหตุผล〕

**บันทึกความเสร็จสมบูรณ์ทุกฉบับ ([L1-7](02-issue-loop.md)) ต้องมีช่อง release** ค่าที่ใส่ต้องเป็นหนึ่งใน 3 คำศัพท์แบบปิดต่อไปนี้ และเลนที่นำ**การเปลี่ยนแปลงระดับ release** (merge ที่เปลี่ยนพฤติกรรมที่ผู้ใช้ต้องเจอ・public API・สิ่งที่แจกจ่าย・บรรทัดฐานที่ผู้ใช้ต้องทำตาม) เข้า main จะเลือก `N/A` ไม่ได้ **merge ที่ตัดสินใจยาก ให้ถือเป็นระดับ release ไว้ก่อน** (ทิศทางเดียวกับ [L2-1](01-milestone-loop.md) "เมื่อไม่แน่ใจให้ปัดไปทางหนักกว่า" — ไม่ปล่อยให้ความลังเลหนีไปทาง N/A ซึ่งเบากว่า):

1. **`release: vX.Y.Z`** — คำประกาศว่าจะสร้างแท็กที่จุดเสถียรของ merge นี้ แท็กต้องเป็น **annotated + SemVer** และสร้างที่**คอมมิตที่ merge นี้ทิ้งไว้บน main** (ถ้าเป็น squash / rebase merge ก็คือ SHA ใหม่บน main) ณ เวลาที่บันทึก แท็กยังไม่ถูกสร้าง — สิ่งที่เขียนในช่องคือคำประกาศ และ**เลนจะประกาศ MERGED ไม่ได้จนกว่าจะสร้างแท็กแล้วใส่ tag URL ไว้ในคอมเมนต์ MERGED** ([L1-4 การสิ้นสุด](../templates/issue-template.md)) ภาระผูกพันเรื่อง tag URL นี้จะถือว่าปฏิบัติตามก็ต่อเมื่อ **Release มีอยู่จริงบน GitHub Releases** ด้วย (แม้มีแค่แท็กเปล่า URL `/releases/tag/<ชื่อ>` ก็คืนค่า 200 — การมี URL ไม่ได้หมายความว่ามี Release) ในรีโปที่มี carrier release-sync ([templates/ci/](../../../templates/ci/README.md)) โดยปกติจะทำให้ครบด้วย **green run** หลัง push แท็ก แต่การตรวจสอบยังเป็นหน้าที่ของเลน — **run ที่ไม่เกิดขึ้น・เป็นสีแดง・หรือไม่มี carrier ไม่ถือว่าได้ปฏิบัติตาม** เลนที่ยังไม่ปฏิบัติตามจะ**ไม่สิ้นสุดและค้างอยู่ในสถานะ WIP** จึงติดอยู่บนนาฬิกา stale ของ [L0-3](03-git-protocol.md) แม้แต่ในรีโปที่ไม่มีเลนถัดไปเข้ามา การลืมสร้างแท็กก็ยังมองเห็นได้ (MERGED ที่ขาด tag URL หรือการมีอยู่จริงของ Release ถือว่า**รูปแบบไม่ถูกต้อง** การสิ้นสุดจึงไม่สำเร็จ = ถือว่าไม่ active ตาม [L1-4](02-issue-loop.md)) การเพิ่มรายงานการปฏิบัติตามนี้ถือเป็นการทำตามคำประกาศ ไม่ใช่การแก้ไขตาม [L1-8](02-issue-loop.md) โดยหลักการแล้ว**ชื่อแท็กต้องตรงกับชื่อที่ประกาศไว้** — จะใช้ชื่ออื่นได้**เฉพาะ**เมื่อ scope เปลี่ยนไปหลัง review จนเวอร์ชันเปลี่ยนไปด้วยเท่านั้น โดยต้องเขียนความต่างและเหตุผลไว้ 1 บรรทัดในคอมเมนต์ MERGED (ห้ามสร้างแท็กเวอร์ชันอื่นแบบเงียบๆ) หากจะเปลี่ยนคำประกาศเองเป็น `deferred` ให้ทำผ่านบันทึกแทนที่ตาม L1-8 (ไม่แก้ไขแบบเงียบๆ) ในการทำงานที่เลนเองไม่มีสิทธิ์สร้างแท็ก **HOLD** ที่ตั้ง owner เป็นผู้มีสิทธิ์สร้างแท็ก (5 ฟิลด์ตาม [L1-5](02-issue-loop.md)) ถือเป็นทางออกที่ถูกต้อง
2. **`release: deferred`** — คำประกาศว่าจะยังไม่สร้างแท็กตอนนี้ ต้องแนบ**การอ้างอิง Issue ที่มีทั้งเหตุผลและทริกเกอร์การออก** (กำหนดเวลาหรือเงื่อนไขความสำเร็จ = [LC-1](08-lifecycle.md)) — ถ้าไม่มี Issue ให้อ้างอิง ก็สร้างขึ้นก่อน (รูปแบบเดียวกับ **T-4** ข้อ③: เนื้อหา PR ที่ merge แล้วจะไม่กลับมาอยู่ในสายตาใครอีก จึงต้องวางไว้บนพื้นที่ที่จะโผล่กลับมาได้ คือ Issue) deferred ที่ขาดการอ้างอิง Issue หรือทริกเกอร์ถือว่าไม่ถูกต้อง (= blocking เหมือนไม่มีช่องเลย) **deferred ที่ทริกเกอร์หมดอายุจะเสีย "สิทธิ์ไม่ต้องสร้างแท็ก"** — MERGED ของเลนนั้นยังคงมีผลอยู่ แต่**merge ระดับ release ครั้งถัดไปเลือก `deferred` ไม่ได้ (ต้องเป็น `vX.Y.Z`)** การหมดอายุเองไม่ปิดกั้นบันทึกความเสร็จสมบูรณ์ครั้งถัดไป (ถ้าปิดกั้น จะไม่มีทางแก้สถานะยังไม่ปฏิบัติตามที่ไม่มีทั้งชื่อที่ประกาศไว้และคอมมิตเป้าหมายได้เลย — เหตุผลเดียวกับที่ **T-4** ข้อ③ ให้แค่ข้อยกเว้นหมดอายุ ไม่ปิดกั้นตัวบันทึก) การทำให้ deferred ที่เลยกำหนดมองเห็นได้เป็นหน้าที่ของ Issue ที่อ้างอิงไว้ deferred จะ**คลี่คลายเมื่อ merge ระดับ release ครั้งถัดไปปฏิบัติตาม `vX.Y.Z` แล้ว** และปิด Issue ที่อ้างอิงไว้ (ถ้ายังมีงานค้าง ให้ประกาศใหม่ด้วยทริกเกอร์ใหม่)
3. **`release: N/A`** — ใช้ได้เฉพาะ merge ที่ไม่ใช่ระดับ release เท่านั้น เหตุผลต้องเขียนเป็น**รายการปิด**: ①เป็น docs ที่ไม่มีบรรทัดฐานให้ผู้ใช้ทำตามเท่านั้น ②เป็นการจัดระเบียบภายในที่ไม่เปลี่ยนพฤติกรรม・public API・สิ่งที่แจกจ่ายเลยสักอย่าง ③เป็นแค่การเชื่อมต่อ CI・สภาพแวดล้อมการพัฒนา ④เป็น merge ระหว่างทางที่ยังไปไม่ถึง main (gate ของ Epic child→epic = [E-6](06-epic-lane.md)②) **กรณีที่ไม่เข้าประเภทข้างต้นเป็นอำนาจของ owner โดยเฉพาะ** — บันทึกข้อเท็จจริงและเหตุผลของการตัดสินนั้นไว้ 1 บรรทัด (รูปแบบเดียวกับ **T-2**) N/A ที่ไม่มีเหตุผลถือว่าไม่ถูกต้อง (= blocking เหมือนไม่มีช่องเลย) ในรีโปที่แจกจ่ายบรรทัดฐาน (เช่นคู่มือเล่มนี้) การเปลี่ยนแปลง docs เองก็ถือเป็นระดับ release แล้ว — อย่าใช้ "แค่ docs" เป็นข้ออ้างเลือก N/A

**ช่องที่ไม่มีอยู่จริง・ค่าว่างเปล่า・placeholder ที่ยังไม่ได้แก้ไข・ค่าที่นอกเหนือจาก 3 คำศัพท์ ทั้งหมดนี้ถือว่ายังไม่กรอกและเป็น blocking** (แรงเท่ากับช่อง CI ของ **T-4**) รูปแบบไม่ใช่ "พยายามอย่าลืม" แต่เป็น "ถ้าลืม บันทึกความเสร็จสมบูรณ์จะผ่านไม่ได้" — นี่คือการใช้แนวคิดของชั้น T (ฝังไว้ในรูปแบบก็บังคับใช้ได้จริง) ในแบบเดียวกัน: CI ถูกทำให้เป็นชั้นด้วย T-1〜T-4 แล้ว แต่ release ยังไม่มีชั้นมาก่อน ข้อนี้จึงมาปิดช่องว่างนั้น

เนื้อหาของแท็กและการเซ็นรับรอง:

- release notes (tag message หรือ Releases) ต้องอ้างอิง**ตัวชี้ไปยังหลักฐานที่ตรวจสอบได้อย่างน้อย 1 จุด** (CI run・PR ที่มีบันทึกความเสร็จสมบูรณ์ ฯลฯ) — สอดคล้องกับหลักการไม่วางตัวเลขที่ตรวจสอบไม่ได้ ([ชั้น R](09-rejection-rubric.md)) นี่เป็นบริบทคนละเรื่องกับวินัยหลักฐานของตัวบันทึกความเสร็จสมบูรณ์เอง ([L1-7](02-issue-loop.md)② "หลักฐานที่มีแค่ลิงก์ถือว่าไม่เข้าเกณฑ์") — ตัวบันทึกยึด inline เป็นหลัก ส่วนแท็กแค่มีตัวชี้ก็พอ
- **รีโปที่มีกลไกตรวจสอบลายเซ็น (เช่น updater・ที่เครื่องตรวจสอบลายเซ็นของแท็ก) ต้องใช้แท็กที่เซ็นรับรอง คีย์เป็นแบบ per-repo** รีโปที่บังคับเซ็นรับรอง ต้องระบุในรายงานการปฏิบัติตามของ MERGED ว่ามีลายเซ็นหรือไม่ด้วยคำเดียว (เพื่อให้เห็นการขาดลายเซ็นได้จากตัวบันทึก) นอกเหนือจากนั้น annotated ก็เพียงพอ ส่วนลายเซ็นเป็น SHOULD
- ขนาดของการขึ้นเวอร์ชัน (MAJOR / MINOR / PATCH) เป็นไปตามกฎทั่วไปของ SemVer ข้อนี้ไม่ได้บังคับ

การเขียนขอบเขตให้ชัดเจน:

- **ป้องกันการใช้ deferred พร่ำเพรื่อ** — ในรีโปเดียวกัน ถ้า deferred ของ merge ระดับ release ติดกัน 2 ครั้ง merge ระดับ release ครั้งที่ 3 จะเลือก deferred ไม่ได้ (ต้องสร้างแท็ก) การนับติดกันให้นับจาก**คอลัมน์ของ merge ระดับ release** (merge ที่เป็น N/A ไม่นับรวม) และ**รีเซ็ตเมื่อปฏิบัติตาม `vX.Y.Z` แล้ว** เพื่อให้นับย้อนหลังตรวจสอบได้ **บันทึกความเสร็จสมบูรณ์ทุกฉบับ**ต้องเขียนกำกับไว้ 1 บรรทัดว่า merge ระดับ release ครั้งก่อนหน้าในรีโปเดียวกันมีค่า release อะไรและปฏิบัติตามแล้วหรือยัง (ช่อง `previous release`) จำนวนครั้ง**ยืนยันได้แค่ไล่ตาม `previous release` ของเลนก่อนหน้าไปทีละขั้น** — ถ้าครั้งก่อนเป็น deferred และครั้งก่อนหน้านั้นก็เป็น deferred ครั้งนี้ต้องเป็น `vX.Y.Z` (ทิศทางเดียวกับการยกระดับของ [R-6](09-rejection-rubric.md) "ทำให้การนับตรวจสอบย้อนหลังได้")
- **การเชื่อมโยงการปฏิบัติตาม** — บันทึกความเสร็จสมบูรณ์ นอกจากช่อง release ของตัวเองแล้ว ยังต้องยืนยันว่า**คำประกาศ release ของ merge ระดับ release ครั้งก่อนหน้าในรีโปเดียวกันได้ปฏิบัติตามแล้ว** ([L1-7](02-issue-loop.md)⑦) **การตัดสิน "ปฏิบัติตามแล้ว" ปิดด้วยเกณฑ์ต่อไปนี้**: `vX.Y.Z` = สร้างแท็กแล้ว, MERGED มี URL และ Release มีอยู่จริง (**หากขาดแท็ก・URL・หรือการมีอยู่จริงของ Release อย่างใดอย่างหนึ่ง ถือว่ายังไม่ปฏิบัติตาม = blocking**) / `deferred` = ตราบใดที่ทริกเกอร์ยังไม่หมดอายุ ถือว่ารอการปฏิบัติตามและไม่ปิดกั้น แม้หมดอายุก็ไม่ถือเป็น blocking แต่จะจำกัดตัวเลือกครั้งถัดไปตามข้อ 2 ข้างต้น / `N/A` = ไม่นับอยู่ในคอลัมน์ระดับ release จึงไม่อยู่ในขอบเขตนี้ ช่อง release **ไม่ใช่สิ่งทดแทนการดำเนินการสร้างแท็กจริง** — ช่องนี้คือบันทึกของการตัดสินใจ คำประกาศ `vX.Y.Z` ที่ยังไม่ปฏิบัติตามจะถูกกันไว้ทั้งสองทาง คือทำให้ MERGED สำเร็จไม่ได้ (ข้อ 1 ข้างต้น) และปิดกั้นเลนถัดไป
- **ความเข้มงวดในการบังคับใช้เท่ากันทุกรีโป** — รีโปที่ไม่มีการเปลี่ยนแปลงระดับ release merge ทุกครั้งจะตกเป็น N/A โดยธรรมชาติ จึงไม่มีภาระจริงกับ scratch ส่วนตัว ส่วนจะแยกความเข้มงวดระหว่างสาธารณะ/ส่วนตัวหรือไม่ เป็นเรื่องที่จะพิจารณาแยกต่างหาก เมื่อได้ข้อสรุปแล้วจะปรับ〔 〕ของข้อนี้ตาม
- **gate ของ Epic child→epic ([E-6](06-epic-lane.md)②) ไม่อยู่ในข้อบังคับเรื่องแท็ก** — ตัวช่องเองยังคงจำเป็นเหมือนทุกบันทึก โดยค่าจะเป็นประเภท④ข้างต้น (`N/A (ก่อนรวม epic)`) การบังคับให้สร้างแท็กใช้กับ merge รวมของ epic→main เท่านั้น (E-6③ แบบ L1-7 เต็มรูปแบบ)
- การย้อนไปใช้กับส่วนที่ยังไม่ได้ติดแท็กในอดีตไม่อยู่ในขอบเขตของข้อนี้ (ข้อนี้มีผลกับ "merge นับจากนี้ไป" ส่วนที่ผ่านมาแล้วเป็นดุลยพินิจของ owner แต่ละรีโป)
- record-vs-reality PR-side check และ scheduled drift sweep ติดตามใน [Issue #106](https://github.com/caty-ai/family-dev-handbook/issues/106) (follow-up ที่มีทริกเกอร์การออกตาม LC-1)

## T-6 สัญญาเอาต์พุตเทสต์ — ทำข้อเท็จจริงของการรันให้เป็นหนึ่งบรรทัดที่เครื่องอ่านได้〔รีโปใหม่ที่มีโค้ด = MUST / รีโปเดิม = จัดเตรียมใน Issue เดียวกันเมื่อมีเลนถัดไปที่แตะโค้ด เทสต์ หรือ CI test job อย่างใดอย่างหนึ่ง (opportunistic แบบเดียวกับ T-1) / รีโปที่ไม่ใช่โค้ดและไม่มีรันเนอร์ = N/A พร้อมเหตุผล〕

**ตัวรันเนอร์เทสต์ต้องทำตามสัญญาเอาต์พุตที่ทำให้เครื่องตัดสินได้ว่า "อะไรได้รัน・อะไรไม่ได้รัน・และเพราะเหตุใด"** ต้องครบ 5 เงื่อนไข:

1. **บรรทัดสรุป (ตัวสัญญาหลัก)** — รันเนอร์ต้องพิมพ์หนึ่งบรรทัดต่อไปนี้ในเอาต์พุต โดยนิพจน์ปรกตินี้เองคือรูปแบบฉบับหลัก:

   ```
   suites: declared=([0-9]+) executed=([0-9]+) skipped=([0-9]+)
   ```

   นิยามความหมาย: `declared` = จำนวน suite ที่ลงทะเบียนทั้งหมด / `executed` = จำนวนที่รันจริงจนถึง PASS หรือ FAIL / `skipped` = จำนวนที่รายงานตามจริงว่า SKIP **เงื่อนไขคงที่คือ `declared = executed + skipped`** หากไม่เป็นจริงถือว่ามีรายการตกหล่น (silent drop) = แดง รันเนอร์ต้องรวมตัวเลขแบบไดนามิก — **การฝังคงที่ (เช่น echo ค่าคงที่) ผิดข้อนี้** (เพราะเครื่องตรวจสอบที่มาของค่าไม่ได้ จึงเป็นรายการตรวจในการรีวิวการนำไปใช้) บรรทัดนี้ต้องปรากฏอย่างน้อยหนึ่งครั้ง และหากมีหลายครั้งให้ถือว่า**ค่าที่ตรงครั้งสุดท้ายเป็นฉบับถูกต้อง** การตัด suite ออกจาก declared (ยกเลิกการลงทะเบียน) ต้องบันทึก 1 บรรทัดใน Issue ของเลนที่ตัดสินใจ — การยกเลิกที่ไม่มีบันทึกถือเหมือนรายการตกหล่น
2. **คำศัพท์ผลลัพธ์** — การแสดงผลของ**รันเนอร์หรือ wrapper ที่ครอบครัวเขียน**ต้องใช้คำสามคำ `PASS` / `FAIL` / `SKIP` ส่วนเอาต์พุตดิบตามธรรมชาติของ framework เช่น pytest / unittest / vitest **ไม่อยู่ใต้ข้อจำกัดนี้** (gate ของเครื่องอ่านบรรทัดสรุปกับ exit code ดังนั้นเอาต์พุต framework ปล่อยผ่านได้ตามเดิม)
3. **เซตปิดของ exit code** — `0` = ไม่มี FAIL / `1` = มี FAIL / `2` = ข้อผิดพลาดด้านวิธีใช้หรืออินพุต / `127` = **dependency ที่จำเป็นหายไป** (ตรวจใน preflight แล้วระบุสาเหตุทาง stderr เป็น `missing-dep: <ชื่อ>` ก่อนออก — ห้ามรายงาน dependency ที่หายเป็นเทสต์ล้มเหลวหรือ input error) การขาดสภาพแวดล้อมที่เป็นทางเลือก (เช่นไม่มีอุปกรณ์จริง) ไม่ใช้ 127 แต่เป็น **SKIP** และนับใน skipped ของบรรทัดสรุป
4. **แม้จบผิดปกติก็ต้องพิมพ์สรุป** — วางโครงสร้างให้บรรทัดสรุปยังออกแม้รันเนอร์ตายกลางทาง (`trap finish EXIT` ใน bash เป็นเพียงตัวอย่างที่ไม่ใช่บทบัญญัติ; Python atexit, การประกอบใน Makefile และกลไกเทียบเท่าล้วนใช้ได้) ไม่มีสรุป = ตัดสินไม่ได้ = แดง ([FP-6](05-fail-posture.md)) — แต่สีแดงนี้จะเกิดจริงหลังการเชื่อมต่อในข้อ 5 ด้านล่าง
5. **การเชื่อมต่อกระทบยอด CI (เงื่อนไขความสำเร็จของการนำไปใช้)** — จะเรียกว่าข้อนี้ "จัดเตรียมแล้ว" ได้ต่อเมื่อ gate กระทบยอดฝั่ง CI ([templates/ci/](../../../templates/ci/README.md) test-lint; อินพุต reusable `require_suite_reconciliation: true`) **เปิดใช้งานแล้ว** แค่พิมพ์บรรทัดสรุปหรืออ้างตัวบท ยังเรียกว่าจัดเตรียมแล้วไม่ได้ ("แค่วางไว้" = [FP-5](05-fail-posture.md)) รีโปนอกขอบเขตต้องทิ้ง N/A ที่ชัดเจนไว้ใน Issue — ความเงียบไม่ใช่ N/A การเชื่อมต่อรูปแบบ skipped (สรุปสามค่า) ให้ทำหลังการรองรับ skipped ของ gate กระทบยอด (#80 delta) เข้า main แล้ว หากสลับลำดับ SKIP ที่รายงานอย่างซื่อตรงจะกลายเป็นแดง

**เพดานอัตรา SKIP** — `skipped × 5 > declared` (= เกิน 20% และ declared > 0) เป็นแดง รีโปที่เปลี่ยนเพดานต้อง**วางค่าฉบับหลักไว้ในอินพุตของ CI caller (ตำแหน่งที่เครื่องอ่าน)** และบันทึกเหตุผลของการเปลี่ยนไว้ 1 บรรทัดใน PR หรือ Issue ที่มีทริกเกอร์ [LC-1](08-lifecycle.md) (รูปแบบเดียวกับ [LC-3](08-lifecycle.md) ที่ "ตัวเลขอยู่ในการตั้งค่าท้องถิ่นและต้องบันทึกการเปลี่ยน") การเปลี่ยนโดยไม่มีบันทึกไม่มีผล จึงใช้ค่าเริ่มต้น 20% สูตรนี้ทำให้รีโปที่ declared ≤ 4 มี "SKIP 0 เป็นค่าเริ่มต้น" — เป็นความตั้งใจ (รีโปยิ่งเล็กยิ่งควรรันได้ทั้งหมด; หากจำเป็นต้องมี SKIP ถาวร ให้ประกาศเปลี่ยนเพดาน) SKIP คือการรายงานตามจริงว่า "ไม่มีสภาพแวดล้อม" ไม่ใช่ทางหนีถาวร — สีแดงเมื่อเกินเพดานเป็นการเร่งให้ "แก้สภาพแวดล้อม หรือบันทึกการตัดสินใจนำเป้าหมายออกจากขอบเขต"

เหตุผล: คำว่า "เทสต์รันแล้ว" กลายเป็นคำกล่าวอ้างด้วยตัวเองได้ง่าย ค่า declared / executed / skipped สามค่าและเงื่อนไขคงที่ ลดเส้นทาง "ทำเหมือนว่ารันแล้ว" (suite หายแบบเงียบ・เอา SKIP ปนใน executed・เปลี่ยนตัวหารด้วยการยกเลิกการลงทะเบียน・รายงาน dependency ที่หายผิดประเภท) ให้เหลือการตรวจด้วยเครื่องหนึ่งบรรทัด การตรึงรูปแบบเป็นนิพจน์ปรกติทำให้การกระทบยอดฝั่ง CI (W0-3 reusable test-lint) ใช้ implementation ร่วมหนึ่งชุดได้กับทุกรีโป

การเขียนขอบเขตให้ชัดเจน:

- ข้อนี้เป็น**สัญญาเอาต์พุต** ไม่บังคับเนื้อหาเทสต์ ความละเอียด หรือการเลือก framework (รันเนอร์แนะนำดูภาคผนวก)
- ระดับ suite ก็เพียงพอ (ไม่ต้องถึงระดับ test case — ความละเอียดเป็นดุลยพินิจของรีโป การทำ SKIP ภายใน suite ให้มองเห็นทำได้ด้วยการแยก suite)
- รีโปใหม่ที่มีเทสต์ 0 รายการ (มีเพียงโครง T-1) อาจไม่พิมพ์สรุป (ยังไม่เชื่อมจึงไม่แดง) หรือพิมพ์ `declared=0 executed=0 skipped=0` (executed=0 เป็นแดง = เลือกฝั่งที่ไม่สร้าง "เขียวทั้งที่เป้าหมาย 0") — ใช้ได้ทั้งคู่และแนะนำแบบหลัง
- รันเนอร์ของแฮนด์บุ๊กนี้เองเป็น**เป้าหมายแรกของข้อนี้** (เลนที่เผยแพร่ตัวบทต้องทำให้ `make test` ของรีโปตัวเองตรงสัญญาก่อน merge — หลัก pilot)

## T-7 ความซื่อตรงของแบดจ์และตัวเลข — สีเขียวต้องเป็นสีที่เครื่องลงเท่านั้น〔รีโปสาธารณะที่มี README = MUST / รีโปอื่น = หากวางตัวเลขหรือแบดจ์ให้ใช้วินัยเดียวกัน (scratch ส่วนตัวที่ไม่วางย่อมเป็น N/A)〕

**สิ่งที่แสดงใน README หรือ docs ซึ่งดูเหมือน "ผ่านการตรวจแล้ว" ต้องเชื่อมกับผลตรวจของเครื่องเท่านั้น** ต้องครบ 3 เงื่อนไข:

1. **ระบุสถานะ CI (ห้ามซ่อน "ยังไม่ตรวจ" ด้วยการไม่มีแบดจ์)** — รีโปสาธารณะที่มี README ต้องแสดงสถานะ CI ด้วย**หนึ่งในสองแบบ**: ① live badge ของ **workflow ที่รัน test gate ของ T-1** (badge.svg ของ GitHub Actions หรือ live endpoint เทียบเท่าที่ชี้ workflow นั้น; **แบดจ์ของ workflow อื่นที่ไม่รันเทสต์ ต่อให้เขียวก็ไม่ผ่านข้อนี้**) ② หากยังไม่มี CI ให้ใช้แบดจ์ static สีเทา `CI: not yet` การไม่แสดง หรือเอาสีเขียวของ workflow อื่นมาแทน ล้วนผิดข้อกำหนด
2. **เซตปิดของสี** — สีที่อนุญาตให้แบดจ์ static ใช้มีเพียง **`lightgrey` / `blue` (รวมการแสดงข้อเท็จจริง เช่น ภาษาและไลเซนส์)** เป็นรายการปิด `green` / `brightgreen` / `success` / `passing` และค่า hex สีเขียวเทียบเท่าห้ามใช้กับแบดจ์ static (ตรวจที่สภาพจริง ไม่ใช่ตัวสะกด — [R-6](09-rejection-rubric.md)) มีเพียง live badge ที่เครื่องลงสีจึงอ้างสีเขียวได้
3. **ตัวเลขวัดจริงและส่วน Project status** — หากเขียนตัวเลขที่อ่านเหมือนค่าที่วัดจริง (จำนวนเทสต์ coverage ประสิทธิภาพ) ใน README / docs ต้องแนบ**run URL ของการวัดนั้นและวันที่วัด** หากแนบไม่ได้ก็ไม่เขียนตัวเลข (ไม่วางตัวเลขที่ตรวจสอบไม่ได้ — [ชั้น R](09-rejection-rubric.md)) ตัวเลขที่**ต่างจากค่าที่วัดจริง**ใน run ที่ใหม่กว่าของ workflow นั้นถือว่า stale — อัปเดตหรือลบ (ถ้าค่าไม่เปลี่ยน แค่มี run ใหม่ยังไม่ถือว่า stale) ค่าออกแบบหรือค่าเป้าหมายเขียนได้หากระบุว่า "เป้าหมาย" แต่ห้ามทำให้ดูเหมือนค่าจริง (เช่น "passed" ที่ไม่มี run URL) หาก README มีส่วนสถานะ รูปแบบมาตรฐานคือด้านล่าง (**รูปแบบนี้เป็นฉบับหลัก** — ไม่ใช้อ้างอิงรีโปภายนอก):

   ```markdown
   ## Project status

   [live badge (badge.svg ของ T-1 test workflow) หรือ CI: not yet (สีเทา)]

   - CI: <มี test-lint gate หรือไม่ และชื่อ workflow ที่เชื่อม>
   - สภาพแวดล้อมที่ตรวจแล้ว: <OS / runtime ที่วัดจริง>
   - maturity: <stable / beta / reference ฯลฯ>
   - ข้อจำกัดที่ทราบ: <แจกแจง หากไม่มีให้เขียน "ไม่มี" ชัดเจน>
   ```

เหตุผล: คนภายนอกตัดสินความน่าเชื่อถือของรีโปทันทีจาก "แบดจ์เขียวหรือไม่" สีเขียวที่เขียนเองแยกจากสีเขียวของเครื่องไม่ได้ และสีเขียวที่เขียนเองเพียงหนึ่งจุดก็**ทำลายพลังหลักฐานของสีเขียวในทุกรีโปของครอบครัว** ในทางกลับกัน การไม่วางแบดจ์เพื่อซ่อน "ยังไม่ตรวจ" ก็เป็นอีกด้านของคำโกหกเดียวกัน (วัดจริง: มีแบดจ์เขียวที่เขียนเอง 9 จุดอยู่ร่วมกับรีโปที่ไม่มี CI และไม่แสดงอะไร) การจำกัดการแสดงให้เชื่อมกับเครื่อง ทำให้ เขียว = การตรวจรันแล้ว / เทา = ไม่มีการตรวจ มีความหมายเดียวกันทุกรีโป

การเขียนขอบเขตให้ชัดเจน:

- เป้าหมายคือ "การแสดงที่อาจปลอมเป็นผลตรวจ" — แบดจ์ข้อเท็จจริง (ภาษา ไลเซนส์ เวอร์ชัน กลุ่ม blue) ใช้ได้อิสระ
- **มีอิสระที่จะไม่เขียนตัวเลขเสมอ** (ข้อนี้คือ "ถ้าจะเขียนต้องซื่อตรง" + "เฉพาะสถานะ CI เป็นหน้าที่ของรีโปสาธารณะ")
- scratch ส่วนตัวที่ไม่มี README และไม่เผยแพร่ย่อมเป็น N/A **รีโปที่เผยแพร่แต่ไม่มี README** จะเข้าสู่ขอบเขตข้อนี้ในเลนที่จัดเตรียม README (B8 ฯลฯ) — การไม่มี README ไม่ใช่ข้อยกเว้นถาวร
- การยกระดับข้อนี้เป็น check (ตรวจแบดจ์ static สีเขียว・ตัวเลข stale ฯลฯ) ให้ทำตาม [R-6](09-rejection-rubric.md) โดยติดตามผ่าน Issue

## ภาคผนวก (ไม่ใช่บทบัญญัติ) — ตารางแนะนำตัวรันเนอร์

สิ่งที่บทบัญญัติเรียกร้องมีแค่ "จัดเตรียมรันเนอร์ + CI" เท่านั้น การเลือกเครื่องมือขึ้นอยู่กับดุลยพินิจของผู้ implement ตารางนี้เป็น**ข้อมูลอ้างอิงที่ไม่ใช่บทบัญญัติ** การอัปเดตตารางไม่นับเป็นการแก้ไขบทบัญญัติ

| ภาษา / runtime | รันเนอร์ที่แนะนำ | หมายเหตุ |
|---|---|---|
| TypeScript / JavaScript (Node) | vitest | ถ้า standard library เพียงพอก็ใช้ `node:test` ได้เช่นกัน |
| Python | pytest | — |
| Shell | bats-core | — |
| Go | `go test` | มาตรฐานของภาษา |
| Rust | `cargo test` | มาตรฐานของภาษา |
| Swift / iOS | XCTest | รันด้วย `xcodebuild test` |
| สภาพแวดล้อมรัน CI | GitHub Actions | ค่าเริ่มต้นเมื่อรีโปอยู่บน GitHub |
