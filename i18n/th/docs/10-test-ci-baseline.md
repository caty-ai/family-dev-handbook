# T เกณฑ์เทสต์ & CI — ชั้นที่สะสมหลักฐานความถูกต้องไว้ที่เครื่อง

ในขณะที่ชั้น L (L2 / L1 / L0) เป็นสัญญาว่า "จะดำเนินงานอย่างไร" และชั้น R เป็นสัญญาว่า "รับอะไร" ชั้น T กำหนด**ขั้นต่ำสุดที่รีโปจะพิสูจน์ความถูกต้องของตัวเองต่อเนื่องด้วยเทสต์และ CI — การจัดเตรียมเบื้องต้น การสะสม regression test การเชื่อมเข้ากับรูปแบบการมอบหมายงาน และการไม่ merge ขณะยังแดง** แต่ละกฎมี rule ID ที่คงที่ (`T-1`ถึง`T-4`) กำกับไว้ และแต่ละข้อระบุขอบเขตการใช้ไว้ใน〔 〕 ฝั่งสรุป ([docs/04](04-adoption.md)) จะอ้างอิง ID เหล่านี้ หลักการทั่วไปของการบังคับใช้ gate ในฐานะ check คือ [R-6](09-rejection-rubric.md) ท่าทีเมื่อไม่สามารถตรวจสอบได้ดูที่ [docs/05](05-fail-posture.md)

ที่มา: ความน่าเชื่อถือของรีโปสาธารณะถูกตัดสินจากภายนอกทันทีด้วย "มีเทสต์หรือไม่・CI เขียวหรือไม่" ประตูหลักฐานสำหรับ merge ([L1-7](02-issue-loop.md)) และการบังคับใช้ check ([R-6](09-rejection-rubric.md)) มีแนวคิดอยู่แล้ว แต่**ยังไม่มีชั้นที่บังคับการจัดเตรียมเบื้องต้นและการสะสมของเทสต์กับ CI** การสะสมเทสต์ไม่ใช่ฟังก์ชันของ CI แต่สร้างได้ด้วยกฎการปฏิบัติงานเท่านั้น ในขณะที่การนำโปรโตคอลนี้ไปปฏิบัติจริงผ่านบรีฟการมอบหมาย ([ชั้น B](07-delegation-brief.md)) ดังนั้นเมื่อฝังไว้ในรูปแบบก็จะทำให้บังคับใช้ได้จริง

## T-1 การจัดเตรียมเบื้องต้น — ตั้งโครงไว้ก่อน〔รีโปใหม่ที่มีโค้ด = MUST / รีโปเดิม = เลนถัดไปที่แตะโค้ด / รีโปที่ไม่มีโค้ด = N/A พร้อมเหตุผล〕

**รีโปที่มีโค้ดต้องจัดเตรียมเทสต์รันเนอร์และ CI workflow ตั้งแต่ตอนสร้าง สิ่งที่ gate ต้องมีคือ test ส่วนภาษาที่มีการตรวจสอบชนิดข้อมูลก็ต้องมี typecheck อยู่ใน gate เดียวกันด้วย แม้เทสต์จะยังมี 0 ตัวก็ต้องตั้งโครงไว้ก่อน**

เหตุผล: การนำเข้ามาทีหลังจะทำให้ "รีโปที่ไม่มีวัฒนธรรมเทสต์" กลายเป็นเรื่องสำเร็จรูปไปแล้ว ขอเพียงมีโครงอยู่ เทสต์ต่อจากนี้ก็จะถูกสะสมขึ้นเองโดย T-2 / T-3 รูปแบบของ CI ที่ใช้เป็นค่าเริ่มต้นคือ [templates/ci/](../templates/ci/README.md) (ใช้ workflow ของตัวเองก็ยังเข้าเงื่อนไขได้) CI ที่จัดเตรียมแล้วให้ลงทะเบียนไว้ใน required status checks เพื่อยืนยันด้วยเครื่อง (ขั้นตอน 5-6 ใน templates/ci ในสภาพแวดล้อมที่ตั้ง branch protection ไม่ได้ ให้รักษาไว้ด้วยการปฏิบัติงานแทน)

การย้อนไปใช้กับรีโปเดิมเป็นแบบ **opportunistic** — ให้จัดเตรียม T-1 ไปพร้อมกันในเลนถัดไปที่แตะโค้ด โดยเพิ่ม 1 บรรทัดใน Issue นั้น ไม่ตั้งเลนสำรวจสำหรับจัดเตรียมโดยเฉพาะ (ไม่จ่ายงานล่วงหน้าให้กับรีโปที่ไม่ได้ใช้งาน — [หลักการเรียบง่าย](why-simple-systems.md))

**รีโปที่ไม่มีโค้ด** ซึ่งมีแต่เอกสาร・วัสดุ・การตั้งค่า **ให้เขียน N/A พร้อมเหตุผล** (คำศัพท์เดียวกับ [L1-7](02-issue-loop.md)) — เขียนเหตุผลไว้ 1 บรรทัดใน Issue ตอนสร้าง อย่าเติมโครงด้วยเทสต์หลอกที่ไม่มีเนื้อหา (อย่าสร้าง "เป้าหมาย 0 รายการแล้วเขียว" ขึ้นเอง — กับดักที่อยู่ใน [templates/ci/](../templates/ci/README.md))

## T-2 ค่าเริ่มต้นของ regression test〔PR แก้บั๊กขนาด M / L / H โดย Issue ลูกใน Epic ให้ตัดสินตามความหนักของ Issue ลูก〕

**PR แก้บั๊กขนาด M / L / H (ตามเกณฑ์แยกขนาดของ [L2-1](01-milestone-loop.md) Issue ลูกใน Epic ให้ตัดสินตามความหนักของ Issue ลูกเช่นเดียวกับ [E-6](06-epic-lane.md)) ให้แนบเทสต์สร้างซ้ำของบั๊กนั้น (fix ก่อนแดง・fix แล้วเขียว) เป็นค่าเริ่มต้น**

ขนาด S (typo・จุดเดียว 1 ไฟล์ระดับนี้) ได้รับการยกเว้น การประเมินขนาดต่ำกว่าจริงเพื่อหวังยกเว้นถูกกันไว้ด้วย "เมื่อไม่แน่ใจให้ปัดไปทางหนักกว่า" ของฝั่งตัดสินขนาด (L2-1) ข้อบังคับเรื่องเทสต์สำหรับการเพิ่มฟีเจอร์ไม่อยู่ในขอบเขตของข้อนี้ — [T-3](#t-3) และ Done when ของแต่ละ Issue เป็นผู้รับผิดชอบแทน

เหตุผลกรณีที่แนบไม่ได้ ให้เขียนเป็น**โครงสร้าง 2 ชั้น**:

1. **3 ประเภทที่กำหนดไว้แล้ว** (รายการปิด — ตัดสินได้ด้วยเครื่อง):
   - **ขึ้นอยู่กับสภาพแวดล้อม** — เกิดซ้ำได้เฉพาะบนเครื่องจริง・อุปกรณ์จริง・OS เฉพาะเท่านั้น
   - **ขึ้นอยู่กับบริการภายนอก** — ต้องการการตอบสนองจริงของ API ภายนอก・ระบบภายนอก
   - **ต้นทุนการสร้างซ้ำสูงเกินไป** — ต้นทุนการสร้างไม่คุ้มกับคุณค่าของการแก้ไข (เฉพาะกรณีที่ owner ยอมรับเท่านั้น)
2. **กรณีที่ไม่เข้า 3 ประเภทข้างต้นเป็นอำนาจของ owner โดยเฉพาะ** — บันทึกข้อเท็จจริงและเหตุผลของการตัดสินโดย owner ไว้ 1 บรรทัดใน PR เหตุผลแบบเขียนอิสระใช้ได้เฉพาะกรณีที่เป็นการตัดสินโดย owner เท่านั้น

เหตุผลที่ทำเป็นรายการปิด: เพื่อป้องกันไม่ให้ "เหตุผลที่เขียนไม่ได้" แบบเขียนอิสระ เพิ่มจำนวนขึ้นอย่างไม่มีที่สิ้นสุดในฐานะข้ออ้าง

## T-3 การเชื่อมกับบรีฟ — ฝังการสะสมไว้ในรูปแบบ〔การมอบหมายที่มีการเปลี่ยนแปลงโค้ด = ในบรรดาที่ใช้ B-1 เฉพาะส่วนที่เปลี่ยนแปลงโค้ดของรีโป〕

**"การตรวจสอบการ implement (Self-verification)" ของบรีฟการมอบหมายที่มีการเปลี่ยนแปลงโค้ด ให้รวม "เทสต์ที่เพิ่ม/แก้ไข พร้อมผลการรัน" ไว้เป็นหัวข้อมาตรฐาน** (ต้นฉบับของรูปแบบ: [templates/brief-template.md](../templates/brief-template.md))

การมอบหมายที่ไม่ได้เพิ่มเทสต์ ให้รวม "ไม่ได้เพิ่ม + เหตุผล" ไว้ในรายงานส่งมอบ เหตุผลให้เขียนเป็น**รายการปิด**:

1. **เข้าเงื่อนไขการยกเว้นของ T-2** (ขนาด S) — เขียนไว้ 1 บรรทัดก็เพียงพอ
2. **การเปลี่ยนแปลงไม่มีเป้าหมายให้เทสต์** (เฉพาะการตั้งค่า・การประกาศ เป็นต้น)
3. **เทสต์ที่มีอยู่แล้วครอบคลุมการเปลี่ยนแปลงนี้อยู่แล้ว** — ต้องระบุเทสต์นั้นได้
4. **เข้าประเภทใดประเภทหนึ่งของ T-2** (ขึ้นอยู่กับสภาพแวดล้อม / ขึ้นอยู่กับบริการภายนอก / ต้นทุนการสร้างซ้ำสูงเกินไป = owner อนุมัติ)
5. **เข้าเงื่อนไขชั้นที่ 2 ของ owner ใน T-2** — ต้องระบุบันทึกการตัดสินนั้นได้

เหตุผล: การสะสมเทสต์จะเป็นไปโดยอัตโนมัติก็ต่อเมื่อฝังไว้ในรูปแบบของการมอบหมายเท่านั้น ฝ่ายรับมอบหมายมี fresh context ดังนั้นสิ่งที่ไม่ได้เขียนไว้ในบรีฟก็เท่ากับไม่มีอยู่จริง (ทิศทางเดียวกับ [B-4](07-delegation-brief.md))

## T-4 fail-closed merge — ห้าม merge ขณะยังแดง〔ทุกรีโป = MUST〕

**ห้าม merge ขณะ CI ยังแดง** ข้อนี้กำหนด**ข้อยกเว้นที่บัญญัติไว้เพียงข้อเดียว**ต่อ "ผ่านทั้งเทสต์และ lint" ในหัวข้อ "นิยามของความเสร็จสมบูรณ์" ของ [docs/02](02-issue-loop.md) และสถานะ CI ให้ระบุไว้ในบันทึกการเสร็จสิ้น (L1-7)

ข้อยกเว้นมีเพียงข้อเดียวเท่านั้นคือ **สีแดงที่รู้อยู่แล้วและไม่เกี่ยวข้องกับ PR นี้** (เช่น สีแดงจากบั๊กที่มีอยู่แล้วในฝั่ง main) เงื่อนไขความสำเร็จคือ**ต้องครบทุกข้อ**:

1. **การพิสูจน์ความไม่เกี่ยวข้อง** — แนบบันทึกที่ยืนยันว่าสีแดงเดียวกันเกิดซ้ำบน base (สถานะที่ไม่มีการเปลี่ยนแปลงของ PR นี้) ไว้แบบ inline ในบันทึกการเสร็จสิ้น (หลักฐาน ไม่ใช่คำกล่าวอ้าง — L1-7②)
2. **การผูก identity ของสีแดง** — เขียนชื่อ check ที่ล้มเหลว + ตัวระบุ workflow run + วันที่สังเกต ให้สอดคล้องกับ candidate SHA
3. **การอ้างอิงถึง Issue ที่เกี่ยวข้อง** — หากไม่มี Issue ที่อ้างอิงได้ ให้สร้างขึ้นก่อน Issue ต้องมีทริกเกอร์การออก ([LC-1](08-lifecycle.md)・กำหนดเวลา หรือเงื่อนไขความสำเร็จ) เสมอ และเมื่อทริกเกอร์หมดอายุ ข้อยกเว้นนี้ก็หมดอายุตามไปด้วย
4. **การตรวจสอบการมีอยู่จริงของการตัดสินโดย owner** — ต้องเหลือร่องรอยในรูปแบบที่**บุคคลที่สามยืนยันการมีอยู่จริงได้** เช่น คอมเมนต์ใน PR จากบัญชีของ owner เอง การเขียนไว้แค่ในเนื้อหาบันทึกการเสร็จสิ้นเพียงอย่างเดียวไม่ถือว่าข้อยกเว้นสำเร็จ ([FP-8](05-fail-posture.md) / [R-6](09-rejection-rubric.md))

การเขียนขอบเขตให้ชัดเจน:

- **สีแดงที่เกิดขึ้นเป็นครั้งคราว (flaky) ไม่นับรวมอยู่ใน "รู้อยู่แล้วและไม่เกี่ยวข้อง"** — หากต้องการรวมด้วย owner ต้องตัดสินและบันทึกทุกครั้ง นอกเหนือจาก 4 เงื่อนไขข้างต้น
- **ห้ามเขียนสถานะที่ไม่มี CI ว่าเป็น green** — เลนที่แตะโค้ดในรีโปที่ยังไม่จัดเตรียม CI ห้าม merge จนกว่าจะเข้าเงื่อนไข T-1 ในเลนเดียวกัน (กรณีแก้ไขฉุกเฉินที่ไม่ทันการณ์ owner สามารถผ่อนปรนได้ด้วยการตัดสินโดยตรง โดยต้องเหลือ Issue สำหรับจัดเตรียม T-1 พร้อมทริกเกอร์การออกตาม LC-1 ไว้ด้วย และการตัดสินนี้ต้องบันทึกในรูปแบบที่ตรวจสอบการมีอยู่จริงได้เช่นเดียวกับเงื่อนไขข้อ 4)
- **`CI: N/A` ใช้ได้เฉพาะกรณีที่ CI ไม่ตรวจสอบการเปลี่ยนแปลงนั้น** (เหตุผล = เขียนหลักฐานว่าเป็นสิ่งที่อยู่นอกขอบเขตการตรวจสอบ) การเปลี่ยนแปลงที่ CI ทำงาน แม้จะไม่ใช่โค้ดก็ห้ามใช้ N/A
- ในรีโปที่ตั้ง required status checks ไว้ ห้ามใช้สิทธิ์ข้อยกเว้นด้วยการ**ปลด required ออก** — ให้บันทึกไว้เป็นการดำเนินการที่ owner ทำอย่างชัดแจ้ง

สีแดงที่ไม่มีการอ้างอิง・ข้อยกเว้นที่ตรวจสอบไม่ได้ ไม่ถือว่าเป็นข้อยกเว้น (fail-open ไม่ได้แปลว่า "ผ่าน" — [docs/05](05-fail-posture.md))

## ภาคผนวก (ไม่ใช่บทบัญญัติ) — ตารางแนะนำตัวรันเนอร์

สิ่งที่บทบัญญัติเรียกร้องมีแค่ "จัดเตรียมรันเนอร์ + CI" เท่านั้น การเลือกเครื่องมือขึ้นอยู่กับดุลยพินิจของผู้ implement ตารางนี้เป็น**ข้อมูลอ้างอิงที่ไม่ใช่บทบัญญัติ** การอัปเดตตารางไม่นับเป็นการแก้ไขบทบัญญัติ

| ภาษา / runtime | รันเนอร์ที่แนะนำ | หมายเหตุ |
|---|---|---|
| TypeScript / JavaScript (Node) | vitest | ถ้า standard library เพียงพอก็ใช้ `node:test` ได้เช่นกัน |
| Python | pytest | — |
| Shell | bats-core | — |
| Go | `go test` | มาตรฐานของภาษา |
| Rust | `cargo test` | มาตรฐานของภาษา |
| Swift / iOS | XCTest | รันด้วย `xcodebuild test` |
| สภาพแวดล้อมรัน CI | GitHub Actions | ค่าเริ่มต้นเมื่อรีโปอยู่บน GitHub |
