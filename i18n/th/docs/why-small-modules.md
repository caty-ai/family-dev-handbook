# ทำไมต้องแบ่งโมดูลให้เล็ก — การแบ่งคือ "การลงทุนเพื่อความสามารถในการทำงานคู่ขนาน"

> หน้านี้ไม่ใช่บทบัญญัติ เนื้อหาของบทบัญญัติอยู่ใน [docs/01](01-milestone-loop.md)〜[docs/03](03-git-protocol.md) และ [docs/05](05-fail-posture.md)〜[docs/08](08-lifecycle.md)
> สิ่งที่เขียนไว้ในหน้านี้คือ **แนวคิดที่บทบัญญัติเหล่านั้นตั้งเป็นข้อสมมติฐาน**

## การจะทำงานคู่ขนานได้หรือไม่นั้น ถูกกำหนดไว้ก่อนที่จะเริ่มลงมือ

การตัดสินการทำงานคู่ขนานในคู่มือฉบับนี้เรียบง่าย นั่นคือ **ถ้าเซตของไฟล์ที่งาน 2 ชิ้นแตะต้องไม่ตัดกัน ก็สามารถทำคู่ขนานกันได้** ([`L2-4`](01-milestone-loop.md))

แต่ลองคิดดูว่า ถ้าในไฟล์หน้าจอขนาด 2,500 บรรทัด มีทั้ง layout, การประมวลผล gesture, และการเรียกใช้ engine อยู่ร่วมกัน จะเกิดอะไรขึ้น ไม่ว่าจะพยายามทำอะไรในพื้นที่นั้น ก็ต้องแตะไฟล์นั้นเสมอ **ไม่ว่าจะทำอะไรก็ตัดกันหมด จึงกลายเป็นการทำแบบเรียงลำดับ (直列) ตลอดเวลา**

ปัญหาในกรณีนี้ไม่ใช่การตัดสินใจ แต่คือ **วิธีการแบ่งนั้นอยู่ในรูปแบบที่ไม่สามารถผ่านการตัดสินใจได้**

กล่าวคือ "จะทำคู่ขนานได้หรือไม่" ไม่ได้ขึ้นอยู่กับความตั้งใจหรือการจัดลำดับงาน แต่ถูกกำหนดไว้ตั้งแต่ก่อนเริ่มลงมือนานแล้ว **รูปร่างของโค้ดเป็นตัวกำหนดขีดจำกัดของความสามารถในการทำงานคู่ขนาน**

## การแบ่งไม่ใช่ "การจัดระเบียบ" แต่คือ "การลงทุน"

โดยทั่วไป การ refactor เพื่อแบ่งแยกมักถูกมองว่าเป็นเรื่องของคุณภาพในแนว "ทำให้อ่านง่ายขึ้น" "ทำให้สะอาดขึ้น" และมักถูกเลื่อนไว้หลังจากการพัฒนาฟีเจอร์

ในคู่มือฉบับนี้ การปฏิบัติต่อเรื่องนี้แตกต่างออกไป การแบ่งไฟล์ขนาดใหญ่ที่มีหลายความรับผิดชอบอยู่ร่วมกัน (**hotspot**) จะถูกเปิดเป็น Issue อิสระโดยให้ความสำคัญเป็นอันดับต้น ในฐานะ **การลงทุนเพื่อความสามารถในการทำงานคู่ขนาน** ([`L2-6`](01-milestone-loop.md))

ที่เรียกว่าการลงทุน เพราะมีสิ่งที่ได้กลับคืนมา 3 อย่าง

**1. ทำให้สามารถทำงานคู่ขนานได้**

หลังจากแบ่งแล้ว Issue ที่แตะพื้นที่นั้นจะไม่ตัดกันอีกต่อไป **ในทันทีที่แบ่งเสร็จ การทำงานคู่ขนานในพื้นที่นั้นจะปลอดภัยในเชิงโครงสร้าง** ([`L2-6`](01-milestone-loop.md)) การแบ่งเพียงครั้งเดียวจะส่งผลต่องานทั้งหมดที่ตามมาหลังจากนั้น

**2. เอเจนต์สามารถโฟกัสกับงานตรงหน้าได้**

ถ้าไฟล์มีความรับผิดชอบเดียว สิ่งที่เอเจนต์ต้องอ่านก็มีเพียงไฟล์นั้นไฟล์เดียว **ยิ่งอ่านน้อยลง ความสนใจก็ยิ่งไม่กระจัดกระจาย และสามารถมุ่งไปที่งานตรงหน้าได้เท่านั้น** ไม่ว่าจะใช้โมเดลไหน ยิ่งขอบเขตที่ต้องดูแคบลงเท่าไหร่ ก็ยิ่งมีแนวโน้มที่จะทำงานจนจบได้ง่ายขึ้นเท่านั้น

ในทางกลับกัน ถ้ามี 3 ความรับผิดชอบอยู่ร่วมกันในไฟล์ 2,500 บรรทัด แม้จะอยากแก้เพียงอย่างเดียวในนั้น ก็ต้องอ่านทั้งหมด ความรับผิดชอบอีก 2 อย่างที่ไม่เกี่ยวข้องจะเข้ามาเติมเต็ม context ทุกครั้ง

> **หมายเหตุ:** นี่ไม่ใช่ข้อกำหนดที่บทบัญญัติกำหนดไว้ แต่เป็นเจตนาในการออกแบบ เรายังไม่มีตัวเลขที่วัดได้ว่ามันมีผลมากเพียงใด

**3. สามารถเปลี่ยนทีหลังได้เหมือนบล็อกต่อกัน**

ถ้าแบ่งตามความรับผิดชอบแต่ละอย่างไว้ เวลาที่บางส่วนพัง ก็สามารถถอดเฉพาะส่วนที่พังออกมาแก้ได้ ใกล้เคียงกับความรู้สึกของการถอดใส่บล็อก และไม่ต้องแตะต้องส่วนรอบข้าง

เหตุผลที่คู่มือฉบับนี้ใส่ "**ความเป็นไปได้ในการ revert**" เข้าไปในมุมมองของการรีวิว merge ([`L1-3`](02-issue-loop.md)) และเหตุผลที่ [`L2-2`](01-milestone-loop.md) บอกว่า "อย่าผสมการเปลี่ยนขอบเขตกับการเปลี่ยนฟีเจอร์" ก็เป็นเหตุผลเดียวกัน หากผสมกัน จะไม่สามารถ revert เฉพาะฝั่งใดฝั่งหนึ่งได้

ดังนั้นการแบ่งจึงไม่ใช่ "การจัดระเบียบที่จะทำทีหลัง" แต่เป็น "การลงทุนที่ต้องทำก่อน"

## "เล็ก" ไม่ใช่จำนวนบรรทัด แต่คือจำนวนความรับผิดชอบ

ถ้าคิดว่าโมดูลเล็กหมายถึงเรื่องจำนวนบรรทัด จะตัดสินใจผิดพลาด สิ่งที่ต้องดูคือ **จำนวนความรับผิดชอบที่อยู่ร่วมกัน**

แม้จะมี 300 บรรทัด แต่ถ้ามี 3 ความรับผิดชอบอยู่ร่วมกัน ก็จะมี Issue 3 ประเภทมาตัดกันที่นั่น แม้จะมี 1,000 บรรทัด แต่ถ้ามีความรับผิดชอบเดียว ก็จะมีเพียง Issue ประเภทเดียวกันเท่านั้นที่ตัดกัน

ดังนั้นในตาราง hotspot ของแผนที่ความปลอดภัยในการทำงานคู่ขนาน ([templates/architecture-parallel-map.md](../templates/architecture-parallel-map.md)) จึงมีช่องสำหรับเขียน "**ความรับผิดชอบที่อยู่ร่วมกัน**" ไม่ใช่แค่ตัวเลขจำนวนบรรทัดเท่านั้น จำนวนบรรทัดเป็นเพียงจุดสังเกต ไม่ใช่วัตถุดิบสำหรับการตัดสินใจ

## เมื่อจะเปลี่ยนขอบเขต ให้ทำเฉพาะเรื่องนั้นเรื่องเดียว

งานที่เปลี่ยนวิธีการแบ่งโมดูล — งานที่เปลี่ยนขอบเขต — จะส่งผลกระทบต่องานอื่นๆ ทั้งหมด ดังนั้นจึงต้องแยกการปฏิบัติออกจากกัน ([`L2-2`](01-milestone-loop.md))

- PR ที่เปลี่ยนขอบเขตให้ **ผ่านเพียง 1 PR ก่อนเป็นอันดับแรก**
- จนกว่า PR นั้นจะถูก merge ให้หยุดการเริ่มงานคู่ขนานใหม่ในรีโปนั้น (ช่วงเรียงลำดับ)
- **ให้ PR ที่เปลี่ยนขอบเขตนั้นมีขนาดน้อยที่สุด อย่าผสมการเปลี่ยนขอบเขตกับการเปลี่ยนฟีเจอร์**

บรรทัดสุดท้ายนี้มีผลมากในทางปฏิบัติ หากการเปลี่ยนขอบเขตกับการเปลี่ยนฟีเจอร์ถูกผสมอยู่ใน PR เดียวกัน ผู้รีวิวจะไม่สามารถแยกแยะได้ว่า "diff นี้เป็นเรื่องของขอบเขต หรือเป็นเรื่องของฟีเจอร์" ถึงแม้ภายหลังจะพบปัญหา ก็ไม่สามารถ revert เฉพาะส่วนขอบเขตได้

## จะเขียนบันทึกไว้ที่ไหน

ให้วาง "แผนที่ความปลอดภัยในการทำงานคู่ขนาน" ไว้ใน `ARCHITECTURE.md` ของแต่ละรีโป ([`L2-6`](01-milestone-loop.md)・template อยู่ที่ [templates/architecture-parallel-map.md](../templates/architecture-parallel-map.md)) สิ่งที่ต้องเขียนมี 2 ตาราง

- **ตารางขอบเขตโมดูล** — path ไหนมีความรับผิดชอบอะไร
- **ตาราง hotspot** — ไฟล์ไหนมีหลายความรับผิดชอบ และมีแผนจะแบ่งด้วย Issue ไหน

เมื่อ merge PR ที่เปลี่ยนขอบเขตแล้ว **ให้อัปเดตแผนที่นี้ใน PR เดียวกัน** เพราะในทันทีที่แผนที่คลาดเคลื่อนจากสภาพจริง วัตถุดิบสำหรับการตัดสินใจ GO การทำงานคู่ขนานก็จะกลายเป็นเท็จ

## ไม่จำเป็นต้องออกแบบเองทั้งหมด

อ่านมาถึงตรงนี้ อาจคิดว่า "ต้องออกแบบโมดูลด้วยตัวเองหรือไม่" คำตอบคือไม่ใช่

**เพียงแค่ส่งคู่มือฉบับนี้ให้เอเจนต์ จุดที่ควรแบ่งจะถูกยกขึ้นมาเป็น Issue จากฝั่งเอเจนต์เอง** กลไกมี 3 อย่าง

- **ทุกครั้งที่เปิด Issue ให้คาดการณ์และเขียนไฟล์ที่จะแตะต้อง** ([`L2-3`](01-milestone-loop.md)) งานที่ขอบเขตกว้างเกินกว่าจะคาดการณ์ได้ ณ จุดนั้นจะถูกถือว่าไม่สามารถทำคู่ขนานได้ จุดที่ติดขัดจะถูกเปิดเผยออกมาทุกครั้งที่มีการทำงาน
- **มีขั้นตอนที่กำหนดไว้แล้วสำหรับตอนที่เจอไฟล์ขนาดใหญ่** ([`L2-6`](01-milestone-loop.md)) เนื่องจากมีเขียนไว้ว่า "ให้เปิด Issue สำหรับการแบ่งก่อน" เอเจนต์จึงจะปฏิบัติตามขั้นตอนนั้น ไม่ต้องตัดสินใจใหม่จากศูนย์ทุกครั้ง
- **เมื่อสร้างใหม่ ให้ 1 child Issue = 1 โมดูล** ([`E-2`](06-epic-lane.md)) ตั้งแต่แรกจะทำให้ความรับผิดชอบไม่ปะปนกันง่ายๆ

อย่างไรก็ตาม **งานการแบ่งเองยังคงต้องเกิดขึ้น** ไม่ใช่ว่าให้อ่านแล้วโค้ดจะจัดระเบียบเองโดยอัตโนมัติ สิ่งที่เปลี่ยนไปคือ การแบ่งจะไม่ใช่ "การจัดระเบียบที่จะทำเมื่อไหร่ก็ได้" แต่จะกลายเป็น "เส้นทางที่ต้องผ่านเสมอเมื่อไหร่ก็ตามที่อยากทำคู่ขนาน" การพูดว่า **จะไม่ถูกเลื่อนไปทำทีหลังอีกต่อไป** จึงเป็นการพูดที่ถูกต้องแม่นยำกว่า

## วิธีแบ่งของคู่มือฉบับนี้เอง

รีโปนี้เองก็ถูกสร้างขึ้นด้วยหลักการเดียวกัน

- **บทบัญญัติ 1 ไฟล์ต่อ 1 ชั้น** — L2 = [docs/01](01-milestone-loop.md), L1 = [docs/02](02-issue-loop.md), L0 = [docs/03](03-git-protocol.md), ท่าทีเมื่อล้มเหลว = [docs/05](05-fail-posture.md), Epic = [docs/06](06-epic-lane.md), delegation brief = [docs/07](07-delegation-brief.md), lifecycle = [docs/08](08-lifecycle.md) แม้แต่ไฟล์ที่ยาวที่สุดก็มีเพียงกว่า 100 บรรทัดเล็กน้อย
- **ไม่ผสมบทบัญญัติกับรูปแบบ** — รูปแบบของ comment และ template ถูกแยกไว้ที่ [templates/](../templates/issue-template.md)
- **การอ้างอิงใช้ rule ID ที่มั่นคง** — ไฟล์ต่างๆ อ้างถึงกันด้วย ID อย่างเช่น `L2-4` แม้จะย้ายไฟล์ การอ้างอิงก็จะไม่พัง
- **ไม่วางนิยามเดียวกันไว้ 2 ที่** — นิยามของพื้นที่เสี่ยงสูงมีอยู่เฉพาะที่ [docs/06](06-epic-lane.md) เท่านั้น บล็อกสรุปสำหรับการเผยแพร่มีอยู่เฉพาะที่ [docs/04](04-adoption.md) เท่านั้น

ข้อสุดท้ายนี้มีผลเป็นพิเศษ หากมีนิยามอยู่ 2 ที่ ในทันทีที่แก้เพียงฝั่งเดียว จะไม่มีใครรู้ได้ว่าฝั่งไหนถูกต้อง ดังนั้นจึงตัดสินใจไว้ก่อนว่า "ต้นฉบับที่แท้จริงมีเพียง 1 ที่" ส่วนที่เหลือให้เป็นเพียงการอ้างอิงเท่านั้น เหตุผลที่ README ไม่มี roadmap แต่ส่งต่อไปยังรายการ Issue แทน ก็เป็นเหตุผลเดียวกัน

## คำถามที่พบบ่อย

**ตั้งแต่แรกไม่สามารถแบ่งได้อย่างสมบูรณ์แบบ**

แบ่งไม่ได้หรอก นั่นจึงเป็นเหตุผลที่ใช้คำว่า "การลงทุน" ถ้าวิธีการแบ่งในปัจจุบันเกิดการตัดกัน ก็ให้เปิดเป็น Issue สำหรับการแบ่ง แล้วทยอยคืนไปทีละอย่าง ไม่จำเป็นต้องจัดการทุกอย่างให้เรียบร้อยก่อนเริ่มลงมือ

**ถ้าแบ่งเล็กเกินไปจะเป็นอย่างไร**

จำนวนไฟล์จะเพิ่มขึ้น และการเปลี่ยนแปลงหนึ่งครั้งจะกระจายไปหลายไฟล์ คราวนี้จะกลายเป็นสถานะ "ไม่ตัดกัน แต่ต้องแตะต้องหลายที่" ซึ่งจะทำให้รีวิวตามได้ยากขึ้น เกณฑ์ในการตัดสินคือจำนวนความรับผิดชอบ ดังนั้น **ถ้ามีความรับผิดชอบเดียวก็ไม่ต้องแบ่ง**

**ไฟล์ขนาดใหญ่ที่มีอยู่เดิมควรทำอย่างไร**

ไม่ต้องรีบแตะต้องตอนนี้ก็ได้ ให้บันทึกไว้ในตาราง hotspot ของแผนที่ความปลอดภัยในการทำงานคู่ขนาน และเมื่อไหร่ที่อยากทำคู่ขนานในพื้นที่นั้น ให้ผ่าน Issue สำหรับการแบ่งก่อน การบันทึกไว้เองก็ถือเป็นการส่งต่อให้กับคนที่จะตัดสินใจในครั้งถัดไป

**ถ้าพัฒนาคนเดียวจะเกี่ยวข้องด้วยหรือไม่**

เกี่ยวข้อง ในทันทีที่ให้ AI agent ทำงาน 2 ตัว นั่นก็คือการพัฒนาแบบคู่ขนานแล้ว นอกจากนี้ ยิ่งความรับผิดชอบถูกแยกออกจากกันมากเท่าไหร่ ก็ยิ่งเขียน "การคาดการณ์ไฟล์ที่จะแตะต้อง" ของแต่ละ Issue ได้ง่ายขึ้นเท่านั้น ทำให้ต้นทุนของข้อที่ 3 ใน [Issue-first](why-issue-first.md) ก็ลดลงไปด้วย
