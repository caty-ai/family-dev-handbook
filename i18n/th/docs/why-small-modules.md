# ทำไมต้องแบ่งโมดูลให้เล็ก — การแบ่งคือ "การลงทุนเพื่อความสามารถในการทำงานคู่ขนาน"

> หน้านี้ไม่ใช่ตัวบทกฎ ตัวบทกฎฉบับเต็มอยู่ที่ [docs/01](01-milestone-loop.md)〜[docs/06](06-epic-lane.md)
> สิ่งที่เขียนไว้ที่นี่คือ **แนวคิดที่ตัวบทกฎเหล่านั้นตั้งอยู่บนพื้นฐาน**

## ว่าจะทำงานคู่ขนานได้หรือไม่ ถูกกำหนดไว้ก่อนที่จะเริ่มลงมือ

การตัดสินเรื่องการทำงานคู่ขนานในคู่มือฉบับนี้เรียบง่าย **ถ้าเซตของไฟล์ที่งานสองชิ้นแตะต้องไม่ทับซ้อนกัน ก็สามารถทำคู่ขนานได้** ([`L2-4`](01-milestone-loop.md))

แต่ลองนึกภาพว่าถ้าในไฟล์หน้าจอที่มี 2,500 บรรทัด มีทั้ง layout, การจัดการ gesture, และการเรียกใช้ engine อยู่ปะปนกันล่ะ ไม่ว่าจะพยายามทำอะไรในพื้นที่นั้น ก็ต้องแตะไฟล์นั้นเสมอ **ไม่ว่าจะทำอะไรก็ทับซ้อนกันหมด จึงกลายเป็นต้องทำแบบเรียงลำดับ (serial) เสมอ**

ปัญหาในกรณีนี้ไม่ได้อยู่ที่การตัดสินใจ แต่ **วิธีการแบ่งต่างหากที่มีรูปแบบที่ทำให้ผ่านการตัดสินไม่ได้**

กล่าวคือ "จะทำงานคู่ขนานได้หรือไม่" ไม่ได้ขึ้นอยู่กับความตั้งใจหรือการวางแผน แต่ถูกกำหนดไว้ตั้งแต่ก่อนเริ่มลงมือทำนานแล้ว **รูปร่างของโค้ดเป็นตัวกำหนดขีดจำกัดสูงสุดของความสามารถในการทำงานคู่ขนาน**

## การแบ่งคือ "การลงทุน" ไม่ใช่ "การจัดระเบียบ"

โดยทั่วไป การ refactor เพื่อแบ่งไฟล์มักถูกมองเป็นเรื่องของคุณภาพในแง่ "ทำให้อ่านง่ายขึ้น" "ทำให้สะอาดขึ้น" และมักถูกผลักไปทำทีหลังการพัฒนาฟีเจอร์

ในคู่มือฉบับนี้ การปฏิบัติต่อเรื่องนี้แตกต่างออกไป การแบ่งไฟล์ขนาดใหญ่ที่มีความรับผิดชอบหลายอย่างปะปนกัน (**hotspot**) จะถูกตั้งเป็น Issue อิสระและให้ความสำคัญเป็นลำดับต้น ในฐานะ **การลงทุนเพื่อความสามารถในการทำงานคู่ขนาน** ([`L2-6`](01-milestone-loop.md))

ที่เรียกว่าการลงทุนก็เพราะมีผลตอบแทนกลับมา 3 อย่าง

**1. ทำให้ทำงานคู่ขนานได้**

หลังจากแบ่งแล้ว Issue ต่าง ๆ ที่แตะพื้นที่นั้นจะไม่ทับซ้อนกันอีกต่อไป **ตั้งแต่วินาทีที่แบ่งเสร็จ การทำงานคู่ขนานในพื้นที่นั้นจะปลอดภัยในเชิงโครงสร้าง** ([`L2-6`](01-milestone-loop.md)) การแบ่งเพียงครั้งเดียวจะส่งผลดีต่อเนื่องไปยังงานทั้งหมดหลังจากนั้น

**2. เอเจนต์สามารถโฟกัสกับงานตรงหน้าได้**

ถ้าไฟล์มีความรับผิดชอบเดียว เอเจนต์ก็อ่านแค่ไฟล์นั้นไฟล์เดียว **ยิ่งอ่านน้อย ความสนใจก็ยิ่งไม่กระจาย และสามารถมุ่งไปที่งานตรงหน้าได้เท่านั้น** ไม่ว่าจะใช้โมเดลไหนก็ตาม ยิ่งขอบเขตที่ต้องดูแคบเท่าไร ก็ยิ่งวิ่งจนจบงานได้ง่ายขึ้นเท่านั้น

ในทางกลับกัน ถ้ามี 3 ความรับผิดชอบปะปนกันอยู่ในไฟล์ 2,500 บรรทัด แม้จะอยากแก้แค่หนึ่งในนั้น ก็ต้องอ่านทั้งหมด ความรับผิดชอบอีกสองอย่างที่ไม่เกี่ยวข้องจะมาเบียดพื้นที่ context ทุกครั้ง

> **หมายเหตุ:** นี่ไม่ใช่ข้อกำหนดที่ตัวบทกฎบังคับไว้ แต่เป็นเจตนาในการออกแบบ เรายังไม่มีตัวเลขที่วัดว่ามันส่งผลมากน้อยแค่ไหน

**3. สามารถสลับเปลี่ยนภายหลังได้เหมือนบล็อกต่อกัน**

ถ้าแบ่งตามความรับผิดชอบไว้แล้ว เมื่อเกิดปัญหาก็สามารถถอดเฉพาะส่วนที่พังออกมาแก้ได้ชิ้นเดียว ใกล้เคียงกับความรู้สึกของการต่อ-ถอดบล็อก โดยไม่ต้องไปแตะส่วนรอบข้าง

เหตุผลที่คู่มือฉบับนี้ใส่ "**ความเป็นไปได้ในการ revert**" ไว้เป็นมุมมองหนึ่งในการรีวิว merge ([`L1-3`](02-issue-loop.md)) และเหตุผลที่ [`L2-2`](01-milestone-loop.md) บอกว่า "อย่าผสมการเปลี่ยนขอบเขตกับการเปลี่ยนฟีเจอร์เข้าด้วยกัน" ก็เป็นเหตุผลเดียวกัน ถ้าผสมกัน จะไม่สามารถ revert แค่ฝั่งใดฝั่งหนึ่งได้

ด้วยเหตุนี้ การแบ่งจึงไม่ใช่ "การจัดระเบียบที่ทำทีหลัง" แต่เป็น "การลงทุนที่ทำก่อน"

## "เล็ก" ไม่ได้วัดที่จำนวนบรรทัด แต่วัดที่จำนวนความรับผิดชอบ

ถ้ามองว่าโมดูลขนาดเล็กคือเรื่องของจำนวนบรรทัด จะตัดสินใจผิดพลาด สิ่งที่ต้องดูคือ **จำนวนความรับผิดชอบที่ปะปนกันอยู่**

แม้จะมี 300 บรรทัด แต่ถ้ามี 3 ความรับผิดชอบปะปนกัน ก็จะมี Issue 3 ประเภททับซ้อนกันที่นั่น แม้จะมี 1,000 บรรทัด แต่ถ้ามีความรับผิดชอบเดียว สิ่งที่จะทับซ้อนกันก็มีแค่ Issue ประเภทเดียวกันเท่านั้น

ด้วยเหตุนี้ ในตาราง hotspot ของแผนที่ความปลอดภัยสำหรับการทำงานคู่ขนาน ([templates/architecture-parallel-map.md](../templates/architecture-parallel-map.md)) จึงมีช่องสำหรับเขียน "**ความรับผิดชอบที่ปะปนกันอยู่**" ไม่ใช่แค่จำนวนบรรทัดโดยประมาณ จำนวนบรรทัดเป็นเพียงเครื่องหมาย ไม่ใช่ปัจจัยในการตัดสินใจ

## เมื่อจะเปลี่ยนขอบเขต ให้ทำแค่เรื่องนั้นเรื่องเดียว

งานเปลี่ยนวิธีการแบ่งโมดูล — งานเปลี่ยนขอบเขต — จะส่งผลกระทบต่องานอื่น ๆ ทั้งหมด ดังนั้นจึงต้องแยกการปฏิบัติต่องานนี้ออกมา ([`L2-2`](01-milestone-loop.md))

- PR ที่เปลี่ยนขอบเขตจะต้อง **ผ่านก่อนเพียงตัวเดียวเท่านั้น**
- จนกว่า PR นั้นจะถูก merge ห้ามเริ่มงานคู่ขนานใหม่ใน repository นั้น (ช่วง serial)
- **ตัว PR ที่เปลี่ยนขอบเขตต้องมีขนาดเล็กที่สุดเท่าที่จะทำได้ อย่าผสมการเปลี่ยนขอบเขตกับการเปลี่ยนฟีเจอร์เข้าด้วยกัน**

บรรทัดสุดท้ายมีผลในทางปฏิบัติ ถ้าการเปลี่ยนขอบเขตกับการเปลี่ยนฟีเจอร์ถูกผสมอยู่ใน PR เดียวกัน ฝ่ายรีวิวจะไม่สามารถแยกแยะได้ว่า "diff นี้เป็นเรื่องของขอบเขตหรือเรื่องของฟีเจอร์" แม้ภายหลังจะพบปัญหา ก็ไม่สามารถ revert เฉพาะส่วนขอบเขตได้

## จะเขียนบันทึกไว้ที่ไหน

ให้วาง "แผนที่ความปลอดภัยสำหรับการทำงานคู่ขนาน" ไว้ที่ `ARCHITECTURE.md` ของแต่ละ repository ([`L2-6`](01-milestone-loop.md)・template อยู่ที่ [templates/architecture-parallel-map.md](../templates/architecture-parallel-map.md)) สิ่งที่ต้องเขียนมี 2 ตาราง

- **ตารางขอบเขตของโมดูล** — path ไหนมีความรับผิดชอบอะไร
- **ตาราง hotspot** — ไฟล์ไหนมีความรับผิดชอบหลายอย่าง และมีแผนจะแบ่งด้วย Issue ไหน

เมื่อ merge PR ที่เปลี่ยนขอบเขตแล้ว **ให้อัปเดตแผนที่นี้ใน PR เดียวกัน** เพราะในวินาทีที่แผนที่เพี้ยนไปจากความเป็นจริง ข้อมูลที่ใช้ตัดสิน parallel GO ก็จะกลายเป็นข้อมูลเท็จ

## ไม่จำเป็นต้องออกแบบเองทั้งหมด

อ่านมาถึงตรงนี้ อาจคิดว่า "ต้องออกแบบโมดูลด้วยตัวเองหรือ" ไม่ใช่แบบนั้น

**แค่ส่งคู่มือฉบับนี้ให้เอเจนต์ จุดที่ควรแบ่งก็จะถูกยกขึ้นมาเป็น Issue จากฝั่งนั้นเอง** กลไกมี 3 อย่าง

- **ทุกครั้งที่ตั้ง Issue ให้คาดการณ์และเขียนไฟล์ที่จะแตะต้อง** ([`L2-3`](01-milestone-loop.md)) งานที่ขอบเขตกว้างเกินกว่าจะคาดการณ์ได้ จะถูกถือว่าไม่สามารถทำคู่ขนานได้ตั้งแต่จุดนั้น จุดที่ติดขัดจะถูกเปิดเผยออกมาทุกครั้งที่ทำงาน
- **มีขั้นตอนที่กำหนดไว้แล้วสำหรับเมื่อเจอไฟล์ขนาดใหญ่** ([`L2-6`](01-milestone-loop.md)) เนื่องจากมีเขียนไว้ว่า "ให้ตั้ง Issue สำหรับแบ่งไฟล์ก่อน" เอเจนต์จึงจะทำตามขั้นตอนนั้น ไม่ต้องตัดสินใจใหม่ตั้งแต่ศูนย์ทุกครั้ง
- **เมื่อสร้างใหม่ ให้ 1 child Issue = 1 โมดูล** ([`E-2`](06-epic-lane.md)) ทำให้ความรับผิดชอบไม่ปะปนกันตั้งแต่แรก

อย่างไรก็ตาม **งานแบ่งไฟล์เองนั้นยังคงต้องเกิดขึ้นอยู่ดี** ไม่ใช่ว่าแค่ให้เอเจนต์อ่านแล้วโค้ดจะจัดระเบียบตัวเองโดยอัตโนมัติ สิ่งที่เปลี่ยนไปคือ การแบ่งจะไม่ใช่ "การจัดระเบียบที่จะทำสักวัน" อีกต่อไป แต่กลายเป็น "เส้นทางที่ต้องผ่านทุกครั้งที่อยากทำงานคู่ขนาน" พูดให้แม่นยำคือ **มันจะไม่ถูกผลักไปทำทีหลังอีกต่อไป**

## วิธีการแบ่งของคู่มือฉบับนี้เอง

repository นี้ก็ถูกสร้างขึ้นด้วยหลักการเดียวกัน

- **ตัวบทกฎแยกเป็น 1 ไฟล์ต่อ 1 ชั้น** — L2 = [docs/01](01-milestone-loop.md), L1 = [docs/02](02-issue-loop.md), L0 = [docs/03](03-git-protocol.md), ท่าทีเมื่อล้มเหลว = [docs/05](05-fail-posture.md), Epic = [docs/06](06-epic-lane.md) แม้แต่ไฟล์ที่ยาวที่สุดก็มีเพียงกว่า 100 บรรทัดเล็กน้อย
- **ไม่ผสมตัวบทกฎกับรูปแบบเข้าด้วยกัน** — รูปแบบการเขียนความคิดเห็นและ template ถูกแยกไว้ที่ [templates/](../templates/issue-template.md)
- **การอ้างอิงใช้ rule ID ที่คงที่** — ไฟล์ต่าง ๆ อ้างอิงถึงกันด้วย ID แบบ `L2-4` แม้จะย้ายไฟล์ การอ้างอิงก็จะไม่พัง
- **ไม่วางคำนิยามเดียวกันไว้ 2 ที่** — คำนิยามของพื้นที่ที่มีความเสี่ยงสูงอยู่ที่ [docs/06](06-epic-lane.md) เท่านั้น ส่วน summary block สำหรับแจกจ่ายอยู่ที่ [docs/04](04-adoption.md) เท่านั้น

ข้อสุดท้ายนี้มีผลเป็นพิเศษ ถ้าคำนิยามอยู่ 2 ที่ ทันทีที่แก้ไขแค่ฝั่งเดียว จะไม่มีใครรู้ว่าฝั่งไหนถูกต้อง ดังนั้นจึงกำหนดไว้ล่วงหน้าว่า "ต้นฉบับที่แท้จริงมีอยู่ที่เดียว" ส่วนที่อื่นเป็นเพียงการอ้างอิงเท่านั้น เหตุผลที่ README ไม่มี roadmap ของตัวเองแต่ส่งไปยังรายการ Issue แทน ก็เป็นเหตุผลเดียวกัน

## คำถามที่พบบ่อย

**ไม่สามารถแบ่งให้สมบูรณ์แบบตั้งแต่แรกได้**

แบ่งไม่ได้จริง ๆ นั่นแหละเหตุผลที่เราใช้คำว่า "การลงทุน" ถ้าวิธีแบ่งในปัจจุบันเกิดการทับซ้อนกัน ก็ให้ตั้งเป็น Issue สำหรับแบ่งไฟล์ แล้วค่อย ๆ คืนหนี้ไปทีละอย่าง ไม่จำเป็นต้องจัดทุกอย่างให้เรียบร้อยก่อนเริ่มลงมือ

**ถ้าแบ่งเล็กเกินไปจะเป็นอย่างไร**

จำนวนไฟล์จะเพิ่มขึ้น และการเปลี่ยนแปลงหนึ่งอย่างจะกระจายไปหลายไฟล์ กลายเป็นสถานะ "ไม่ทับซ้อนกัน แต่ต้องแตะหลายที่" ทำให้รีวิวตามได้ยากขึ้น เกณฑ์ในการตัดสินใจคือจำนวนความรับผิดชอบ ดังนั้น **ถ้ามีความรับผิดชอบเดียว ก็ไม่ต้องแบ่ง**

**ไฟล์ขนาดใหญ่ที่มีอยู่แล้วควรทำอย่างไร**

ไม่จำเป็นต้องแตะตอนนี้ก็ได้ ให้บันทึกไว้ในตาราง hotspot ของแผนที่ความปลอดภัยสำหรับการทำงานคู่ขนาน แล้วเมื่อไรที่อยากทำงานคู่ขนานในพื้นที่นั้น ก็ให้ตั้ง Issue สำหรับแบ่งไฟล์ก่อน การบันทึกไว้เองก็ถือเป็นการส่งต่อให้คนที่จะมาตัดสินใจในครั้งถัดไป

**ถ้าพัฒนาคนเดียวจะเกี่ยวข้องด้วยหรือไม่**

เกี่ยวข้อง ทันทีที่รัน AI agent 2 ตัวพร้อมกัน นั่นก็คือการพัฒนาแบบคู่ขนานแล้ว นอกจากนี้ ยิ่งความรับผิดชอบถูกแยกออกจากกันมากเท่าไร การเขียน "คาดการณ์ไฟล์ที่จะแตะ" ของแต่ละ Issue ก็จะยิ่งง่ายขึ้น ทำให้ต้นทุนของข้อที่ 3 ใน [Issue-first](why-issue-first.md) ลดลงด้วย
