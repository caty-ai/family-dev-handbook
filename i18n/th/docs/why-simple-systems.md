# ทำไมถึงต้องสร้างแบบเรียบง่าย — ความซับซ้อนควรถูกกำจัดด้วยข้อกำหนด ไม่ใช่แก้ด้วยการออกแบบ

> หน้านี้ไม่ใช่ตัวบทข้อบังคับ ตัวบทข้อบังคับฉบับเต็มอยู่ที่ [docs/01](01-milestone-loop.md)〜[docs/06](06-epic-lane.md)
> สิ่งที่เขียนไว้ที่นี่คือ **แนวคิดที่ข้อบังคับเหล่านั้นตั้งเป็นสมมติฐาน**

## สิ่งที่เรามุ่งหวัง

ตัวบทข้อบังคับ (L2 / L1 / L0) ของ handbook นี้เป็นกลไกที่ช่วยรักษา "จะสร้างอย่างไร・จะทำงานคู่ขนานอย่างไร" แต่ก่อนหน้านั้น — ในขั้นตอนของ **จะสร้างอะไร** มีบางสิ่งที่ถูกกำหนดไว้แล้วล่วงหน้า นั่นคือความเปราะบางและภาระในการดูแลรักษา

สภาวะที่เรามุ่งหวังมี 4 ข้อ

- **เรียบง่ายและไม่เปราะบาง** — ยิ่งชิ้นส่วนน้อย จุดที่จะพังก็ยิ่งน้อยตามไปด้วย
- **ทนต่อการถูกปล่อยทิ้งไว้** — ระยะเวลานำ (lead time) จนกว่าจะต้องบำรุงรักษาครั้งถัดไปยาวนาน ไม่ต้องการความสนใจจากมนุษย์เพื่อให้ระบบทำงานต่อไปได้
- **ใครก็ตามสามารถเข้าใจโครงสร้างได้** — ตัวเราเองในอีกไม่กี่เดือนข้างหน้า หรือ agent ที่เข้ามาใหม่เป็นครั้งแรก สามารถอ่านและตามเข้าใจได้โดยไม่ต้องมีคำอธิบาย "เข้าใจได้เฉพาะคนที่สร้าง" หรือ "ต้องใช้เวลาถอดรหัสภายหลัง" ถือเป็นข้อบกพร่องในตัวมันเอง
- **โครงสร้างโมดูลตามจำนวนความรับผิดชอบ** — ไม่แบ่งมากกว่าหรือน้อยกว่าจำนวนความรับผิดชอบ (วิธีวัดเหมือนกับ "จำนวนความรับผิดชอบ" ใน [ทำไมถึงต้องแบ่งโมดูลให้เล็ก](why-small-modules.md))

## เมื่อติดขัดในการออกแบบ ให้สงสัยข้อกำหนดก่อน

ระหว่างที่กำลังสร้าง อาจเกิดสถานการณ์แบบนี้ได้

- ตรรกะเริ่มซับซ้อนเกินเข้าใจ
- แก้ไม่ได้ด้วยการผสมผสานโมดูล ดูเหมือนจะต้องมีกลไกพิเศษ
- ติดขัดอยู่กับตัวการออกแบบเอง

ในสถานการณ์นี้ สิ่งแรกที่ควรทำไม่ใช่ "หาการออกแบบที่ฉลาดกว่าเดิม" แต่คือ **การสงสัยข้อกำหนดเอง**

ความยากส่วนใหญ่ไม่ได้มาจากการออกแบบ แต่มาจากข้อกำหนด หากตัดข้อกำหนดออกไปได้หนึ่งข้อ จุดยากในการออกแบบที่ข้อกำหนดนั้นเรียกร้อง จะหายไปทั้งหมด ทั้งการ implement การทดสอบ และการบำรุงรักษาในอนาคต การปรับแต่งการออกแบบทำได้เพียง **เจือจาง** ความยาก แต่การทบทวนข้อกำหนดสามารถ **กำจัด** ความยากได้เลย

## คำถามที่ควรถามเมื่อสงสัย

ถามตามลำดับ แต่ละข้อไม่ใช่คำถามว่า "ตัดข้อกำหนดได้ไหม" แต่เป็นคำถามที่มองหาว่า **กำจัดสมมติฐาน แล้วกำจัดตัวปัญหาไปเลยได้หรือไม่**

1. **จริง ๆ แล้วใครเป็นคนใช้?** — ยิ่งกำหนดกลุ่มผู้ใช้ที่คาดหวังไว้กว้างเท่าไร การ authentication・การจัดการสิทธิ์・การจัดการ error・การซัพพอร์ตก็จะยิ่งหนาขึ้นเท่านั้น เมื่อตรวจสอบผู้ใช้จริงแล้ว อาจพบว่าความหนานั้นส่วนใหญ่ไม่จำเป็นเลย
2. **จริง ๆ แล้วจำเป็นต้องออนไลน์หรือไม่?** — ถ้าการรันแบบ local หรือ network แบบปิด (เช่น VPN) เพียงพอแล้ว การออกแบบ login สำหรับการเปิดใช้งานสาธารณะ・มาตรการป้องกันการโจมตี・การออกแบบ availability จะไม่มีอยู่จริงตั้งแต่แรกในฐานะปัญหา
3. **ถ้าจำกัดขอบเขตการใช้งาน จะกำจัดจุดยากได้หรือไม่?** — หากเลิก "รองรับได้ทุกอย่าง" แล้วจำกัด input หรือวิธีการใช้งาน บางครั้ง branch ที่ซับซ้อนก็จะหายไปทั้งหมด
4. **ข้อกำหนดนั้นมีคนขอมาจริง ๆ หรือไม่?** — ข้อกำหนดที่ถูกเพิ่มเข้ามาด้วยเหตุผลว่า "น่าจะมีไว้ดีกว่า" มักมีต้นทุนแพงที่สุด คำตอบต้องยืนยันกับผู้ที่ร้องขอ — ข้อกำหนดที่ยังคงอยู่ใน Issue คือบันทึกของข้อตกลงในอดีต จึงไม่ใช่สิ่งที่ agent จะตัดสินเองแต่ผู้เดียวว่า "ไม่มีใครขอ" แล้วลบทิ้ง

### ตัวอย่าง: "อยากให้สร้าง SaaS สำหรับใช้ภายในบริษัท"

หากรับคำขอตามตัวอักษร การออกแบบเพื่อเปิดให้ใช้งานอย่างปลอดภัยก็จะเริ่มต้นขึ้น ทั้ง login, การรีเซ็ตรหัสผ่าน, การจัดการ session, ตาราง permission — ล้วนแล้วแต่ยาก เปราะบาง และต้องดูแลรักษาต่อเนื่อง

ตรงนี้ให้กลับไปที่คำถามที่ 1 "ใครเป็นคนใช้?" — ถ้าคำตอบคือ "แค่ทีมของเราเอง" ก็ไม่จำเป็นต้องเปิดให้ใช้งานสาธารณะตั้งแต่แรก หากรันแบบ local หรือวางไว้ใน network แบบปิด **ปัญหาเรื่อง login จะหายไปเอง** เพียงแค่ถามคำถามเดียวก่อนลงมือสร้าง ส่วนที่เปราะบางที่สุดก็กลายเป็นไม่จำเป็นไปทั้งหมด

นี่คือความหมายของ "กำจัดสมมติฐานเพื่อแก้ปัญหา"

> **ข้อควรระวัง:** นี่เป็นตัวอย่างของ "การตรวจสอบข้อกำหนดเรื่องขอบเขตผู้ใช้ก่อนลงมือสร้าง" ไม่ใช่เรื่องการถอด authentication ออกจากระบบที่ตั้งใจเปิดให้ใช้งานสาธารณะตั้งแต่แรก การตัดสินใจที่แตะขอบเขตอย่าง authentication・permission・ขอบเขตการเปิดให้ใช้งาน — ไม่ว่าจะก่อนสร้างหรือโดยเฉพาะกับระบบที่ทำงานอยู่แล้ว — ถือเป็น**พื้นที่ความเสี่ยงสูง**(นิยามเดียวใน [docs/06](06-epic-lane.md)) จึงเป็นเรื่องที่ต้องให้มนุษย์ตัดสินใจ

## สงสัยได้อย่างอิสระ แต่การตัดสินใจตัดออกเป็นของผู้ร้องขอ

นี่คือเส้นแบ่งที่สำคัญที่สุด **ผลลัพธ์ของการสงสัยไม่ใช่การลบข้อกำหนด แต่คือ "คำถาม" และ "ข้อเสนอ" ที่นำกลับไปสู่ข้อตกลงเป้าหมาย ([`L2-1`](01-milestone-loop.md))**

- agent ทำได้แค่เสนอทางเลือก **ผู้ที่ตัดสินใจขั้นสุดท้ายว่าจะทิ้งอะไรคือผู้ที่ร้องขอ**
- agent จะไม่แก้ไขหรือลดทอนข้อกำหนดหรือเงื่อนไขความสำเร็จ (Done when) ที่ตกลงกันแล้วด้วยตัวเองแต่ผู้เดียว ห้ามทำให้เงื่อนไขความสำเร็จเป็น N/A ด้วยเหตุผลว่า "สงสัยแล้วตัดสินว่าไม่จำเป็น"
- หากระหว่างทางอยากตัดข้อกำหนดทิ้ง: อย่าแก้ไข Done when ในขณะที่ดำเนินการ implement ต่อไป แต่ **ยืนยันกับผู้ร้องขอบน Issue** เมื่อตกลงกันแล้วให้อัปเดต Why / Done when ก่อนจึงดำเนินการต่อ
- **ห้ามใช้แทน** ทางออกเมื่อทำงานติดขัด ทางออกที่เป็นทางการเมื่อ implement ติดขัดคือ HOLD ตาม [`L1-4`](02-issue-loop.md) / [`L1-6`](02-issue-loop.md) หรือ escalation ไปยังมนุษย์ ไม่ใช่ "การสงสัยข้อกำหนด" **"ทำไม่ได้" กับ "ไม่จำเป็นแล้ว" เป็นคนละเรื่องกัน ต้องบันทึกแยกกัน**
- แม้ว่าการลบข้อกำหนดจะทำให้ภาระงานเบาลง แต่นั่น**ไม่ใช่วิธีหลีกเลี่ยง**ความหนักของการ review ([`L1-9`](02-issue-loop.md) / จำนวนที่นั่ง) ข้อตกลงในการลบเองก็ถือเป็นการเปลี่ยนแปลงข้อกำหนด และในงานฝั่งที่หนักถือเป็นเป้าหมายของ upstream review
- ในงานที่หนัก เส้นแบ่งนี้ถูกกำหนดไว้แล้วในตัวบทข้อบังคับ — การนิยามข้อกำหนดเป็นเป้าหมายของ heterogeneous review ก่อนเริ่ม implement ([`L1-9`](02-issue-loop.md)) Done when ภายใน Epic เป็น deliverable ที่ถูกแช่แข็งไว้ การเปลี่ยนแปลงเป็นเป้าหมายที่ต้องหยุดที่ human checkpoint ([`E-3`](06-epic-lane.md)) หน้านี้ไม่ได้ผ่อนปรนสิ่งเหล่านั้น

## ไม่ใช่ทุกอย่างจะทำแบบนี้ได้

บางครั้งข้อกำหนดก็เป็นของจริง และความซับซ้อนก็หลีกเลี่ยงไม่ได้ ข้อกำหนดอย่างการปฏิบัติตามกฎระเบียบ・บันทึกการตรวจสอบ・การคุ้มครองข้อมูลส่วนบุคคล・การเรียกเก็บเงิน เป็น **ข้อกำหนดที่เราไม่มีอิสระในการตัดออกตั้งแต่แรก** — สิ่งเหล่านี้ไม่ใช่เป้าหมายของการสงสัย แต่เป็นเป้าหมายที่ต้องตรวจสอบและปฏิบัติตาม หน้านี้ไม่ได้บอกว่า "ห้ามสร้างสิ่งที่ซับซ้อน" แต่บอกว่า "**ก่อนที่จะยอมรับความซับซ้อน ให้ลองสงสัยข้อกำหนดสักครั้ง**"

หากสงสัยแล้วยังยอมรับก็ไม่เป็นไร แต่**ให้บันทึกเหตุผลว่าทำไมถึงยอมรับไว้ 1 บรรทัดในวัตถุประสงค์ (Why) ของ Issue** (วิธีเขียน Why ดูที่ [`L1-2`](02-issue-loop.md)) หากมีบันทึกไว้ อีกไม่กี่เดือนข้างหน้าใครสักคนก็สามารถถามใหม่ได้ว่า "ความซับซ้อนนี้จำเป็นจริงหรือ?" แต่ถ้าไม่มีบันทึกไว้ ความซับซ้อนนั้นก็จะกลายเป็นข้อเท็จจริงที่ตายตัวไปเลย

## ความสัมพันธ์กับกฎการทำงานคู่ขนาน

สมมติฐานนี้เชื่อมโยงกับโลกของตัวบทข้อบังคับ

- เมื่อลดข้อกำหนดลง ไฟล์ที่ต้องแตะก็จะลดลงตามไปด้วย เมื่อไฟล์ที่ต้องแตะลดลง **การคาดการณ์ไฟล์ที่จะแตะ** ([`L2-3`](01-milestone-loop.md)) ก็เขียนได้ง่ายขึ้น และ parallel GO ([`L2-4`](01-milestone-loop.md)) ก็จะออกได้ง่ายขึ้น ระบบที่เรียบง่ายคือระบบที่แข็งแรงสำหรับการพัฒนาแบบคู่ขนานด้วยเช่นกัน
- "โครงสร้างโมดูลตามจำนวนความรับผิดชอบ" ใช้เกณฑ์การตัดสินใจเดียวกันกับ [การแบ่งคือการลงทุนเพื่อความสามารถในการทำงานคู่ขนาน](why-small-modules.md) ถ้าความรับผิดชอบอยู่ปะปนกันก็แยกออก (เรื่องของหน้านั้น) ถ้าไม่มีความรับผิดชอบก็อย่าเพิ่มชิ้นส่วน (เรื่องของหน้านี้) — ทิศทางต่างกัน แต่เกณฑ์วัดคือ **จำนวนความรับผิดชอบ** เหมือนกันทั้งคู่
- "ถ้าลังเลให้เลือกฝั่งที่หนัก" ของ [`L2-1`](01-milestone-loop.md) เป็นการตัดสินใจในระดับ **process** (การทำเป็น Epic・ความหนาของ review) ไม่ใช่เรื่องของการเพิ่มฟีเจอร์ "ข้อกำหนดเบา แต่ process หนัก" สามารถอยู่ร่วมกันได้
- การที่ใครก็ตามสามารถเข้าใจโครงสร้างได้ มีแรงจูงใจเดียวกันกับการวางตัวบทหลักของการส่งต่องานไว้ใน Issue ([Issue-first](why-issue-first.md)) โดยยึดผู้อ่านคนถัดไปที่**เข้ามาโดยไม่มีความทรงจำใด ๆ**เป็นมาตรฐาน

## คำถามที่พบบ่อย

**agent จะใช้ "การสงสัยข้อกำหนด" เป็นข้ออ้างเพื่อลบข้อกำหนดเองตามใจชอบไหม?**

การอ่านหน้านี้ไม่อนุญาตให้ทำเช่นนั้น การสงสัย = แค่ตั้งคำถามและเสนอแนะ การตัดสินใจลบ・จำกัดขอบเขตเป็นของผู้ร้องขอ (ตามหัวข้อ "สงสัยได้อย่างอิสระ แต่การตัดสินใจตัดออกเป็นของผู้ร้องขอ" ด้านบน) การลดทอน Done when โดยไม่มีข้อตกลง ให้ถือเป็นความเบี่ยงเบนประเภทที่จะถูกเปิดโปงเมื่อตรวจสอบกับบันทึกความสำเร็จ ([`L1-7`](02-issue-loop.md))

**การสงสัยข้อกำหนดเป็นการไม่ให้เกียรติผู้ร้องขอหรือไม่?**

สิ่งที่ถูกสงสัยไม่ใช่ผู้ร้องขอ แต่คือการแปลงจากข้อกำหนดไปสู่การออกแบบ คำถาม "ใครเป็นคนใช้?" ไม่ใช่การต่อรองเพื่อลดคำขอ แต่เป็นการทำงานเพื่อยืนยันวัตถุประสงค์ที่แท้จริงของคำขอนั้น ถ้าบรรลุวัตถุประสงค์ได้ ปริมาณที่สร้างยิ่งน้อยก็ยิ่งเป็นประโยชน์ต่อผู้ร้องขอ

**ถ้าสร้างแบบเรียบง่าย จะขยายในภายหลังไม่ได้หรือไม่?**

ส่วนใหญ่มักเป็นตรงกันข้าม กลไกที่ใส่ไว้ล่วงหน้าเพื่อเตรียมพร้อมสำหรับการขยายในอนาคต ส่วนใหญ่มักมีการขยายมาในทิศทางที่คาดไม่ถึง จึงไม่ได้ถูกใช้งาน และกลับเป็นอุปสรรคต่อความเข้าใจของผู้อ่านเท่านั้น โครงสร้างที่เล็กและเข้าใจง่ายคือความสามารถในการขยายที่ปรับใช้ได้กว้างที่สุด

**ควรสงสัยข้อกำหนดเมื่อไหร่?**

มี 2 ครั้ง ครั้งแรกคือก่อนเริ่มลงมือ — ตอนที่กำหนดข้อกำหนดในข้อตกลงเป้าหมาย ([`L2-1`](01-milestone-loop.md)) ตรงนี้เป็นเวทีสนทนากับผู้ร้องขอ จึงเพียงแค่ถามในตอนนั้นก็เพียงพอ ครั้งที่สองคือระหว่างทาง — เมื่อรู้สึกว่าการออกแบบเริ่มซับซ้อนหรือติดขัด ตรงนี้ผู้ร้องขอไม่ได้อยู่ในเวทีนั้น ดังนั้นตามเส้นแบ่งด้านบน งานของ agent มีแค่ "เขียนคำถามลงใน Issue เพื่อยืนยัน" เมื่อติดขัด ทั้งมนุษย์และ agent มักมีแนวโน้มมุ่งไปที่ "ทางแก้ที่ซับซ้อนยิ่งขึ้น" หน้านี้มีไว้เพื่อหยุดยั้งแนวโน้มนั้น
