# PB การเตรียมพร้อมเผยแพร่ — ชั้นที่ใช้เช็คลิสต์เป็นประตูของการเผยแพร่รีโพ

ในขณะที่ชั้น L (L2 / L1 / L0) เป็นสัญญาว่า "จะดำเนินงานอย่างไร" และชั้น R เป็นสัญญาว่า "รับอะไร" ชั้น T เป็นสัญญาว่า "จะสะสมหลักฐานความถูกต้องอย่างไร" ชั้น PB กำหนดสัญญาว่า**เลนที่เผยแพร่รีโปจะแสดงได้อย่างไรว่าได้ทำการตรวจสอบก่อนเผยแพร่ครบทุกรายการด้วยหลักฐานรายข้อ** แต่ละกฎมี rule ID ที่คงที่ (`PB-1`ถึง`PB-5`) กำกับไว้ และแต่ละข้อระบุขอบเขตการใช้ไว้ใน〔 〕 ต้นฉบับของบันทึกความเสร็จสมบูรณ์วางไว้ที่ [docs/02](02-issue-loop.md) ท่าทีเมื่อไม่สามารถตรวจสอบได้วางไว้ที่ [docs/05](05-fail-posture.md) วินัยของการส่งมอบและหลักฐานวางไว้ที่ [docs/10](10-test-ci-baseline.md) ตำแหน่งของต้นฉบับเป็นไปตามบันไดการจัดวางของ [R-5](09-rejection-rubric.md) การยกระดับเป็น check ในภายหลังเป็นไปตามหลักการทั่วไปของ [R-6](09-rejection-rubric.md) และไม่ก้าวล่วงการตัดสินคุณค่าเกินกว่า [R-1](09-rejection-rubric.md)

`PB-1`ถึง`PB-5` ของชั้นนี้เป็นคนละเรื่องกับสัญญาแกน `P1`ถึง`P5` ของ README (v0.1.0・แช่แข็งแล้ว)

ที่มา: ใน consistency campaign ของรีโปตระกูลบ้าน ได้ตรวจสอบด้วยมือทีละรีโปในเรื่องความซื่อตรงของการแสดงผล ประสิทธิผลของ CI ความลับ・ประวัติ การรีวิว บันทึกความเสร็จสมบูรณ์ และการเชื่อมต่อกับองค์กร ผลงานนี้ถูกนำมาสำรวจใน Phase 1〜4 ของ [Issue #100](https://github.com/caty-ai/family-dev-handbook/issues/100) แล้วจัดระเบียบเป็น[28 รายการของ Phase 2](https://github.com/caty-ai/family-dev-handbook/issues/100#issuecomment-5355210694) และ[โครงร่างบทบัญญัติของ Phase 4](https://github.com/caty-ai/family-dev-handbook/issues/100#issuecomment-5355215540) ก่อนจะยืนยันรูปแบบการประกาศ・ระดับความจำเป็น・ลำดับ pilot ด้วย[การตัดสินของ owner](https://github.com/caty-ai/family-dev-handbook/issues/100#issuecomment-5359570954) บทนี้กำหนดผลลัพธ์ดังกล่าวให้เป็นประตูของเลนเผยแพร่

<a id="pb-1"></a>

## PB-1 ผูกประตูกับหลักฐาน — หยุดการเผยแพร่ด้วยหลักฐานรายข้อ〔private→public การสลับ・การสร้าง public ใหม่ = MUST〕

**เลนที่เผยแพร่รีโปให้ทำประตูด้วยเช็คลิสต์ฉบับหลักของ [PB-2](#pb-2) บันทึกความเสร็จสมบูรณ์ต้องมีตาราง PASS / FAIL / N/A รายข้อ (ฉบับหลักของรูปแบบคือหัวเช็คลิสต์) พร้อมหลักฐาน artifact ที่แต่ละข้อกำหนดไว้ รายการที่ตรวจสอบไม่ได้ถือว่ายังไม่ผ่าน และห้ามเผยแพร่**

เหตุผล: ใน campaign ทุกรายการมีตัวอย่างความล้มเหลวจริง คำเตือนแบบร้อยแก้วเพียงอย่างเดียวป้องกันไม่ได้ การเรียกร้องหลักฐานรายข้อจะปิดเส้นทางที่นำสถานะ "ยังไม่ตรวจ" มาปฏิบัติเหมือน "ตรวจแล้ว" นี่คือการนำท่าที fail-closed ของ [docs/05](05-fail-posture.md) มาใช้กับเลนเผยแพร่ และรักษาความหมายของความซื่อตรงในการแสดงผลให้เท่ากับ [T-7](10-test-ci-baseline.md)

การเขียนขอบเขตให้ชัดเจน:

- fork ของรีโปตระกูลบ้าน หรือการเผยแพร่ public remote ที่สองใหม่ อยู่ในขอบเขต
- fork ของรีโปที่บุคคลที่สามภายนอกเผยแพร่อยู่แล้ว ไม่อยู่ในขอบเขต การตัดสินคุณค่าที่จะใช้เป็นอำนาจของ owner โดยเฉพาะ ([R-1](09-rejection-rubric.md) ระเบียบการตัดสินคุณค่า)
- การเผยแพร่ซ้ำแบบ public→private→public ให้รันเช็คลิสต์ใหม่อีกครั้ง วิธีรันซ้ำเฉพาะส่วนต่างโดยอ้างอิงบันทึกล่าสุดเป็นไปตามหัวเช็คลิสต์
- การเผยแพร่ไปยัง mirror นอก GitHub และ package registry ไม่อยู่ในขอบเขต
- การย้อนไปใช้กับรีโปที่เผยแพร่ไปแล้ว ไม่อยู่ในขอบเขต แต่ในเลนถัดไปที่แตะจุดที่เกี่ยวข้อง ให้ทำแบบ opportunistic แบบเดียวกับ [T-1](10-test-ci-baseline.md) โดยไม่ตั้งเลนสำรวจเฉพาะ

<a id="pb-2"></a>

## PB-2 ที่เก็บและเวอร์ชันของเช็คลิสต์ — ตรึงฉบับหลักที่รันจริงให้แน่น〔ตัวเช็คลิสต์การเผยแพร่・ทุกเลนเผยแพร่〕

**ฉบับหลักของเช็คลิสต์คือ [templates/publication-checklist.md](../templates/publication-checklist.md) และเวอร์ชันของมันขึ้นกับแท็ก release ของ handbook เลนเผยแพร่ตามหลักแล้วให้บันทึกแท็ก release ที่อ้างอิงไว้ในบันทึกความเสร็จสมบูรณ์ เฉพาะกรณีที่รันในสถานะที่ยังไม่รวมอยู่ในแท็กเท่านั้น ให้บันทึก commit SHA แล้วเพิ่มแท็ก release ที่รวมสถานะนั้นไว้ในบันทึกความเสร็จสมบูรณ์เดียวกันในภายหลัง**

เหตุผล: ใน [handbook#80](https://github.com/caty-ai/family-dev-handbook/issues/80#issuecomment-5344053714) เกิด race ที่ caller สำหรับแจกจ่ายถูก pin ก่อนแท็ก `ci-v1` จะมีอยู่จริง หากไม่ตรึงเวอร์ชันที่แก้ปัญหาได้ว่ารันเนื้อหาอะไรจริง นอกเหนือจากตำแหน่งของฉบับหลัก การตัดสินก็จะต่างกันได้แม้เป็นเช็คลิสต์ชื่อเดียวกัน

<a id="pb-3"></a>

## PB-3 ขอบเขตของการจำแนก — ปิดรูปแบบผ่านตามประเภท〔ทุกรายการของเช็คลิสต์เผยแพร่〕

**รายการประเภท (a) ผ่านด้วยหลักฐานเชิงกล คือ run URL รายการประเภท (b) ผ่านด้วยขั้นตอนมือที่เช็คลิสต์ระบุไว้เป็นรายข้อพร้อมบันทึก จนกว่าจะมีการทำให้เป็นกลไก รายการประเภท (c) ผ่านได้เฉพาะด้วยป้ายของ owner หรือการตัดสินที่บันทึกไว้เท่านั้น รายการประเภท (c) ไม่มีวันผ่านด้วยการอ้างตนเอง**

ข้อกำหนดผู้ออกของ (c) มีเพียง 3 รูปแบบต่อไปนี้:

1. เหตุการณ์ป้ายจากบัญชี owner
2. คอมเมนต์ที่ owner โพสต์เอง
3. การรับรองย้อนหลังที่ตรวจสอบได้จาก owner ต่อบันทึกแบบ relay (ต้องมีลิงก์การรับรอง)

นอกเหนือจากนี้ถือว่ายังไม่ผ่าน ระดับความจำเป็นและรูปแบบการประกาศของแต่ละรายการเป็นไปตามที่เช็คลิสต์กำหนด

เหตุผล: ใน harness#121 เกิดความเสียหายจริงที่การอ้างตนเองว่า "owner ตัดสินแล้ว" ไม่มีการอนุญาตของ owner ตัวจริงที่ตรวจสอบได้อยู่จริง ได้รับการช่วยเหลือเพียงครั้งเดียวด้วย[การรับรองย้อนหลัง](https://github.com/caty-ai/caty-agent-harness/issues/121#issuecomment-5341374987) หากบุคคลที่สามตรวจสอบผู้ออกไม่ได้ ไม่ใช่แค่เนื้อหาของการตัดสิน อำนาจเฉพาะของ owner ([R-1](09-rejection-rubric.md) ระเบียบการตัดสินคุณค่า) ก็ไม่อาจสำเร็จได้

<a id="pb-4"></a>

## PB-4 ความสมบูรณ์ของบันทึก — รักษา 1 เลน 1 บันทึกให้แก้ปัญหาได้〔บันทึกความเสร็จสมบูรณ์ของเลนเผยแพร่〕

**เลนเผยแพร่หนึ่งเลนมีบันทึกความเสร็จสมบูรณ์ได้เพียงหนึ่งฉบับพอดี และวางไว้ที่ Issue ของเลน นี่คือข้อยกเว้นเฉพาะสำหรับเลนเผยแพร่ที่กำหนดให้ที่เก็บบันทึกความเสร็จสมบูรณ์ตาม [L1-7](02-issue-loop.md) เป็น Issue ของเลน โดยเนื้อหา PR ให้วางเพียงตัวชี้ 1 บรรทัดไปยัง Issue ของเลน ไม่ใช่ตัวบันทึกเอง ให้ใช้ห่วงโซ่ release / previous release ของ [T-5](10-test-ci-baseline.md) และ run URL ต้องแก้ปัญหาได้ไปยัง run ที่มีอยู่จริง โดย head SHA ต้องตรงกับ candidate SHA**

เหตุผล: ใน [family-memory-architecture#33](https://github.com/caty-ai/family-memory-architecture/issues/33#issuecomment-5354966162) พบว่าบันทึกความเสร็จสมบูรณ์ถูกวางไว้ที่ Issue ติดตาม ทำให้ scanner ที่ดูแค่ PR มองข้ามไป ในทางกลับกัน persona-growth-loop#16 เกิดความผิดปกติที่มีบันทึกความเสร็จสมบูรณ์ที่ขัดแย้งกันหลงเหลืออยู่ 2 ฉบับ คือ[บันทึกล่วงหน้า](https://github.com/caty-ai/persona-growth-loop/issues/16#issuecomment-5341012500)กับ[บันทึกภายหลัง](https://github.com/caty-ai/persona-growth-loop/issues/16#issuecomment-5345278041) การตรึงที่เก็บและจำนวนไว้ และให้การแก้ไขของ [L1-8](02-issue-loop.md) หลงเหลือเป็นบันทึกแทนที่ในห่วงโซ่เดียวกัน จะรักษาทางเข้าตรวจสอบให้เป็นจุดเดียว ความสามารถในการแก้ปัญหาของหลักฐานใช้เกณฑ์เดียวกับ[บันทึกแก้ไขของ L1-8](https://github.com/caty-ai/family-os/issues/64#issuecomment-5353192649) ของ campaign

<a id="pb-5"></a>

## PB-5 บทบัญญัติ pilot (มีกำหนดเวลา) — ส่งช่องว่างการใช้งานจริงกลับสู่ฉบับหลัก〔ช่วงเริ่มต้นของการใช้งานเช็คลิสต์〕

**เลนผู้บริโภคที่ 1 และที่ 2 ที่ owner แต่งตั้งไว้ ให้รายงานช่องว่างการใช้งานของแต่ละรายการไปที่ [Issue #100](https://github.com/caty-ai/family-dev-handbook/issues/100) แล้วสะท้อนกลับเข้าเช็คลิสต์ฉบับหลัก เลนที่รันก่อนการสะท้อนกลับของ pilot ให้บันทึกสถานะเช็คลิสต์ที่รันจริงตาม PB-2**

บันทึกการแต่งตั้งผู้บริโภคคือ[คอมเมนต์การตัดสินของ owner ใน #100](https://github.com/caty-ai/family-dev-handbook/issues/100#issuecomment-5359570954) ข้อเสนอ merge ของข้อนี้ตามหลักแล้วให้ทำหลังจากสะท้อนช่องว่างของผู้บริโภคที่ 1 เข้าเช็คลิสต์แล้ว การทำก่อนเป็นอำนาจของ owner โดยเฉพาะ ([R-1](09-rejection-rubric.md) ระเบียบการตัดสินคุณค่า)

ข้อนี้จะหมดอายุเมื่อรายงานช่องว่างของเลนผู้บริโภคที่ 1 และที่ 2 ครบใน #100 และถูกสะท้อนเข้าเช็คลิสต์ฉบับหลักแล้ว การลบออกจากบทบัญญัติให้ทำใน PR ถัดไป และถือว่าการเปลี่ยนแปลงบรรทัดฐาน = การเปลี่ยนแปลงระดับ release โดยใช้ [T-5](10-test-ci-baseline.md)

เหตุผล: ต้นทุนและความคลุมเครือของขั้นตอนมือวัดได้จริงก็ต่อเมื่อผ่านเลนเผยแพร่จริงเท่านั้น ในขณะที่แก้ไขฉบับหลักด้วยการสะท้อนกลับจากเลนผู้บริโภค 2 เลน การเก็บบันทึกไว้ว่าตัดสินด้วยสถานะใด จะไม่ทำให้การเปลี่ยนแปลงระหว่าง pilot ย้อนไปกระทบการตัดสินในอดีตอย่างเงียบๆ
