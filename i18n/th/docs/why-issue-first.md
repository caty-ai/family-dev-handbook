# Issue-first คืออะไร — ทำไมต้องเริ่มจาก Issue ไม่ใช่การสนทนา

> หน้านี้ไม่ใช่ตัวบทกฎ ตัวบทกฎฉบับเต็มอยู่ที่ [docs/01](01-milestone-loop.md)〜[docs/03](03-git-protocol.md) และ [docs/05](05-fail-posture.md)〜[docs/08](08-lifecycle.md)
> สิ่งที่เขียนอยู่ที่นี่คือ**แนวคิดที่เป็นพื้นฐาน**ของกฎเหล่านั้น สำหรับผู้ที่อยากรู้ว่าทำไมถึงเป็นแบบนั้น ก่อนที่จะจดจำกฎ

## เมื่อสั่งงานด้วยการสนทนา จะเกิดอะไรขึ้น

ลองขอให้ AI agent ว่า "ช่วยแก้บั๊กตัวนั้นที" มันก็แก้ให้ วันรุ่งขึ้น เปิด session ใหม่

agent จำเรื่องเมื่อวานไม่ได้เลย สิ่งที่แก้ไป ทำไมถึงเลือกวิธีแก้แบบนั้น ตรวจสอบไปถึงไหนแล้ว ทั้งหมดนี้หายไปพร้อมกับ terminal ที่ปิดไป สิ่งที่เหลืออยู่มีเพียงการเปลี่ยนแปลงของโค้ด แต่การตัดสินใจที่นำไปสู่มันไม่เหลืออยู่เลย

เรื่องแบบนี้เกิดขึ้นระหว่างมนุษย์ด้วยกันเองได้เช่นกัน สิ่งที่ตัดสินใจกันในแชทก็ไหลลอยไปกับการเลื่อนหน้าจอ สิ่งที่ต่างออกไปคือ ในกรณีของ AI เราไม่สามารถแม้แต่จะ "ให้มันช่วยนึกย้อนกลับไป" ได้ **ทุกครั้งต้องเริ่มจากความทรงจำที่เป็นศูนย์**

และตอนนี้ agent ก็ไม่ได้มีแค่ตัวเดียวอีกต่อไป เมื่อมี 2 ตัวทำงานพร้อมกัน ทั้งสองก็ไม่มีทางรู้ว่าอีกฝ่ายกำลังทำอะไรอยู่ และอาจไปแตะไฟล์เดียวกันโดยไม่รู้ตัว

## Issue-first คืออะไร

สิ่งที่ต้องทำมีเพียงข้อเดียว

**ก่อนแตะโค้ด ให้ตั้ง Issue ใน GitHub ขึ้นมา 1 ฉบับ**

แค่นั้นเอง ไม่ต้องใช้เครื่องมือพิเศษ ไม่ต้องมีบริการเพิ่มเติม การ implement จะเริ่มก็ต่อเมื่อมี Issue ตั้งขึ้นแล้ว จะไม่ implement โดยไม่มี Issue

## ทำไมวิธีนี้ถึงได้ผล

เมื่อตั้ง Issue ขึ้นมา **จุดอ้างอิงหลักสำหรับการส่งต่องานจะถูกตรึงไว้ในที่เดียว**

เมื่องานเสร็จ จะเหลืออยู่ 2 สิ่ง คือเนื้อหาของ Issue (จะทำอะไร・เมื่อไหร่ถึงจะถือว่าเสร็จ) และ diff ของ Pull Request (จริง ๆ แล้วมีอะไรเปลี่ยนไปบ้าง) ถ้าทั้งสองอย่างนี้ครบถ้วน ใครก็ตามที่เข้ามากลางทาง — ไม่ว่าจะเป็นคนอื่น, agent อื่น, หรือแม้แต่ตัวเราเองในวันพรุ่งนี้ที่ลืมทุกอย่างไปแล้ว — ก็สามารถทำงานต่อได้เพียงแค่อ่าน Issue

ประวัติการสนทนาจะหายไป ความทรงจำของ agent ก็จะหายไป **แต่ Issue กับ PR จะไม่หายไป** เพราะฉะนั้นเราจึงให้ตรงนี้เป็นจุดอ้างอิงหลักเพียงจุดเดียว

นี่ไม่ใช่ปัญหาเรื่องความไว้ใจ แต่เป็นปัญหาเรื่องที่เก็บข้อมูล ไม่ใช่ว่าเขียน Issue เพราะใครขี้ลืม แต่เป็นการ**กำหนดที่เก็บข้อมูลไว้ล่วงหน้า 1 ที่ โดยตั้งสมมติฐานว่าทุกอย่างจะถูกลืม**

## ใน Issue ควรเขียนอะไรบ้าง

สิ่งที่จำเป็นมีเพียง 3 อย่าง (ในตัวบทกฎคือ [`L1-2`](02-issue-loop.md)) รูปแบบมาตรฐานอยู่ที่ [templates/issue-template.md](../templates/issue-template.md)

**1. วัตถุประสงค์ (Why)** — ทำไมต้องทำ ถ้าไม่ทำจะเกิดปัญหาอะไร

เขียนไว้เพื่อตัวเราในอีกไม่กี่วันข้างหน้า และเพื่อ agent อีกตัวที่จะเข้ามาในวันพรุ่งนี้ ถ้าไม่มีเหตุผลที่ตัดสินใจ "จะทำ" หลงเหลืออยู่ เมื่อการตัดสินใจแตกแขนงระหว่างทาง ก็จะไม่มีจุดให้กลับไปอ้างอิง

**2. เงื่อนไขความสำเร็จ (Done when)** — เมื่อไหร่ถึงจะถือว่าเสร็จ

เขียนเป็น checkbox และทำให้อยู่ใน**รูปแบบที่เครื่องหรือเครื่องจริงสามารถตัดสินได้** ไม่ใช่เขียนว่า "ทำงานได้ดี" แต่ให้เขียนว่า "test ผ่าน" "แสดงผลบนเครื่องจริงได้" นี่คือวิธีเดียวที่จะทำให้คำว่า "เสร็จแล้ว" ตรวจสอบได้ เพราะมีข้อนี้อยู่ เมื่อถึงเวลา merge จึงสามารถนำมาตรวจสอบทีละข้อว่า PASS หรือ FAIL ได้ ([`L1-7`](02-issue-loop.md))

**3. การคาดการณ์ไฟล์ / module ที่จะแตะ** — ตั้งใจว่าจะแตะไฟล์ไหนบ้าง

ข้อนี้ไม่ใช่เพื่อตัวเราเอง แต่เป็นข้อที่มีไว้**เพื่องานอื่น** ถ้ารู้ก่อนเริ่มงานว่ากลุ่มไฟล์ที่ทั้งสองงานจะแตะไม่ทับซ้อนกัน ก็สามารถทำงานคู่ขนานกันได้ แต่ถ้าไม่รู้ ก็จะไม่ทำคู่ขนาน ([`L2-3`](01-milestone-loop.md) / [`L2-4`](01-milestone-loop.md)) เนื่องจากเป็นการคาดการณ์ ต่อให้คลาดเคลื่อนก็ไม่เป็นไร เมื่อเริ่มลงมือทำจริงจึงค่อยประกาศเวอร์ชันที่ยืนยันแล้วอีกครั้ง

## กรณีที่ไม่จำเป็นต้องมี Issue

ไม่ใช่ว่าทุกอย่างต้องตั้ง Issue ต่อไปนี้เป็นข้อยกเว้น ([`L1-1`](02-issue-loop.md))

- การแก้ typo 1 บรรทัด
- ไฟล์ที่ไม่ใช่โค้ด (md / json / yaml เป็นต้น)
- scratch ที่อยู่นอกการจัดการของ git
- การสำรวจ・การอ่านทำความเข้าใจ・การสนทนา (งานที่ไม่เปลี่ยนแปลงอะไรเลย)

ถ้าลังเล ให้คิดแบบนี้ **ถ้าดูแล้วน่าจะข้ามหลาย session ให้ตั้ง Issue** ถ้าจบได้ในทีเดียวก็ไม่จำเป็น

## เมื่อทำงานร่วมกับ AI จะเปลี่ยนไปอย่างไร

Issue-first ไม่ใช่แนวคิดที่เกิดขึ้นเพื่อ AI โดยเฉพาะ เป็นวิธีการที่ใช้กันมาก่อนแล้วในวงการพัฒนาซอฟต์แวร์ แต่เมื่อนำมาใช้ร่วมกับ AI agent คุณค่าของมันจะพุ่งสูงขึ้นด้วยเหตุผล 3 ข้อ

- **ความทรงจำเริ่มจากศูนย์** — ถ้าเป็นมนุษย์ก็ยังมี "อ้อ เมื่อสัปดาห์ที่แล้ว..." แต่ agent ไม่มีสิ่งนั้น Issue จึงกลายเป็นความทรงจำเพียงหนึ่งเดียว
- **มีหลายตัวทำงานพร้อมกัน** — ถ้าไม่ประกาศว่าใครกำลังแตะอะไรอยู่ การชนกันก็จะขึ้นอยู่กับดวง
- **การรายงาน "เสร็จแล้ว" ด้วยตัวเอง** — วิธีเดียวที่จะป้องกันรายงานความสำเร็จโดยไม่ผ่านการตรวจสอบ คือการเขียนเงื่อนไขความสำเร็จไว้ก่อนเริ่มงาน

## คำถามที่พบบ่อย

**แม้แต่การแก้เล็ก ๆ น้อย ๆ ก็ต้องตั้ง Issue ทุกครั้งเลยหรือ**

ไม่ใช่ ตามที่กล่าวไว้ใน "กรณีที่ไม่จำเป็นต้องมี Issue" ข้างต้น เกณฑ์ตัดสินคือดูว่าจะข้ามหลาย session หรือไม่

**Issue จะเยอะเกินไปไหม**

เยอะขึ้นแน่นอน แต่สิ่งที่จะเป็นปัญหาเมื่อเยอะขึ้นคือ "Issue ที่เปิดค้างอยู่" ส่วน Issue ที่ปิดไปแล้วมีประโยชน์ในฐานะบันทึก การแสดงสถานะของ lane ด้วยคำเพียง 5 คำ (WIP / HOLD / MERGED / SUPERSEDED / ABANDONED) ก็เพื่อให้แยกออกได้ในพริบตาว่าอันไหนเปิดอยู่ อันไหนจบแล้ว ([`L1-4`](02-issue-loop.md))

**ถ้าพัฒนาคนเดียว จะมีประโยชน์ไหม**

ถ้าใช้ agent ก็มีประโยชน์ แม้จะทำงานคนเดียว แต่การส่งต่องานก็เกิดขึ้นในทุกช่วงที่ข้าม session กลับกัน ถ้าทำแต่งานที่จบในตัวภายใน session เดียว ผลของ Issue-first แทบจะไม่มีเลย

**เขียน Issue จะเสียเวลาไปเปล่า ๆ ไหม**

สิ่งที่ต้องเขียนมีแค่ 3 หัวข้อ ถ้าเริ่มงานโดยไม่เขียนสิ่งนี้ ภายหลังจะต้องเสียเวลามาปะติดปะต่อว่า "ตรวจสอบอะไรไปแล้วนะ" "ทำไปถึงไหนแล้วนะ" ว่าแบบไหนคุ้มกว่าขึ้นอยู่กับความยาวของงาน ยิ่งงานสั้นก็ยิ่งไม่จำเป็นต้องมี Issue เพราะฉะนั้นเราจึงกำหนด "กรณีที่ไม่จำเป็น" ไว้ล่วงหน้าแล้ว
