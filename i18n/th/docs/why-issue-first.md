# Issue-first คืออะไร — ทำไมต้องเริ่มจาก Issue ไม่ใช่จากการสนทนา

> หน้านี้ไม่ใช่ตัวบทกฎ ตัวบทกฎจริงอยู่ที่ [docs/01](01-milestone-loop.md)〜[docs/06](06-epic-lane.md)
> สิ่งที่เขียนไว้ที่นี่คือ **แนวคิดที่กฎเหล่านั้นตั้งอยู่บนพื้นฐาน** สำหรับคนที่อยากรู้ว่าทำไมถึงเป็นแบบนั้น ก่อนที่จะจำกฎ

## เมื่อสั่งงานด้วยการสนทนา จะเกิดอะไรขึ้น

ลองขอให้ AI เอเจนต์ "ช่วยแก้บั๊กตัวนั้นที" มันก็แก้ให้ วันรุ่งขึ้น เปิดเซสชันใหม่

เอเจนต์ไม่จำอะไรเกี่ยวกับเมื่อวานได้เลย สิ่งที่แก้ไป เหตุผลที่เลือกวิธีแก้แบบนั้น และตรวจสอบไปถึงขั้นไหนแล้ว ทั้งหมดหายไปพร้อมกับเทอร์มินัลที่ปิดไป สิ่งที่เหลืออยู่มีแค่การเปลี่ยนแปลงของโค้ด ส่วนการตัดสินใจที่นำไปสู่จุดนั้นไม่เหลืออยู่เลย

ระหว่างมนุษย์ด้วยกันก็เกิดเรื่องคล้ายกันได้ สิ่งที่ตกลงกันในแชทก็เลื่อนหายไปตามการสกรอลล์ แต่สิ่งที่ต่างออกไปคือ ในกรณีของ AI นั้น แม้แต่การ "ให้มันช่วยนึกย้อนกลับ" ก็ทำไม่ได้ **ทุกครั้งต้องเริ่มจากความจำเป็นศูนย์**

และตอนนี้ก็ไม่ได้จำกัดว่ามีเอเจนต์แค่ตัวเดียวอีกต่อไป หากเอเจนต์ 2 ตัวทำงานพร้อมกัน ก็จะไม่มีวิธีรู้ว่าอีกฝ่ายกำลังทำอะไร แล้วก็แตะไฟล์เดียวกันเข้าโดยไม่รู้ตัว

## Issue-first คืออะไร

สิ่งที่ต้องทำมีแค่อย่างเดียว

**ก่อนแตะโค้ด ให้ตั้ง Issue บน GitHub ขึ้นมา 1 อัน**

แค่นั้นเอง ไม่ต้องใช้เครื่องมือพิเศษ ไม่ต้องมีบริการเพิ่มเติมใดๆ การลงมือทำเริ่มได้ก็ต่อเมื่อ Issue ถูกตั้งขึ้นแล้ว จะไม่มีการลงมือทำโดยไม่มี Issue

## ทำไมถึงได้ผล

เมื่อตั้ง Issue ขึ้นมาแล้ว **ต้นฉบับสำหรับการส่งต่องานจะถูกตรึงไว้ในที่เดียว**

เมื่องานเสร็จ จะเหลือสิ่งของอยู่ 2 อย่าง คือเนื้อหาของ Issue (จะทำอะไร・เสร็จเมื่อไหร่) และ diff ของ Pull Request (จริงๆ แล้วมีอะไรเปลี่ยนไปบ้าง) ถ้ามีทั้งสองอย่างนี้ครบ ใครก็ตามที่เข้ามาระหว่างทาง — ไม่ว่าจะเป็นคนอื่น เอเจนต์ตัวอื่น หรือแม้แต่ตัวเองในวันพรุ่งนี้ที่ความจำหายไปแล้ว — ก็สามารถอ่าน Issue แล้วทำงานต่อได้

ประวัติการสนทนาจะหายไป ความจำของเอเจนต์ก็จะหายไป **แต่ Issue และ PR จะไม่หายไป** เพราะฉะนั้นจึงกำหนดให้จุดนั้นเป็นต้นฉบับเพียงหนึ่งเดียว

นี่ไม่ใช่ปัญหาเรื่องความไว้วางใจ แต่เป็นปัญหาเรื่องที่เก็บข้อมูล ไม่ใช่ว่าเขียน Issue เพราะใครขี้ลืม แต่คือการ **กำหนดที่เก็บข้อมูลไว้ล่วงหน้าโดยตั้งสมมติฐานว่าจะลืม**

## ต้องเขียนอะไรใน Issue

สิ่งที่จำเป็นมีแค่ 3 อย่าง (ในตัวบทกฎคือ [`L1-2`](02-issue-loop.md)) ต้นฉบับของรูปแบบอยู่ที่ [templates/issue-template.md](../templates/issue-template.md)

**1. วัตถุประสงค์ (Why)** — ทำไมถึงต้องทำ ถ้าไม่ทำจะเดือดร้อนตรงไหน

เขียนไว้เพื่อตัวเองในอีกไม่กี่วันข้างหน้า และเพื่อเอเจนต์ตัวอื่นที่จะเข้ามาในวันพรุ่งนี้ ถ้าไม่มีเหตุผลที่ตัดสินใจว่า "จะทำ" หลงเหลืออยู่ เมื่อความเห็นแตกแยกกันระหว่างทาง ก็จะไม่มีที่ให้กลับไปอ้างอิง

**2. เงื่อนไขความสำเร็จ (Done when)** — เสร็จเมื่อไหร่

เขียนเป็น checkbox และทำให้อยู่ในรูปแบบที่ **เครื่องจักรหรือเครื่องจริงตัดสินได้** ไม่ใช่เขียนว่า "ทำงานได้ดี" แต่ให้เขียนว่า "เทสต์ผ่าน" "แสดงผลบนเครื่องจริงได้" นี่คือวิธีเดียวที่จะทำให้ "ทำเสร็จแล้ว" ตรวจสอบได้จริง เพราะมีรายการนี้อยู่ เวลา merge จึงสามารถเทียบ PASS / FAIL ทีละข้อได้ ([`L1-7`](02-issue-loop.md))

**3. การคาดการณ์ไฟล์ / โมดูลที่จะแตะ** — ตั้งใจจะแตะไฟล์ไหนบ้าง

รายการนี้ไม่ได้มีไว้เพื่อตัวเอง แต่มีไว้ **เพื่องานอื่น** หากรู้ก่อนลงมือทำว่ากลุ่มไฟล์ที่งาน 2 ชิ้นจะแตะไม่ทับซ้อนกัน ก็จะสามารถทำคู่ขนานกันได้ ถ้าไม่รู้ ก็จะไม่ทำคู่ขนาน ([`L2-3`](01-milestone-loop.md) / [`L2-4`](01-milestone-loop.md)) เนื่องจากเป็นการคาดการณ์ ต่อให้คลาดเคลื่อนก็ไม่เป็นไร เมื่อเริ่มลงมือทำจริงค่อยประกาศเวอร์ชันที่ยืนยันแล้วอีกครั้ง

## กรณีที่ไม่จำเป็นต้องมี Issue

ไม่ใช่ว่าทุกอย่างต้องตั้ง Issue กรณีต่อไปนี้ไม่อยู่ในขอบเขตที่ต้องทำ ([`L1-1`](02-issue-loop.md))

- การแก้ typo 1 บรรทัด
- ไฟล์ที่ไม่ใช่โค้ด (md / json / yaml ฯลฯ)
- scratch ที่อยู่นอกการจัดการของ git
- การสำรวจ・อ่านทำความเข้าใจ・การสนทนา (งานที่ไม่เปลี่ยนแปลงอะไรเลย)

ถ้าลังเล ให้คิดแบบนี้ **ถ้าดูท่าจะยืดยาวข้ามหลายเซสชัน ให้ตั้ง Issue** ถ้าจบในตอนนั้นเลย ก็ไม่จำเป็น

## เมื่อจับคู่กับ AI จะเปลี่ยนไปอย่างไร

Issue-first ไม่ใช่แนวคิดที่เกิดขึ้นเพื่อ AI มันเป็นวิธีการที่ใช้กันมาตั้งแต่ก่อนในวงการพัฒนาซอฟต์แวร์ แต่เมื่อจับคู่กับ AI เอเจนต์ คุณค่าของมันจะพุ่งสูงขึ้นด้วยเหตุผล 3 ข้อ

- **ความจำเริ่มจากศูนย์** — ถ้าเป็นมนุษย์ก็ยังมี "อ้อ เมื่อสัปดาห์ก่อน" แต่เอเจนต์ไม่มี Issue จะกลายเป็นความจำเพียงหนึ่งเดียว
- **มีหลายตัวทำงานพร้อมกัน** — ถ้าไม่ประกาศว่าใครกำลังแตะอะไรอยู่ การชนกันก็จะขึ้นอยู่กับดวง
- **การรายงานตัวเองว่า "ทำเสร็จแล้ว"** — วิธีเดียวที่จะป้องกันรายงานความสำเร็จที่ไม่ผ่านการตรวจสอบ คือการเขียนเงื่อนไขความสำเร็จไว้ก่อนลงมือทำ

## คำถามที่พบบ่อย

**แม้แต่การแก้เล็กๆ ก็ต้องตั้ง Issue ทุกครั้งเลยหรือ?**

ไม่ใช่ เป็นไปตามหัวข้อ "กรณีที่ไม่จำเป็นต้องมี Issue" ข้างต้น เกณฑ์การตัดสินคือดูว่าจะยืดยาวข้ามหลายเซสชันหรือไม่

**Issue จะไม่เพิ่มขึ้นเยอะเกินไปหรือ?**

เพิ่มขึ้นแน่นอน แต่สิ่งที่เป็นปัญหาเมื่อเพิ่มขึ้นคือ "Issue ที่เปิดค้างไว้" ส่วน Issue ที่ปิดไปแล้วมีประโยชน์ในฐานะบันทึก การแสดงสถานะของเลนด้วยคำเพียง 5 คำ (WIP / HOLD / MERGED / SUPERSEDED / ABANDONED) ก็เพื่อให้แยกระหว่างสิ่งที่ยังเปิดอยู่กับสิ่งที่จบแล้วได้ในพริบตา ([`L1-4`](02-issue-loop.md))

**ถ้าพัฒนาคนเดียว จะมีความหมายไหม?**

ถ้าใช้เอเจนต์ ก็มีความหมาย เพราะแม้จะทำคนเดียว ก็จะเกิดการส่งต่องานขึ้นในจังหวะที่ข้ามเซสชัน ในทางกลับกัน ถ้าทำแต่งานที่จบในเซสชันเดียวเท่านั้น ประสิทธิผลของ Issue-first แทบจะไม่มีเลย

**เสียเวลาเขียน Issue ไปเปล่าๆ หรือไม่?**

สิ่งที่ต้องเขียนมีแค่ 3 รายการ หากเริ่มโดยไม่เขียนสิ่งนี้ ภายหลังก็จะต้องใช้เวลาในการปะติดปะต่อว่า "ตรวจสอบอะไรไปแล้วนะ" "ทำไปถึงไหนแล้วนะ" ว่าแบบไหนคุ้มกว่ากันก็ขึ้นอยู่กับความยาวของงาน งานที่สั้นก็ยิ่งไม่จำเป็นต้องมี Issue เพราะฉะนั้นจึงกำหนด "กรณีที่ไม่จำเป็น" ไว้ล่วงหน้าแล้ว
