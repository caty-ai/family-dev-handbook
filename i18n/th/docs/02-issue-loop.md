# L1 Issue Loop — เลเยอร์ที่ทำงานหนึ่งชิ้นให้เสร็จสมบูรณ์

แต่ละกฎมี rule ID ที่คงที่ (`L1-1`〜`L1-11`) กำกับไว้ ฝั่งสรุป ([docs/04](04-adoption.md)) จะอ้างอิง ID เหล่านี้ ท่าทีเมื่อไม่สามารถตรวจสอบได้ ดูที่ [docs/05](05-fail-posture.md)

## L1-1 หลักการ Issue-first

การเปลี่ยนแปลงโค้ดภายใน repository ต้อง **เริ่มต้นจาก GitHub Issue** จะไม่ทำการ implement โดยไม่มี Issue (ข้อยกเว้นคือการแก้ไข 1 บรรทัดอย่าง typo, ไฟล์ที่ไม่ใช่โค้ดอย่าง md/json/yaml, และ scratch ที่ไม่อยู่ภายใต้การจัดการของ git)

เหตุผล: เนื้อหาของ Issue รวมกับ diff ของ PR จะกลายเป็น **SoT สำหรับการส่งต่องานระหว่าง session และระหว่าง agent** ไม่ว่า agent ตัวใดจะเข้ามารับงานต่อในช่วงกลาง ก็ต้องสามารถอ่าน Issue แล้วทำงานต่อได้

## L1-2 สามองค์ประกอบที่จำเป็นในเนื้อหา Issue

ใช้ [เทมเพลต](../templates/issue-template.md)

1. **จุดประสงค์ Why** — ทำไมต้องทำสิ่งนี้ ความเป็นมา และจะเกิดปัญหาอะไรถ้าไม่ทำ
2. **เงื่อนไขความสำเร็จ Done when** — ในรูปแบบ checkbox เขียนในรูปแบบที่ตัดสินได้ด้วยเครื่องหรือตรวจสอบบนอุปกรณ์จริงได้ เช่น "เทสต์ green" หรือ "ยืนยันบนอุปกรณ์จริงแล้ว"
3. **การคาดการณ์ไฟล์ / โมดูลที่จะแก้ไข** — เป็น input สำหรับการตัดสิน GO ของการทำงานคู่ขนานใน L2 เมื่อเริ่มลงมือทำจริง ให้ประกาศเวอร์ชันที่ยืนยันแล้วอีกครั้งผ่านคอมเมนต์ WIP

## ขั้นตอน Implement → Review → Merge

```
Issue 起票 → WIP宣言（L0-1）→ worktree で実装 → テスト/lint green
→ クロスレビュー → 指摘対応 → PR（完了記録 = L1-7 を本文に）
→ merge → Issue close → 安定点で git tag
```

## L1-3 หลักการ Cross Review

- **ห้าม self-approve** — ห้าม merge ด้วยการอนุมัติจากผู้ implement เพียงคนเดียว
- **การ review ที่จะปล่อยให้ merge ผ่านได้ ต้องมาจากคนละโมเดลหรือคนละ agent กับผู้ implement**（ตัวอย่าง: Claude implement → GPT/GLM review, Codex implement → Claude review）ถึงแม้จะเป็นโมเดลเดียวกัน แต่ถ้าเป็น **agent คนละตัว** ก็ถือว่า merge ได้ ส่วนโมเดลเดียวกันและ agent เดียวกัน แม้จะเป็น session คนละครั้งก็ยังไม่พอสำหรับ merge — session คนละครั้งเพียงพอสำหรับ checkpoint อื่นที่ไม่ใช่ merge เท่านั้น
- ค่าเริ่มต้นคือให้ reviewer รอบที่ 1 (Round-1) เป็น reviewer ที่ตรวจจนจบ หากจะเปลี่ยนตัว ต้องประกาศให้ทราบ และ reviewer คนใหม่ต้อง **review candidate ปัจจุบันทั้งหมดใหม่อีกครั้ง**（ห้าม merge ด้วยการต่อ review แบบทำทีละส่วน）
- วนลูป implementer → reviewer จนกว่าข้อ blocking จะเป็น 0
- มุมมองในการ review: ความถูกต้อง / ขอบเขต (ไม่ได้แก้ไขไฟล์ที่อยู่นอก scope) / ความเหมาะสมของเทสต์ / ความเป็นไปได้ในการ revert

## L1-4 สถานะของ Lane — คำศัพท์ 5 สถานะแบบปิด

สถานะของ lane ให้ประกาศผ่านคอมเมนต์ที่มี label ใน Issue ที่รับผิดชอบ **ต้นฉบับที่แท้จริงของสถานะ lane คือ Issue**（PR ที่ค้างอยู่จะอ้างอิงกลับไปที่ Issue）:

`WIP / HOLD / MERGED / SUPERSEDED / ABANDONED`

- **WIP คือสถานะที่ต้องประกาศอย่างชัดเจน ไม่ใช่ค่าเริ่มต้น**
- `STUCK` **ไม่ใช่**สถานะที่ 6 — มันคือเงื่อนไข trigger และทางออกที่ถูกต้องเพียงทางเดียวคือ HOLD ที่สมบูรณ์ (หรือการส่งต่อให้มนุษย์ตัดสินใจ)
- lane ที่สถานะขาดหายไป ไม่รู้จัก หรือมีรูปแบบไม่ถูกต้อง ให้ **ถือว่าไม่ active（ท่าทีเทียบเท่า HOLD: ไม่มีการเขียนใดๆ）และรอการซ่อมแซมสถานะ** ในการตัดสิน GO จะไม่นับ lane นี้ว่า "ว่าง" — งานที่อาจ intersect กับ scope ที่ประกาศไว้ให้ทำแบบ serial จนกว่าจะซ่อมแซมเสร็จ（[FP-1](05-fail-posture.md)）ห้ามสร้าง record HOLD ที่สมบูรณ์ขึ้นมาจาก input ที่ไม่ถูกต้อง (field ที่จำเป็นของ HOLD ไม่สามารถสร้างขึ้นจาก input ที่ไม่ถูกต้องได้) — หน้าที่แรกของ agent ตัวต่อไปที่เข้ามาแก้ไขคือ **การซ่อมแซมสถานะ** ไม่ใช่การเขียนงาน（[FP-7](05-fail-posture.md)）
- **การประกาศจบงาน / blocker มีความสำคัญมากกว่าความกดดันให้ทำต่อ** หากมี blocker อยู่ใน update เดียวกัน การอ้างว่างานเสร็จสมบูรณ์ใน update นั้นจะถือเป็นโมฆะ

## L1-5 field ที่จำเป็นของ HOLD

HOLD คือสถานะที่ **สามารถกลับมาทำต่อได้และไม่ใช่สถานะสุดท้าย** จะถือว่าถูกต้องก็ต่อเมื่อมีครบทุกอย่างต่อไปนี้:

`owner / reason / review-by / lock disposition（ロックを review-by まで保持 or 解放）/ 残作業 or 後継`

- **HOLD ที่ไม่ได้ระบุการจัดการ lock ถือว่าไม่ถูกต้อง** — เพราะทั้งการตีความว่าเป็น ghost lock หรือ double write ต่างก็เป็นเส้นทางที่นำไปสู่ความขัดแย้งได้
- การเกิน review-by จะก่อให้เกิด **หน้าที่ในการ review ที่มองเห็นได้**（จะถูกหยิบขึ้นมาอีกครั้งโดย weekly ops probe）จะไม่มีการปล่อย lock อัตโนมัติหรือเปลี่ยนเป็น ABANDONED อัตโนมัติ
- `retained until review-by` **ไม่ได้หมายความว่า** "จะถูกปล่อยอัตโนมัติเมื่อถึง review-by" — review-by คือวันที่ที่หน้าที่ในการ review จะเกิดขึ้น ส่วน lock จะยังคงถูกถือไว้จนกว่าจะมีการดำเนินการอย่างชัดเจน（อัปเดต HOLD / RELEASE / ขั้นตอน TAKEOVER หลังจากกลายเป็น stale）

## L1-6 การรีทรายมีจำนวนจำกัด

การรีทรายทำได้จำนวนจำกัด เมื่อใช้ครบแล้วต้องประกาศ **HOLD / ABANDONED พร้อมหลักฐาน** — การใช้ครบไม่ใช่ความสำเร็จ (ถ้าตั้งใจจะทำต่อให้ใช้ HOLD ถ้าจะยุติให้ใช้ ABANDONED ทางออกผ่าน STUCK trigger ยังคงใช้ HOLD ที่ถูกต้องหรือ escalation ไปยังมนุษย์ตามที่ระบุใน L1-4)

> เชิงอรรถ (นอกเนื้อหาสัญญา / เป็นข้อเสนอ policy ที่ปรับได้): trigger เฉพาะเจาะจงที่ว่า "ความล้มเหลวแบบเดียวกัน 2 ครั้งติดต่อกัน (review comment เดียวกัน หรือ CI signature เดียวกัน) ⇒ STUCK" เป็นข้อเสนอจาก reviewer คนเดียว ไม่ได้รวมอยู่ในสัญญานี้ ค่าเริ่มต้นให้ขึ้นอยู่กับดุลยพินิจของ maintainer หรือให้แต่ละ repo เลือกเอง

## L1-7 Merge Gate ด้วยหลักฐานความสำเร็จ

จะ merge PR ได้ก็ต่อเมื่อมี **บันทึกความสำเร็จ** ([เทมเพลต](../templates/issue-template.md)) อยู่ใน PR body ที่เป็นไปตามเงื่อนไขต่อไปนี้เท่านั้น:

1. **ทุกข้อใน Done when ต้องระบุผลเป็น `PASS` / `FAIL` / `N/A` พร้อมเหตุผล** — การที่คำสั่ง "รันแล้ว" ไม่นับเป็น PASS ข้อที่จำเป็นแต่เป็น FAIL หรือ N/A โดยไม่มีเหตุผล จะ block การ merge
2. แต่ละข้อต้องมี **หลักฐานถาวรพร้อมผลลัพธ์สุดท้าย** (คำสั่ง หรือขั้นตอนที่ทำด้วยมือ + ผลที่สังเกตได้ + วันที่) **ต้องมีข้อความคัดลอกฝังไว้โดยตรง (inline excerpt) เป็นหลัก** — ต้องอ่านผลลัพธ์สุดท้ายได้จากตัวบันทึกเอง URL ไปยัง CI หรือ log ภายนอกเป็นเพียงตัวช่วยอ้างอิง หลักฐานที่มีแค่ลิงก์อย่างเดียวถือว่าไม่เข้าเงื่อนไข
3. ต้องระบุ **candidate commit SHA** — และต้องตรงกับ PR head ณ เวลาที่ review (ถ้าเปลี่ยนไปก่อนถึง merge ต้องบันทึกการแทนที่ตาม L1-8)
4. ต้องตรวจสอบให้ตรงกันระหว่างชุดไฟล์ที่ประกาศไว้กับผลของ `git diff --stat origin/main...<candidate SHA>` (ไฟล์ที่อยู่ใน diff แต่ไม่อยู่ในรายการถือเป็น blocking — [L0-6](03-git-protocol.md))
5. ต้องลิงก์ตัวตนของผู้ implement และผู้ review และ **ต้องเป็นคนละ model หรือคนละ agent** (L1-3)

**หลักฐานต้องมีอยู่ก่อนการกล่าวอ้าง** สถานะที่ความสำเร็จอยู่แค่ในเครื่อง local ยังไม่ถือว่าเสร็จสมบูรณ์

## L1-8 การแก้ไขให้ทำด้วย superseding record

การแก้ไขบันทึกความสำเร็จ ให้ **เผยแพร่บันทึกแทนที่ฉบับสมบูรณ์ใหม่ และเปิด review ขึ้นใหม่อีกครั้ง** ห้ามแก้แบบเงียบๆ

## L1-9 การ review ข้าม model ในชั้นต้นน้ำ — ส่วนขยายของกฎห้าม self-approve

- **ขนาด L / H / Epic** (= ฝั่งที่หนักกว่าตามเกณฑ์แยกขนาดของ [L2-1](01-milestone-loop.md) ซึ่งรวมถึงการเปลี่ยนแปลง architecture และการกำหนด requirement ด้วย) ต้องผ่านการ review แบบข้าม model (cross review) **ก่อนเริ่มลงมือ implement** (ที่นั่งตาม L1-10 จำนวนที่นั่งตาม L1-11) ต้นฉบับของนิยามขนาดคือ L2-1 — ไม่คัดลอกมาซ้ำที่นี่ สำหรับ Epic จังหวะเวลาคือ "หลังจากเปิด EPIC Issue ก็ได้ อย่างช้าที่สุดต้องก่อนเริ่ม implement child Issue แรก" โดยทำครั้งเดียว (เป็น timing เดียวกับ [E-6①](06-epic-lane.md) — ไม่ให้มีการตีความคู่ขนานระหว่าง "ก่อนเปิด Issue" กับ "ก่อนเริ่ม implement") เพราะถ้าทิศทางแรกคลาดเคลื่อน จะส่งผลกระทบต่อทุกอย่างที่ตามมา ดังนั้นยิ่งอยู่ต้นน้ำยิ่งต้อง review ให้หนักขึ้น
- ใช้เฉพาะฝั่งที่หนักกว่า**เท่านั้น**: Issue เดี่ยวขนาด S / M (bug fix, ฟีเจอร์เดียว) ไม่ต้องผ่าน upstream review — ยังคงใช้แค่ implementation review ตามเดิม (L1-3 / L1-11) ถ้าขยายขอบเขตตรงนี้จะทำให้การรอ review แบบ per-Issue กลับมาอีก ซึ่งขัดกับเป้าหมายด้านความเร็ว ([docs/06](06-epic-lane.md))
- ถ้า**ไม่สามารถตรวจสอบได้ว่ามีการทำ upstream review จริง ห้ามเริ่ม implement** (fail-closed — ทิศทางเดียวกับการหยุดเขียนข้อมูล บันทึกให้ลิงก์จาก EPIC Issue — ส่วน kickoff ของ[เทมเพลต](../templates/epic-template.md) สำหรับ L / H เดี่ยวให้ลิงก์จาก Issue ที่รับผิดชอบ)

## L1-10 หลักการสูงสุดของความหลากหลาย model ในที่นั่ง review

- ที่นั่ง review ต้องเลือกจาก model ที่**แตกต่างกัน**ทั้งหมด และต้องเป็น model ที่**ต่างจาก writer ที่ implement** ด้วย ("ที่นั่งต่าง model N ที่นั่ง" หมายถึง N ที่นั่งที่ต่างกันทั้งหมดซึ่งกันและกัน agent คนละตัวแต่ model เดียวกันจำนวน N ตัว ไม่นับเป็นที่นั่งต่าง model N ที่นั่ง)
- **ผู้ที่ออกแบบหรือ implement สิ่งที่กำลังถูกตรวจสอบ ไม่นับเป็นที่นั่ง review** (รวมถึง orchestrator ด้วย การให้ตัวเองมา review งานออกแบบของตัวเองขัดกับเจตนารมณ์ของ L1-3 / FP-8) กรณี model เดียวกันแต่คนละ agent ยังคงใช้ได้ตาม L1-3 ในฐานะเงื่อนไขขั้นต่ำสำหรับการ merge แต่ไม่นับรวมในจำนวนที่นั่งตาม L1-11 (ข้อยกเว้นมีเฉพาะขั้นตอนการลดระดับตาม L1-11 เท่านั้น)
- ที่นั่งต้องใช้ **model ระดับสูงสุดที่สามารถเรียกใช้ได้ในบ้านนั้น** วิธีบังคับใช้: แต่ละบ้านต้องดูแล **รายชื่อ model ที่มีสิทธิ์นั่งเก้าอี้ review** ไว้ใน local config (เช่น CLAUDE.md / AGENTS.md) โดย handbook กำหนดให้ ① ต้องมีรายชื่อนี้อยู่จริง ② ห้ามตั้ง model ที่ไม่อยู่ในรายชื่อให้มานั่งเก้าอี้ ③ การอัปเดตรายชื่อต้องมองเห็นได้ ส่วนว่าจะใส่ model ตัวไหน (ชื่อจริง) ลงในรายชื่อนั้น handbook จะไม่ระบุ — เพราะ model มีการเปลี่ยนแปลงอยู่เรื่อยๆ จึงไม่ให้ต้นฉบับต้องตามแก้ผ่าน PR
- บันทึกการ review ต้องระบุ **model ที่ requested / actual** เสมอ (เพื่อให้ตรวจสอบย้อนหลังได้ — หลักฐานต้องมีอยู่ก่อนการกล่าวอ้าง)

## L1-11 สเกลจำนวนที่นั่ง

จำนวนที่นั่งในตารางนี้ใช้กับ **implementation review ที่จะให้ผ่านเพื่อ merge** และ **upstream review (L1-9)** (L1-3 เป็นเงื่อนไขขั้นต่ำด้าน identity ส่วนจำนวนที่นั่งกำหนดโดยตารางนี้ — ทั้งสองไม่ขัดแย้งกัน) gate จาก child ไปยัง epic ภายใน Epic ก็ใช้ตารางนี้โดยอิง**น้ำหนักของ child** เช่นกัน ([E-6②](06-epic-lane.md) — child ที่แตะพื้นที่ความเสี่ยงสูงให้ใช้ 5 ที่นั่งเป็นอันดับแรก)

| เป้าหมาย | จำนวนที่นั่ง |
|---|---|
| S / M (เฉพาะจุด / ฟีเจอร์เดียว) | ต่าง model 2 ที่นั่ง |
| L / H (หลาย module / เปลี่ยนขอบเขต / ฟีเจอร์ใหม่) | ต่าง model 3 ที่นั่ง |
| **พื้นที่ความเสี่ยงสูง** (นิยามอยู่ที่ [docs/06 ตอนต้น](06-epic-lane.md) เป็นนิยามเดียว มีความสำคัญเหนือกว่าการตัดสินขนาด) | ต่าง model 5 ที่นั่ง |
| **upstream review** (L1-9) ของ Epic / architecture / การกำหนด requirement | ก่อนเริ่ม implement ต้องใช้ระบบ L/H (ถ้ารวมพื้นที่ความเสี่ยงสูงให้ใช้ 5 ที่นั่ง) |

- การขาดที่นั่งให้เติมด้วย**ที่นั่ง model อื่นที่ต่างกัน**
- บ้านที่ไม่สามารถจัดที่นั่งต่าง model ได้จริงทางกายภาพ (จำนวนสาย model ที่เรียกใช้ได้น้อยกว่าจำนวนที่นั่งที่กำหนด) สามารถใช้ **ขั้นตอนการลดระดับ** ได้: ใช้ที่นั่ง model เดียวกันแต่คนละ agent + **การอนุมัติอย่างชัดเจนจากเจ้าของ (มนุษย์)** + การระบุการลดระดับไว้ในบันทึก review การลดระดับโดยไม่มีการอนุมัติ ถือว่าเทียบเท่ากับจำนวนที่นั่งไม่ครบ
- ถ้าเติมที่นั่งหรือใช้การลดระดับแล้วยังไม่ครบ ให้หยุดด้วยสถานะ **SEAT-WAIT** (สถานะรอก่อนเริ่ม review เป็นคำที่แยกจากสถานะเลน HOLD ตาม L1-4 และไม่ใช้ 5 field บังคับตาม L1-5 — เพื่อแยกไม่ให้ weekly probe ตรวจจับผิดว่าเป็น HOLD) SEAT-WAIT ต้องแสดงให้เห็นผ่าน comment บน Issue ที่รับผิดชอบ โดยต้องระบุ 3 อย่างคือ **owner / ที่นั่งที่ขาด / กำหนดวันลองใหม่** (SEAT-WAIT ที่ขาด 3 อย่างนี้ถือว่าไม่ถูกต้อง) comment SEAT-WAIT นับเป็นการอัปเดตกิจกรรมตาม [L0-3](03-git-protocol.md) (แม้ว่าเลนที่ขาดที่นั่งจะกลายเป็น stale → TAKEOVER ก็ไม่ได้ทำให้ที่นั่งเพิ่มขึ้น ดังนั้นแทนที่จะเดินนาฬิกาต่อ ให้ทำให้ต้นตอของปัญหามองเห็นได้แทน)
- การปรับตัวเลขจำนวนที่นั่งทำได้เฉพาะผ่าน PR ของ handbook เท่านั้น (ปฏิบัติเหมือนกับ 72 ชม. ใน [L0-3](03-git-protocol.md))

## นิยามของความสำเร็จ

- test และ lint ผ่าน
- PR ที่มีบันทึกความสำเร็จตาม L1-7 ถูก merge แล้ว และ Issue ถูก close แล้ว
- **repo ออนไลน์กลายเป็นต้นฉบับล่าสุด** (ไม่จบลงในสถานะที่ผลงานมีอยู่แค่ใน local เท่านั้น)
- ถ้างานข้าม session หลายครั้ง ต้องมีจุดเริ่มต้นสำหรับขั้นตอนถัดไป (สิ่งที่จะทำต่อ) เหลือไว้ใน comment ของ Issue หรือใน handoff
