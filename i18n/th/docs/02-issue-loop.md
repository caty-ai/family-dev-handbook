# L1 วงจร Issue — ชั้นที่ทำงานหนึ่งชิ้นให้เสร็จสมบูรณ์

แต่ละกฎติด rule ID ที่เสถียร (`L1-1` ถึง `L1-11`) ฝั่งสรุป ([docs/04](04-adoption.md)) จะอ้างอิง ID เหล่านี้ ท่าทีเมื่อไม่สามารถตรวจสอบได้ ดูที่ [docs/05](05-fail-posture.md)

## L1-1 หลักการ Issue-first

การเปลี่ยนแปลงโค้ดในรีพอสิทอรีต้อง **เริ่มต้นจาก GitHub Issue** ห้ามลงมือ implement โดยไม่มี Issue (ข้อยกเว้นคือการแก้ typo แบบบรรทัดเดียว, ไฟล์ md/json/yaml ที่ไม่ใช่โค้ด, และ scratch ที่ไม่ได้อยู่ภายใต้ git)

เหตุผล: เนื้อหาของ Issue + diff ของ PR จะกลายเป็น **SoT สำหรับการส่งต่องานข้ามเซสชันและข้ามเอเจนต์** ไม่ว่าเอเจนต์ตัวไหนจะเข้ามากลางคัน ก็ต้องอ่าน Issue แล้วทำงานต่อได้

## L1-2 องค์ประกอบที่จำเป็น 3 อย่างในเนื้อหา Issue

ใช้ [เทมเพลต](../templates/issue-template.md)

1. **จุดประสงค์ Why** — ทำไมถึงต้องทำ พื้นหลังของงาน และถ้าไม่ทำจะเกิดปัญหาอะไร
2. **เงื่อนไขความสำเร็จ Done when** — รูปแบบ checkbox ในรูปที่ตัดสินได้ด้วยเครื่องหรือตรวจสอบบนอุปกรณ์จริงได้ เช่น "test green" หรือ "ยืนยันบนเครื่องจริงแล้ว"
3. **ไฟล์ / โมดูลที่คาดว่าจะแตะต้อง** — เป็นข้อมูลนำเข้าสำหรับการตัดสิน GO แบบขนานของ L2 เมื่อเริ่มลงมือให้ประกาศเวอร์ชันที่ยืนยันแล้วอีกครั้งผ่านคอมเมนต์ WIP

## กระแสงาน implement → review → merge

```
Issue 起票 → WIP宣言（L0-1）→ worktree で実装 → テスト/lint green
→ クロスレビュー → 指摘対応 → PR（完了記録 = L1-7 を本文に）
→ merge → Issue close → 安定点で git tag
```

## L1-3 หลักการของ cross review

- **ห้าม self-approve** — ห้าม merge ด้วยการอนุมัติจากผู้ implement เพียงคนเดียว
- **การ review ที่จะอนุมัติให้ merge ได้ ต้องมีโมเดลหรือเอเจนต์ต่างจากผู้ implement** (เช่น Claude implement → GPT/GLM review, Codex implement → Claude review) แม้จะเป็นโมเดลเดียวกัน แต่ถ้าเป็น**เอเจนต์คนละตัว** ก็ถือว่า merge ได้ถูกต้อง โมเดลเดียวกันและเอเจนต์เดียวกัน แม้จะเป็นคนละเซสชันก็ยังไม่พอสำหรับ merge — สิ่งที่คนละเซสชันเพียงพอคือ checkpoint อื่นที่ไม่ใช่ merge เท่านั้น
- ค่าเริ่มต้นคือให้ reviewer รอบที่ 1 เป็นผู้ review จนจบ หากจะเปลี่ยนตัวต้องประกาศ และ reviewer คนใหม่ต้อง**review ทั้งหมดของผู้สมัครปัจจุบันใหม่อีกครั้ง** (ห้าม merge ด้วยการต่อ review บางส่วนเข้าด้วยกัน)
- วนลูป implementer → reviewer จนกว่าข้อบ่งชี้ที่ blocking จะเหลือ 0
- มุมมองในการ review: ความถูกต้อง / ขอบเขต (ไม่ได้แตะไฟล์นอกสโคป) / ความเหมาะสมของ test / ความสามารถในการ revert

## L1-4 สถานะของ lane — คำศัพท์ปิด 5 สถานะ

สถานะของ lane ประกาศผ่านคอมเมนต์ที่ติด label บน Issue ที่รับผิดชอบ **ต้นฉบับของสถานะ lane คือ Issue** (PR ที่ค้างอยู่จะชี้กลับไปที่ Issue):

`WIP / HOLD / MERGED / SUPERSEDED / ABANDONED`

- **WIP เป็นสถานะที่ต้องประกาศอย่างชัดเจน ไม่ใช่ค่าเริ่มต้น**
- `STUCK` **ไม่ใช่** สถานะที่ 6 — มันคือเงื่อนไขที่กระตุ้น (trigger) และทางออกที่ถูกต้องเพียงทางเดียวคือ HOLD ที่สมบูรณ์ (หรือส่งต่อให้มนุษย์ตัดสินใจ)
- lane ที่สถานะขาดหาย / ไม่รู้จัก / รูปแบบไม่ถูกต้อง จะถูก**ถือว่าไม่ทำงาน (ท่าทีเทียบเท่า HOLD: ไม่มีการเขียน) และรอการซ่อมแซมสถานะ** การตัดสิน GO จะไม่นับ lane นี้เป็น "ว่าง" — งานที่อาจไปตัดกับสโคปที่ประกาศไว้จะต้องทำแบบ serial จนกว่าจะซ่อมแซมเสร็จ ([FP-1](05-fail-posture.md)) ห้ามสร้างเรคคอร์ด HOLD ที่สมบูรณ์ขึ้นมาจากอินพุตที่ไม่ถูกต้อง (ฟิลด์ที่จำเป็นของ HOLD ไม่สามารถสร้างจากอินพุตที่ไม่ถูกต้องได้) — หน้าที่แรกของเอเจนต์ตัวถัดไปที่เข้ามาแตะคือ**การซ่อมแซมสถานะ** ไม่ใช่การเขียนงาน ([FP-7](05-fail-posture.md))
- **การประกาศสิ้นสุด / blocker มีความสำคัญเหนือแรงกดดันให้ทำงานต่อ** ถ้ามี blocker อยู่ใน update เดียวกัน การอ้างว่างานเสร็จสมบูรณ์ใน update นั้นถือเป็นโมฆะ

## L1-5 ฟิลด์ที่จำเป็นของ HOLD

HOLD **สามารถกลับมาทำต่อได้และไม่ใช่สถานะสุดท้าย** จะสมบูรณ์ก็ต่อเมื่อมีครบทุกอย่างต่อไปนี้:

`owner / reason / review-by / lock disposition（รักษา lock ไว้จนถึง review-by หรือปล่อย）/ งานที่เหลือ หรือผู้สืบทอด`

- **HOLD ที่ไม่ระบุการจัดการ lock ถือเป็นโมฆะ** — เพราะทั้งการอ่านแบบ ghost lock และแบบเขียนซ้อนสองครั้งต่างก็เป็นเส้นทางที่นำไปสู่การชนกัน
- การเกิน review-by จะก่อให้เกิด**ภาระหน้าที่ในการ review ที่มองเห็นได้** (จะถูกหยิบขึ้นมาอีกครั้งโดย weekly ops probe) จะไม่มีการปล่อยอัตโนมัติหรือ ABANDONED อัตโนมัติ
- `retained until review-by` **ไม่ได้** หมายความว่า "ปล่อยอัตโนมัติที่ review-by" — review-by คือวันที่ที่ภาระหน้าที่ในการ review เกิดขึ้น ส่วน lock จะยังคงถูกรักษาไว้จนกว่าจะมีการดำเนินการที่ชัดเจน (อัปเดต HOLD / RELEASE / ขั้นตอน TAKEOVER หลังจากกลายเป็น stale)

## L1-6 การรีทรายมีจำกัด

การรีทรายทำได้จำนวนจำกัด เมื่อใช้ครบแล้วต้องประกาศ**HOLD / ABANDONED พร้อมหลักฐาน** — การใช้ครบไม่ได้แปลว่าสำเร็จ (ถ้าตั้งใจจะทำต่อให้ใช้ HOLD ถ้าจะยุติให้ใช้ ABANDONED ทางออกผ่าน STUCK trigger ก็ยังคงเป็น HOLD ที่ถูกต้องตาม L1-4 หรือส่งต่อให้มนุษย์ตัดสินใจ)

> เชิงอรรถ (นอกเนื้อหาสัญญา — เป็นนโยบายที่ปรับได้): trigger ที่ระบุว่า "ล้มเหลวแบบเดียวกันติดต่อกัน 2 ครั้ง (คำติจาก review เดียวกัน หรือ CI signature เดียวกัน) ⇒ STUCK" เป็นข้อเสนอจาก reviewer เพียงคนเดียว ไม่ได้รวมอยู่ในสัญญานี้ ค่าเริ่มต้นขึ้นอยู่กับดุลยพินิจของ maintainer หรือการเลือกของแต่ละ repo

## L1-7 ประตูตรวจก่อน merge ด้วยหลักฐานความสำเร็จ

จะ merge PR ได้ก็ต่อเมื่อมี**บันทึกความสำเร็จ** ([เทมเพลต](../templates/issue-template.md)) อยู่ใน PR body ที่ครบตามนี้เท่านั้น:

1. **ผูกทุกข้อของ Done when กับ `PASS` / `FAIL` / `N/A` พร้อมเหตุผล** — คำสั่งที่ "รันแล้ว" ไม่ได้แปลว่า PASS ข้อที่จำเป็น (required) ที่เป็น FAIL หรือ N/A ที่ไม่มีเหตุผลจะบล็อกการ merge
2. แต่ละข้อต้องมี**หลักฐานถาวรที่ระบุผลลัพธ์สุดท้าย**ชัดเจน (คำสั่งหรือขั้นตอนแบบ manual + ผลที่สังเกตได้ + วันที่) **ต้องมี excerpt แบบ inline เป็นตัวหลัก** — ตัวบันทึกเองต้องอ่านผลลัพธ์สุดท้ายได้ในทันที URL ไปยัง CI หรือ log ภายนอกเป็นเพียงตัวชี้เพื่อความสะดวก หลักฐานที่มีแต่ลิงก์ไม่ถือว่าครบตามเงื่อนไข
3. ระบุ **candidate commit SHA** ให้ชัดเจน — ต้องตรงกับ PR head ณ เวลา review (ถ้าเปลี่ยนก่อนถึง merge ให้ทำบันทึกแทนที่ตาม L1-8)
4. เทียบชุดไฟล์ที่ประกาศไว้กับผลของ `git diff --stat origin/main...<candidate SHA>` (ถ้ามีไฟล์ใน diff ที่ไม่อยู่ในรายการ จะ blocking — [L0-6](03-git-protocol.md))
5. เชื่อมโยงตัวตนของผู้ implement และ reviewer ให้ชัดเจน โดยต้องเป็น**model หรือ agent คนละตัวกัน** (L1-3)

**หลักฐานต้องมีอยู่ก่อนคำกล่าวอ้าง** สถานะที่สำเร็จแค่ในเครื่อง (local) เท่านั้นไม่ถือว่าเสร็จงาน

## L1-8 การแก้ไขให้ทำผ่าน superseding record

การแก้ไขบันทึกความสำเร็จ ต้อง**เผยแพร่บันทึกแทนที่ฉบับสมบูรณ์ใหม่ และเปิด review ขึ้นใหม่อีกครั้ง** ห้ามแก้แบบเงียบๆ

## L1-9 การ review ข้ามสายพันธุ์ในชั้นต้นน้ำ — ส่วนขยายของกฎห้าม self-approve

- **Epic การเปลี่ยนแปลง architecture และการนิยาม requirement** (ฝั่งที่หนักกว่าใน [L2-1](01-milestone-loop.md)) ต้องผ่าน cross-review แบบข้ามสายพันธุ์ (ที่นั่งตาม L1-10 จำนวนที่นั่งตาม L1-11) **ก่อนเริ่มลงมือ implement** จังหวะเวลาคือ "จะทำหลังจากเปิด EPIC Issue ก็ได้ แต่อย่างช้าที่สุดต้องก่อนเริ่ม implement child Issue แรก" ทำครั้งเดียว (นาฬิกาเดียวกับ [E-6①](06-epic-lane.md) — ไม่ให้มีสองการตีความ "ก่อนเปิด issue" กับ "ก่อนเริ่ม implement" อยู่คู่กัน) เพราะถ้าทิศทางแรกเบี้ยว ทุกอย่างที่ตามมาจะเบี้ยวไปด้วย ดังนั้นยิ่งอยู่ต้นน้ำยิ่งต้อง review หนักขึ้น
- ใช้กับฝั่งที่หนัก**เท่านั้น**: Issue เดี่ยว (bug fix ฟีเจอร์เดียว) ไม่ต้องผ่าน upstream review — ใช้แค่ review ระดับ implementation ตามเดิม (L1-3 / L1-11) ถ้าขยายไปกว่านี้จะทำให้การรอ review แบบ per-Issue กลับมาอีก ซึ่งขัดกับเป้าหมายด้านความเร็ว ([docs/06](06-epic-lane.md))
- ถ้า**ตรวจสอบไม่ได้ว่า upstream review ทำจริง ห้ามเริ่ม implement** (fail-closed — ทิศทางเดียวกับการหยุดเขียน) บันทึกต้องเชื่อมโยงมาจาก EPIC Issue (ส่วน kickoff ใน [เทมเพลต](../templates/epic-template.md))

## L1-10 หลักการสูงสุดของความหลากหลาย (異種) ในที่นั่ง review

- ที่นั่ง review ต้องเลือกจาก**model ที่แตกต่างกัน** และ**แตกต่างจาก model ของ implementation writer** ("N ที่นั่งแบบข้ามสายพันธุ์" หมายถึง N ที่นั่งที่แตกต่างกันทั้งหมด agent คนละตัวแต่ model เดียวกัน N ตัว ไม่นับเป็น N ที่นั่งแบบข้ามสายพันธุ์)
- **ผู้ที่ออกแบบหรือ implement สิ่งที่กำลังถูกตรวจ ห้ามนับเป็นที่นั่ง** (รวมถึง orchestrator ด้วย — การให้ตัวเองมา review งานออกแบบของตัวเองขัดกับเจตนารมณ์ของ L1-3 / FP-8) การใช้ model เดียวกันแต่ agent ต่างกัน ยังคงใช้ได้ตามเงื่อนไขขั้นต่ำของ merge ตาม L1-3 แต่ไม่นับรวมในจำนวนที่นั่งตาม L1-11 (ยกเว้นเฉพาะขั้นตอนการลดระดับ (降格) ตาม L1-11)
- ที่นั่งต้องใช้**model ระดับสูงสุดที่บ้านนั้นสามารถเปิดใช้งานได้** วิธีบังคับใช้: แต่ละบ้านต้องดูแลรักษา**รายชื่อ model ที่มีสิทธิ์เป็นที่นั่ง review** ไว้ใน local config (CLAUDE.md / AGENTS.md เป็นต้น) โดย handbook กำหนดให้ ① ต้องมีรายชื่อนี้อยู่ ② ห้ามใช้ model ที่ไม่อยู่ในรายชื่อเป็นที่นั่ง ③ การอัปเดตรายชื่อต้อง visible ได้ ส่วนว่าจะใส่ model ตัวไหน (ชื่อจริง) ไว้ในรายชื่อนั้น handbook จะไม่เขียนไว้ — เพราะ model เปลี่ยนแปลงตลอดเวลา จึงไม่ให้ต้องไล่ตาม PR ของแหล่งข้อมูลหลัก
- บันทึกของ review ต้องเก็บทั้ง **requested / actual model** ไว้เสมอ (เพื่อให้ตรวจสอบย้อนหลังได้ — หลักฐานต้องมีอยู่ก่อนคำกล่าวอ้าง)

## L1-11 จำนวนที่นั่งตามระดับความหนัก

จำนวนที่นั่งในตารางนี้ใช้กับ**implementation review ที่ใช้ผ่านเพื่อ merge** และ**upstream review (L1-9)** (L1-3 เป็นเงื่อนไขขั้นต่ำด้าน identity ส่วนจำนวนที่นั่งกำหนดโดยตารางนี้ — ทั้งสองไม่ขัดแย้งกัน) gate จาก child ไปยัง epic ภายใน Epic ก็ใช้ตารางนี้โดยอิงจาก**ความหนักของ child** เช่นกัน ([E-6②](06-epic-lane.md) — child ที่แตะ high-risk area จะให้ความสำคัญกับ 5 ที่นั่งก่อน)

| เป้าหมาย | จำนวนที่นั่ง |
|---|---|
| S / M (จุดเดียว ฟีเจอร์เดียว) | 2 ที่นั่งข้ามสายพันธุ์ |
| L / H (หลาย module เปลี่ยนขอบเขต ฟีเจอร์ใหม่) | 3 ที่นั่งข้ามสายพันธุ์ |
| **high-risk area** (นิยามอยู่ใน [docs/06 ตอนต้น](06-epic-lane.md) นิยามเดียว มีความสำคัญเหนือกว่าการตัดสินตามขนาด) | 5 ที่นั่งข้ามสายพันธุ์ |
| **upstream review** ของ Epic / architecture / requirement definition (L1-9) | ใช้ระบบ L/H ก่อนเริ่ม implement (ถ้ารวม high-risk area ให้ใช้ 5 ที่นั่ง) |

- การขาดที่นั่งให้เติมด้วย**ที่นั่งข้ามสายพันธุ์อื่น**
- บ้านที่ไม่สามารถจัดที่นั่งข้ามสายพันธุ์ได้จริง (จำนวนสาย model ที่เปิดใช้งานได้น้อยกว่าจำนวนที่นั่งที่ต้องการ) สามารถใช้**ขั้นตอนลดระดับ (降格)** ได้: ใช้ที่นั่งจาก model เดียวกันแต่ agent ต่างกัน + **การอนุมัติอย่างชัดเจนจาก owner (มนุษย์)** + ระบุการลดระดับไว้ในบันทึกของ review การลดระดับที่ไม่มีการอนุมัติ ถือเท่ากับจำนวนที่นั่งไม่ครบ
- ถ้าเติมที่นั่งหรือลดระดับแล้วยังไม่ครบ ให้หยุดด้วยสถานะ **SEAT-WAIT** (สถานะรอก่อนเริ่ม review เป็นคำที่แยกจาก HOLD ซึ่งเป็น lane state ตาม L1-4 และไม่ใช้ 5 field บังคับตาม L1-5 — เพื่อแยกไม่ให้ weekly probe ตรวจจับผิดว่าเป็น HOLD) ต้องทำให้ SEAT-WAIT มองเห็นได้โดย comment ใน Issue ที่รับผิดชอบ และต้องเขียน 3 อย่างคือ **owner / ที่นั่งที่ขาด / กำหนดวันลองใหม่** (SEAT-WAIT ที่ขาดสามอย่างนี้ถือว่าไม่ถูกต้อง) comment SEAT-WAIT นับเป็นการอัปเดตกิจกรรมตาม [L0-3](03-git-protocol.md) (แม้ lane ที่ขาดที่นั่งจะ stale → TAKEOVER ก็ไม่ทำให้ที่นั่งเพิ่มขึ้น จึงควรเปิดเผยสาเหตุที่แท้จริง แทนที่จะเดินนาฬิกาต่อไป)
- การปรับตัวเลขจำนวนที่นั่งทำได้เฉพาะผ่าน PR ของ handbook เท่านั้น (ปฏิบัติเหมือนกับ 72h ของ [L0-3](03-git-protocol.md))

## นิยามของความสำเร็จ

- test และ lint ผ่านหมด
- PR ที่มีบันทึกความสำเร็จตาม L1-7 ถูก merge แล้ว และ Issue ถูกปิดแล้ว
- **online repo กลายเป็นแหล่งข้อมูลล่าสุดที่ถูกต้อง** (ไม่จบด้วยสถานะที่มีผลงานอยู่แค่ในเครื่อง local)
- ถ้างานข้ามหลาย session ทางเข้าสำหรับงานต่อ (สิ่งที่ต้องทำต่อไป) ต้องถูกทิ้งไว้ใน Issue comment หรือ handoff
