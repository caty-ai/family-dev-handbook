# L1 Issue Loop — เลเยอร์ที่ทำงานหนึ่งชิ้นให้เสร็จสมบูรณ์

แต่ละกฎมี rule ID ที่คงที่ (`L1-1`〜`L1-11`) กำกับไว้ ฝั่งสรุป ([docs/04](04-adoption.md)) จะอ้างอิง ID เหล่านี้ ท่าทีเมื่อไม่สามารถตรวจสอบได้ดูที่ [docs/05](05-fail-posture.md)

## L1-1 หลักการ Issue-first

การเปลี่ยนแปลงโค้ดในรีโพต้อง **เริ่มต้นจาก GitHub Issue** ห้ามทำ implementation ที่ไม่มี Issue รองรับ (ข้อยกเว้นคือการแก้ typo แบบ 1 บรรทัด, ไฟล์ที่ไม่ใช่โค้ดอย่าง md/json/yaml, และ scratch ที่ไม่อยู่ภายใต้การจัดการของ git)

เหตุผล: เนื้อหาของ Issue + diff ของ PR คือ **SoT สำหรับการส่งต่องานข้าม session และข้าม agent** ไม่ว่า agent ตัวไหนจะเข้ามาทำต่อกลางทาง แค่อ่าน Issue ก็ต้องทำงานต่อได้

## L1-2 องค์ประกอบที่จำเป็น 3 อย่างในเนื้อหา Issue

ใช้ [เทมเพลต](../templates/issue-template.md)

1. **จุดประสงค์ Why** — ทำไปทำไม พร้อมภูมิหลังและถ้าไม่ทำจะเกิดปัญหาอะไร
2. **เงื่อนไขความสำเร็จ Done when** — เขียนในรูปแบบ checkbox ให้อยู่ในรูปที่ตรวจสอบได้ด้วยเครื่องหรือของจริง เช่น "test green" หรือ "ยืนยันบนอุปกรณ์จริงแล้ว"
3. **ไฟล์ / โมดูลที่คาดว่าจะแตะ** — เป็น input สำหรับการตัดสิน GO ของการทำงานคู่ขนานใน L2 เมื่อเริ่มลงมือให้ประกาศเวอร์ชันที่ยืนยันแล้วอีกครั้งใน WIP comment

## ขั้นตอน Implementation → Review → Merge

```
เปิด Issue → ประกาศ WIP (L0-1) → implement ใน worktree → test/lint green
→ cross review → แก้ไขตามข้อเสนอแนะ → PR (บันทึกความสำเร็จ = L1-7 ไว้ในเนื้อหา)
→ merge → close Issue → ติด git tag ที่จุดที่เสถียร
```

## L1-3 หลักการ Cross Review

- **ห้าม self-approve** — ห้าม merge ด้วยการอนุมัติจากคนที่ implement เองเพียงคนเดียว
- **การ review ที่จะปล่อยให้ merge ผ่านได้ ต้องเป็น model หรือ agent ที่ต่างจากคน implement** (เช่น Claude implement → GPT/GLM review, Codex implement → Claude review) แม้จะเป็น model เดียวกันแต่ถ้าเป็น **agent คนละตัว** ก็ถือว่า merge ได้ ส่วน model เดียวกันและ agent เดียวกัน ต่อให้เป็นคนละ session ก็ยังไม่พอสำหรับ merge — สิ่งที่คนละ session ทำได้พอคือ checkpoint อื่นที่ไม่ใช่ merge เท่านั้น
- ค่าเริ่มต้นคือให้ reviewer ของ round-1 เป็นคนรีวิวจนจบ หากจะเปลี่ยนตัวต้องประกาศให้ชัดเจน และ reviewer คนใหม่ต้อง **รีวิวผู้สมัครปัจจุบันทั้งหมดใหม่อีกครั้ง** (ห้าม merge ด้วยการต่อ review บางส่วนเข้าด้วยกัน)
- วนลูป implementer → reviewer จนกว่าข้อเสนอแนะระดับ blocking จะเหลือ 0
- มุมมองในการ review: ความถูกต้อง / ขอบเขต (แตะไฟล์นอก scope หรือไม่) / ความเหมาะสมของ test / ความเป็นไปได้ในการ revert

## L1-4 สถานะของ Lane — คำศัพท์ปิด 5 สถานะ

สถานะของ lane ประกาศผ่าน comment ที่ติด label บน Issue ที่รับผิดชอบ **ต้นฉบับของสถานะ lane คือ Issue** (PR ที่ค้างอยู่จะชี้กลับไปที่ Issue):

`WIP / HOLD / MERGED / SUPERSEDED / ABANDONED`

- **WIP คือสถานะที่ต้องประกาศอย่างชัดเจน ไม่ใช่ค่าเริ่มต้น**
- `STUCK` **ไม่ใช่** สถานะที่ 6 — มันคือเงื่อนไข trigger และทางออกที่ถูกต้องมีทางเดียวคือ HOLD ที่สมบูรณ์ (หรือ escalate ไปให้มนุษย์)
- lane ที่สถานะขาดหาย / ไม่ทราบ / มีรูปแบบไม่ถูกต้อง ให้ถือว่า **ไม่ active (ท่าทีเทียบเท่า HOLD คือไม่มีการเขียน) และรอการซ่อมแซมสถานะ** ในการตัดสิน GO ห้ามนับ lane นี้ว่า "ว่าง" — งานใดก็ตามที่อาจ intersect กับ scope ที่ประกาศไว้ ให้ทำแบบเรียงลำดับ (serial) จนกว่าจะซ่อมแซมเสร็จ ([FP-1](05-fail-posture.md)) ห้ามสร้าง record HOLD ที่สมบูรณ์ขึ้นมาจาก input ที่ไม่ถูกต้อง (field ที่จำเป็นของ HOLD สร้างจาก input ที่ไม่ถูกต้องไม่ได้) — หน้าที่แรกของ agent คนต่อไปที่มาแตะคือ **ซ่อมแซมสถานะ** ไม่ใช่การเขียนงาน ([FP-7](05-fail-posture.md))
- **การประกาศจบงาน / blocker มีความสำคัญเหนือแรงกดดันให้ทำงานต่อ** ถ้าใน update เดียวกันมี blocker อยู่ การอ้างว่างานเสร็จใน update นั้นถือเป็นโมฆะ

## L1-5 Field ที่จำเป็นของ HOLD

HOLD คือสถานะที่ **กลับมาทำต่อได้ ไม่ใช่สถานะปลายทาง** จะถือว่าสมบูรณ์ก็ต่อเมื่อมีครบทุกอย่างต่อไปนี้:

`owner / reason / review-by / lock disposition (จะเก็บ lock ไว้จนถึง review-by หรือปล่อย) / งานที่เหลือ หรือผู้สืบทอด`

- **HOLD ที่ไม่ระบุการจัดการ lock ถือเป็นโมฆะ** — เพราะทั้งการตีความแบบ ghost lock และแบบเขียนซ้ำซ้อนต่างก็เป็นเส้นทางที่นำไปสู่ conflict ได้ทั้งคู่
- การเลย review-by ไปแล้วจะก่อให้เกิด **ภาระหน้าที่ในการ review ที่มองเห็นได้** (จะถูกหยิบขึ้นมาอีกครั้งใน weekly ops probe) ห้ามปล่อย lock อัตโนมัติหรือเปลี่ยนเป็น ABANDONED อัตโนมัติ
- `retained until review-by` **ไม่ได้แปลว่า** "ปล่อย lock อัตโนมัติเมื่อถึง review-by" — review-by คือวันที่ที่ภาระหน้าที่ในการ review เกิดขึ้น ส่วน lock จะยังถูกเก็บไว้จนกว่าจะมีการจัดการอย่างชัดเจน (อัปเดต HOLD / RELEASE / ขั้นตอน TAKEOVER หลังจากกลายเป็น stale)

## L1-6 การรีทรายมีจำกัด

การรีทรายทำได้จำนวนจำกัด เมื่อใช้ครบแล้วต้อง**ประกาศ HOLD / ABANDONED พร้อมหลักฐาน** — การใช้ครบไม่ได้แปลว่าสำเร็จ (หากตั้งใจจะทำต่อให้ใช้ HOLD หากจะยุติให้ใช้ ABANDONED ทางออกผ่าน STUCK trigger ยังคงใช้ HOLD ที่ถูกต้องหรือ escalate ไปยังมนุษย์ตาม L1-4)

> เชิงอรรถ (นอกเนื้อหาสัญญา · เป็นตัวเลือกนโยบายที่ปรับได้): trigger เฉพาะเจาะจงที่ว่า "ความล้มเหลวแบบเดียวกัน 2 ครั้งติดต่อกัน (ข้อคิดเห็นรีวิวเดียวกัน หรือ CI signature เดียวกัน) ⇒ STUCK" เป็นข้อเสนอจาก reviewer คนเดียว ไม่ได้รวมอยู่ในสัญญานี้ ค่าเริ่มต้นให้เป็นดุลยพินิจของ maintainer หรือเลือกตาม repo แต่ละแห่ง

## L1-7 Merge gate ที่ต้องมีหลักฐานความสำเร็จ

จะ merge PR ได้ก็ต่อเมื่อมี**บันทึกความสำเร็จ** ([template](../templates/issue-template.md)) อยู่ใน PR body ที่ตรงตามเงื่อนไขต่อไปนี้:

1. **จับคู่ทุกรายการใน Done when กับ `PASS` / `FAIL` / `N/A` พร้อมเหตุผล** — การที่คำสั่ง "รันแล้ว" ไม่นับเป็น PASS รายการบังคับที่เป็น FAIL หรือ N/A ที่ไม่มีเหตุผลจะ block การ merge
2. แต่ละรายการต้องมี**หลักฐานถาวรพร้อมผลลัพธ์สุดท้าย** (คำสั่ง หรือขั้นตอนแบบ manual + ผลที่สังเกตได้ + วันที่) **ข้อความคัดลอกแบบ inline คือตัวหลัก** — ต้องอ่านผลลัพธ์สุดท้ายได้จากตัวบันทึกเอง URL ไปยัง CI หรือ log ภายนอกเป็นเพียงตัวชี้ทางเพื่อความสะดวก หลักฐานที่เป็นแค่ลิงก์ไม่ผ่านเกณฑ์
3. ต้องระบุ **candidate commit SHA** ให้ชัดเจน — ต้องตรงกับ PR head ณ เวลารีวิว (หากเปลี่ยนก่อน merge ต้องมีบันทึกแทนที่ตาม L1-8)
4. ตรวจสอบชุดไฟล์ที่ประกาศไว้เทียบกับ `git diff --stat origin/main...<candidate SHA>` (ไฟล์ที่อยู่ใน diff แต่ไม่อยู่ในรายการ = blocking — [L0-6](03-git-protocol.md))
5. เชื่อมโยงตัวตนของผู้ implement และ reviewer เข้าด้วยกัน โดยต้อง**เป็นคนละ model หรือ agent** (L1-3)

**หลักฐานต้องมีอยู่ก่อนการอ้างสิทธิ์เสมอ** สถานะที่มีแค่ความสำเร็จบน local ไม่นับว่าเสร็จสมบูรณ์

## L1-8 การแก้ไขต้องทำผ่าน superseding record

การแก้ไขบันทึกความสำเร็จ ให้**เผยแพร่บันทึกแทนที่ฉบับสมบูรณ์ใหม่ และเปิดรีวิวขึ้นใหม่** ห้ามแก้แบบเงียบๆ

## L1-9 การรีวิวข้าม model ระดับต้นน้ำ — ส่วนขยายของกฎห้าม self-approve

- **Epic · การเปลี่ยนแปลง architecture · การกำหนด requirement** (ฝั่งที่หนักกว่าใน [L2-1](01-milestone-loop.md)) ต้องผ่านการรีวิวข้าม model ต่างสายพันธุ์ (ที่นั่งตาม L1-10 · จำนวนที่นั่งตาม L1-11) **ก่อนเริ่ม implement** จังหวะเวลาคือ "จะหลังจากเปิด EPIC Issue แล้วก็ได้ · อย่างช้าที่สุดคือก่อนเริ่ม implement child Issue แรก" ทำเพียงครั้งเดียว (นาฬิกาเรือนเดียวกับ [E-6①](06-epic-lane.md) — ไม่ให้มีสองการตีความ "ก่อนเปิด Issue" กับ "ก่อนเริ่ม implement" อยู่คู่กัน) เพราะถ้าทิศทางแรกเบี้ยว ทุกอย่างที่ตามมาจะเบี้ยวไปด้วย จึงต้องรีวิวให้หนักที่สุดที่ต้นน้ำ
- ใช้กับฝั่งที่หนัก**เท่านั้น**: Issue เดี่ยว (bug fix · single feature) ไม่ต้องผ่านการรีวิวต้นน้ำ — ยังคงใช้แค่การรีวิว implementation ตามปกติ (L1-3 / L1-11) หากขยายขอบเขตตรงนี้ การรอรีวิวแบบ per-Issue จะกลับมา ซึ่งขัดกับเป้าหมายด้านความเร็ว ([docs/06](06-epic-lane.md))
- **หากตรวจสอบไม่ได้ว่าได้ทำการรีวิวต้นน้ำแล้ว ห้ามเริ่ม implement** (fail-closed — ทิศทางเดียวกับการหยุดเขียน บันทึกให้ลิงก์จาก EPIC Issue — ส่วน kickoff ของ [template](../templates/epic-template.md))

## L1-10 หลักการสูงสุดของความหลากหลายที่นั่งรีวิว

- ที่นั่งรีวิวต้องมาจาก**model ที่แตกต่างกัน** และ**แตกต่างจาก model ที่เป็น writer ที่ implement** ("N ที่นั่งต่างสายพันธุ์" หมายถึง N ที่นั่งที่แตกต่างกันทั้งหมด agent หลายตัวจาก model เดียวกันไม่นับเป็น N ที่นั่งต่างสายพันธุ์)
- **ผู้ที่ออกแบบหรือ implement สิ่งที่ถูกตรวจสอบ ไม่นับเป็นที่นั่งรีวิว** (รวมถึง orchestrator ด้วย ที่นั่งที่รีวิวการออกแบบของตัวเองขัดกับเจตนารมณ์ของ L1-3 / FP-8) กรณี model เดียวกันแต่คนละ agent ยังคงมีผลตาม L1-3 ในฐานะเงื่อนไขขั้นต่ำสำหรับการ merge แต่ไม่นับเข้าจำนวนที่นั่งตาม L1-11 (ยกเว้นเฉพาะขั้นตอนการลดระดับตาม L1-11)
- ที่นั่งต้องใช้**model ระดับสูงสุดที่เปิดใช้งานได้ในบ้านนั้น** วิธีบังคับใช้: แต่ละบ้านต้องดูแล**รายชื่อ model ที่มีสิทธิ์เป็นที่นั่งรีวิว**ไว้ในการตั้งค่าท้องถิ่น (CLAUDE.md / AGENTS.md เป็นต้น) handbook กำหนดว่าต้อง ① มีรายชื่อนี้อยู่ ② ห้ามใช้ model นอกรายชื่อเป็นที่นั่ง ③ การอัปเดตรายชื่อต้องมองเห็นได้ ส่วนว่าจะใส่ model ตัวใด (ชื่อจริง) ลงในรายชื่อนั้น handbook จะไม่เขียนไว้ — เพราะ model เปลี่ยนแปลงตลอดเวลา จึงไม่ควรให้ต้องตาม PR ของต้นฉบับ
- บันทึกการรีวิวต้องเก็บ **model ที่ร้องขอ / model ที่ใช้จริง** ไว้เสมอ (เพื่อให้ตรวจสอบย้อนหลังได้ — หลักฐานต้องมีอยู่ก่อนการอ้างสิทธิ์เสมอ)

## L1-11 การปรับขนาดจำนวนที่นั่ง

จำนวนที่นั่งในตารางนี้ใช้กับ**การรีวิว implementation ที่ใช้ผ่าน merge** และ**การรีวิวต้นน้ำ (L1-9)** (L1-3 เป็นเงื่อนไขขั้นต่ำด้าน identity ส่วนจำนวนที่นั่งกำหนดโดยตารางนี้ — ทั้งสองไม่ขัดแย้งกัน) ประตู child→epic ภายใน Epic ก็ใช้ตารางนี้โดยอิงจาก**น้ำหนักของ child**เช่นกัน ([E-6②](06-epic-lane.md) · child ที่แตะพื้นที่ high-risk ให้ใช้ 5 ที่นั่งเป็นอันดับแรก)

| เป้าหมาย | จำนวนที่นั่ง |
|---|---|
| S / M (เฉพาะจุด · single feature) | 2 ที่นั่งต่างสายพันธุ์ |
| L / H (หลาย module · เปลี่ยนขอบเขต · feature ใหม่) | 3 ที่นั่งต่างสายพันธุ์ |
| **พื้นที่ high-risk** (นิยามอยู่ที่ [docs/06 ส่วนต้น](06-epic-lane.md) · นิยามเดียว มีความสำคัญเหนือการตัดสินตามขนาด) | 5 ที่นั่งต่างสายพันธุ์ |
| **การรีวิวต้นน้ำ** ของ Epic · Architecture · Requirement definition (L1-9) | ใช้ระบบ L/H ก่อนเริ่ม implement (หากรวมพื้นที่ high-risk ใช้ 5 ที่นั่ง) |

- การขาดที่นั่งให้เติมด้วย**ที่นั่งต่างสายพันธุ์อื่น**
- บ้านที่ไม่สามารถจัดที่นั่งต่างสายพันธุ์ได้จริง (จำนวนสาย model ที่เปิดใช้งานได้น้อยกว่าจำนวนที่นั่งที่ต้องการ) สามารถใช้**ขั้นตอนการลดระดับ**ได้: ที่นั่งจาก model เดียวกันแต่คนละ agent + **การอนุมัติชัดเจนจาก owner (มนุษย์)** + ระบุการลดระดับไว้ในบันทึกการรีวิว การลดระดับที่ไม่มีการอนุมัติถือเหมือนจำนวนที่นั่งไม่ครบ
- หากเติมที่นั่งหรือลดระดับแล้วยังไม่ครบ ให้หยุดที่สถานะ **SEAT-WAIT** (สถานะรอก่อนเริ่มรีวิว เป็นคำที่แยกจากสถานะเลน HOLD ตาม L1-4 และไม่ใช้ 5 ฟิลด์บังคับตาม L1-5 — เพื่อแยกไม่ให้ weekly probe ตรวจจับผิดว่าเป็น HOLD) ให้แสดง SEAT-WAIT ผ่าน comment บน Issue ที่รับผิดชอบ และเขียนให้ครบ 3 จุด คือ **owner / ที่นั่งที่ขาด / กำหนดลองใหม่** (SEAT-WAIT ที่ขาด 3 จุดนี้ถือว่าไม่สมบูรณ์) comment ของ SEAT-WAIT นับเป็นการอัปเดตกิจกรรมตาม [L0-3](03-git-protocol.md) — เพราะแม้เลนที่ขาดที่นั่งจะ stale แล้วถูก TAKEOVER ก็ไม่ได้ทำให้มีที่นั่งเพิ่มขึ้น จึงต้องแสดงต้นตอของปัญหาให้เห็น แทนที่จะปล่อยให้นาฬิกาเดินต่อไป
- การปรับตัวเลขจำนวนที่นั่งทำได้เฉพาะผ่าน PR ของ handbook เท่านั้น (ปฏิบัติเหมือนกับ 72h ใน [L0-3](03-git-protocol.md))

## นิยามของความเสร็จสมบูรณ์

- ทดสอบและ lint ผ่านแล้ว
- PR ที่มีบันทึกความสำเร็จตาม L1-7 ถูก merge แล้ว และ Issue ถูก close แล้ว
- **repo ออนไลน์กลายเป็นต้นฉบับล่าสุด** (ไม่จบด้วยสถานะที่ผลงานมีอยู่แค่บน local)
- หากงานข้ามหลายเซสชัน ต้องมีทางเข้าสำหรับงานต่อ (สิ่งที่ต้องทำถัดไป) ระบุไว้ใน comment ของ Issue หรือใน handoff
