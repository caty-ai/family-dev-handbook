# L1 Issue Loop — เลเยอร์ที่ทำงานหนึ่งชิ้นให้เสร็จสมบูรณ์

แต่ละกฎมี rule ID ที่คงที่ (`L1-1` ถึง `L1-11`) กำกับไว้ ฝั่งสรุป ([docs/04](04-adoption.md)) จะอ้างอิง ID เหล่านี้ ท่าทีเมื่อไม่สามารถตรวจสอบได้ดูที่ [docs/05](05-fail-posture.md)

## L1-1 หลักการ Issue-first

การเปลี่ยนแปลงโค้ดภายใน repository **ต้องเริ่มจาก GitHub Issue** จะไม่ดำเนินการ implement โดยไม่มี Issue (ข้อยกเว้นคือการแก้ไข 1 บรรทัดเช่น typo, md/json/yaml ที่ไม่ใช่โค้ด, scratch ที่อยู่นอกการควบคุมของ git)

เหตุผล: เนื้อหา Issue + PR diff จะกลายเป็น **SoT สำหรับการส่งต่องานระหว่าง session และระหว่าง agent** ไม่ว่า agent ตัวไหนจะเข้ามากลางคัน หากอ่าน Issue แล้วก็ต้องทำงานต่อได้

## L1-2 สามส่วนที่จำเป็นในเนื้อหา Issue

ใช้ [เทมเพลต](../templates/issue-template.md)

1. **จุดประสงค์ Why** — ทำไมถึงต้องทำ พื้นหลังและปัญหาที่จะเกิดขึ้นถ้าไม่ทำ
2. **เงื่อนไขความสำเร็จ Done when** — รูปแบบ checkbox ในรูปแบบที่ตัดสินได้ด้วยเครื่องหรือตรวจสอบบนอุปกรณ์จริงได้ เช่น "test green" "ตรวจสอบบนอุปกรณ์จริง"
3. **ไฟล์ / โมดูลที่คาดว่าจะแตะต้อง** — เป็น input สำหรับการตัดสินใจ GO แบบขนานของ L2 เมื่อเริ่มลงมือทำ ให้ประกาศเวอร์ชันที่ยืนยันแล้วอีกครั้งผ่านคอมเมนต์ WIP

## ขั้นตอน implement → review → merge

```
Issue 起票 → WIP宣言（L0-1）→ worktree で実装 → テスト/lint green
→ クロスレビュー → 指摘対応 → PR（完了記録 = L1-7 を本文に）
→ merge → Issue close → 安定点で git tag
```

## L1-3 หลักการของ cross review

- **ห้าม self-approve** — ห้าม merge ด้วยการอนุมัติจากผู้ implement เพียงคนเดียว
- **การ review ที่ใช้ผ่าน merge ได้ ต้องเป็นโมเดลหรือ agent ที่ต่างจากผู้ implement** (เช่น: implement ด้วย Claude → review ด้วย GPT/GLM, implement ด้วย Codex → review ด้วย Claude) แม้จะเป็นโมเดลเดียวกันแต่ถ้าเป็น **agent คนละตัว** ก็ใช้ merge ได้ โมเดลเดียวกัน・agent เดียวกัน แม้จะเป็นคนละ session ก็ยังไม่เพียงพอสำหรับ merge — session ที่ต่างกันเพียงพอสำหรับ checkpoint อื่นที่ไม่ใช่ merge เท่านั้น
- โดยปกติแล้ว reviewer รอบที่ 1 จะเป็น reviewer ที่ทำจนจบ หากต้องการเปลี่ยนตัว ให้ประกาศไว้ และ reviewer คนใหม่ต้อง **review candidate ปัจจุบันทั้งหมดใหม่อีกครั้ง** (ห้าม merge ด้วยการต่อ review บางส่วนเข้าด้วยกัน)
- หมุนวนลูป implementer → reviewer จนกว่าข้อบ่งชี้ระดับ blocking จะเป็น 0
- มุมมองของการ review: ความถูกต้อง / ขอบเขต (ไม่ได้แตะไฟล์นอก scope) / ความเหมาะสมของ test / ความเป็นไปได้ในการ revert

## L1-4 สถานะของ lane — คำศัพท์ 5 สถานะแบบปิด

สถานะของ lane จะประกาศผ่านคอมเมนต์ที่มี label บน Issue ที่รับผิดชอบ **ต้นฉบับของสถานะ lane คือ Issue** (PR ที่ pending จะชี้ไปที่ Issue):

`WIP / HOLD / MERGED / SUPERSEDED / ABANDONED`

- **WIP คือสถานะที่ต้องประกาศอย่างชัดเจน ไม่ใช่ค่าเริ่มต้น**
- `STUCK` **ไม่ใช่** สถานะที่ 6 — มันคือเงื่อนไข trigger และทางออกที่ถูกต้องเพียงทางเดียวคือ HOLD ที่สมบูรณ์ (หรือการ escalate ไปยังมนุษย์)
- lane ที่มีสถานะขาดหาย ไม่ทราบ หรือรูปแบบไม่ถูกต้อง จะถูก **ถือว่าไม่ active (ท่าทีเทียบเท่า HOLD: ไม่มีการเขียน) และรอการซ่อมแซมสถานะ** ในการตัดสินใจ GO จะไม่นับ lane นี้เป็น "ว่าง" — งานที่อาจซ้อนทับกับ scope ที่ประกาศไว้จะต้องทำแบบเรียงลำดับ (serial) จนกว่าจะซ่อมแซมเสร็จ ([FP-1](05-fail-posture.md)) ห้ามสร้าง HOLD record ที่สมบูรณ์ขึ้นมาปลอมจาก input ที่ไม่ถูกต้อง (ฟิลด์ที่จำเป็นของ HOLD ไม่สามารถสร้างจาก input ที่ไม่ถูกต้องได้) — หน้าที่แรกของ agent ตัวถัดไปที่เข้ามาแตะคือ **การซ่อมแซมสถานะ** ไม่ใช่การเขียน ([FP-7](05-fail-posture.md))
- **การประกาศสิ้นสุด / blocker มีความสำคัญเหนือแรงกดดันให้ทำต่อ** หากมี blocker อยู่ใน update เดียวกัน การอ้างว่า update นั้นเสร็จสมบูรณ์จะถือเป็นโมฆะ

## L1-5 ฟิลด์ที่จำเป็นของ HOLD

HOLD คือสถานะที่ **กลับมาทำต่อได้ / ไม่ใช่จุดสิ้นสุด** จะถือว่าสมบูรณ์ก็ต่อเมื่อมีครบทุกอย่างต่อไปนี้:

`owner / reason / review-by / lock disposition（ロックを review-by まで保持 or 解放）/ 残作業 or 後継`

- **HOLD ที่ไม่ระบุการจัดการล็อกถือว่าไม่สมบูรณ์** — เพราะการตีความทั้งแบบ ghost lock และแบบเขียนซ้อนทับ (double write) ล้วนเป็นเส้นทางที่นำไปสู่การชนกัน
- การเลย review-by จะก่อให้เกิด **ภาระหน้าที่การ review ที่มองเห็นได้** (จะถูกหยิบขึ้นมาอีกครั้งผ่าน weekly ops probe) จะไม่มีการปล่อยล็อกอัตโนมัติหรือเปลี่ยนเป็น ABANDONED อัตโนมัติ
- `retained until review-by` **ไม่ได้** หมายความว่า "จะปล่อยล็อกอัตโนมัติเมื่อถึง review-by" — review-by คือวันที่ภาระหน้าที่การ review เกิดขึ้น ส่วนล็อกจะยังคงถูกถือไว้จนกว่าจะมีการดำเนินการอย่างชัดเจน (อัปเดต HOLD / RELEASE / ขั้นตอน TAKEOVER หลังจากกลายเป็น stale)

## L1-6 รีทรายมีจำนวนจำกัด

รีทรายมีจำนวนจำกัด เมื่อใช้ครบแล้วต้องประกาศ **HOLD / ABANDONED พร้อมหลักฐาน** — การใช้ครบไม่ได้แปลว่าสำเร็จ (หากตั้งใจจะดำเนินต่อให้ใช้ HOLD หากจะยุติให้ใช้ ABANDONED ทางออกผ่านทริกเกอร์ STUCK ก็ยังคงเป็น HOLD ที่ถูกต้องตาม L1-4 หรือการส่งต่อให้มนุษย์ตัดสินใจ)

> เชิงอรรถ (นอกเนื้อหาสัญญา・ตัวเลือกนโยบายที่ปรับได้): ทริกเกอร์ที่เจาะจงว่า "ความล้มเหลวเดียวกัน 2 ครั้งติดต่อกัน (ข้อบ่งชี้รีวิวเดียวกัน หรือลายเซ็น CI เดียวกัน) ⇒ STUCK" เป็นข้อเสนอของรีวิวเออร์คนเดียว จึงไม่รวมอยู่ในสัญญานี้ ค่าเริ่มต้นขึ้นอยู่กับดุลยพินิจของ maintainer หรือการเลือกของแต่ละ repo

## L1-7 Merge gate ด้วยหลักฐานความเสร็จสมบูรณ์

การ merge PR ทำได้ก็ต่อเมื่อ PR body มี **บันทึกความเสร็จสมบูรณ์** ([เทมเพลต](../templates/issue-template.md)) ที่เป็นไปตามเงื่อนไขต่อไปนี้เท่านั้น:

1. **จับคู่ทุกรายการใน Done when กับ `PASS` / `FAIL` / `N/A` พร้อมเหตุผล** — การที่คำสั่ง "รันแล้ว" ไม่ได้แปลว่า PASS รายการบังคับที่เป็น FAIL หรือ N/A ที่ไม่มีเหตุผลจะบล็อกการ merge
2. แต่ละรายการต้องมี **หลักฐานถาวรพร้อมผลลัพธ์สุดท้าย** (คำสั่ง หรือขั้นตอนแบบ manual + ผลที่สังเกตได้ + วันที่) **การคัดลอกแบบ inline คือสิ่งที่ถูกต้อง** — ต้องอ่านผลลัพธ์สุดท้ายได้จากตัวบันทึกเพียงอย่างเดียว URL ไปยัง CI หรือ log ภายนอกเป็นเพียงตัวชี้เพื่อความสะดวก หลักฐานที่มีแค่ลิงก์ถือว่าไม่เข้าเกณฑ์
3. ระบุ **candidate commit SHA** ให้ชัดเจน — ต้องตรงกับ PR head ณ เวลาที่รีวิว (หากเปลี่ยนไปก่อนถึง merge ให้ใช้บันทึกแทนที่ตาม L1-8)
4. ตรวจสอบชุดไฟล์ที่ประกาศไว้กับผลลัพธ์ของ `git diff --stat origin/main...<候補SHA>` (ไฟล์ที่อยู่ใน diff แต่ไม่อยู่ในรายการถือเป็น blocking — [L0-6](03-git-protocol.md))
5. เชื่อมโยงตัวตนของผู้ implement และ reviewer โดย **ต้องเป็นโมเดลหรือ agent ที่แตกต่างกัน** (L1-3)
6. **ระบุสถานะ CI** — ห้าม merge ขณะ CI ยังแดง เงื่อนไขข้อยกเว้นของสีแดงที่รู้อยู่แล้วและไม่เกี่ยวข้อง (ข้อยกเว้นข้อเดียว) ดูที่ [T-4](10-test-ci-baseline.md)

**หลักฐานต้องมีอยู่ก่อนคำกล่าวอ้าง** สถานะที่มีแค่ความสำเร็จในเครื่อง local ไม่ถือว่าเสร็จสมบูรณ์

## L1-8 การแก้ไขทำผ่าน superseding record

การแก้ไขบันทึกความเสร็จสมบูรณ์ต้อง **เผยแพร่บันทึกแทนที่ฉบับสมบูรณ์ใหม่ และเปิดการรีวิวใหม่อีกครั้ง** ห้ามแก้ไขแบบเงียบๆ

## L1-9 การรีวิวต่างสายพันธุ์ต้นน้ำ — การขยายกฎห้าม self-approve ไปยังต้นน้ำ

- **ขนาด L / H / Epic** (= ฝั่งที่หนักกว่าตามเกณฑ์แยกขนาดของ [L2-1](01-milestone-loop.md) การเปลี่ยนแปลง architecture และการกำหนด requirement ก็รวมอยู่ในนี้ด้วย) ต้องผ่านการรีวิวข้ามสายพันธุ์ (ที่นั่งตาม L1-10・จำนวนที่นั่งตาม L1-11) **ก่อนเริ่ม implementation** ต้นฉบับของนิยามขนาดคือ L2-1 — จะไม่คัดลอกมาซ้ำที่นี่ สำหรับจังหวะเวลาใน Epic คือ "จะทำหลังจากเปิด EPIC Issue ก็ได้ อย่างช้าที่สุดคือก่อนเริ่ม implementation ของ child Issue แรก" เพียงครั้งเดียว (นาฬิกาเรือนเดียวกับ [E-6①](06-epic-lane.md) — ไม่ให้มีการตีความสองแบบคือ "ก่อนเปิด Issue" กับ "ก่อนเริ่ม implementation" อยู่ร่วมกัน) เพราะถ้าทิศทางแรกเบี้ยว ทุกอย่างที่อยู่ปลายน้ำจะเบี้ยวตามไปด้วย การรีวิวจึงต้องหนาแน่นขึ้นเมื่อยิ่งอยู่ต้นน้ำ
- ใช้กับฝั่งที่หนัก**เท่านั้น**: Issue เดี่ยวขนาด S / M (bug fix・ฟีเจอร์เดียว) ไม่ต้องผ่านการรีวิวต้นน้ำ — ใช้แค่การรีวิว implementation ตามเดิม (L1-3 / L1-11) หากขยายขอบเขตนี้ออกไป การรอรีวิวแบบ per-Issue จะกลับมาอีกครั้ง และขัดกับเป้าหมายด้านความเร็ว ([docs/06](06-epic-lane.md))
- หากไม่สามารถตรวจสอบยืนยันได้ว่า**ได้ทำการรีวิวต้นน้ำแล้ว ห้ามเริ่ม implementation** (fail-closed — ทิศทางเดียวกับการหยุดเขียน บันทึกให้ลิงก์จาก EPIC Issue — ที่ส่วน kickoff ของ[เทมเพลต](../templates/epic-template.md) สำหรับ L / H แบบเดี่ยว ให้ลิงก์จาก Issue ที่รับผิดชอบ)

## L1-10 หลักการสูงสุด: ความหลากหลายของที่นั่งรีวิว

- เลือกที่นั่งรีวิวจาก**โมเดลที่แตกต่างกัน**และ**แตกต่างจากโมเดลของ implementation writer** ("N ที่นั่งต่างสายพันธุ์" = N ที่นั่งที่แตกต่างกันทั้งหมด agent ต่างตัวกัน N ตัวแต่เป็นโมเดลเดียวกัน ไม่นับเป็น N ที่นั่งต่างสายพันธุ์)
- **ผู้ที่ออกแบบหรือ implement สิ่งที่กำลังถูกตรวจสอบจะไม่ถูกนับเป็นที่นั่ง** (รวมถึง orchestrator ด้วย ที่นั่งที่รีวิวการออกแบบของตัวเองขัดกับเจตนารมณ์ของ L1-3 / FP-8) การปฏิบัติต่อกรณีโมเดลเดียวกันแต่ agent ต่างตัว ยังคงใช้ได้ในฐานะเงื่อนไขขั้นต่ำของการ merge ตาม L1-3 แต่ไม่นับรวมในจำนวนที่นั่งของ L1-11 (ข้อยกเว้นมีเฉพาะขั้นตอนการลดระดับของ L1-11 เท่านั้น)
- ที่นั่งต้องใช้**โมเดลระดับสูงสุดที่สามารถเรียกใช้ได้ในบ้านนั้นๆ** วิธีบังคับใช้: แต่ละบ้านต้องดูแล**รายชื่อโมเดลที่มีคุณสมบัติสำหรับที่นั่งรีวิว**ไว้ใน local config (เช่น CLAUDE.md / AGENTS.md) โดย handbook กำหนดให้ ① ต้องมีรายชื่อนี้อยู่ ② ห้ามใช้โมเดลนอกรายชื่อเป็นที่นั่ง ③ การอัปเดตรายชื่อต้องมองเห็นได้ ส่วนว่าจะใส่โมเดลใด (ชื่อจริง) ลงในรายชื่อนั้น handbook จะไม่เขียนไว้ — เพราะโมเดลมีการเปลี่ยนแปลงอยู่เสมอ จึงไม่ให้ต้นฉบับต้องถูกไล่ตามผ่าน PR
- บันทึกการรีวิวต้องระบุ **requested / actual model** เสมอ (เพื่อให้ตรวจสอบย้อนหลังได้ — หลักฐานต้องมีอยู่ก่อนคำกล่าวอ้าง)

## L1-11 มาตราส่วนจำนวนที่นั่ง

จำนวนที่นั่งในตารางนี้ใช้กับทั้ง**การรีวิว implementation ที่ทำให้ merge ผ่านได้**และ**การรีวิวต้นน้ำ (L1-9)** (L1-3 เป็นเงื่อนไขขั้นต่ำด้าน identity ส่วนจำนวนที่นั่งถูกกำหนดโดยตารางนี้ — ทั้งสองอย่างไม่ขัดแย้งกัน) gate จาก child ไปยัง epic ภายใน Epic ก็อ้างอิงตารางนี้ตาม**ความหนักของ child** เช่นกัน ([E-6②](06-epic-lane.md)・child ที่แตะพื้นที่ high-risk จะให้ความสำคัญกับ 5 ที่นั่งก่อน)

| เป้าหมาย | จำนวนที่นั่ง |
|---|---|
| S / M (เฉพาะจุด・ฟีเจอร์เดียว) | 2 ที่นั่งต่างสายพันธุ์ |
| L / H (หลาย module・เปลี่ยน boundary・ฟีเจอร์ใหม่) | 3 ที่นั่งต่างสายพันธุ์ |
| **พื้นที่ high-risk** (นิยามอยู่ที่ [docs/06 ส่วนต้น](06-epic-lane.md)・นิยามเดียว มีความสำคัญเหนือกว่าการตัดสินขนาด) | 5 ที่นั่งต่างสายพันธุ์ |
| **การรีวิวต้นน้ำ** (L1-9) ของขนาด L / H / Epic | ระบบ L/H ก่อนเริ่ม implementation (5 ที่นั่งหากรวมพื้นที่ high-risk) |

- ที่นั่งที่ขาดให้เติมด้วย**ที่นั่งต่างสายพันธุ์อื่น**
- บ้านที่ไม่สามารถจัดหาที่นั่งต่างสายพันธุ์ได้จริง (สายพันธุ์โมเดลที่เรียกใช้ได้มีน้อยกว่าจำนวนที่นั่งที่ต้องการ) สามารถใช้**ขั้นตอนการลดระดับ**ได้ คือ ที่นั่งแบบโมเดลเดียวกัน・agent ต่างตัว + **การอนุมัติอย่างชัดเจนจาก owner (มนุษย์)** + การระบุการลดระดับไว้ในบันทึกการรีวิว การลดระดับที่ไม่มีการอนุมัติถือเท่ากับจำนวนที่นั่งไม่ครบ
- หากยังไม่ครบแม้จะเติมหรือลดระดับแล้ว ให้หยุดด้วยสถานะ **SEAT-WAIT** (สถานะรอก่อนเริ่มการรีวิว เป็นคำที่แยกจากสถานะเลน HOLD ใน L1-4 และไม่ใช้ 5 ฟิลด์บังคับของ L1-5 — เพื่อแยกไม่ให้ weekly probe ตรวจจับผิดว่าเป็น HOLD) ให้แสดง SEAT-WAIT ผ่านคอมเมนต์ใน Issue ที่รับผิดชอบ โดยเขียน 3 อย่างคือ **owner / ที่นั่งที่ขาด / กำหนดวันลองใหม่** (SEAT-WAIT ที่ขาด 3 อย่างนี้ถือว่าไม่ถูกต้อง) คอมเมนต์ SEAT-WAIT นับเป็นการอัปเดตกิจกรรมตาม [L0-3](03-git-protocol.md) — เพราะแม้จะทำ stale → TAKEOVER กับเลนที่ขาดที่นั่ง ที่นั่งก็ไม่ได้เพิ่มขึ้น จึงควรทำให้เห็นสาเหตุที่แท้จริงแทนที่จะเดินนาฬิกาต่อไป
- การปรับตัวเลขจำนวนที่นั่งทำได้เฉพาะผ่าน PR ของ handbook เท่านั้น (ปฏิบัติเหมือนกับ 72h ของ [L0-3](03-git-protocol.md))

## นิยามของความเสร็จสมบูรณ์

- ผ่านทั้ง test และ lint (ข้อยกเว้นที่บัญญัติไว้ข้อเดียวคือ [T-4](10-test-ci-baseline.md))
- PR ที่มีบันทึกความเสร็จสมบูรณ์ตาม L1-7 ถูก merge แล้ว และ Issue ถูกปิดแล้ว
- **online repo กลายเป็นต้นฉบับล่าสุด** (ไม่จบลงด้วยสถานะที่มีผลงานอยู่แค่ใน local)
- หากงานข้ามหลาย session จุดเริ่มต้นสำหรับทำต่อ (สิ่งที่ต้องทำถัดไป) ถูกบันทึกไว้ใน Issue comment หรือ handoff
