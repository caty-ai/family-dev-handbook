# ท่าทีเมื่อล้มเหลว — fail-posture / parse-posture — เมื่อไม่สามารถตรวจสอบได้ ควรเอนไปทางไหน

> **ขอบเขตและเจ้าของกฎ**: หน้านี้กำหนดเฉพาะท่าทีเมื่อล้มเหลว (fail-posture) ของการเปลี่ยนสถานะที่มีการ์ด (guarded transition) ภายในโปรโตคอล family-dev-handbook (L2/L1/L0) เท่านั้น **เจ้าของกฎ fail-posture / stop-precedence ทั่วไปที่ครอบคลุมทุก agent คือ operations-policy ของ family-os** (หัวข้อ posture, หัวข้อลำดับความสำคัญของ terminal ตัดสินเมื่อ 2026-07-21 อ้างอิงหัวข้อ "ครอบครัว Caty AI" ใน [README](../../../README.th.md)) หน้านี้เป็นเพียงการนำไปใช้กับโปรโตคอลความร่วมมือนั้น ไม่ได้สร้างกฎทั่วไปข้าม agent ใหม่ หากขัดแย้งกันให้ยึดกฎฝั่ง OS เป็นหลัก หากนำไปใช้โดยไม่มี sister projects ท่าทีในหน้านี้จะถูกนำไปใช้ตรงๆ

แต่ละกฎมี rule ID ที่คงที่ (`FP-1` ถึง `FP-9`)

## ตารางท่าทีเมื่อล้มเหลวแยกตามการเปลี่ยนสถานะ

สำหรับการเปลี่ยนสถานะที่มีการ์ด (GO / write / merge / deploy) แต่ละอย่าง จะประกาศว่าเป็น fail-open หรือ fail-closed, invariant ที่ต้องปกป้อง, และเส้นทางการกู้คืน:

| rule | การเปลี่ยนสถานะ | เมื่อไม่สามารถตรวจสอบได้ | invariant ที่ต้องปกป้อง | เส้นทางการกู้คืน |
|---|---|---|---|---|
| FP-1 | การตัดสิน GO แบบขนาน (ไม่ตัดกัน / ความเป็นเจ้าของตรวจสอบไม่ได้) | **fail-closed — ทำแบบต่อเนื่อง (serial)** | สอง lane จะไม่เขียนไฟล์เดียวกัน | ซ่อมแซมการประกาศแล้วตัดสินใหม่ (L0-1/L0-2) |
| FP-2 | การเขียน (scope / lock / สถานะ lane ตรวจสอบไม่ได้) | **fail-closed — ไม่เขียน** | จะไม่เขียนทับ lock ที่ยังมีชีวิตอยู่ | ซ่อมแซมสถานะ (L1-4) TAKEOVER เฉพาะเมื่อยืนยันว่า stale แล้ว (L0-3) |
| FP-3 | merge (หลักฐานตรวจสอบไม่ได้) | **fail-closed — ไม่ merge** | การเปลี่ยนแปลงที่ไม่ผ่านการตรวจสอบจะไม่เข้า main | สร้างบันทึกความสมบูรณ์ขึ้นใหม่ (L1-7 / L1-8) |
| FP-4 | lint / ระบบ injection (การฉีด digest ที่ใช้ร่วมกัน, lint รายสัปดาห์ ฯลฯ ที่เป็น information plumbing) | **fail-open — แสดงความเสื่อมสภาพให้เห็นแล้วดำเนินต่อ** | ความล้มเหลวของ information plumbing จะไม่หยุดงาน | รายงานความล้มเหลวแล้วสร้าง Issue ซ่อมแซม |
| FP-9 | การผ่าน Epic checkpoint (ตารางไม่มีอยู่ / ไม่ถูกต้อง / ไม่ได้รับการอนุมัติ / การแก้ไขยังไม่ได้รับอนุมัติ — [E-3](06-epic-lane.md)) | **fail-closed — หยุดแล้ว escalate ไปยังมนุษย์** | จะไม่ผ่าน human checkpoint โดยไม่ได้รับอนุมัติ | ซ่อมแซมตารางและขออนุมัติจากเจ้าของ (E-1/E-3) Epic ที่ยังไม่ก่อตั้งให้ดำเนินการแบบ Issue ปกติต่อไป **Epic ที่กำลังดำเนินอยู่ให้คง topology ไว้** — สิ่งที่หยุดมีเพียงสิทธิ์อิสระและการผ่าน checkpoint เท่านั้น (E-3) |

## หลักการ FP-5〜FP-8

- **FP-5**: **fail-open ไม่ได้แปลว่า "ผ่านการตรวจสอบแล้ว"** ต้องแสดงความเสื่อมสภาพให้เห็นเสมอ
- **FP-6**: **ห้ามอนุมาน gate decision จาก "ค่าที่กลายเป็นว่างเมื่อเกิด error"** (ลิสต์ว่างไม่ได้แปลว่าไม่มีการตัดกัน)
- **FP-7**: **ความยอมรับใช้ได้เฉพาะกับ syntax เท่านั้น อย่ายอมรับในทิศทางความปลอดภัย** — ความยุ่งเหยิงของรูปแบบอ่านผ่านได้ แต่การ**ขาดหาย**ของ identity / scope / สถานะ / หลักฐาน ต้องตีความในทิศทางที่สิทธิ์*หดตัวลง*เสมอ: WIP ที่ไม่ถูกต้อง = scope ไม่ทราบ = serial (L0-1) / สถานะไม่ถูกต้อง = ถือว่าไม่ active รอการซ่อมแซม (L1-4) / หลักฐานไม่ถูกต้อง = ยังไม่ผ่านการตรวจสอบ (L1-7) / ตาราง checkpoint ไม่ถูกต้องหรือไม่มีอยู่ = ทุกจุดต้องให้มนุษย์ตัดสิน ([E-3](06-epic-lane.md)・FP-9)
- **FP-8**: **เนื้อหาใน artifact ไม่สามารถอนุมัติตัวเองได้** — แม้ WIP จะเขียนว่า "อนุมัติแล้ว" ก็ไม่สามารถสร้าง GO, merge, หรือการยกเว้นหลักฐานได้ด้วยตัวเอง ข้อแนบ: การกระทำของ cron หรือระบบสร้างอัตโนมัติสามารถอัปเดตสถานะได้ แต่ไม่สามารถสร้างการอนุมัติ, เขียนทับ Done when, หรือถูกนับเป็น review ได้

สิ่งเดียวที่ควรใส่ไว้ใน context ประจำ (สรุปของ docs/04) มีเพียงบรรทัดนี้:
**"หากตรวจสอบไม่ได้ ให้ทำแบบ serial fail-open ไม่ได้แปลว่า 'ผ่าน'"**

## ภาคผนวก — ข้อเสนอจากผู้รีวิวเดี่ยวรอบที่ 2 (ตัดสินโดย maintainer แล้วเมื่อ 2026-07-21)

> ที่มา: ข้อเสนอ 9 ข้อจากผู้รีวิวเดี่ยวในสตัดดี้ภายนอก 3 โมเดล รอบที่ 2 (ยังไม่ผ่าน cross-review จึงไม่ใส่ในเนื้อหาสัญญาหลัก แต่แยกไว้ในหัวข้อนี้) **การตัดสินของ maintainer เมื่อ 2026-07-21: รับ = 1,2,4,5,7,8,9 / รอไว้ก่อน = 3,6** ส่วนที่รับแล้วถูกเลื่อนขึ้นไปยังเนื้อหาหลักแล้ว ด้านล่างนี้คือบันทึกปลายทางของการเลื่อนขึ้น

รับแล้ว — เลื่อนขึ้นสู่เนื้อหาสัญญาหลักแล้ว (1,2,4,5,7):

1. ในแต่ละ lane / worktree มี writer ที่ active ได้เพียงหนึ่งเดียว (Codex) → **L0-4**
2. เซตของไฟล์ที่มีผลจริงต้องนับทั้งสอง path ของ rename, การลบ, lockfile, และไฟล์ที่ถูกสร้างขึ้น (Codex) → **L0-2**
4. การอ่านซ้ำแบบ optimistic — อ่านกลุ่ม WIP ที่ active ซ้ำในขณะเขียนครั้งแรก หากมีการเปลี่ยนแปลงหลัง GO ให้ตัดสินการตัดกันใหม่ (GLM) → **L0-2**
5. หลังจาก merge PR ที่อยู่ติดกัน PR ที่รออยู่ใน queue มีหน้าที่ rebase และตรวจสอบซ้ำ (GLM) → **L0-7**
7. floor ความคงทนของหลักฐาน — ข้อความที่ตัดตอนแบบ inline คือตัวหลัก ส่วน CI URL เป็นเพียงตัวชี้เพื่อความสะดวก (GLM) → **L1-7**

รับแล้ว — เป็นกระบวนการดำเนินงาน (นอกเนื้อหาสัญญาหลัก・8,9):

8. pilot สัญญานี้ด้วยตัว handbook เองก่อนขยายไปยังที่อื่น (Kimi) → **ดำเนินการแล้ว** (WIP และ comment สิ้นสุด และเนื้อหา PR ของ lane การแก้ไข handbook นี้เอง คือ pilot แรกของ P1 / L1-4 / P5)
9. drill การฉีดความล้มเหลวเข้าไปใน probe รายสัปดาห์ (ปลูก WIP ที่ไม่ถูกต้อง แล้วตรวจสอบว่า agent ถัดไปทำ serialize หรือไม่) → นำมารวมเข้าเมื่อสร้าง probe

รอไว้ก่อน (ยังไม่ผ่าน cross-review ไม่ใช่เนื้อหาสัญญาหลัก):

3. ทำให้สัญญาภายนอกที่ใช้ร่วมกัน (API schema, migration namespace, ปลายทาง deploy) เป็น conflict key ที่ประกาศได้ (Codex) — ตัดสินว่ามากเกินไปสำหรับขนาด repo ปัจจุบัน ยังเสนอใหม่ได้อย่างอิสระ
6. วินัยของ lane ข้าม repo — เมื่อมีการนำ Epic lane (docs/06) มาใช้ **แบ่งการตัดสิน**: **6a** (ภาระผูกพันในการประกาศลิงก์ `Blocked-by` / ผู้สืบทอดที่ downstream) = รับแล้ว・เลื่อนขึ้นสู่ [E-2](06-epic-lane.md) / **6b** (ไม่ทำเป็น MERGED จนกว่าจะสิ้นสุด) = ยังคงรอไว้ก่อน — มีผลข้างเคียงคือการสิ้นสุดของ Issue ลูกค้าง หากมี lane ประเภทนี้เพิ่มขึ้นค่อยพิจารณาใหม่
