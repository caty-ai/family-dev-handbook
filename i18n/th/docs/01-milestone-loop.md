# L2 milestone loop — เลเยอร์ที่ตัดสินว่าจะทำงานคู่ขนานได้หรือไม่

เลเยอร์นี้อยู่**เหนือ** Issue loop (L1) แปลง "จะสร้างอะไร" ให้กลายเป็น "ใครจะแตะส่วนไหน" และตัดสินใจในเลเยอร์นี้ว่าจะทำงานคู่ขนานได้หรือไม่ ก่อนที่จะส่งต่อลงไปยัง L1
แต่ละกฎจะมี rule ID ที่คงที่ (`L2-1`〜`L2-6`) กำกับไว้ ฝั่งสรุป ([docs/04](04-adoption.md)) จะอ้างอิง ID เหล่านี้

## ทำไมถึงต้องมีเลเยอร์นี้

เงื่อนไขเดียวที่ทำให้การแบ่งงานปลอดภัยคือ — **รู้ล่วงหน้าก่อนเริ่มงานว่าชุดไฟล์ที่จะแตะไม่ทับซ้อนกัน**
worktree และ Issue lock (L0) เป็นกลไกที่ลดความเสียหายเมื่อเกิดการชนกัน แต่สิ่งที่ป้องกันการชนกันโดยตรงคือ "การตกลงขอบเขตล่วงหน้า" หากข้ามเลเยอร์นี้แล้วทำงานคู่ขนาน งานสองสายที่แตะ hotspot เดียวกัน (ไฟล์ขนาดใหญ่) จะชนกันอย่างแน่นอน

## ขั้นตอนของ loop

### L2-1 ตกลงเป้าหมาย

- ตกลงข้อกำหนดผ่านการสนทนาให้ชัดเจนก่อนเริ่มงาน (ด้วยวิธีที่แต่ละ agent มีอยู่แล้ว เช่น deep-interview / session วางแผน เป็นต้น)
- ตั้งคำถามกับข้อกำหนดที่ทำให้การออกแบบซับซ้อนขึ้นอีกครั้ง (วิธีตั้งคำถามดูที่ [ทำไมถึงสร้างแบบเรียบง่าย](why-simple-systems.md)) การตัดสินใจลบหรือจำกัดขอบเขตต้องได้รับความเห็นชอบจากผู้ร้องขอ และห้ามลด Done when ลงโดยไม่มีความเห็นชอบ ความซับซ้อนที่ยอมรับหลังจากตั้งคำถามแล้ว ให้บันทึกเหตุผลไว้ใน Why ของ Issue
- **การประเมินความหนัก (จำแนกขนาด)**: ตัดสินขนาดของงานให้เป็นหนึ่งใน **S / M / L / H / Epic** ก่อนเริ่มงาน (เกณฑ์ดูด้านล่าง) ขนาดนี้เป็น input ให้กับจำนวนที่นั่ง review ([L1-11](02-issue-loop.md))・ความจำเป็นของ upstream review ต่างสายก่อนเริ่ม implement ([L1-9](02-issue-loop.md))・ทางเข้า Epic ([E-1](06-epic-lane.md))
- งานที่ตัดสินว่าเป็น **Epic** จะใช้ **EPIC Issue + แตกเป็น child Issue + ผูกกับ GitHub Milestone** การดำเนินงาน (integration branch・human checkpoint・การ review แบบ砂時計) ดูที่ [docs/06 Epic lane](06-epic-lane.md) (E-1〜E-10)

#### เกณฑ์จำแนกขนาด

| ขนาด | คำนิยาม |
|---|---|
| **S** | เฉพาะจุด・risk ต่ำ — ระดับ 1 ไฟล์・แก้ไขพฤติกรรมเดิมเล็กน้อย |
| **M** | bug fix・feature เดียวแบบครั้งเดียว — จบภายใน 1 module ไม่ขยับขอบเขต |
| **L** | แตะหลาย module・รวมถึงการเปลี่ยนขอบเขตของ module |
| **H** | feature ใหม่・เปลี่ยน architecture・security・migration・การเปลี่ยนแปลงที่เชื่อมโยงตรงกับลูกค้า / ภายนอก |
| **Epic** | ก้อนงานที่แตกออกเป็นหลาย Issue (การก่อตั้งต้องได้รับ kickoff approval จาก owner = [E-1](06-epic-lane.md)) |

การตัดสินใจให้ดูจาก 3 แกนนี้ **กรณีผสมที่แตะหลายแกน ให้แกนที่หนักกว่าชนะ** (เช่น "feature เดียวแต่เชื่อมโยงตรงกับภายนอก" = H, "เฉพาะจุดแต่เป็น migration" = H):

1. **ขอบเขตผลกระทบ** — จำนวนไฟล์ / module ที่แตะ หากข้าม・ขยับขอบเขต module ให้เป็น L ขึ้นไป
2. **ความย้อนกลับไม่ได้** — หากรวม migration・เปิดเผยสู่ภายนอก・การลบ ซึ่งย้อนกลับยาก ให้เป็น H
3. **ระยะเวลา・จำนวนคน** — หากมีความเป็นไปได้ที่จะข้ามหลาย session / หลาย agent ให้เป็นตัวเลือก Epic

มีแกนเสริมอีกหนึ่งแกนคือ **พื้นที่ high-risk** (นิยามที่เป็นทางการอยู่ที่ [docs/06](06-epic-lane.md) เพียงที่เดียว ไม่คัดลอกมาที่นี่) นี่คือ**แกนที่เพิ่มจำนวนที่นั่ง review โดยอิสระจากขนาด** หากเข้าเงื่อนไข จำนวนที่นั่งจะเพิ่มขึ้นโดยมีสิทธิ์เหนือกว่าขนาด ([L1-11](02-issue-loop.md)) H ในตารางขนาดกับพื้นที่ high-risk ให้ถือเป็นคนละเรื่องกัน

- **กฎยุติ: เมื่อลังเลให้เลือกฝั่งที่หนักกว่า** เมื่อตัดสินใจไม่ได้ด้วยแกนเหล่านี้・ข้อมูลไม่เพียงพอ ให้ถือว่าเป็นขนาดที่หนักขึ้นอีกหนึ่งระดับ

### L2-2 การตัดสินผลกระทบต่อ architecture

ก่อนเริ่มงานต้องถามเสมอ: "**งานนี้จะขยับขอบเขตของ module หรือไม่?**"

- **ไม่ขยับ** → ไปยังขั้นตอนแตก Issue ได้เลย
- **ขยับ**（การแบ่ง module, การจัดโครงสร้าง directory ใหม่, การเปลี่ยน shared interface ฯลฯ）→ ให้ **boundary PR นำหน้าเพียง 1 ฉบับ**
  - จนกว่า boundary PR จะถูก merge ห้าม**เริ่มงานคู่ขนานใหม่**ใน repo นั้น（ช่วงที่ต้องทำแบบ serial）
  - ตัว boundary PR เองต้องคงให้เล็กที่สุด — ห้ามปนการเปลี่ยนขอบเขตกับการเปลี่ยน feature เข้าด้วยกัน
  - ภายใน Epic **child Issue หมายเลข 0 ของการแช่แข็ง contract** เทียบเท่ากับ boundary PR ([E-2](06-epic-lane.md))

### L2-3 การแตก Issue — บังคับให้คาดการณ์ไฟล์ที่จะแตะ

เมื่อตัด child Issue ต้องเขียนสิ่งต่อไปนี้ไว้ใน body ของแต่ละ Issue เสมอ（[template](../templates/issue-template.md)）:

- **วัตถุประสงค์ Why**
- **เงื่อนไขความสำเร็จ Done when**
- **การคาดการณ์ไฟล์ / module ที่จะแตะ** ← เป็น input สำหรับการตัดสินใจ GO ทำงานคู่ขนาน หากคาดการณ์ไม่ได้ให้ระบุชัดเจนว่า "คาดการณ์ไม่ได้"（= Issue นั้นทำงานคู่ขนานไม่ได้）

### L2-4 การตัดสินใจ GO ทำงานคู่ขนาน

การที่จะให้ 2 Issue รันพร้อมกันได้ ต้องเป็น**กรณีที่ชุดไฟล์ที่ประกาศไว้ไม่ทับซ้อนกันเท่านั้น**

- ทับซ้อนกัน → ทำแบบ serial ตามลำดับ
- คาดการณ์ไม่ได้ → ทำแบบ serial ตามลำดับ หรือทำ spike สำรวจก่อนเพื่อให้คาดการณ์ได้
- **ตรวจสอบการทับซ้อนไม่ได้**（ไม่มีการประกาศ・รูปแบบไม่ถูกต้อง・`UNKNOWN`）→ serial（fail-closed — [FP-1](05-fail-posture.md)）
- หากอยากทำคู่ขนานให้ได้จริงๆ → ให้ทำ **boundary separation Issue**（refactor เพื่อแยกส่วนที่ชนกันออกมา）ให้ผ่านก่อน 1 ฉบับ

### L2-5 การแยก Issue ขอบเขตกว้าง

Issue ที่แตะพื้นที่กว้างของ repo เช่น refactor ทั้งหมด / ปรับ design ใหม่ทั้งหมด / format แบบรวด / อัปเดต dependency ทั้งชุด ฯลฯ **ให้รันเดี่ยว** ระหว่างที่กำลังรันอยู่ให้หยุดการทำงานคู่ขนานใน repo เดียวกันทั้งหมด

ลำดับที่แนะนำ: **เคลียร์ Issue feature ปกติก่อน → Issue ขอบเขตกว้างให้รวมทำเดี่ยวเป็นลำดับสุดท้าย**

### L2-6 การลงทุนกับ hotspot

ไฟล์ขนาดใหญ่ที่รวมความรับผิดชอบหลายอย่างไว้ด้วยกัน（เช่น View 2,500 บรรทัด + gesture + การเรียก engine）คือศัตรูตัวฉกาจที่สุดของการพัฒนาแบบคู่ขนาน

- วางไฟล์ "**แผนที่ความปลอดภัยสำหรับการทำงานคู่ขนาน**" ไว้ที่ `ARCHITECTURE.md` ของแต่ละ repo เพื่อบันทึกขอบเขต module และ hotspot（[template](../templates/architecture-parallel-map.md)）
- ตั้ง Issue อิสระโดยให้ความสำคัญสูงกับการ refactor แยก hotspot ในฐานะ "**การลงทุนเพื่อความเป็นไปได้ในการทำงานคู่ขนาน**" — หลังจากแยกแล้ว การทำงานคู่ขนานในพื้นที่นั้นจะปลอดภัยในเชิงโครงสร้าง
