# L2 ระบบวนรอบไมล์สโตน — ชั้นที่ตัดสินว่าจะทำงานคู่ขนานได้หรือไม่

ชั้นนี้อยู่**เหนือ**ระบบวนรอบ Issue (L1) โดยแปลง "จะสร้างอะไร" ให้เป็น "ใครแตะส่วนไหน" แล้วตัดสินที่ชั้นนี้ก่อนว่าจะทำงานคู่ขนานได้หรือไม่ ก่อนจะส่งต่อลงไปยัง L1
แต่ละกฎมี rule ID ที่คงที่ (`L2-1` ถึง `L2-6`) กำกับไว้ ฝั่งสรุป ([docs/04](04-adoption.md)) จะอ้างอิง ID เหล่านี้

## ทำไมชั้นนี้จึงจำเป็น

เงื่อนไขเดียวที่ทำให้การแบ่งงานปลอดภัยคือ — **รู้ก่อนเริ่มลงมือว่าเซตของไฟล์ที่จะแตะไม่ทับซ้อนกัน**
worktree หรือการล็อก Issue (L0) เป็นกลไกที่ลดความเสียหายเมื่อเกิดการชนกันขึ้นแล้ว แต่สิ่งที่ป้องกันการชนกันตั้งแต่ต้นคือ "การตกลงขอบเขตล่วงหน้า" หากข้ามชั้นนี้แล้วทำงานคู่ขนาน งานสองสายที่แตะจุดร้อนแรง (hotspot) เดียวกัน (ไฟล์ขนาดใหญ่) จะชนกันอย่างแน่นอน

## ขั้นตอนของระบบวนรอบ

### L2-1 ตกลงเป้าหมาย

- ตกผลึกความต้องการผ่านการสนทนาก่อนเริ่มลงมือ (ด้วยวิธีที่แต่ละ agent มีอยู่แล้ว เช่น deep-interview / เซสชันวางแผน เป็นต้น)
- ตั้งคำถามกับข้อกำหนดที่ทำให้การออกแบบยากขึ้นสักครั้งหนึ่ง (แนวทางการตั้งคำถามดูที่ [ทำไมต้องออกแบบให้เรียบง่าย](why-simple-systems.md)) การตัดสินใจตัดทิ้งหรือจำกัดขอบเขตต้องทำบนความยินยอมของผู้ร้องขอ และห้ามลด Done when ลงโดยไม่มีความยินยอม ความซับซ้อนที่ยอมรับหลังจากตั้งคำถามแล้วให้บันทึกเหตุผลไว้ใน Why ของ Issue
- **ประเมินความหนัก (จำแนกขนาด)**: กำหนดขนาดของงานเป็น **S / M / L / H / Epic** อย่างใดอย่างหนึ่งก่อนเริ่มลงมือ (เกณฑ์ดูด้านล่าง) ขนาดนี้จะเป็นอินพุตสำหรับจำนวนที่นั่งรีวิว ([L1-11](02-issue-loop.md)) ความจำเป็นของ upstream review ต่างสายก่อนเริ่มลงมือทำ implementation ([L1-9](02-issue-loop.md)) และทางเข้าสู่ Epic ([E-1](06-epic-lane.md))
- งานที่ตัดสินว่าเป็น **Epic** ให้ใช้ **EPIC Issue + แตกเป็น child Issue + ผูกกับ GitHub Milestone** การดำเนินงาน (integration branch, human checkpoint, การรีวิวแบบนาฬิกาทราย) ดูที่ [docs/06 Epic Lane](06-epic-lane.md) (E-1 ถึง E-10)

#### เกณฑ์จำแนกขนาด

| ขนาด | นิยาม |
|---|---|
| **S** | เฉพาะจุด — ประมาณ 1 ไฟล์ · การแก้ไขเล็กน้อยต่อพฤติกรรมเดิม |
| **M** | bug fix เดี่ยว · การเปลี่ยนแปลงเดี่ยวภายในฟีเจอร์เดิม — จบภายใน 1 module ไม่ขยับขอบเขต |
| **L** | แตะหลาย module · รวมถึงการเปลี่ยนแปลงขอบเขตของ module |
| **H** | ฟีเจอร์ใหม่ (สิ่งที่ตั้งขึ้นใหม่ในฐานะคุณค่าของผู้ใช้) · การเปลี่ยนแปลงสถาปัตยกรรม · ความปลอดภัย · migration · การเปลี่ยนแปลงที่เชื่อมโยงตรงกับลูกค้า / ภายนอก |
| **Epic** | ก้อนงานที่แตกออกเป็นหลาย Issue (การก่อตั้งต้องผ่านการอนุมัติ kickoff จากเจ้าของ = [E-1](06-epic-lane.md)) |

การตัดสินให้พิจารณาจาก 3 แกนต่อไปนี้ **กรณีผสมที่แตะหลายแกน ให้แกนที่หนักกว่าเป็นตัวชี้ขาด** (เช่น "ฟีเจอร์เดี่ยวแต่เชื่อมโยงตรงกับภายนอก" = H, "เฉพาะจุดแต่เป็น migration" = H):

1. **ขอบเขตผลกระทบ** — จำนวนไฟล์ / module ที่แตะ หากข้ามหรือขยับขอบเขต module ถือเป็น L ขึ้นไป
2. **ความไม่สามารถย้อนกลับได้** — หากรวม migration · การเปิดเผยสู่ภายนอก · การลบ หรือการกระทำที่ย้อนกลับยาก ถือเป็น H
3. **ระยะเวลา / จำนวนคน** — หากมีความเป็นไปได้ที่จะข้ามหลายเซสชัน / หลาย agent ถือเป็นตัวเลือก Epic

มีอีก 1 แกนเสริมคือ **พื้นที่เสี่ยงสูง** (ต้นฉบับหลักคือคำนิยามเดียวใน [docs/06](06-epic-lane.md) ไม่คัดลอกมาซ้ำที่นี่) นี่คือ**แกนที่เพิ่มจำนวนที่นั่งรีวิวโดยอิสระจากขนาด** หากเข้าข่าย จำนวนที่นั่งจะถูกเพิ่มโดยมีความสำคัญเหนือกว่าขนาด ([L1-11](02-issue-loop.md)) H ในตารางขนาดกับพื้นที่เสี่ยงสูงถือเป็นคนละเรื่องกัน (การเปลี่ยนแปลงที่เนื้อหาซ้อนทับกันอาจเข้าข่ายทั้งสองแกน — ขนาดกำหนดจำนวนที่นั่งพื้นฐาน ส่วนการเข้าข่ายพื้นที่เสี่ยงสูงกำหนดส่วนที่เพิ่มเติม)

- **กฎยุติ: หากลังเลให้เลือกฝั่งที่หนักกว่า** เมื่อตัดสินด้วยแกนไม่ได้ หรือข้อมูลไม่เพียงพอ ให้จัดเป็นขนาดที่หนักขึ้นอีกหนึ่งระดับ**ภายในช่วง S ถึง H** การเลื่อนขั้นไปเป็น Epic ไม่ทำผ่านบันไดนี้ แต่ตัดสินจากความจำเป็นในการแตกเป็นหลาย Issue เท่านั้น (แกนที่ 3 · [E-1](06-epic-lane.md))

### L2-2 การตัดสินผลกระทบต่อสถาปัตยกรรม

ก่อนเริ่มลงมือ ต้องตั้งคำถามเสมอว่า: "**งานนี้จะขยับขอบเขตของ module หรือไม่?**"

- **ไม่ขยับ** → ไปสู่การแตก Issue ได้เลย
- **ขยับ** (การแบ่ง module, การจัดระเบียบไดเรกทอรีใหม่, การเปลี่ยน shared interface เป็นต้น) → ให้ **PR ขอบเขตเดินหน้าไปก่อนเพียง 1 ฉบับ**
  - จนกว่า PR ขอบเขตจะถูก merge ห้าม**เริ่มงานคู่ขนานใหม่ในรีโปนั้น** (ช่วงเรียงลำดับ)
  - PR ขอบเขตเองต้องคงให้เล็กที่สุด — ห้ามผสมการเปลี่ยนแปลงขอบเขตกับการเปลี่ยนแปลงฟีเจอร์เข้าด้วยกัน
  - ภายใน Epic **child Issue หมายเลข 0 ของการล็อกสัญญา (contract freeze)** เทียบเท่ากับ PR ขอบเขตนี้ ([E-2](06-epic-lane.md))

### L2-3 การแตก Issue — บังคับให้พยากรณ์ไฟล์ที่จะแตะ

เมื่อแตก child Issue เนื้อหาของแต่ละ Issue ต้องมีสิ่งต่อไปนี้เสมอ ([template](../templates/issue-template.md)):

- **วัตถุประสงค์ Why**
- **เงื่อนไขความสำเร็จ Done when**
- **การพยากรณ์ไฟล์ / module ที่จะแตะ** ← เป็นอินพุตสำหรับการตัดสินใจ GO ทำงานคู่ขนาน หากพยากรณ์ไม่ได้ให้ระบุว่า "พยากรณ์ไม่ได้" (= Issue นั้นไม่สามารถทำคู่ขนานได้)

### L2-4 การตัดสินใจ GO ทำงานคู่ขนาน

จะปล่อยให้ 2 Issue ทำงานพร้อมกันได้ก็ต่อเมื่อ **เซตของไฟล์ที่ประกาศไว้ไม่ทับซ้อนกันเท่านั้น**

- ทับซ้อนกัน → เรียงลำดับตามลำดับ
- พยากรณ์ไม่ได้ → เรียงลำดับตามลำดับ หรือทำ spike สำรวจก่อนเพื่อให้พยากรณ์ได้
- **ตรวจสอบการทับซ้อนไม่ได้** (ไม่มีการประกาศ · รูปแบบไม่ถูกต้อง · `UNKNOWN`) → เรียงลำดับ (fail-closed — [FP-1](05-fail-posture.md))
- หากยังต้องการทำคู่ขนานให้ได้ → ให้ผ่าน **Issue แยกขอบเขต** (refactor เพื่อตัดส่วนที่ชนกันออกมา) ก่อน 1 ฉบับ

### L2-5 การแยก Issue ขอบเขตกว้าง

Issue ที่แตะพื้นที่กว้างของรีโป เช่น refactor ทั้งระบบ / ปรับดีไซน์ใหม่ทั้งหมด / จัดฟอร์แมตรวด / อัปเดต dependency ยกชุด ให้**ทำแบบเดี่ยว**เท่านั้น ระหว่างที่กำลังดำเนินการอยู่ ให้หยุดการทำงานคู่ขนานในรีโปเดียวกันทั้งหมด

หลักการเรียงลำดับมาตรฐาน: **ทำ Issue ของฟีเจอร์ปกติให้เสร็จก่อน → Issue ขอบเขตกว้างค่อยรวบทำแบบเดี่ยวเป็นลำดับสุดท้าย**

### L2-6 การลงทุนในจุดร้อนแรง (Hotspot)

ไฟล์ขนาดใหญ่ที่รวมความรับผิดชอบหลายอย่างไว้ด้วยกัน (เช่น View 2,500 บรรทัด + gesture + การเรียก engine) คือศัตรูตัวฉกาจของการพัฒนาแบบคู่ขนาน

- วาง "**แผนที่ความปลอดภัยสำหรับงานคู่ขนาน**" ไว้ใน `ARCHITECTURE.md` ของแต่ละรีโป เพื่อบันทึกขอบเขต module และจุดร้อนแรง ([template](../templates/architecture-parallel-map.md))
- ให้ตั้ง Issue อิสระโดยให้ความสำคัญกับการ refactor แบ่งจุดร้อนแรงในฐานะ "**การลงทุนเพื่อความเป็นไปได้ของงานคู่ขนาน**" — หลังแบ่งแล้ว การทำงานคู่ขนานในพื้นที่นั้นจะปลอดภัยในเชิงโครงสร้าง
