# L2 Milestone Loop — เลเยอร์ตัดสินว่าจะทำงานคู่ขนานได้หรือไม่

เลเยอร์ที่วางไว้**เหนือ** Issue loop (L1) แปลง "จะสร้างอะไร" ให้กลายเป็น "ใครจะแตะส่วนไหน" แล้วตัดสินใจว่าจะทำงานคู่ขนานได้หรือไม่ที่ชั้นนี้ก่อนส่งลง L1
แต่ละกฎมี rule ID ที่คงที่ (`L2-1` ถึง `L2-6`) กำกับไว้ ฝั่งสรุป ([docs/04](04-adoption.md)) จะอ้างอิง ID เหล่านี้

## ทำไมจึงต้องมีเลเยอร์นี้

เงื่อนไขเดียวที่ทำให้การแบ่งงานปลอดภัยคือ — **รู้ก่อนเริ่มลงมือว่าชุดไฟล์ที่จะแตะไม่ทับซ้อนกัน**
worktree และ Issue lock (L0) เป็นกลไกที่ช่วยลดความเสียหายเมื่อเกิดการชนกัน แต่สิ่งที่ป้องกันการชนกันเองคือ "การตกลงขอบเขตล่วงหน้า" หากข้ามเลเยอร์นี้แล้วทำงานคู่ขนาน งานสองสายที่แตะ hotspot เดียวกัน (ไฟล์ขนาดใหญ่) จะชนกันอย่างแน่นอน

## ขั้นตอนของ loop

### L2-1 ตกลงเป้าหมายร่วมกัน

- ตกผลึกความต้องการผ่านการสนทนาก่อนลงมือ (ใช้วิธีที่แต่ละ agent มีอยู่แล้ว เช่น deep-interview หรือ session วางแผน)
- ตั้งคำถามกับความต้องการที่ทำให้การออกแบบซับซ้อนขึ้นสักครั้งหนึ่ง (แนวทางการตั้งคำถามดูที่ [ทำไมจึงสร้างให้เรียบง่าย](why-simple-systems.md)) การตัดสินใจตัดทิ้งหรือจำกัดขอบเขตต้องได้รับความเห็นชอบจากผู้ร้องขอ และห้ามลด Done when โดยไม่มีความเห็นชอบ ความซับซ้อนที่ยอมรับหลังจากตั้งคำถามแล้วให้บันทึกเหตุผลไว้ใน Why ของ Issue
- **การประเมินความหนัก**: bug fix เดี่ยว / ฟีเจอร์เดียว = Issue 1 ฉบับ ฟีเจอร์ใหม่ / เปลี่ยนแปลงสถาปัตยกรรม / หลายโมดูล = **EPIC Issue + แตกเป็น Issue ย่อย + ผูกกับ GitHub Milestone**
- หากลังเลให้เลือกฝั่งที่หนักกว่าไว้ก่อน เกณฑ์การตัดสินคือ "**มีความเป็นไปได้ที่จะข้ามหลาย session / หลาย agent หรือไม่?**"
- การดำเนินงานของสิ่งที่เข้าข่าย EPIC Issue (integration branch, human checkpoint, sandglass review) ดูที่ [docs/06 Epic Lane](06-epic-lane.md) (E-1 ถึง E-10)

### L2-2 ตัดสินผลกระทบต่อสถาปัตยกรรม

ก่อนเริ่มลงมือ ต้องถามเสมอว่า: "**งานนี้จะขยับขอบเขตของโมดูลหรือไม่?**"

- **ไม่ขยับ** → ไปแตก Issue ต่อได้เลย
- **ขยับ**(เช่น การแบ่งโมดูล, การจัดโครงสร้างไดเรกทอรีใหม่, การเปลี่ยน shared interface) → ให้ **boundary PR นำหน้าไปหนึ่งฉบับเท่านั้น**
  - จนกว่า boundary PR จะ merge เสร็จ ห้าม**เริ่มงานคู่ขนานใหม่**ในรีโปนั้น (ช่วง serial)
  - ตัว boundary PR เองต้องคงให้เล็กที่สุด — อย่าผสมการเปลี่ยนแปลงขอบเขตกับการเปลี่ยนแปลงฟีเจอร์เข้าด้วยกัน
  - ภายใน Epic **child Issue ลำดับที่ 0 ของการแช่แข็ง contract** จะเทียบเท่ากับ boundary PR ([E-2](06-epic-lane.md))

### L2-3 แตก Issue — บังคับให้คาดการณ์ไฟล์ที่จะแตะ

เมื่อจะแตก child Issue ให้เขียนสิ่งต่อไปนี้ลงในเนื้อหา Issue แต่ละฉบับเสมอ ([template](../templates/issue-template.md)):

- **วัตถุประสงค์ Why**
- **เงื่อนไขความสำเร็จ Done when**
- **การคาดการณ์ไฟล์ / โมดูลที่จะแตะ** ← เป็น input ของการตัดสินใจ GO ทำงานคู่ขนาน หากคาดการณ์ไม่ได้ให้ระบุชัดเจนว่า "คาดการณ์ไม่ได้" (= Issue นั้นไม่สามารถทำงานคู่ขนานได้)

### L2-4 ตัดสินใจ GO ทำงานคู่ขนาน

จะปล่อยให้ Issue สองฉบับรันพร้อมกันได้ก็ต่อเมื่อ **ชุดไฟล์ที่ประกาศไว้ไม่ทับซ้อนกันเท่านั้น**

- ทับซ้อนกัน → ทำแบบ serial ตามลำดับ
- คาดการณ์ไม่ได้ → ทำแบบ serial ตามลำดับ หรือทำ spike สืบสวนก่อนเพื่อให้คาดการณ์ได้
- **ตรวจสอบการทับซ้อนไม่ได้**(ไม่มีการประกาศ / รูปแบบไม่ถูกต้อง / `UNKNOWN`) → serial (fail-closed — [FP-1](05-fail-posture.md))
- หากยังต้องการทำคู่ขนานให้ได้ → ให้ผ่าน **boundary-separation Issue** (refactor เพื่อแยกส่วนที่ชนกันออกมา) ให้เสร็จก่อนหนึ่งฉบับ

### L2-5 แยกงาน Issue ขอบเขตกว้าง

Issue ที่แตะขอบเขตกว้างของรีโป เช่น refactor ทั้งหมด / ปรับดีไซน์ใหม่ทั้งระบบ / จัด format ยกชุด / อัปเดต dependency พร้อมกันทั้งหมด ให้**รันแบบเดี่ยว**เท่านั้น ระหว่างที่รันอยู่ให้หยุดการทำงานคู่ขนานทั้งหมดในรีโปนั้น

หลักการเรียงลำดับ: **เคลียร์ Issue ฟีเจอร์ทั่วไปก่อน → Issue ขอบเขตกว้างค่อยรวบทำแบบเดี่ยวทีหลังสุด**

### L2-6 การลงทุนใน Hotspot

ไฟล์ขนาดใหญ่ที่มีหลายความรับผิดชอบอยู่รวมกัน (เช่น View + gesture + engine call รวม 2,500 บรรทัด) คือศัตรูตัวฉกาจที่สุดของการพัฒนาแบบคู่ขนาน

- วาง "**แผนที่ความปลอดภัยสำหรับงานคู่ขนาน**" ไว้ใน `ARCHITECTURE.md` ของแต่ละรีโป เพื่อบันทึกขอบเขตโมดูลและ hotspot ([template](../templates/architecture-parallel-map.md))
- ให้ตั้ง Issue แยกต่างหากเพื่อจัดลำดับความสำคัญของการ refactor แยก hotspot ในฐานะ "**การลงทุนเพื่อความเป็นไปได้ในการทำงานคู่ขนาน**" — หลังจากแยกแล้ว การทำงานคู่ขนานในพื้นที่นั้นจะปลอดภัยในเชิงโครงสร้าง
