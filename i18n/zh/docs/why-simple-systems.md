# 为什么要做得简单——复杂度靠需求消除，而不是靠设计化解

> 本页不是条文。条文正文在 [docs/01](01-milestone-loop.md)〜[docs/03](03-git-protocol.md) 和 [docs/05](05-fail-posture.md)〜[docs/08](08-lifecycle.md)。
> 这里写的，是那些条文**默认成立的前提思路**。

## 我们想要达成的目标

本手册的条文（L2 / L1 / L0）是用来守住「怎么做・怎么并行」的机制。但在此之前——**决定要做什么**的阶段，其实已经决定了一些东西：脆弱程度，以及维护的重量。

想要达成的状态有四个。

- **简单、不易坏** — 部件越少，能坏的地方也越少
- **经得起放置** — 距离下一次必须维护的时间越长越好。持续运行不需要人时刻盯着
- **任何人都能看懂结构** — 几个月后的自己，或者第一次接触的 agent，不用额外说明也能读懂并跟上。「只有作者本人才懂」「事后要花很久才能解读」本身就要当作缺陷处理
- **模块数量只对应职责数量** — 切分不多于也不少于职责数（衡量方式与 [为什么要把模块切小](why-small-modules.md) 中的「职责数量」一致）

## 设计上卡住时，先怀疑需求

做的过程中，会出现这样的情况。

- 逻辑变得异常难以理解
- 靠模块组合解决不了，看起来需要一些特殊机制
- 卡在设计本身上

这时候第一个该采取的动作，不是「去找更聪明的设计」，而是**怀疑需求本身**。

大部分的难度，不是设计带来的，而是需求带来的。如果能消掉一个需求，那个需求所要求的设计难点，会连同实现、测试、未来的维护一起整个消失。设计上的巧思只能**稀释**难度，而重新审视需求可以直接**消除**难度。

## 怀疑时要问的问题

按顺序发问。每一个问题问的都不是「能不能削减需求」，而是「**能不能消掉前提，从而让问题本身消失**」。

1. **真正的使用者到底是谁？** — 预设的用户范围越广，认证、权限、错误处理、支持工作就会越厚重。确认实际使用者之后，往往会发现这些厚度中的大半都不需要
2. **真的需要联网吗？** — 如果本地执行或封闭网络（VPN 等）就够用，那么为了对外公开而需要的登录设计、防攻击对策、可用性设计，从一开始就不存在
3. **限定用途，能不能消掉难点？** — 放弃「什么都能处理」，把输入或用法限定下来，原本难解的分支有可能整个消失
4. **这个需求，真的是有人提出的吗？** — 「有了好像会更好」而加上去的需求，代价往往最高。答案要向提出者确认——留在 Issue 里的需求，是过去达成一致的记录，不是 agent 可以单方面判定「没人要」就删掉的对象

### 例子：「希望做一个面向内部的 SaaS」

如果照字面接受，就会开始为了安全公开而设计。登录、密码重置、会话管理、权限表——每一项都很难，每一项都容易坏，每一项都要持续维护。

这时候回到问题 1。「谁来用？」——如果答案是「只有我们自己团队」，那么根本不需要对外公开。放到本地跑，或者放进封闭网络，**登录这个问题本身就消失了**。做之前只问了一个问题，就让最容易坏的部分整个变得不再需要。

这就是「消掉前提来解决问题」。

> **注意：** 这只是「动手之前，先确认使用者范围这个需求」的例子，不是说要把认证从已公开的系统里去掉。触及认证、权限、公开范围这类边界的判断——无论是动手之前，尤其是系统已经在运行时——都属于**高风险领域**（[docs/06](06-epic-lane.md) 的单一定义），需要人来拍板。

## 怀疑是自由的，但删除的决定权在委托方

这是最重要的一条界线。**怀疑得出的结论，不是删除需求，而是把问题和提案带回目标共识（[`L2-1`](01-milestone-loop.md)）。**

- agent 只能做到提出替代方案。**最终决定舍弃什么的，是委托方**
- 已经达成共识的需求、完成条件（Done when），agent 不能单方面改写或稀释。不能以「怀疑之后判断不需要」为理由，把完成条件改成 N/A
- 中途想要放弃某个需求时：不要在继续实现的同时改写 Done when，而是**在 Issue 上向委托方确认**。达成一致后，先更新 Why / Done when，再继续
- 不能**替代**卡壳时的出口。实现卡住时的正规出口是 [`L1-4`](02-issue-loop.md) / [`L1-6`](02-issue-loop.md) 的 HOLD 或上报给人，而不是「怀疑需求」。**「做不到」和「不再需要」是两回事，要分别记录**
- 即便消掉需求让工作变轻了，也**不能拿来当作规避评审重量**（[`L1-9`](02-issue-loop.md) / 席位数）**的手段**。删除本身作为一次需求变更，在重活里依然属于上游评审的对象
- 在重活里，这条线条文已经划好了——需求定义属于动手前的异构评审对象（[`L1-9`](02-issue-loop.md)），Epic 内的 Done when 是冻结产物，变更属于人类检查点的停止对象（[`E-3`](06-epic-lane.md)）。本页不会放松这些

## 不是所有情况都能这样处理

也存在需求确实真实存在、复杂度无法避免的情况。像合规对应、审计记录、个人信息保护、计费这类需求，**本来就不是我们自己有权删除的**——这些不是拿来怀疑的对象，而是要确认并满足的对象。本页说的不是「不要做复杂的东西」，而是「**在接受复杂度之前，先怀疑一次需求**」。

如果怀疑过后仍然选择接受，那也没问题。只是**要在 Issue 的目的（Why）里留下一行，说明为什么接受**（Why 的写法见 [`L1-2`](02-issue-loop.md)）。留下了，几个月后就有人能重新问「这份复杂度真的需要吗？」。没留下，复杂度就会变成既成事实。

## 与并行规则的关系

这个前提，和条文的世界是相通的。

- 消掉需求，触碰的文件就会变少。触碰的文件变少，**触碰文件预测**（[`L2-3`](01-milestone-loop.md)）就更容易写，并行GO（[`L2-4`](01-milestone-loop.md)）也更容易出现。简单的系统，同时也是更适合并行开发的系统
- 「模块数量只对应职责数量」，和 [切分是对并行可能性的投资](why-small-modules.md) 的判断轴是一致的。职责挤在一起就拆开（那边讲的事），没有职责就不要多切部件（本页讲的事）——方向不同，但衡量标准都是**职责数量**
- [`L2-1`](01-milestone-loop.md) 里「拿不准就按重的算」判断的是**流程**（是否 Epic 化、评审的厚度），不是要不要增加功能。「需求要轻，流程要重」是可以并存的
- 任何人都能看懂结构，和把交接的正本放在 Issue 上（[Issue-first](why-issue-first.md)）出于同样的动机。基准都是**零记忆进入的下一个读者**

## 常见疑问

**agent 会不会拿「怀疑需求」当借口，擅自删减需求？**

按本页的读法，这是被禁止的。怀疑到提出问题和方案为止。删除、收窄的决定权在委托方（见上面「怀疑是自由的，但删除的决定权在委托方」）。未经一致同意就稀释 Done when 的行为，会在完成记录（[`L1-7`](02-issue-loop.md)）的比对中露出马脚，应当作违规处理。

**怀疑需求，会不会对委托方不礼貌？**

被怀疑的不是委托方本人，而是需求和设计之间的转换过程。「谁来用？」这类问题，不是在压价谈判，而是在确认委托真正的目的。只要目的能被满足，做的东西越少，对委托方越有利。

**做得简单，以后会不会没法扩展？**

情况往往相反。为将来的扩展预先埋下的机制，大多数时候扩展的方向和预想的不一样，最后没派上用场，只是妨碍了读者理解。结构小而易懂，本身就是最经得起折腾的可扩展性。

**什么时候该怀疑需求？**

有两个时机。第一次是动手之前——在目标共识（[`L2-1`](01-milestone-loop.md)）阶段把需求定下来的时候。这里是和委托方对话的场合，当场问就够了。第二次是过程中——感觉设计变得难以理解、卡壳的时候。这时候委托方不在现场，所以按上面划好的界线，agent 能做的只到「把问题写进 Issue 确认」为止。一旦卡壳，人和 agent 都容易倾向「找更复杂的解法」。本页就是用来叫停这个倾向的。
