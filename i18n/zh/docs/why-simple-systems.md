# 为什么要简单地构建 —— 用需求消灭复杂度，而不是靠设计化解它

> 本页不是条文。条文正文在 [docs/01](01-milestone-loop.md)〜[docs/06](06-epic-lane.md)。
> 这里写的是那些条文**所依赖的思考方式**。

## 我们想要达成的目标

本手册的条文（L2 / L1 / L0）是用来守护"怎么做、怎么并行"的机制。但在此之前 —— 在**决定要做什么**的阶段，有些东西其实已经被决定了。那就是脆弱程度和维护的重量。

我们想要达成的状态有四个：

- **简单且不易损坏** —— 部件越少，能坏的地方就越少
- **经得起放置** —— 距离下一次需要维护的时间越长越好。持续运转不需要人时刻盯着
- **任何人都能理解结构** —— 无论是几个月后的自己，还是第一次接触的 agent，都能不靠额外说明读懂并跟上。"只有做的人自己懂""事后需要花时间解读"，本身就应当被当作缺陷处理
- **模块数量恰好等于职责数量** —— 既不多切也不少切（衡量方式与 [为什么要把模块切小](why-small-modules.md) 中的"职责数量"相同）

## 设计上卡住时，先怀疑需求

在制作过程中，会出现这样的情况：

- 逻辑变得异常难懂
- 无法用模块组合解决，似乎需要一些特殊机制
- 卡在设计本身上

这时首先该采取的手段，不是"去找更聪明的设计"，而是**怀疑需求本身**。

难度的大部分，不是设计带来的，而是需求带来的。只要能消掉一个需求，这个需求所要求的设计难点，就会连同实现、测试、未来的维护一起整体消失。设计上的巧思只能**稀释**难度，而重新审视需求却能**消灭**难度。

## 怀疑时该问的问题

按顺序发问。每一个问题都不是在问"能不能削减需求"，而是在探索"**能否消除前提，从而消灭问题本身**"。

1. **真正的使用者是谁？** —— 假定的用户范围越广，认证、权限、错误处理、支持就会越厚重。确认实际使用者之后，往往会发现这些厚重的部分大半都不需要
2. **真的需要在线吗？** —— 如果本地运行或封闭网络（如 VPN）就足够，那么为公开而设计的登录方案、攻击防范、可用性设计，从一开始就不存在
3. **能否通过限定用途来消灭难点？** —— 放弃"什么都能处理"，转而限定输入或用法，往往能让原本难解的分支整片消失
4. **这个需求，真的有人提出过吗？** —— 因为"有了会更好"而添加的需求，代价往往最高。答案要向提出需求的人确认 —— 留在 Issue 中的需求是过去达成共识的记录，不是 agent 可以单方面判定"没人要求"就自行删除的对象

### 例子："希望做一个面向内部的 SaaS"

如果照字面接受这个委托，就会开始为安全上线而设计。登录、密码重置、会话管理、权限表 —— 每一个都很难做，每一个都容易出问题，每一个都会持续产生维护负担。

这时回到问题 1。"谁会使用它？"——如果答案是"只有我们自己团队"，那么根本不需要对外公开。只要在本地运行，或放在封闭网络里，**登录这个问题本身就消失了**。在动手之前只问了一个问题，就让最容易出问题的部分整块变得不再需要。

这就是"消除前提来解决问题"。

> **注意：**这只是"动手前先确认使用者范围这一需求"的例子，并不是说要从以公开为前提的系统中去掉认证。触及认证、权限、公开范围这类边界的判断 —— 无论是在动手之前，还是对已经在运行的系统而言 —— 都属于**高风险领域**（[docs/06](06-epic-lane.md) 中的统一定义），需要人类做出决策。

## 怀疑是自由的，但"消不消"的决定权在委托方

这是最重要的分界线。**怀疑所产生的输出，不是删除需求，而是把问题拉回目标共识（[`L2-1`](01-milestone-loop.md)）的"提问"与"提案"。**

- agent 只能做到提出替代方案。**最终决定舍弃什么的，是委托方**
- 不能由 agent 单方面改写或稀释已达成共识的需求、完成条件（Done when）。不能以"怀疑之后判断不需要"为理由，把完成条件改成 N/A
- 如果在过程中想要放弃某个需求：不要在保留原有实现的同时改写 Done when，而应**在 Issue 上向委托方确认**。达成共识后再更新 Why / Done when，然后继续
- 不能**当作**卡壳时的出口替代品。实现过程中卡壳时的正规出口是 [`L1-4`](02-issue-loop.md) / [`L1-6`](02-issue-loop.md) 的 HOLD 或上报给人类，而不是"怀疑需求"。**"做不到"和"不再需要"是两回事，要分开记录**
- 即便因为消掉需求而让工作量变轻，这也**不能作为规避审查重量**（[`L1-9`](02-issue-loop.md) / 席位数）的手段。消除需求这件事本身作为一种需求变更，在重量级工作中也属于上游审查的对象
- 在重量级工作中，条文已经划好了这条线 —— 需求定义是实现着手前的异构审查对象（[`L1-9`](02-issue-loop.md)），Epic 内的 Done when 是已冻结的交付物，变更属于人类检查点的暂停对象（[`E-3`](06-epic-lane.md)）。本页不会放松这些规定

## 并非所有情况都能这样处理

有些需求是真实存在的，复杂度无法避免。像合规对应、审计记录、个人信息保护、计费这类需求，**本来就不是我们能自由消除的** —— 这些不是用来怀疑的对象，而是需要确认并满足的对象。本页想说的不是"不要做复杂的东西"，而是"**在接受复杂度之前，先怀疑一次需求**"。

如果怀疑之后仍然选择接受，那也没问题。只是**要在 Issue 的目的（Why）里留一行说明为什么接受**（Why 的写法见 [`L1-2`](02-issue-loop.md)）。只要留下了记录，几个月后就会有人能够重新追问"这个复杂度真的有必要吗？"。如果没有留下，复杂度就会变成既成事实。

## 与并行规则的关系

这个前提与条文的世界是相连的。

- 消掉需求，触及的文件就会减少。触及文件减少，**触碰文件预测**（[`L2-3`](01-milestone-loop.md)）就更容易写清楚，也更容易拿到并行 GO（[`L2-4`](01-milestone-loop.md)）。简单的系统，也是更适合并行开发的系统
- "模块数量恰好等于职责数量"，与 [拆分是对并行可能性的投资](why-small-modules.md) 采用的是同一个判断轴。职责挤在一起就拆开（那是那边的话题），没有职责却增加部件就不要加（这是本页的话题）—— 方向不同，但衡量标准都是**职责数量**
- [`L2-1`](01-milestone-loop.md) 中"拿不准就选重的一边"，判断的是**流程**（是否 Epic 化、审查的厚度），而不是要不要增加功能。"需求要轻，流程可以重"这两者是可以并存的
- 让任何人都能理解结构，与把交接的正本放在 Issue 里（[Issue-first](why-issue-first.md)）出于同样的动机。基准都是**带着零记忆进来的下一个读者**

## 常见疑问

**agent 会不会以"怀疑需求"为借口，擅自削减需求？**

按照本页的读法，这是被禁止的。怀疑仅止于提出问题和提案。删除或缩小范围的决定权在委托方（见上文"怀疑是自由的，但'消不消'的决定权在委托方"）。未经共识就稀释 Done when 的行为，应当被当作一种在完成记录（[`L1-7`](02-issue-loop.md)）核对时会暴露出来的偏差来处理。

**怀疑需求，会不会对委托人失礼？**

被怀疑的不是委托人，而是需求与设计之间的转换过程。"谁会使用它？"这类问题，不是在压价谈判，而是在确认委托的真正目的。只要目的能够达成，做得越少，对委托人越有利。

**做得简单，以后会不会没法扩展？**

情况往往相反。为将来的扩展预先埋下的机关，大多会等来一个和预想方向不同的扩展需求，结果既没用上，还妨碍了读者的理解。结构小而易懂，才是最百搭的扩展性。

**什么时候该怀疑需求？**

有两个时机。第一次是在着手之前 —— 在目标共识（[`L2-1`](01-milestone-loop.md)）阶段确定需求的时候。这里是与委托方对话的场合，当场提问就够了。第二次是在过程中 —— 感觉设计变得难解、卡住的时候。这时委托方不在现场，所以按照上面划定的界线，agent 能做的到"把问题写进 Issue 确认"为止。人和 agent 一旦卡壳，都容易走向"更复杂的解决方案"。这一页就是用来阻止这种倾向的。
