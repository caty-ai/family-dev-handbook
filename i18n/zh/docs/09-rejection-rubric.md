# R 拒绝准则 —— 接受什么、拒绝什么的层级

L 层（L2 / L1 / L0）是"如何推进"、B 层是"如何委托"的契约，与之相对，R 层规定的是**什么会被合并、什么会被拒绝**这一意图层面的契约。用途有两个:

1. **为创作者服务** —— 让贡献（包括来自 agent 的提议、任务、PR）能够精准瞄准目标
2. **为一线裁定服务** —— 什么时候可以不经人工判断就关闭，以及同样重要的"什么时候不能关闭"的指引

各条的规范性程度不同: **R-1 / R-4 / R-5 / R-6 是契约**，**R-2 / R-3 是接受判断的基准列表**；以 R-2 / R-3 为依据的拒绝执行，始终要经过 R-1 的权限规律（价值判断由 owner 专断）。

每条规则都赋予稳定的 rule ID（`R-1`〜`R-6`），条目以 ①②③… 引用（与 [E-6](06-epic-lane.md)① 同一格式）。摘要一侧（[docs/04](04-adoption.md)）引用这些 ID。无法验证时的姿态见 [docs/05](05-fail-posture.md)。

## R-1 自动拒绝的3个理由 —— 价值判断由 owner 专断

**适用对象是已记录的提议（Issue、PR、以记录形式提交的任务提议）**。可以不经人工判断就拒绝的，**只有能机械判定黑白的3个理由**。每个理由都必须同时满足成立条件并附有证据才算成立:

1. **main 上已经有了**（implemented on main）—— 必须能指出当前 main 上存在该行为的具体 commit 或行。"有功能类似的东西"不属于本理由（那属于价值判断 = owner 专断）
2. **无法复现**（cannot reproduce）—— **仅限 bug 报告**。要留下针对当前 main 的复现尝试记录（命令 / 步骤・观察结果・日期）。信息不足不是拒绝理由 —— 应该询问并挂起
3. **内容不成立**（incoherent）—— 仅限矛盾、空白、垃圾内容等读不出实质主张的情形，且**经过1次询问后仍然读不出来**时才成立。只是读起来费力的提议不属于此类

- "不需要・与方针不符・超出范围"等**基于价值判断的拒绝由 owner（人类）专断**。agent 只能做到附上推荐意见和依据后上报（以 R-2 / R-3 为依据的拒绝同理 —— 不属于这3个理由）
- **拿不准就不要关闭** —— "关闭"是权限行使，无法验证时应向权限收缩的方向（保持打开、交给 owner）倾斜（[FP-7](05-fail-posture.md) 的方向）。一线裁定的工作，是读懂设计意图，**不要误关正当的贡献**
- **记录**: 已经立起 lane 的提议（已声明 WIP）的终止，遵循 [L1-4](02-issue-loop.md) 的5个词汇。**尚未立起 lane 就被拒绝的提议不使用 lane 词汇**，只记录关闭理由（3个理由之一 + 上述证据，或指向 owner 裁定的链接）
- **重新打开是不对称的**: 基于3个理由关闭的提议，一旦出现新证据，无需 owner 批准即可重新打开（重新打开是权限收缩的方向）
- 触及 R-4 四种模式的提议，是自动关闭"不安全"的典型情形 —— 应交给人类
- Epic 运行期间的拒绝判断，**在不停止 lane 的情况下异步交给 owner**（不增加 [E-3](06-epic-lane.md) 的停止点）

## R-2 欢迎的贡献 —— 6条

1. **修复真实的 bug，并覆盖整个类别** —— 在当前 main 上复现症状，指出出现问题的行，不只修复被报告的那一处，也要修复兄弟调用路径（与 R-4 的口诀相对）
2. **末端可以扩展・腰部要保守** —— 扩展末端（各产品・各家的功能）的贡献值得欢迎。抑制只针对腰部（家族共享的基础设施・所有人都要承担恒久成本的地方）。"占用面积最小"说的是接入腰部的布线，不是产品能不能成长
3. **声明为重构的变更，diff 再大也欢迎** —— "每一行都能追溯到需求"这项检查适用于功能性变更，对于声明为重构的变更请求，抽取本身就是需求（拆分热点 = [L2-6](01-milestone-loop.md) 的投资）。**被放宽的只是对 diff 大小的怀疑** —— 声明文件集合（[L0-2](03-git-protocol.md) default-deny）与 [L1-7](02-issue-loop.md)④ 的 diff 核对，对重构也绝不放宽（重构是通过广泛声明将要触及的文件预测来通过，而不是省略声明来通过）。广域重构的单独执行（[L2-5](01-milestone-loop.md)）、合并流程（[L0-7](03-git-protocol.md)）也照常适用
4. **扩展而非复制** —— 在新增模块・manager・hook 之前，先确认现有工具是否够用（放置位置见 R-5）
5. **测试要断言不变量** —— 检验"两份数据应当如何关联"，不要写冻结当前值（清单・件数・版本号硬编码）的变更检测测试
6. **边界・传播・I/O 要用真实路径验证** —— 涉及解析链・配置传播・权限边界・外部 I/O 的变更，要给出实际跑通该路径的 E2E 证据。不要把只有 mock 通过的 green 当作完成。**本条是选取证据的指引，merge 门槛要求的正本仍是 [L1-7](02-issue-loop.md)**（不增加要求）

## R-3 即便做得再好也要拒绝的 —— 7条

这不是质量标准，而是**结构性判断**下要拒绝的内容。即便做得再好，拒绝的理由也不会因此消失。**以本条为依据的拒绝不属于 R-1 的3个理由 —— 执行始终由 owner 专断**，agent 只能指出可疑之处并上报:

1. **投机性的基础设施** —— 没有具体使用者的 hook・callback・扩展点。只要存在明确表达的实际用例，就不算投机（即使使用者在别的仓库也可以）
2. **为非密配置新增环境变量** —— 密钥的存放位置（.env 等）专用于密钥。行为配置（超时・阈值・flag・显示）应放入配置文件
3. **明明有现成工具够用，却新建 skill・hook・常驻系统** —— 没有从 R-5 的阶梯最小段开始考虑过的新建，一律拒绝
4. **给应当完整阅读的内容开偷懒阅读的后门** —— 不要为 agent 应当完整阅读的内容（skill、prompt、操作手册）的加载器添加翻页・摘录选项。这会导致只读第一页就跳过其余部分
5. **破坏原本要守护的功能的"修复"** —— 扼杀功能目的的缓解措施是错误的缓解措施。在限制行为之前先读懂原始 commit 的意图（`git log -p -S`）
6. **未经证明的接线・未经许可的非密遥测** —— 没有 E2E 证明就接线的代码・运行时从未走到过的分支・没有 opt-in 门控的外发遥测 / 标识符附加（**包括非密的使用信息**）。密信息的外发不属于本条范畴，**遵循 [E-5](06-epic-lane.md) 及各家的密钥规律 —— 本条不改变 E-5 封闭式禁止清单的边界**
7. **把外部工具・他人的产品塞进核心代码树** —— 维护负担会永久落到自己头上。应放在 wrapper・隔离的存放处（例如: 用于隔离的独立目录・外部管理的独立仓库 —— 示例非规范性），不要放进核心。这是耦合与维护层面的判断，质量再高，该关闭还是要关闭

## R-4 前提验证 —— 在称之为 bug 之前

口诀: **"如果指不出 bug 出现的那一行，前提就是未经验证的"**

做得再好的变更被拒绝，最大的原因往往不是质量，而是建立在**错误的前提**之上，或者**把有意的设计当成了缺陷**。以下4种模式是双向起作用的 —— 对 review 席位来说，它告诉你该精查哪里；对一线裁定来说，它告诉你什么时候不能关闭:

1. **是有意的设计，不是缺陷** —— 看似是疏漏的限制，往往是有意为之。在修复之前先问一句"这个隔离会不会正是设计所在？"，并阅读原始 commit 的意图
2. **前提对照实际运行方式并不成立** —— 在接受说法之前，先追踪实际代码・运行时的实际行为。如果说不出修复会改变哪一行的行为，就是未经验证的
3. **缺失本身在支撑着某种承重** —— 补上"明显缺失"的那一块，有时会破坏这一省略原本守护的东西
4. **矫枉过正・已成定论的方针死灰复燃** —— 超出已达成共识范围的扩张，或对已经有意关闭的方向的重提，哪怕能跑通也要拒绝。变更应停留在已达成共识的狭窄范围内，其余部分作为后续跟进另行提出

贯穿的基调: **在写代码之前・合并之前，把主张和意图都对照代码库进行验证**。已确认的复现 + 行级说明，任何时候都胜过看似合理的说辞。对意图拿不准时，与其提出一个与设计相悖的修复，不如先问一句更划算。

（具体实例可以替换成各家自己的事故记录 —— 正文中的示例非规范性。委托 review 时，可以把这4种模式作为 [B-4](07-delegation-brief.md)"点名最坏失败形态"的视角前置说明）

## R-5 放置位置的阶梯 —— 恒久占用面积用最小的那一段解决

创建新能力时，越靠下的段位，恒久的占用面积（所有人都要持续承担的成本）就越大。**选择能正确解决问题的、编号最小的那一段**:

1. **扩展现有代码** —— 如果只是已有东西的变种，新增表面为零
2. **脚本 / skill** —— 能用 shell 表达的操作。不常驻，只在被调用时运行
3. **带条件门控的 hook** —— 只在满足前提条件时才出现的自动化
4. **在现有仓库中新增功能** —— 如果已经有对应的存放位置，就放进去
5. **拆分为 MCP server・独立仓库** —— 如果确实是真正独立的能力，就放在核心之外
6. **新建仓库・新建常驻系统** —— 最后手段。**需要 owner（人类）的批准**。如果 Epic 运行期间出现这种情形，**作为 [E-3](06-epic-lane.md) 的临时检查点停止**（不追加到 E-3 的正表中）

- 拿不准就往上一段（占用面积最小）走。"下面那段更省事"不构成理由
- **选定段位后，要同时定好放置物的退场触发条件**（[LC-1](08-lifecycle.md) —— 阶梯决定放置位置，LC-1 决定退场方式。两者配套使用）
- **同类第3个时建立公共接口** —— 同一类别的集成攒到3个时，不要一个个单独接入，而是设计一个公共接口，把已有实现包装成第一个 provider。接口的设计属于边界变更，因此适用 [L2-2](01-milestone-loop.md) 边界 PR 先行的规则

## R-6 方针用 check 来强制执行

**不要让不能被打破的方针停留在"拜托了"的层面。** 被动式规则（.gitignore・文档・口头约定）只能防住"不小心" —— 想要强制执行的方针，应升级为一旦被打破就会变红的 check。

- **升级触发条件**: 同一方针被打破两次，就以 Issue 的形式起草 check 化提案。**被打破的记录要留存在 Issue 或各家的事故记录中，在第2次记录时起草**（让计数事后也能被验证）
- check 要**通过实体来检测**（不是靠目录名或扩展名拼写，而是靠内容・模式的本质进行匹配 —— 出处中有被拼写差异绕过的实例）
- check 的姿态要与既有条文保持一致: **阻止合并的门是 fail-closed**（[FP-3](05-fail-posture.md) 的方向），**报告・合成・通知的管道是 fail-open**（[FP-4](05-fail-posture.md)）。check 不移动文件（[LC-5](08-lifecycle.md) —— 只检测并阻止・不做自动修复或自动退场）
- 审批类的 check（人工标签等）要**验证审批的真实存在** —— 不能仅凭正文或标签的存在就放行（[FP-8](05-fail-posture.md) 的方向）。审批的验证可能存在局限（例如共享身份的环境等）—— 此时应在 check 的说明中明确写出该局限，不要伪装成"已验证"（[FP-5](05-fail-posture.md)）
- 类型的正本在本仓库的 `templates/ci/`（在 #18 中整理完成）
