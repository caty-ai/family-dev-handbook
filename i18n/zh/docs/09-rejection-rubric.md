# R 驳回准则 — 什么被接受，什么被拒绝的层级

L 层（L2 / L1 / L0）是"如何推进"的契约，B 层是"如何委托"的契约，而 R 层则规定的是**什么会被合并、什么会被拒绝**这一意图层面的契约。用途有两个:

1. **面向创建者** — 让贡献（包括 agent 发起的提案、任务、PR）能够瞄准目标
2. **面向一次判定** — 作为"什么时候可以不经人类判断就关闭"、以及同样重要的"什么时候不能关闭"的指导

规范性因条款而异: **R-1 / R-4 / R-5 / R-6 是契约**，**R-2 / R-3 是接受判断的基准清单**，以 R-2 / R-3 为依据的驳回执行始终要经过 R-1 的权限规律（价值判断由 owner 专属决定）。

每条规则都附有稳定的 rule ID（`R-1`〜`R-6`），条目以 ①②③… 引用（与 [E-6](06-epic-lane.md)① 同样的格式）。摘要侧（[docs/04](04-adoption.md)）会引用这些 ID。无法验证时的姿态见 [docs/05](05-fail-posture.md)。

出处: 本章是对 NousResearch/hermes-agent 的 AGENTS.md 中「Contribution Rubric」（MIT）的改编。

## R-1 自动驳回的3个理由 — 价值判断由 owner 专属决定

**适用对象是已记录的提案（Issue、PR、作为记录提交的任务提案）**。可以不经人类判断就驳回的，**仅限机械可判定黑白的3个理由**。每个理由都必须附带成立条件与证据才能成立:

1. **已经存在于 main**（implemented on main）— 必须能通过 commit 或具体行指出该行为当前确实存在于 main。"存在功能上相似的东西"不属于本理由（那属于价值判断 = owner 专属决定）
2. **无法复现**（cannot reproduce）— **仅限于 bug 报告**。必须留下针对当前 main 的复现尝试记录（命令 / 步骤・观察结果・日期）。信息不足不是驳回理由 — 应当询问后保留（HOLD）
3. **内容不成立**（incoherent）— 矛盾、空白、垃圾内容等，无法读出实质主张的情况，**且仅限于经过1次询问后仍然无法读懂**时。只是读起来费劲的提案不属于此项

- "不需要・与方针不符・超出范围"等**基于价值判断的驳回，由 owner（人类）专属决定**。Agent 只能做到附上建议和依据后上报（以 R-2 / R-3 为依据的驳回也一样 — 不包含在这3个理由之中）
- **拿不准就不要关闭** — "关闭"是一种权限行使，无法验证时应向权限收缩的方向（保持开启并交给 owner）倾斜（[FP-7](05-fail-posture.md) 的方向）。一次判定的职责是读懂设计意图，**不要误关正当的贡献**
- **记录**: 已经立起 lane 的提案（已完成 WIP 声明）的终结遵循 [L1-4](02-issue-loop.md) 的5词汇。**对于在 lane 立起之前就被驳回的提案，不使用 lane 词汇**，只记录关闭理由（3个理由之一 + 上述证据，或指向 owner 裁定的链接）
- **重新开启是非对称的**: 基于3个理由关闭的提案，一旦出现新证据，无需 owner 批准即可重新开启（重新开启是权限收缩方向）
- 触及 R-4 中4种模式的提案，是"用3个理由自动关闭**不安全**"的典型 — 应交给人类
- Epic 运行期间的驳回判断，应**异步转交给 owner**，不停止 lane（不增加 [E-3](06-epic-lane.md) 的停止点）

## R-2 欢迎的贡献 — 6条

1. **修复真实的 bug，且按整个类别修复** — 在当前 main 上复现症状，指出具体出现的行，不仅修复报告中的那一处，还要一并修复兄弟调用路径（与 R-4 的口诀相对应）
2. **末端可以扩展・腰部要维护** — 扩展末端（各产品・各个家的功能）的贡献值得欢迎。抑制只针对腰部（家族共享的基础设施・所有人都要承担永久成本的地方）。"占用面积最小化"说的是通往腰部的接线问题，而不是产品是否可以成长的问题
3. **声明为重构的改动，即使 diff 很大也值得欢迎** — "每一行都能追溯到需求"的检查适用于功能变更，而声明为重构的变更需求本身就是提炼（热点拆分 = [L2-6](01-milestone-loop.md) 的投资）。**被放宽的只是对 diff 大小的怀疑** — 声明文件集合（[L0-2](03-git-protocol.md) default-deny）与 [L1-7](02-issue-loop.md)④ 的 diff 核对，即使是重构也绝不放宽（重构是通过广泛声明预计触及的文件来通过，而不是省略声明来通过）。广域重构的单独执行（[L2-5](01-milestone-loop.md)）・合并流程（[L0-7](03-git-protocol.md)）同样照常适用
4. **扩展而不是重复造轮子** — 在添加新模块・manager・hook 之前，先确认现有工具是否够用（放置位置见 R-5）
5. **测试应断言不变量** — 检验"两份数据应当如何关联"，不要写把当前值（列表・数量・版本号硬编码）冻结起来的变更检测测试
6. **边界・传播・I/O 要用真实路径验证** — 涉及解析链・配置传播・权限边界・外部 I/O 的变更，要给出实际跑通真实路径的 E2E 证据。不要把只有 mock 的 green 当作完成。**本条是证据选取方式的指引，merge 门槛要求的正本仍是 [L1-7](02-issue-loop.md)**（不增加要求）

## R-3 即使做得再好也要拒绝的 — 7条

这不是质量标准，而是作为**结构性判断**而拒绝的东西。即使做得很好，拒绝的理由也不会因此消失。**以本条为依据的驳回不属于 R-1 的3个理由 — 执行始终由 owner 专属决定**，Agent 只能指出相应疑点并上报:

1. **投机性基础设施** — 没有具体使用者的 hook・回调・扩展点。如果有明确表达的实际用例，就不算投机（即使使用者在别的仓库也可以）
2. **为非机密配置新增环境变量** — 机密的存放位置（.env 等）仅限于机密专用。行为配置（超时・阈值・flag・显示）应放入配置文件
3. **明明现有工具就够用，却新建 skill・hook・常驻系统** — 如果没有记录先按 R-5 的阶梯从最小的一级开始考虑过，这样的新建就要拒绝
4. **给应该完整阅读的内容开偷懒阅读的后门** — 不要在 Agent 应当完整阅读的内容（skill、prompt、操作手册）的加载器上加分页・摘录选项。这会导致只读第一页就跳过其余部分
5. **破坏了本应守护的功能的"修复"** — 扼杀功能目的的缓解措施是错误的缓解措施。在限制某个行为之前，先阅读原始 commit 的意图（`git log -p -S`）
6. **未经证明的接线・未经授权的非机密遥测** — 没有 E2E 证明就接入的代码、运行时从未走到过的分支、没有 opt-in 门控的对外遥测 / 标识符附加（**包括非机密的使用信息**）。机密信息的外发不在本条范围内，**遵循 [E-5](06-epic-lane.md) 及各个家的机密规律 — 本条不改变 E-5 封闭禁止列表的范围**
7. **把外部工具・他人产品塞进核心代码树** — 维护负担会永久落在这一方。应放在 wrapper・隔离的存放处（例如: 用于隔离的隔离目录・外部管理的独立仓库 — 示例为非规范性质），不要放入核心。这是耦合与维护的判断，即使质量再高，该关闭还是要关闭

## R-4 前提验证 — 在称之为 bug 之前

口诀: **"如果指不出 bug 出现的具体行，那前提就是未经验证的"**

做得再好的改动被拒绝，最大的原因往往不是质量，而是建立在**错误的前提**之上，或者**把有意为之的设计当成了缺陷**。以下4种模式是双向起作用的 — 对 review 席位而言，教会他们"该仔细审查哪里"；对一次判定而言，教会它"什么时候不能关闭":

1. **是有意为之的设计，而不是缺陷** — 看起来像疏漏的限制往往是有意为之的。在修复之前，先问一句"这种隔离会不会正是设计所在?"，并阅读原始 commit 的意图
2. **前提对照实际运行方式不成立** — 在接受说法之前，先追踪实际代码・运行时的实际行为。如果说不出修复会改变哪一行的行为，那就是未经验证
3. **"不存在"本身承担了负荷** — 添加看起来"明显缺失"的部件，有时会破坏那个省略原本守护的东西
4. **矫枉过正・已被否决方针的复活** — 超出已达成共识范围的扩展，或者对已被有意关闭的方向的翻案，即使能跑通也要拒绝。改动应停留在已达成共识的狭窄范围内，其余部分作为后续跟进提出

基调: **在写代码前・合并前，把主张和意图都对照代码库进行验证**。已确认的复现 + 行级别的说明，永远胜过看似有理的推论。对意图有疑问时，与其提出和设计相冲突的修复，不如先问一句，这样成本更低。

（具体案例可以用各个家的事故记录来替换 — 正文中的示例属非规范性质。委托 review 时，可以把这4种模式作为 [B-4](07-delegation-brief.md) 中"点名最坏失败形态"的观察角度前置说明）

## R-5 放置位置的阶梯 — 用最小的一级换取最小的永久占用面积

创建新能力时，越靠下的一级，永久性的表面积（所有人都要持续承担的成本）就越大。**选择能正确解决问题的、编号最小的那一级**:

1. **扩展现有代码** — 如果只是已有东西的变体，新增表面积为零
2. **脚本 / skill** — 能用 shell 表达的操作。不常驻・只在被调用时运行
3. **带条件门控的 hook** — 只有当前提条件被设置时才出现的自动化
4. **在现有仓库中添加功能** — 如果放置位置已经存在，就放在那里
5. **拆分为 MCP 服务器・独立仓库** — 如果是真正独立的能力，就放到核心之外
6. **新建仓库・新建常驻系统** — 最后手段。**需要 owner（人类）批准**。如果在 Epic 运行期间出现这种情况，应作为**[E-3](06-epic-lane.md) 的临时检查点而停止**（不追加到 E-3 的正式表格中）

- 拿不准就选靠上的一级（占用面积最小）。"因为下面一级更省事"不构成理由
- **选定一级后，同时决定要放置的东西的退场触发条件**（[LC-1](08-lifecycle.md) — 阶梯决定放置位置，LC-1 决定退场方式。二者配对使用）
- **同类第3个时要设计共用入口** — 当同一类别的集成积累到3个时，不要一个一个地往里加，而应设计一个共用接口，把现有实现作为第一个 provider 包裹进去。入口的设计属于边界变更，遵循 [L2-2](01-milestone-loop.md) 的边界 PR 先行原则

## R-6 方针要通过 check 来强制执行

**不能让不容违反的方针停留在"拜托了"的层面。** 被动式规则（.gitignore・文档・口头约定）只能拦住"一时疏忽"——想要强制执行的方针，应当升级为一旦违反就会变红的 check。

- **升级触发条件**: 同一方针被违反2次，就要通过 Issue 起草 check 化。**违反记录要留在 Issue 或各个家的事故记录中，并在第2次记录时起草**（这样计数后续才能被核实）
- check 应当**基于实体进行检测**（用内容・模式的本质来匹配，而不是靠目录名或扩展名的拼写 — 出处中有拼写变体绕过检测的实际案例）
- check 的姿态要与既有条文保持一致: **阻止合并的门要 fail-closed**（[FP-3](05-fail-posture.md) 的方向），**报告・汇总・通知类的管道要 fail-open**（[FP-4](05-fail-posture.md)）。check 不移动文件（[LC-5](08-lifecycle.md) — 只检测并停止・不自动修复也不自动退场）
- 审批类 check（人类标签等）要**验证审批的真实存在** — 不能仅凭正文或标签的存在就放行（[FP-8](05-fail-posture.md) 的方向）。审批验证可能存在局限（如身份共享环境等）— 此时应在 check 说明中明确写出局限，不能假装"已验证"（[FP-5](05-fail-posture.md)）
- 类型的正本见本仓库的 [templates/ci/](../templates/ci/)
