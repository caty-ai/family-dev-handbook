# R 驳回评判标准 — 接受什么、拒绝什么的分层

L 层（L2 / L1 / L0）是"如何推进"的契约，B 层是"如何委托"的契约，与此相对，R 层则规定了**什么会被合并、什么会被拒绝**这一意图层面的契约。用途有两个:

1. **为了制作方** — 让贡献（包括 Agent 发起的提案、任务、PR）能够对准目标
2. **为了一次判定** — 作为"什么情况下可以不经人类判断就关闭"以及同样重要的"什么情况下不可以关闭"的指导方针

规范性因条款而异: **R-1 / R-4 / R-5 / R-6 是契约**，**R-2 / R-3 是接受判断的基准清单**，以 R-2 / R-3 为依据的驳回执行始终要经过 R-1 的权限规律（价值判断由 owner 专断）。

每条规则附有稳定的 rule ID（`R-1`〜`R-6`），条目以 ①②③… 引用（与 [E-6](06-epic-lane.md)① 格式相同）。摘要一侧（[docs/04](04-adoption.md)）引用此 ID。无法验证时的姿态见 [docs/05](05-fail-posture.md)。

## R-1 自动驳回的 3 个理由 — 价值判断由 owner 专断

**适用对象是已记录的提案（Issue、PR、作为记录提交的任务提案）**。可以不经人类判断就驳回这些提案的情形，**仅限机械地能分黑白的 3 个理由**。每个理由只有在满足成立条件并附有证据时才成立:

1. **已经存在于 main 中**（implemented on main）— 必须指出该行为存在于当前 main 中的具体 commit 或行。"有功能上相似的东西"不属于本理由（那属于价值判断 = owner 专断）
2. **无法复现**（cannot reproduce）— **仅限 bug 报告**。需留下针对当前 main 的复现尝试记录（命令 / 步骤・观测结果・日期）。信息不足不是驳回理由 — 应询问并保留
3. **内容不成立**（incoherent）— 仅限矛盾、空白、垃圾内容等无法读出实质主张的情况，且**经过 1 次询问后仍无法读出**才成立。仅仅是阅读起来费劲的提案不属于此类

- "不需要・与方针不符・超出范围"等**基于价值判断的驳回由 owner（人类）专断**。Agent 只能做到附上建议和依据后上报（以 R-2 / R-3 为依据的驳回也一样 — 不属于这 3 个理由）
- **拿不准就不要关闭** — "关闭"是权限行使，无法验证时应向权限收缩的方向（保持打开、交给 owner）倾斜（[FP-7](05-fail-posture.md) 的方向）。一次判定的工作是读懂设计意图，**不要把正当的贡献误关**
- **记录**: 已经立起 lane 的提案（已声明 WIP）的终止遵循 [L1-4](02-issue-loop.md) 的 5 个词汇。**在 lane 立起之前被驳回的提案不使用 lane 词汇**，只记录关闭理由（3 个理由之一 + 上述证据，或指向 owner 裁定的链接）
- **重新打开是非对称的**: 基于 3 个理由的关闭，一旦出现新证据，无需 owner 批准即可重新打开（重新打开是权限收缩的方向）
- 触及 R-4 中 4 种模式的提案，是自动关闭在 3 个理由下**不安全**的典型 — 应转交人类
- Epic 运行中的驳回判断应**异步转交给 owner**，且不停止该 lane（不增加 [E-3](06-epic-lane.md) 的停止点）

## R-2 欢迎的贡献 — 6 条

1. **针对整个问题类别修复真实的 bug** — 在当前 main 上复现症状，指出出现问题的具体行，不仅修复被报告的那一处，还要修复兄弟调用路径（与 R-4 的口诀相对）
2. **扩展末端・保守腰部** — 欢迎扩展末端（各产品・各家的功能）的贡献。抑制只针对腰部（家族共享的基础设施・所有人都要付出恒久成本的地方）。"footprint 最小化"说的是通向腰部的配线，而不是产品能否成长的问题
3. **已声明的重构即使 diff 很大也欢迎** — "每一行都能追溯到需求"这项检查适用于功能变更，而被声明为重构的变更需求本身就是抽取（热点拆分 = [L2-6](01-milestone-loop.md) 的投资）。**放宽的仅仅是对 diff 大小的怀疑** — 声明文件集合（[L0-2](03-git-protocol.md) default-deny）和 [L1-7](02-issue-loop.md)④ 的 diff 核对，即便是重构也绝不放宽（重构应该是通过广泛声明预计触及的文件来通过，而不是省略声明来蒙混过关）。广域重构的单独执行（[L2-5](01-milestone-loop.md)）・合并流程（[L0-7](03-git-protocol.md)）也照常适用
4. **扩展而非重复** — 在新增模块・manager・hook 之前，先确认现有工具是否够用（放置位置见 R-5）
5. **测试要主张不变式** — 检验"两份数据应当如何关联"，不要写把当前值（列表・件数・版本号硬编码）冻结下来的变更检测测试
6. **边界・传播・I/O 用真实路径验证** — 涉及解析链、配置传播、权限边界、外部 I/O 的变更，需要给出实际跑通该路径的 E2E 证据。不要把只靠 mock 的 green 当作完成。**本条是选取证据的指南，merge gate 要求的正本仍是 [L1-7](02-issue-loop.md)**（不增加要求）

## R-3 即使做得很好也要拒绝的 — 7 条

这不是质量门槛，而是作为**结构性判断**而拒绝的事项。即使做得很好，拒绝的理由也不会因此消失。**以本条为依据的驳回不属于 R-1 的 3 个理由 — 执行始终由 owner 专断**，Agent 只能做到指出相关疑虑并上报:

1. **投机性的基础设施** — 没有具体使用者的 hook・回调・扩展点。如果有明确表明的实际使用场景，就不算投机（即使使用者在别的 repo 也可以）
2. **为非秘密配置新增环境变量** — 秘密的存放处（.env 等）专用于秘密。行为配置（超时・阈值・flag・显示方式）应放入配置文件
3. **明明现有工具已经够用却新建的 skill・hook・常驻系统** — 没有从 R-5 的阶梯最小一级开始考虑过的新建项一律拒绝
4. **给本应完整阅读的内容开偷懒阅读的后门** — 不要给 Agent 应当完整阅读的内容（skill、prompt、操作手册）的加载器加上翻页・摘录选项。这会导致只读第一页就跳过其余部分
5. **破坏了本应保护的功能的"修复"** — 扼杀功能目的的缓解措施是错误的缓解措施。在限制行为之前，先读懂原始 commit 的意图（`git log -p -S`）
6. **没有证明的接线・未经许可的非秘密遥测** — 没有 E2E 证明就接入的代码・运行时从未走到过的分支・没有 opt-in 门控的对外遥测 / 标识符附加（**包括非秘密的使用信息**）。秘密信息的对外发送不属于本条对象，**遵循 [E-5](06-epic-lane.md) 及各家的秘密规律 — 本条不改变 E-5 封闭禁止列举的范围**
7. **把外部工具・他人产品揽入核心代码树** — 保守负担会永久性地压到这一边。应放在 wrapper・隔离的存放处（例如: 用于隔离的独立目录・外部管理的另一个 repo — 举例仅供参考、非规范性），不要放入核心。这是耦合与维护的判断，即使质量很高，关闭依然是关闭

## R-4 前提验证 — 在称之为 bug 之前

口诀: **"如果指不出 bug 出现的那一行，前提就未经验证"**

做得很好的变更最常被拒绝的原因不是质量，而是建立在**错误的前提**之上，或者把**刻意的设计当成了缺陷**。以下 4 种模式双向起作用 — 对 review 席位来说，它指明"该仔细审查哪里"；对一次判定来说，它指明"什么时候不能关闭":

1. **是刻意的设计，而不是缺陷** — 看似疏漏的限制往往是刻意为之。动手修复之前先问"这个隔离会不会正是设计所在?"，并读懂原始 commit 的意图
2. **前提对照实际的运行方式站不住脚** — 在接受说法之前，先追踪实际代码・运行时的实际行为。如果说不出修复会改变哪一行的行为，就是未经验证
3. **不存在本身在支撑着某种负荷** — 添加看似"明显缺失"的部分，有可能破坏该省略原本所保护的东西
4. **过度・已经过去的方针复活** — 超出已达成共识范围的扩展，或对刻意关闭方向的重提，即使能跑通也要拒绝。变更应限定在已达成共识的狭窄范围内，其余部分作为后续跟进提出

贯穿始终的原则: **在书写之前、合并之前，把主张和意图两者都对照代码库进行验证**。已确认的复现 + 行级说明，任何时候都胜过看似合理的说辞。对意图拿不准时，与其提出与设计相悖的修复，不如先去询问，这样更划算。

（具体实例可以用各家的事故记录替换 — 正文中的举例是非规范性的。委托 review 时，可以把这 4 种模式作为 [B-4](07-delegation-brief.md) "点名最坏的失败形态"的视角提前给出）

## R-5 放置位置的阶梯 — 恒久表面积在最小的一级

创建新能力时，层级越低，恒久性的表面积（所有人都要持续付出的成本）越大。**选择能正确解决问题的、编号最小的那一级**:

1. **扩展现有代码** — 如果只是已有事物的变体，新增的表面就是零
2. **脚本 / skill** — 能用 shell 表达的操作。不常驻・只在被调用时运行
3. **带条件门控的 hook** — 只有在满足前提条件时才出现的自动化
4. **在现有 repo 中新增功能** — 如果已经有放置的位置，就放进去
5. **拆分为 MCP server・独立 repo** — 如果是真正独立的能力，就放在核心之外
6. **新建 repo・新的常驻系统** — 最后的手段。**需要 owner（人类）批准**。Epic 运行中出现该情形时，应**作为 [E-3](06-epic-lane.md) 的临时检查点停止**（不追加到 E-3 的表格中）

- 拿不准就选上面的一级（表面积最小）。"下面一级更省事"不是理由
- **选定层级后，同时决定所放置事物的退出触发条件**（[LC-1](08-lifecycle.md) — 阶梯决定放置位置，LC-1 决定退出方式。两者成对使用）
- **同类第 3 个时设立共通接口** — 同一类别的集成积累到 3 个时，不要逐个塞入，而应设计共通接口，把现有实现包装为第一个 provider。接口的设计属于边界变更，因此适用 [L2-2](01-milestone-loop.md) 的边界 PR 先行原则

## R-6 方针用 check 来强制执行

**不能容忍被打破的方针，不要停留在"拜托了"的层面。** 被动的规则（.gitignore・文档・口头约定）只能防住"不小心"——想要强制执行的方针，应当升级为一旦被打破就变红的 check。

- **升级触发条件**: 同一方针被打破 2 次，就要通过 Issue 起草 check 化提案。**被打破的记录应留在 Issue 或各家的事故记录中，在第 2 次记录时起草**（使计数事后可以核实）
- check 应**通过实体检测**（不是靠目录名或扩展名的拼写，而是靠内容・模式的本质来匹配 — 出处中有被拼写差异绕过的实例）
- check 的姿态应与既有条文保持一致: **阻止合并的 gate 是 fail-closed**（[FP-3](05-fail-posture.md) 的方向），**报告・合成・通知的管道是 fail-open**（[FP-4](05-fail-posture.md)）。check 不移动文件（[LC-5](08-lifecycle.md) — 只检测并停止・不自动修复也不自动退出）
- 审批类的 check（如人类标签等）应**验证审批的真实存在** — 不能仅凭正文或标签的存在就放行（[FP-8](05-fail-posture.md) 的方向）。审批的验证可能存在局限（如身份共享环境等）— 此时应在 check 的说明中明确写出该局限，不能佯装"已验证"（[FP-5](05-fail-posture.md)）
- 类型的正本在本 repo 的 `templates/ci/` 中
