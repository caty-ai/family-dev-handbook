# R 驳回准则 — 接受什么、拒绝什么的分层

L 层（L2 / L1 / L0）是"如何推进"的契约，B 层是"如何委托"的契约，与此相对，R 层规定的是**什么会被合并、什么会被拒绝**这一意图层面的契约。用途有两个:

1. **面向创作方** — 让贡献（包括来自 agent 的提议、任务、PR）能够对准靶心
2. **面向一次判定** — 作为"何时可以不经人类判断而关闭"、以及同样重要的"何时不可以关闭"的指引

规范性因条目而异: **R-1 / R-4 / R-5 / R-6 是契约**，**R-2 / R-3 是接受判断的基准清单**，以 R-2 / R-3 为依据的驳回执行必须始终经过 R-1 的权限规律（价值判断由 owner 专属决定）。

每条规则附有稳定的 rule ID（`R-1`〜`R-6`），条款以 ①②③… 的形式引用（与 [E-6](06-epic-lane.md)① 同形式）。摘要一侧（[docs/04](04-adoption.md)）引用该 ID。无法验证时的姿态见 [docs/05](05-fail-posture.md)。

## R-1 自动驳回的3个理由 — 价值判断由 owner 专属决定

**适用对象为已记录的提议（Issue、PR、以记录形式提交的任务提议）**。可以不经人类判断而驳回的，**仅限机械上能分出黑白的3个理由**。每个理由只有在满足成立条件并附有证据时才成立:

1. **已存在于 main 中**（implemented on main）— 必须能用 commit 或具体行指出该行为已存在于当前 main 中。"存在功能相似的东西"不属于本理由（那是价值判断 = owner 专属决定）
2. **无法复现**（cannot reproduce）— **仅限于 bug 报告**。需留下针对当前 main 的复现尝试记录（命令 / 步骤、观察结果、日期）。信息不足不是驳回理由 — 应先询问再保留（HOLD）
3. **内容不存在**（incoherent）— 仅限于矛盾、空白、垃圾内容等无法解读出实质主张的情况，且**须经过1次询问后仍无法解读**时方可成立。仅仅是阅读费力的提议不属于此类

- 出于"不需要、与方针不符、超出范围"等的**价值判断驳回，由 owner（人类）专属决定**。agent 只能做到附上建议和依据后上报（以 R-2 / R-3 为依据的驳回也一样 — 不包含在3个理由之内）
- **拿不准就不要关闭** — "关闭"是一种权限行使，无法验证时应向权限收缩的方向（保持开放并交给 owner）倾斜（[FP-7](05-fail-posture.md) 的方向）。一次判定的工作是读懂设计意图，**不要误关正当的贡献**
- **记录**: 已经立起 lane 的提议（已声明 WIP）的终止，按 [L1-4](02-issue-loop.md) 的5词汇处理。**尚未立 lane 就被驳回的提议不使用 lane 词汇**，只记录关闭理由（3个理由中的哪一个 + 上述证据，或指向 owner 裁定的链接）
- **重新开启是非对称的**: 因3个理由而关闭的提议，一旦出现新证据，可以不经 owner 批准重新开启（重新开启是权限收缩方向的行为）
- 触及 R-4 四种模式的提议，是"用3个理由自动关闭并不安全"的典型情形 — 应交给人类
- Epic 运行期间的驳回判断，**在不停止 lane 的情况下异步交给 owner**（不要增加 [E-3](06-epic-lane.md) 的停止点）

## R-2 值得欢迎的贡献 — 6条

1. **针对真实 bug，按整个类别一并修复** — 在当前 main 中重现症状，指出出现的具体行，不只修复报告中的那一处，还要修复同类的兄弟调用路径（与 R-4 的口号相对）
2. **端可以扩展，腰要保守** — 扩展端（各产品、各家庭特有功能）的贡献值得欢迎。需要克制的仅限于腰部（家庭共享的基础设施、全员需为此长期付出成本的地方）。"占用面最小化"说的是通向腰部的接线问题，不是产品能否成长的问题
3. **声明为重构的改动，即便 diff 很大也值得欢迎** — "所有行都能追溯到需求"这一检查适用于功能变更，而对被声明为重构的改动，需求本身就是抽取（热点拆分 = [L2-6](01-milestone-loop.md) 的投资）。**被放宽的只是对 diff 大小的疑虑** — 声明文件集合（[L0-2](03-git-protocol.md) default-deny）与 [L1-7](02-issue-loop.md)④ 的 diff 比对，即使是重构也绝不放宽（重构是通过广泛声明将触及的文件预告清楚而获得通过，而不是省略声明就能通过）。广域重构的单独执行（[L2-5](01-milestone-loop.md)）、合并流程（[L0-7](03-git-protocol.md)）同样照常适用
4. **扩展而非复制** — 在新增模块、manager、hook 之前，先确认现有工具是否已经够用（放置位置见 R-5）
5. **测试断言不变量** — 检查"两份数据应如何关联"，不要写死当前值（列表、计数、版本号直接硬编码）的变更检测测试
6. **边界、传播、I/O 用真实路径验证** — 涉及解析链、配置传播、权限边界、外部 I/O 的改动，需给出跑通真实路径的 E2E 证据。不要把仅有 mock 的 green 当作完成。**本条只是证据选取的指引，merge 门槛要求的正本仍是 [L1-7](02-issue-loop.md)**（不增加要求）

## R-3 即便做得好也要拒绝的 — 7条

这不是质量标准，而是**结构性判断**下的拒绝。即便做得很好，拒绝的理由也不会因此消失。**以本条为依据的驳回不属于 R-1 的3个理由 — 执行始终由 owner 专属决定**，agent 只能做到指出可疑之处并上报:

1. **投机性基础设施** — 没有具体使用者的 hook、callback、扩展点。如果已有明确的实际用例，就不算投机（即便使用者在别的仓库）
2. **为非机密配置新增环境变量** — 存放机密的位置（.env 等）应专用于机密信息。行为配置（超时、阈值、开关、显示）应放入配置文件
3. **明明现有工具已够用却新建的 skill、hook、常驻系统** — 没有先按 R-5 的阶梯从最小的一档开始考量的记录的新建，应予拒绝
4. **给"应当完整阅读的内容"提供偷懒阅读的退路** — 不要给 agent 应该完整阅读的内容（skill、prompt、操作手册）的加载器加上翻页或摘录选项。这会导致只读第一页就跳过其余内容
5. **破坏原本应守护的功能的"修复"** — 扼杀功能目的的缓解措施是错误的缓解措施。在限制某个行为之前，先读懂原始 commit 的意图（`git log -p -S`）
6. **未经证明的接线、未经许可的非机密遥测** — 没有 E2E 证明就接线的代码、运行时从未走到过的分支、没有 opt-in 开关的对外遥测 / 标识附加（**包括非机密的使用信息**）。机密信息的对外发送不属于本条的适用范围，**遵循 [E-5](06-epic-lane.md) 以及各家庭的机密规律 — 本条不改变 E-5 封闭式禁止列表的边界**
7. **把外部工具、他人产品揽入核心代码树** — 维护负担会永久落到自己头上。应放在 wrapper、隔离的存放位置（例如: 用于隔离的目录、由外部管理的独立仓库 — 示例非规范性）中，不放入核心。这是耦合与维护上的判断，即使质量再高，该关闭还是要关闭

## R-4 前提验证 — 在称之为 bug 之前

口号: **"如果指不出 bug 出现的具体行，前提就是未经验证的"**

做得很好的改动被拒绝，最大的原因往往不是质量，而是建立在**错误的前提**之上，或是**把有意为之的设计当成了缺陷**。以下4种模式是双向起作用的 — 对 review 席位而言，它们指出"该重点核查什么"；对一次判定而言，它们指出"什么时候不该关闭":

1. **是有意为之的设计，而非缺陷** — 看似疏漏的限制往往是刻意设计的。修改前先问一句"这种隔离会不会正是设计所在？"，并读懂原始 commit 的意图
2. **前提在实际运行方式下站不住脚** — 在接受某种说法之前，先追踪实际代码、实际运行时的行为。如果说不清修复会改变哪一行的行为，就说明前提未经验证
3. **缺失本身在支撑着某种负载** — 看似"明显缺失"的部分一旦被补上，可能会破坏原本由这种省略所保护的东西
4. **做过头、已经被驳回过的方针的复活** — 超出已达成共识范围的扩展，或对已经刻意关闭的方向的重提，即便能跑通也要拒绝。改动应限制在已达成共识的狭窄范围内，其余部分作为后续跟进提出

贯穿始终的基调: **主张和意图，都要在动笔前、合并前对照代码库进行验证**。经过确认的复现 + 行级说明，永远胜过看似合理的说辞。对意图拿不准时，与其硬推一个与设计相悖的修复，不如先去问一问，成本更低。

这一证据水位同样适用于评审席位的意见: **指不出 path:line 或无法引用执行日志的意见不能被标记为 blocking**（作为 non-blocking 的担忧提出是自由的）。对于后续轮次新增的 blocking，[L1-3](02-issue-loop.md) 的禁止 ratchet 除了这一要求之外，**还**要求实证（复现或执行日志） — 这是两层约束，并非同一水位。

（具体案例可以用各家庭自己的事故记录替换 — 正文中的示例不具规范性。在委托 review 时，可以把这4种模式作为 [B-4](07-delegation-brief.md) 中"点名最坏失败形态"的视角前置说明）

## R-5 放置位置的阶梯 — 用最小的一档换取最小的永久占用面

创建新能力时，档位越靠下，永久性的占用面（全员要持续承担的成本）就越大。**选择能正确解决问题的、编号最小的那一档**:

1. **扩展已有代码** — 如果只是已有事物的变体，新增表面为零
2. **脚本 / skill** — 可以用 shell 表达的操作。不常驻，只在被调用时运行
3. **带条件门控的 hook** — 只有在满足预设条件时才出现的自动化
4. **在既有仓库中新增功能** — 如果已有合适的放置位置，就放在那里
5. **拆分到 MCP server、独立仓库** — 如果确实是真正独立的能力，就放到核心之外
6. **新仓库、新常驻系统** — 最后手段。**需要 owner（人类）批准**。若在 Epic 运行期间出现这种情况，**作为 [E-3](06-epic-lane.md) 的临时 checkpoint 停下**（不追加到 E-3 的正式表中）

- 拿不准时，选择上面的档位（占用面最小）。"下面的档位更省事"不是理由
- **选定档位的同时，也要一并决定所放置事物的退场触发条件**（[LC-1](08-lifecycle.md) — 阶梯决定放置位置，LC-1 决定退场方式。两者应配对使用）
- **同类第3个时，设计共用入口** — 当同一类别的集成累积到3个时，不要再逐一接入，而应设计共用接口，把既有实现作为第一个 provider 加以封装。入口设计属于边界变更，因此适用 [L2-2](01-milestone-loop.md) 的边界 PR 先行原则

## R-6 用 check 强制执行方针

**不能让"不容违反"的方针停留在"拜托遵守"的层面。** 被动式规则（.gitignore、文档、口头约定）只能防住"不小心"的情况 — 想要强制执行的方针，应升级为一旦被违反就会变红的 check。

- **升级触发条件**: 同一方针被违反2次时，通过 Issue 立项 check 化。**违反记录应留存在 Issue 或各家庭的事故记录中，在第2次记录时立项**（使计数能够事后被验证）
- check 应**基于实体检测**（不要用目录名或扩展名的拼写来匹配，而要匹配内容 / 模式的本质 — 出处中有被拼写变体绕过的实例）
- check 的姿态应与既有条文保持一致: **阻止合并的 gate 是 fail-closed**（[FP-3](05-fail-posture.md) 的方向），**报告、汇总、通知的管道是 fail-open**（[FP-4](05-fail-posture.md)）。check 不移动文件（[LC-5](08-lifecycle.md) — 只检测并停止，不做自动修复或自动退场）
- 涉及批准的 check（例如人类打的标签等），应**验证批准是否真实存在** — 不能仅凭正文或标签的存在就放行（[FP-8](05-fail-posture.md) 的方向）。批准的验证可能存在局限（例如共享身份的环境等）— 此时应在 check 的说明中明确标注该局限，不得假装"已验证"（[FP-5](05-fail-posture.md)）
- 类型的正本见本仓库的 [templates/ci/](../../../templates/ci/)
