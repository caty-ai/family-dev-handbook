# Issue-first 是什么——为什么要从 Issue 开始，而不是从对话开始

> 本页不是条文本身。条文正文在 [docs/01](01-milestone-loop.md)〜[docs/06](06-epic-lane.md)。
> 这里写的是那些条文**所依据的思路**。想在记住规则之前先了解为什么会这样的人，可以看这一页。

## 用对话下指令，会发生什么

你让 AI agent「把那个 bug 修一下」。修好了。第二天，你打开另一个 session。

agent 完全不记得昨天的事。修了什么、为什么选那种修法、验证到什么程度，这些都随着关闭的终端一起消失了。留下来的只有代码的改动，通向这个改动的判断却没有留下来。

人与人之间也会发生类似的事。在聊天里定下来的事，会随着滚动条流向远方。不同的是，对 AI 来说，连「让它想起来」都做不到。**每次都是从零记忆开始。**

而且现在，动手的 agent 不一定只有一个。如果有两个同时在跑，双方都没有办法知道对方在做什么，就会在不知情的情况下碰到同一个文件。

## Issue-first 是什么

要做的事只有一件。

**在动代码之前，先建一个 GitHub Issue。**

仅此而已。不需要特殊工具，也不需要额外的服务。实现从 Issue 建立之后才开始。没有 Issue 的实现，不做。

## 为什么这样做有效

建了 Issue 之后，**交接的正本就固定在了一个地方。**

工作结束时，会留下两样东西：Issue 的正文（打算做什么、怎样算结束），以及 Pull Request 的差异（实际改了什么）。只要这两样齐全，中途加入的任何人——不管是别的人，还是别的 agent，还是失去记忆的明天的自己——只要读 Issue 就能接着做下去。

对话的历史会消失。agent 的记忆也会消失。**Issue 和 PR 不会消失。** 所以把它定为唯一的正本。

这不是信任的问题，而是存放位置的问题。不是因为谁健忘才去写 Issue，而是**提前定好一个以「会遗忘」为前提的存放位置**。

## Issue 里要写什么

必填的只有三项（条文中为 [`L1-2`](02-issue-loop.md)）。样式的正本在 [templates/issue-template.md](../templates/issue-template.md)。

**1. 目的（Why）** —— 为什么要做。不做的话会有什么问题。

这是写给几天后的自己，以及明天加入进来的另一个 agent 看的。如果「要做」这个决定的理由没有留下来，中途出现判断分歧时就没有地方可以回头查证。

**2. 完成条件（Done when）** —— 怎样才算结束。

用 checkbox 写，并写成**机器或实机能够判定的形式**。不要写「能正常运作」，而要写「测试通过」「在实机上能显示出来」。这是让「完成了」可被验证的唯一方法。正因为有这一项，merge 时才能逐条核对 PASS / FAIL（[`L1-7`](02-issue-loop.md)）。

**3. 预计会动到的文件 / 模块** —— 打算动哪些文件。

这一项不是为了自己，而是**为了其他工作**而设的。如果在着手之前就能看出两项工作要动的文件集合不交叉，就可以并行推进。看不出来的话，就不并行（[`L2-3`](01-milestone-loop.md) / [`L2-4`](01-milestone-loop.md)）。因为是预计，猜错也没关系。着手时会重新宣告确定版本。

## 不需要 Issue 的情况

不是所有事都要建 Issue。以下不在此列（[`L1-1`](02-issue-loop.md)）。

- typo 的单行修正
- 非代码文件（md / json / yaml 等）
- git 管理之外的临时脚本
- 探索、阅读、对话（不做任何改动的工作）

犹豫的时候，可以这样想：**如果可能会跨多个 session，就建 Issue。** 如果当场就能结束，就不需要。

## 和 AI 搭配后，会有什么变化

Issue-first 并不是为 AI 而生的思路。在软件开发中早已被使用。只是，和 AI agent 搭配之后，出于三个原因，它的价值会大幅提升。

- **记忆从零开始** —— 人类还有「说起来上周……」，但 agent 没有。Issue 会成为唯一的记忆
- **同时有多个在动** —— 如果不宣告谁在动什么，冲突就只能靠运气
- **自己申报「完成了」** —— 要防止未经验证就报告完成，唯一的办法就是在着手之前先写好完成条件

## 常见疑问

**小修改也每次都要建 Issue 吗？**

不需要。就像上面「不需要 Issue 的情况」里写的那样。判断标准是是否会跨多个 session。

**Issue 会不会太多？**

会增多。但真正会造成困扰的是「一直开着不关的 Issue」，已关闭的 Issue 反而是有用的记录。之所以只用五个词（WIP / HOLD / MERGED / SUPERSEDED / ABANDONED）来表示 lane 的状态，就是为了一眼分清哪些还开着、哪些已经结束（[`L1-4`](02-issue-loop.md)）。

**一个人开发的话，也有意义吗？**

如果用 agent，就有意义。即使是一个人，跨越 session 的那一刻也会产生交接。反过来说，如果只做在单个 session 内就能完结的工作，Issue-first 的效果就几乎不存在。

**写 Issue 的时间是不是浪费？**

要写的只有三项。不写就动手的话，之后要花时间去重新拼凑「我到底确认过什么」「做到哪一步了」。哪种更划算取决于工作的长短，工作越短，越不需要 Issue。所以才提前定好了「不需要的情况」。
