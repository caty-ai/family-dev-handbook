# Issue-first 是什么——为什么要从 Issue 而不是对话开始

> 本页不是条文。条文正文在 [docs/01](01-milestone-loop.md)〜[docs/03](03-git-protocol.md) 和 [docs/05](05-fail-posture.md)〜[docs/08](08-lifecycle.md) 中。
> 这里写的是这些条文所**依据的思考方式**。适合想在记住规则之前先了解其原因的人阅读。

## 用对话下达指令,会发生什么

拜托 AI agent"把那个 bug 修一下"。修好了。第二天,打开另一个 session。

agent 完全不记得昨天发生的事。修了什么、为什么选那种修法、验证到什么程度,都随着关闭的终端一起消失了。留下来的只有代码变更,而通往那个结果的判断过程并没有留下。

人与人之间也会发生类似的事。聊天中决定的事会随着滚动条流向远方。不同的是,对 AI 来说连"让它想起来"这个选项都没有。**每次都是从零记忆开始。**

而且现在,那个 agent 未必只有一个。当两个 agent 同时行动时,双方没有手段知道对方在做什么,却可能同时触碰同一个文件。

## Issue-first 是什么

要做的事只有一个。

**在动代码之前,先建立一个 GitHub Issue。**

仅此而已。不需要特殊工具,也不需要额外的服务。实现工作从 Issue 建立之后才开始。没有 Issue 的实现不做。

## 为什么这样做有效

建立 Issue 之后,**交接的正本就固定在一个地方了。**

工作结束时,会留下两样东西:Issue 正文(打算做什么、什么算完成)和 Pull Request 的 diff(实际改动了什么)。只要这两者齐全,中途加入的任何人——无论是别的人、别的 agent,还是失去记忆的明天的自己——只需读 Issue 就能接着做下去。

对话记录会消失。agent 的记忆也会消失。**但 Issue 和 PR 不会消失。** 所以就把它们定为唯一的正本。

这不是信任的问题,而是存放位置的问题。不是因为谁健忘才写 Issue,而是**预先确定一个假设"会遗忘"的存放位置**。

## Issue 里要写什么

必写项目只有三个(条文中为 [`L1-2`](02-issue-loop.md))。样式的正本在 [templates/issue-template.md](../templates/issue-template.md)。

**1. 目的(Why)** —— 为什么要做。不做的话会有什么困扰。

这是写给几天后的自己,以及明天加入进来的另一个 agent 看的。如果没有留下"要做"这个决定的理由,一旦中途出现判断分歧,就没有地方可以回去参照。

**2. 完成条件(Done when)** —— 什么状态算完成。

用勾选框写,并且要写成**机器或实机能判定的形式**。不要写"能正常运作",而要写"测试通过""在实机上能显示"。这是让"完成了"变得可验证的唯一方法。正因为有这一项,在 merge 时才能逐条核对 PASS / FAIL([`L1-7`](02-issue-loop.md))。

**3. 预计触及的文件 / 模块** —— 打算触碰哪些文件。

这一项不是为了自己,而是**为了其他工作**而写的。如果在着手前就能判断两项工作要触及的文件集合不交叉,就可以并行推进。如果无法判断,就不并行([`L2-3`](01-milestone-loop.md) / [`L2-4`](01-milestone-loop.md))。因为只是预测,所以猜错也没关系。着手时会重新宣告确定版。

## 不需要 Issue 的情况

并非所有事情都要建 Issue。以下情况不在范围内([`L1-1`](02-issue-loop.md))。

- typo 的单行修正
- 非代码文件(md / json / yaml 等)
- git 管理范围外的草稿
- 探索、阅读、对话(不改动任何东西的工作)

拿不准时,可以这样想。**如果可能跨越多个 session,就建 Issue。** 如果当场就能结束,就不需要。

## 与 AI 搭配后,会有什么变化

Issue-first 并不是为 AI 而诞生的思路。这是软件开发中早已使用的做法。只不过,与 AI agent 搭配之后,基于三个原因,它的价值会飙升。

- **记忆从零开始** —— 人类还有"话说上周"这种回忆,但 agent 没有。Issue 成了唯一的记忆
- **多个同时行动** —— 如果不宣告谁在触碰什么,冲突就只能听天由命
- **"完成了"是自我申报** —— 要防止未经验证的完成报告,唯一的办法就是在着手前先写好完成条件

## 常见疑问

**再小的修改也要每次都建 Issue 吗?**

不需要。按上面"不需要 Issue 的情况"处理。判断标准是是否可能跨越多个 session。

**Issue 会不会太多?**

会增多。但真正造成困扰的是"一直开着的 Issue",已关闭的 Issue 会作为记录发挥作用。之所以只用五个词(WIP / HOLD / MERGED / SUPERSEDED / ABANDONED)来表示 lane 的状态,就是为了一眼区分正在进行的和已经结束的([`L1-4`](02-issue-loop.md))。

**一个人开发的话,这也有意义吗?**

如果使用 agent,就有意义。即使只有一个人,一旦跨越 session 的瞬间,交接就会发生。反过来说,如果只做能在一个 session 内完结的工作,Issue-first 的效果就几乎没有。

**写 Issue 的时间不是白费吗?**

要写的只有三项。不写就开始的话,之后要重新拼凑"当时确认了什么""做到哪一步了",反而要花时间。哪种更划算取决于工作的长短,工作越短,越不需要 Issue。所以才事先定好了"不需要的情况"。
