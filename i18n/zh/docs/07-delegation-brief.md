# B 委托简报 — 让一次委托成为一份契约的层级

如果说 L 层（L2 / L1 / L0）是 lane 与人之间的契约，那么 B 层规定的则是**agent 向 subagent（实现 worker、review 席、其他 CLI agent）交付一次工作时，委托文本本身的契约**。每条规则都附有稳定的 rule ID（`B-1`〜`B-5`）。摘要侧（[docs/04](04-adoption.md)）会引用这些 ID。样式的正本见 [templates/brief-template.md](../templates/brief-template.md)。无法验证时的姿态见 [docs/05](05-fail-posture.md)。

背景: lane 的交接由 Issue 作为 SoT（[L1-1](02-issue-loop.md)）来保障，但**每一次委托的质量，仅靠 lane 规律是守不住的**。委托对象不持有这边的对话历史（fresh context），委托文本中没写到的事情，就等同于不存在。把委托文本本身变成一份小契约，就是 B 层的作用。

## B-1 三层简报的必须结构

对于实质性的委托（涉及代码、文档的实现 / 修改 / 生成），委托文本中必须包含以下三个部分:

1. **实现规格（Goal）** — 目标、约束、预先给出的上下文、可以触碰的范围
2. **实现检查（Self-verification）** — 交付前作业者自己要过一遍的验证清单
3. **评审标准（Reviewer criteria）** — 后续 review 环节会关注的角度

理由: 如果只给出规格，那么「做完了」这句话就变得无法验证。通过**在委托的当下**就给出「以什么为完成标准」（self-verification）和「该带着怀疑去看什么」（review 视角），就能让交付物凭证据而非凭口头声明来判定（与 [L1-7](02-issue-loop.md) 方向一致）。

补充: 涉及代码变更的简报，其「实现检查」应**将「新增/变更的测试及其运行结果」列为标准项目**（[T-3](10-test-ci-baseline.md)。若未新增测试，需依据 T-3 的闭合列举附上理由后报告）。

## B-2 适用条件 — 拿不准就加上

- **必须**: 涉及实现、修改、生成的委托。即使规模是 S，只要成果物会留在仓库里，就要加上
- **豁免**: 只读的搜索、调查、简短提问（成果物当场用完即弃的情况）
- 拿不准就加上（往重的一侧靠 — 与 [L2-1](01-milestone-loop.md) 的重量判定姿态一致）

## B-3 Issue 是正本 — 简报是派生物

- 简报中的 Goal / 完成条件 / 可触碰范围，要从对应 Issue 的 **Why / Done when / 预计要改动的文件**（[L1-2](02-issue-loop.md)）中派生出来
- 如果简报和 Issue 出现分歧，**以 Issue 为准**。发现分歧的人要先修正 Issue，再进行委托 — 不能放任二者默默偏离（与 [L1-8](02-issue-loop.md) 方向一致）
- 一个 Issue 派生出多份简报是正常的（实现、修改轮次、review 席各自对应不同的简报）

## B-4 上下文要预先给足 — 不要让对方自己去探索

- 委托对象所需要的事实（路径、规格、约束、禁止事项、环境的特殊习性）要**预先写进**简报里。不要指望委托对象自己去探索
- 理由: 探索的结果会因委托对象不同而摇摆不定。在 read-only 的席位或 sandbox 环境中，探索本身可能都做不到。预先给足上下文，是让 fresh context 和 read-only 情况下都能保持同等质量的唯一方法
- 委托 review 时要**明确指出最坏的失败形态**（「这次变更最糟糕的情况是发生 ◯◯」）。这比单纯说「找找看有没有 bug」更能让检测目标聚焦
- 在需要 blind 的委托（独立 review 席）中，**不要混入**其他席位的指摘或自己事先的分析。预先给出的应该是事实，而不是结论

## B-5 格式要保持在机器可检查的形态

- 三个部分要保持**用固定的标题字符串就能被机器判定**的形态（不要把它们溶解进自由描述里）。标题字符串各团队可以自行本地化，但一旦定下来就要固定
- 建议在委托工具一侧设置检查（hook 等），在着手前就拦截缺失项。检查的具体实现不在本手册的范围内（属于各团队自己的工具层）
- **即使在没有检查的环境中，B-1〜B-4 作为契约依然有效** — fail-open 并不意味着「不需要格式」（与 [docs/05](05-fail-posture.md) 方向一致）
