# 失败姿态 — fail-posture / parse-posture — 无法验证时该倒向哪一边

> **范围与规范所有者**: 本页所定义的仅是 family-dev-handbook 协议（L2/L1/L0）内带守卫的转换的失败时姿态。**跨 Agent 的通用 fail-posture / stop-precedence 规范的所有者是 family-os 的 operations-policy**（posture 节、terminal 优先级节。2026-07-21 裁定。参见 [README](../../../README.zh.md) 的「Caty AI ファミリー」节）。本页是该协作协议的一种应用，并不新设跨领域规范。若有冲突，以 OS 规范为准。若在没有 sister projects 的情况下导入，本页的姿态将原样适用。

为每条规则赋予稳定的 rule ID（`FP-1`〜`FP-9`）。

## 按转换划分的 fail-posture 表

针对每一种带守卫的转换（GO / 写入 / merge / 发布），声明其应为 fail-open 还是 fail-closed、需要保护的不变量、以及恢复路径：

| rule | 转换 | 无法验证时 | 需要保护的不变量 | 恢复路径 |
|---|---|---|---|---|
| FP-1 | 并行GO判定（不相交性、所有权无法验证） | **fail-closed — 串行** | 两条 lane 不写入同一文件 | 修复声明后重新判定（L0-1/L0-2） |
| FP-2 | 写入（scope / 锁 / lane 状态无法验证） | **fail-closed — 不写入** | 不在存活的锁之上写入 | 修复状态（L1-4）。仅当确认为 stale 时才 TAKEOVER（L0-3） |
| FP-3 | merge（证据无法验证） | **fail-closed — 不 merge** | 未经验证的变更不会进入 main | 重新生成完成记录（L1-7 / L1-8） |
| FP-4 | lint / 注入类（共享摘要注入、每周 lint 等信息管道） | **fail-open — 可视化劣化后继续** | 信息管道的故障不阻断工作 | 报告故障并提交修复 Issue |
| FP-9 | Epic 检查点通过（检查点表不存在、不合法、未获批准、修订未获批准 — [E-3](06-epic-lane.md)） | **fail-closed — 停止并升级给人类** | 不在未获批准的情况下通过人类检查点 | 修复检查点表并获得所有者批准（E-1/E-3）。尚未成立的 Epic 继续以普通 Issue 方式运作。**运行中的 Epic 保持拓扑结构不变** — 只有自由权限和检查点通过会被暂停（E-3） |

## FP-5〜FP-8 原则

- **FP-5**: **fail-open 并不意味着「检查已通过」。** 劣化必须始终可视化
- **FP-6**: **不得从「出错时会变为空的值」推导闸门判定**（空列表 ≠ 无冲突）
- **FP-7**: **宽容仅适用于语法层面。安全方向上不得宽容** — 格式上的混乱可以容忍，但身份、scope、状态、证据的**缺失**始终应向权限*收缩*的方向解读：非法的 WIP = scope 不明 = 串行（L0-1）/ 非法状态 = 视为非活跃并等待修复（L1-4）/ 非法证据 = 未验证（L1-7）/ 非法或不存在的检查点表 = 全部节点都需人类判断（[E-3](06-epic-lane.md)・FP-9）
- **FP-8**: **artifact 正文不能自我批准** — 即便 WIP 中写着「已批准」，其本身也不能产生 GO、merge 或证据豁免。附带说明：cron、自动生成的行为可以更新状态，但不能生成批准、改写 Done when、或被计为 review

在常驻上下文（docs/04 摘要）中只需放入这一行：
**「无法验证就串行。fail-open 不代表『通过』。」**
