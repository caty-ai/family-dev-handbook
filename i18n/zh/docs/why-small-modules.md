# 为什么要把模块拆小 —— 拆分是"对并行可能性的投资"

> 本页不是条文。条文正文在 [docs/01](01-milestone-loop.md)〜[docs/03](03-git-protocol.md) 以及 [docs/05](05-fail-posture.md)〜[docs/08](08-lifecycle.md) 中。
> 这里写的，是这些条文所**依赖的思考方式**。

## 能否并行，在着手之前就已经决定了

这份手册对并行的判定很简单。**如果两项工作所触及的文件集合不交叉，就可以并行**（[`L2-4`](01-milestone-loop.md)）。

但是，比如说，一个2,500行的界面文件里，布局、手势处理、引擎调用全都混在一起，会发生什么呢？无论想在这块区域做什么，都必然会触碰到这个文件。**做什么都会交叉，于是永远只能串行。**

这时候，问题不在于判定本身。**是拆分的方式，让判定无法通过。**

也就是说，"能否并行"并不取决于干劲或安排，而是在着手之前很久就已经决定了。**代码的形态，决定了并行可能性的上限。**

## 拆分不是"整理"，而是"投资"

通常，拆分重构被当作"让代码更易读""让代码更整洁"这类质量问题来处理，往往被排在功能开发之后。

这份手册的处理方式不同。多个职责混杂在一起的巨型文件（**热点，hotspot**）的拆分，会**作为对并行可能性的投资**，以独立的 Issue 优先起票（[`L2-6`](01-milestone-loop.md)）。

之所以称之为投资，是因为它能带来三样回报。

**1. 变得可以并行**

拆分之后，触及该区域的各个 Issue 之间就不再交叉了。**从拆分完成的那一刻起，该区域的并行就在结构上变得安全**（[`L2-6`](01-milestone-loop.md)）。一次拆分，会持续影响此后的所有工作。

**2. Agent 能专注于眼前的工作**

如果一个文件只有一个职责，Agent 需要读的就只有这一个。**读的内容越少，注意力就越不会分散，就越能专注于眼前的工作。** 无论用的是哪个模型，视野范围越窄，就越容易坚持到最后完成任务。

反过来，如果2,500行里混杂了3个职责，哪怕只想修复其中一个，也得把全部读一遍。两个无关的职责，每次都会占满上下文。

> **说明:** 这不是条文所规定的要求，而是设计意图。目前并没有测量出具体能带来多大效果的数字。

**3. 像积木一样，事后可以替换**

如果是按职责拆分的，出问题时只需拆下坏掉的那一个来修，不必动周围的部分。这种感觉更接近拼装积木的拆装，不需要动周围的东西。

这份手册在 merge 审查的评判标准中加入"**可回滚性（revert 可能性）**"（[`L1-3`](02-issue-loop.md)），以及 [`L2-2`](01-milestone-loop.md) 中强调"不要把边界的变更和功能的变更混在一起"，都是出于同样的理由。一旦混在一起，就无法只回滚其中一方。

所以拆分不是"以后再做的整理"，而是"要先做的投资"。

## "小"指的不是行数,而是职责的数量

如果把"模块小"理解成行数问题,判断就会出错。要看的是**同一处混杂了多少个职责**。

哪怕只有300行,如果混杂了3个职责,就会有3种 Issue 在那里交叉。哪怕有1,000行,如果职责只有一个,交叉的也只是同一种 Issue。

所以在并行安全地图（[templates/architecture-parallel-map.md](../templates/architecture-parallel-map.md)）的热点表中，不仅要写行数的大致参考，还专门有一栏用来记录"**混杂的职责**"。行数只是一个标记，不是判断的依据。

## 移动边界时,只做这一件事

改变模块拆分方式的工作 —— 也就是移动边界的工作 —— 会影响到所有其他工作。所以要区别对待（[`L2-2`](01-milestone-loop.md)）。

- 移动边界的 PR **只优先合并这一个**
- 在它被 merge 之前,该仓库暂停任何新的并行着手（串行区间）
- **边界 PR 本身要保持最小化。不要把边界的变更和功能的变更混在一起**

最后一条在实践中非常关键。如果边界的变更和功能的变更混在同一个 PR 里,审查方就无法判断"这处差异是出于边界的需要,还是功能的需要"。就算之后出了问题,也无法只回滚边界部分。

## 写在哪里

在每个仓库的 `ARCHITECTURE.md` 中放置"并行安全地图"（[`L2-6`](01-milestone-loop.md)，模板见 [templates/architecture-parallel-map.md](../templates/architecture-parallel-map.md)）。要写的是两张表。

- **模块边界表** —— 哪个路径承担哪个职责
- **热点表** —— 哪个文件职责过多,计划在哪个 Issue 中拆分

移动边界的 PR 一旦 merge，**要在同一个 PR 中同步更新这份地图**。因为一旦地图和实际情况出现偏差，并行 GO 判定所依据的材料就会变成谎言。

## 不需要自己设计

读到这里，你可能会觉得"难道要自己来做模块设计吗"。并非如此。

**只要把这份手册交给 Agent，该拆分的地方自然会以 Issue 的形式主动冒出来。** 机制有三个。

- **每次起 Issue 时，都要预测并写下会触及的文件**（[`L2-3`](01-milestone-loop.md)）。范围太广、无法预测的工作，届时会被当作不可并行处理。哪里堵塞，会在每次工作时暴露出来
- **遇到巨型文件时的处理步骤已经确定**（[`L2-6`](01-milestone-loop.md)）。因为写明了"先起拆分 Issue"，Agent 就会按这个步骤来做，不必每次都从零判断
- **新建时遵循1个子 Issue = 1个模块**（[`E-2`](06-epic-lane.md)）。从一开始就不容易让职责混杂

不过，**拆分这项工作本身依然会发生**。并不是读进去代码就会自动整理好。改变的是，拆分不再是"迟早要做的整理"，而是变成"想要并行时必然要走的路"。更准确的说法是：**它不会再被推迟**。

## 这份手册自身的拆分方式

这个仓库也是按同样的原则构建的。

- **条文按层分为一个文件一个** —— L2 = [docs/01](01-milestone-loop.md)、L1 = [docs/02](02-issue-loop.md)、L0 = [docs/03](03-git-protocol.md)、失败时姿态 = [docs/05](05-fail-posture.md)、Epic = [docs/06](06-epic-lane.md)、委托 brief = [docs/07](07-delegation-brief.md)、生命周期 = [docs/08](08-lifecycle.md)。就算是最长的一份，也只有100多行
- **条文和样式不混在一起** —— 注释格式和模板都分离放在 [templates/](../templates/issue-template.md) 中
- **引用通过稳定的 rule ID 进行** —— 文件之间通过像 `L2-4` 这样的 ID 互相指向。即使移动文件，引用也不会失效
- **同一份定义不放在两处** —— 高风险区域的定义只在 [docs/06](06-epic-lane.md) 中,用于分发的摘要区块只在 [docs/04](04-adoption.md) 中

最后一点尤其重要。如果同一份定义存在于两处,一旦只有一处被修改,就没人能分清哪个才是正确的。所以要先确定"正本只有一处",其余都只是引用。README 不持有路线图,而是把它交给 Issue 列表来承载,也是出于同样的理由。

## 常见疑问

**没办法一开始就拆得完美怎么办？**

拆不完美是正常的。所以才用"投资"这个说法。如果当前的拆分方式导致交叉，就把它作为拆分 Issue 起票，按顺序逐步偿还。不需要在着手之前把一切都整理好。

**拆得太小会怎样？**

文件数量会增加，一次改动会分散到多个文件中。这样一来就会变成"虽然不交叉，但要到处改动"的状态，导致审查变得难以跟进。判断的依据是职责数量，所以**如果只有一个职责，就不要拆分**。

**已有的巨型文件该怎么办？**

不需要立刻去动它。先把它记录到并行安全地图的热点表中，等到想在那块区域并行时，再优先通过拆分 Issue。记录本身，就是留给下一个做判断的人的交接。

**如果本来就是一个人开发，这些也有关系吗？**

有关系。只要同时运行两个 AI Agent，那就已经是并行开发了。而且，职责分得越清楚，一个 Issue 的"触及文件预测"就越容易写，[Issue-first](why-issue-first.md) 第3项的成本也会随之降低。
