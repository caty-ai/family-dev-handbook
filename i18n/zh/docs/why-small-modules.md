# 为什么要把模块拆小 —— 拆分是"对并行可能性的投资"

> 本页不是条文。条文正文在 [docs/01](01-milestone-loop.md)～[docs/06](06-epic-lane.md)。
> 这里写的是这些条文所**依据的思考方式**。

## 能否并行，在着手之前就已经决定了

本手册对并行的判定很简单。**只要两项工作触及的文件集合不交叉，就可以并行**（[`L2-4`](01-milestone-loop.md)）。

但是，比如一个2500行的界面文件里，布局、手势处理、引擎调用都混在一起，会怎么样呢？无论要在那个区域做什么，都必然会触及这个文件。**无论做什么都会交叉，于是永远只能串行。**

这时问题不在于判定本身。而是**切分方式导致判定无法通过**。

也就是说，"能否并行"不是取决于干劲或安排，而是在着手之前很久就已经决定了。**代码的形态决定了并行可能性的上限。**

## 拆分不是"整理"，而是"投资"

通常，拆分重构被当作"让代码更易读""让代码更整洁"这类质量问题来处理，会被排在功能开发之后。

本手册的处理方式不同。多个职责混杂在一起的巨型文件（**热点，hotspot**）的拆分，会**作为对并行可能性的投资**，以独立的 Issue 优先立项（[`L2-6`](01-milestone-loop.md)）。

之所以称为投资，是因为它会带来三样回报。

**1. 变得可以并行**

拆分之后，触及该区域的多个 Issue 之间就不再相互交叉。**从拆分完成的那一刻起，该区域的并行在结构上就变得安全了**（[`L2-6`](01-milestone-loop.md)）。一次拆分会持续对之后所有的工作起作用。

**2. 让 agent 能专注于眼前的任务**

如果一个文件只有一个职责，agent 需要读的就只有这一个。**读的内容越少，注意力就越不容易分散，能够专注于眼前的任务。** 无论用的是哪个模型，需要关注的范围越窄，就越容易坚持到最后完成任务。

反过来，如果2500行代码里混杂着3个职责，哪怕只想修复其中一个，也得把全部读一遍。两个无关的职责，每次都会占用上下文。

> **备注：** 这不是条文规定的要求，而是设计意图。具体能带来多大效果，目前没有测量过的数据。

**3. 可以像积木一样，事后替换**

如果按职责切分好了，出问题时只需拆下坏掉的那一个来修复。这更接近于拼装积木的感觉，不必动周围的部分。

本手册在 merge 评审的考察点中加入"**可 revert 性**"（[`L1-3`](02-issue-loop.md)），以及 [`L2-2`](01-milestone-loop.md) 中所说的"不要把边界变更和功能变更混在一起"，都是出于同样的理由。一旦混在一起，就无法只回退其中一方。

所以拆分不是"以后再做的整理"，而是"要先做的投资"。

## "小"不是指行数，而是指职责的数量

如果把模块小当成是行数的问题，就会判断失误。要看的是**共存于其中的职责数量**。

即使只有300行，如果混杂了3个职责，也会有3种类型的 Issue 在那里交叉。即使有1000行，只要职责只有一个，交叉的也只会是同一类型的 Issue。

因此，在并行安全地图（[templates/architecture-parallel-map.md](../templates/architecture-parallel-map.md)）的热点表格中，除了行数的参考值之外，还有一栏用来写"**共存的职责**"。行数只是一个标记，不是判断的依据。

## 变动边界时，只做这一件事

改变模块切分方式的工作——变动边界的工作——会影响所有其他工作。因此要区别对待（[`L2-2`](01-milestone-loop.md)）。

- 变动边界的 PR **只先通过一个**
- 在它被 merge 之前，该仓库暂停新的并行着手（串行区间）
- **边界 PR 本身要保持最小。不要把边界变更和功能变更混在一起**

最后一条在实务中很关键。如果边界变更和功能变更混在同一个 PR 里，评审方就无法判断"这段差异是出于边界的需要，还是功能的需要"。事后出了问题，也无法只回退边界部分。

## 写在哪里

在各个仓库的 `ARCHITECTURE.md` 中放置"并行安全地图"（[`L2-6`](01-milestone-loop.md)，模板见 [templates/architecture-parallel-map.md](../templates/architecture-parallel-map.md)）。要写的是两张表。

- **模块边界表** —— 哪个路径承担哪个职责
- **热点表** —— 哪个文件职责过多，计划用哪个 Issue 来拆分

变动边界的 PR 一旦 merge，**要在同一个 PR 中更新这张地图**。因为地图一旦与实际情况脱节，并行 GO 判定所依据的信息就变成了假的。

## 不需要自己去做设计

读到这里，你可能会想"难道要自己去做模块设计吗"。并非如此。

**只要把本手册交给 agent，需要拆分的地方就会由它自己以 Issue 的形式提出来。** 机制有三个。

- **每次拆分 Issue 时，都要预测并写下会触及的文件**（[`L2-3`](01-milestone-loop.md)）。范围太广而无法预测的工作，此时就会被视为不可并行。哪里卡住了，每次工作时都会浮现出来
- **遇到巨型文件时的处理流程是固定的**（[`L2-6`](01-milestone-loop.md)）。因为写明了"先立拆分 Issue"，agent 就会按这个流程走。不需要每次都从零判断
- **新建时遵循1个子 Issue = 1个模块**（[`E-2`](06-epic-lane.md)）。从一开始就不容易出现职责混杂

不过，**拆分工作本身依然会发生。** 并不是读进去之后代码就会自动变整齐。变化的是，拆分不再是"迟早要做的整理"，而是变成了"想要并行时必然要经过的路"。准确地说，是**不会再被一拖再拖了**。

## 本手册自身的切分方式

这个仓库也是按同样的原则构建的。

- **条文按层分为1个文件** —— L2 = [docs/01](01-milestone-loop.md)、L1 = [docs/02](02-issue-loop.md)、L0 = [docs/03](03-git-protocol.md)、失败时姿态 = [docs/05](05-fail-posture.md)、Epic = [docs/06](06-epic-lane.md)。即便是最长的一个，也就100多行
- **条文和样式不混在一起** —— 注释格式和模板另外放在 [templates/](../templates/issue-template.md) 中
- **引用通过稳定的 rule ID 进行** —— 文件之间通过 `L2-4` 这样的 ID 互相指向。即使移动文件，引用也不会失效
- **同一个定义不放在两处** —— 高风险领域的定义只在 [docs/06](06-epic-lane.md)，分发用的摘要块只在 [docs/04](04-adoption.md)

最后一条尤其关键。如果一个定义存在于两处，一旦只有其中一处被修改，就没人能分清哪个才是对的。所以要先决定"正本只有一处"，其他地方只做引用。README 不持有路线图、而是转交给 Issue 列表，也是出于同样的理由。

## 常见疑问

**一开始就无法切分得完美怎么办？**

切不完美是正常的。所以才用"投资"这个说法。如果按现在的切分方式会产生交叉，就把它作为拆分 Issue 立项，按顺序逐步偿还。不需要在着手前把一切都整理好。

**切得太小会怎么样？**

文件数量会增加，一次变更会分散到多个文件中。这时会变成"虽然不交叉，但要到处触碰"的状态，评审也会变得难以跟进。判断的依据是职责数量，所以**如果职责只有一个，就不要拆分**。

**现有的巨型文件该怎么办？**

不需要现在立刻去动它。先记录在并行安全地图的热点表中，等到想在那个区域并行时，再先把拆分 Issue 通过。记录本身，就是留给下一个做判断的人的交接。

**如果本来就是一个人在开发，这些还有关系吗？**

有关系。一旦运行了两个 AI agent，那就已经是并行开发了。而且，职责分得越清楚，一个 Issue 的"触及文件预测"就越容易写，[Issue-first](why-issue-first.md) 第三项的成本也会随之降低。
