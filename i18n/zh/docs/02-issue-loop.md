# L1 Issue 循环 — 完成单个任务的层级

为每条规则赋予稳定的 rule ID（`L1-1`〜`L1-11`）。摘要一侧（[docs/04](04-adoption.md)）引用这些 ID。无法验证时的姿态见 [docs/05](05-fail-posture.md)。

## L1-1 Issue-first 原则

仓库内的代码变更**以 GitHub Issue 为起点**。不进行没有 Issue 的实现（例外情况是 typo 等一行修改、非代码的 md/json/yaml、以及 git 管理之外的草稿）。

理由：Issue 正文 + PR diff 是**跨会话、跨 agent 交接的 SoT**（唯一可信源）。无论哪个 agent 中途接手，只要读 Issue 就能继续工作。

## L1-2 Issue 正文的必备三要素

使用[模板](../templates/issue-template.md)。

1. **目的 Why** — 为什么要做。背景，以及不做会造成什么问题
2. **完成条件 Done when** — 用复选框形式。用「测试 green」「实机确认」等可机器判定、可实机判定的形式表述
3. **将触及的文件 / 模块预测** — 作为 L2 并行 GO 判定的输入。着手时通过 WIP 评论重新宣告确定版

## 实现 → 审查 → 合并的流程

```
Issue 起票 → WIP宣言（L0-1）→ worktree で实现 → テスト/lint green
→ クロスレビュー → 指摘対応 → PR（完了記録 = L1-7 を本文に）
→ merge → Issue close → 安定点で git tag
```

## L1-3 交叉审查的原则

- **禁止 self-approve** — 不能仅凭实现者本人的批准就 merge
- **能通过 merge 的审查，必须实现者与审查者的模型或 agent 不同**（例如：Claude 实现 → GPT/GLM 审查，Codex 实现 → Claude 审查）。即使是同一模型，只要是**不同的 agent**，merge 就有效。同一模型、同一 agent，即便是不同会话，也不足以支撑 merge —— 不同会话所能满足的，仅限于 merge 以外的检查点
- 默认以 Round-1 审查者作为全程审查者。如需更换，须明确宣告，替换审查者要**重新审查当前候选的全部内容**（不允许拼接式的局部审查来完成 merge）
- implementer → reviewer 的循环持续进行，直到 blocking 指摘归零为止
- 审查关注点：正确性 / 边界（是否触碰了范围外的文件）/ 测试有效性 / 可 revert 性

## L1-4 Lane 状态 — 封闭的五状态词汇表

Lane 的状态通过在对应 Issue 上添加带标签的评论来宣告。**Lane 状态的唯一可信源是 Issue**（挂起的 PR 指向该 Issue）：

`WIP / HOLD / MERGED / SUPERSEDED / ABANDONED`

- **WIP 是需要明确宣告的状态，而不是默认值**
- `STUCK` **不是**第六种状态 —— 它是一个触发条件，唯一合法的出口是有效的 HOLD（或上报给人类）
- 状态缺失、未知或格式不正确的 lane，一律**视为非活跃状态（相当于 HOLD 的姿态：不写入），等待状态修复**。GO 判定不将该 lane 计为「空闲」——可能与宣告范围交叉的工作，须串行进行直到修复完成（[FP-1](05-fail-posture.md)）。不得从不正确的输入中伪造出有效的 HOLD 记录（HOLD 的必备字段无法从不正确的输入中生成）——下一个接触该 lane 的 agent，首要义务是**修复状态**，而不是写入（[FP-7](05-fail-posture.md)）
- **终止 / 阻塞声明优先于继续推进的压力**。同一次更新中若含有阻塞声明，该次更新中关于完成的主张一律无效

## L1-5 HOLD 的必备字段

HOLD **可恢复、非终态**。只有具备以下全部要素时才有效：

`owner / reason / review-by / lock disposition（在 review-by 之前保留锁还是释放锁）/ 剩余工作或后继者`

- **对锁的处置保持沉默的 HOLD 无效** —— 因为幽灵锁 / 双重写入这两种解读都会成为冲突路径
- 超过 review-by 会产生**可见的审查义务**（在每周的 ops probe 中重新浮现）。不会自动释放，也不会自动变为 ABANDONED
- `retained until review-by` **并不等于**「到 review-by 就自动释放」——review-by 是审查义务产生的日期，锁仍会保持，直到经过明确处置（HOLD 更新 / RELEASE / stale 化后的 TAKEOVER 流程）为止

## L1-6 重试次数有限

重试次数有限。用尽后须宣告**附带证据的 HOLD / ABANDONED**——用尽重试次数本身不能算作成功（若打算继续则用 HOLD，若要终止则用 ABANDONED。经由 STUCK 触发的出口，仍按 L1-4 所述，须为有效的 HOLD 或上报给人类）。

> 脚注（不属于契约正文，属于可调整的候选策略）：「同一失败连续出现两次（同一审查指摘或同一 CI 特征）⇒ STUCK」这一具体触发条件，仅为单一审查者的提议，不包含在本契约中。默认值交由维护者裁定或按各仓库自行选择。

## L1-7 完成证据合并门禁

只有当 PR 正文中包含满足以下条件的**完成记录**（[模板](../templates/issue-template.md)）时，才可以 merge 该 PR：

1. **将 Done when 的全部项目对应到 `PASS` / `FAIL` / 附理由的 `N/A`** —— 命令「跑过了」不等于 PASS。必需项目的 FAIL、或不附理由的 N/A，均会阻塞 merge
2. 每一项都要有**附带终态结果的永久性证据**（命令或手动步骤 + 观测结果 + 日期）。**以内联摘录为准**——仅凭记录本身就能读出终态结果。指向 CI 或外部日志的 URL 只是便利性的指针，仅有链接的证据不合格
3. 须明确写出**候选 commit SHA**——须与审查时的 PR head 一致（若在 merge 前发生变化，则按 L1-8 进行替换记录）
4. 对照宣告的文件集合与 `git diff --stat origin/main...<候选SHA>`（diff 中出现但清单中没有的文件属于 blocking —— [L0-6](03-git-protocol.md)）
5. 将实现者与审查者的身份关联起来，且**模型或 agent 必须不同**（L1-3）

**证据先于主张而存在。** 仅在本地取得成功的状态，不算作完成。

## L1-8 更正须以替换记录进行

对完成记录的更正，须**新发布一份完整的替换记录，并重新开放审查**。不允许悄悄编辑。

## L1-9 上游异构审查 —— 禁止 self-approve 原则向上游的扩展

- **Epic、架构变更、需求定义**（[L2-1](01-milestone-loop.md) 中偏重的一侧），须在**着手实现之前**通过异构交叉审查（席位见 L1-10，席位数见 L1-11）。时机为「可以在 EPIC Issue 起票之后，最迟不晚于第一个子 Issue 着手实现之前」进行一次（与 [E-6①](06-epic-lane.md) 采用同一时钟——不允许「起票前」与「着手实现前」两种解读并存）。因为最初的方向一旦偏离，下游全部都会随之偏离，所以审查要在越上游的地方越充分
- 该规则**仅适用于**偏重的一侧：单独的 Issue（bug fix、单一功能）不要求上游审查——仍旧只需实现审查（L1-3 / L1-11）。若将此范围扩大，会使按 Issue 逐一等待审查的情况死灰复燃，与速度目标（[docs/06](06-epic-lane.md)）相矛盾
- 若**上游审查的执行情况无法验证，则不得着手实现**（fail-closed —— 与停止写入的方向一致。记录须从 EPIC Issue 中链接——参见[模板](../templates/epic-template.md)的 kickoff 小节）

## L1-10 审查席位的异构性 —— 最高优先原则

- 审查席位须从**互不相同的模型**中选取，且须与**实现 writer 使用不同的模型**（「异构 N 席」指 N 个席位彼此互不相同。同一模型的多个不同 agent 不构成异构 N 席）
- **设计或实现了审查对象的人，不计入席位**（包括 orchestrator。让自己审查自己的设计这一席位,违背了 L1-3 / FP-8 的宗旨）。同一模型、不同 agent 的处理方式,按 L1-3 所述,作为 merge 的最低条件仍然有效,但不计入 L1-11 的席位数(唯一例外是 L1-11 的降级流程)
- 席位须由**该家庭中可启动的最高级别模型**担任。执行方式:各家庭须在本地配置(CLAUDE.md / AGENTS.md 等)中维护**审查席位合格模型名册**,handbook 要求满足:①存在该名册 ②不将名册之外的模型安排到席位上 ③名册的更新可见。至于名册中具体列入哪些模型(实名),不写入 handbook——因为模型会更替,不应让 PR 去追逐这份可信源
- 审查记录中必须留下 **requested / actual model**(可审计性——证据先于主张而存在)

## L1-11 席位数量的规模

本表所定的席位数,适用于**通过 merge 的实现审查**与**上游审查(L1-9)**(L1-3 是 identity 层面的最低条件,而席位数量由本表决定——两者并不矛盾)。Epic 内部子 Issue → epic 的关卡,同样**按子 Issue 的分量**参照本表(参见 [E-6②](06-epic-lane.md)——涉及高风险领域的子 Issue 优先适用 5 席)。

| 对象 | 席位数 |
|---|---|
| S / M(局部、单一功能) | 异构2席 |
| L / H(涉及多个模块、边界变更、新功能) | 异构3席 |
| **高风险领域**(定义见 [docs/06 开头](06-epic-lane.md)、单一定义、优先于规模判定) | 异构5席 |
| Epic、架构、需求定义的**上游审查**(L1-9) | 着手实现前采用 L/H 体制(若涉及高风险领域则为5席) |

- 缺席的席位须由**另一个异构席位**补充
- 若物理上无法凑齐异构席位的家庭(可启动的模型系列数量少于所需席位数),可以采用**降级流程**:同一模型、不同 agent 的席位 + **owner(人类)的明确批准** + 在审查记录中注明降级。未经批准的降级,视同席位数未达标
- 补充、降级之后仍未达标的,须以 **SEAT-WAIT** 停止(这是审查启动前的等待状态。与 L1-4 的 lane 状态 HOLD 是不同的用语,不适用 L1-5 的必备5字段——这一区分是为了避免每周 probe 将其误判为 HOLD)。SEAT-WAIT 须通过在对应 Issue 上评论使其可见,并写明**owner / 缺少的席位数 / 重试期限**这三项(缺少任何一项的 SEAT-WAIT 无效)。SEAT-WAIT 评论计入 [L0-3](03-git-protocol.md) 所定义的活动更新——因为将席位不足的 lane 判定为 stale → TAKEOVER 并不能增加席位,所以此举意在暴露根本原因,而不是拨动时钟
- 席位数字的调整,只能通过 handbook 的 PR 进行(与 [L0-3](03-git-protocol.md) 的 72 小时规则同等对待)

## 完成的定义

- 测试、lint 均已通过
- 附带 L1-7 完成记录的 PR 已经 merge,Issue 已经 close
- **线上仓库成为最新的可信源**(不会以仅在本地留有成果的状态结束)
- 若跨越多个会话,后续的入口(接下来要做什么)须留存在 Issue 评论或 handoff 中
