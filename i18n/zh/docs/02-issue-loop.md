# L1 Issue 循环 — 完成单项工作的层级

每条规则附带稳定的 rule ID（`L1-1`〜`L1-11`）。摘要侧（[docs/04](04-adoption.md)）引用这些 ID。无法验证时的姿态见 [docs/05](05-fail-posture.md)。

## L1-1 Issue-first 原则

仓库内的代码变更**以 GitHub Issue 为起点**。不进行没有 Issue 的实现（例外为 typo 等一行修复、非代码的 md/json/yaml、git 管理外的草稿）。

理由：Issue 正文 + PR diff 构成**跨 session、跨 agent 交接的 SoT**。无论哪个 agent 中途接手，只要读 Issue 就能继续工作。

## L1-2 Issue 正文的必备三点

使用[模板](../templates/issue-template.md)。

1. **目的 Why** — 为什么做。背景，以及不做会带来什么问题
2. **完成条件 Done when** — 用复选框形式。写成「测试 green」「实机确认」等可机器判定、可实机判定的形式
3. **将触及的文件 / 模块预测** — 作为 L2 并行 GO 判定的输入。着手时通过 WIP 评论重新宣告确定版

## 实现 → 审查 → 合并的流程

```
Issue 起票 → WIP宣言（L0-1）→ worktree で実装 → テスト/lint green
→ クロスレビュー → 指摘対応 → PR（完了記録 = L1-7 を本文に）
→ merge → Issue close → 安定点で git tag
```

## L1-3 交叉审查原则

- **禁止 self-approve** — 不能仅凭实现者本人的批准就 merge
- **通过 merge 的审查必须由实现者以外的模型或 agent 完成**（例如：Claude 实现 → GPT/GLM 审查，Codex 实现 → Claude 审查）。即使是同一模型，只要是**不同的 agent**，merge 就有效。同一模型、同一 agent 即使跨 session 也不足以支撑 merge — 跨 session 只能满足 merge 以外的检查点
- 默认由 Round-1 审查者担任跑完全程的审查者。若要更换，需明确宣告，替换的审查者须**重新审查当前候选的全部内容**（不允许在部分审查的基础上拼接后就 merge）
- 在 blocking 指摘归零之前，反复循环 implementer → reviewer
- 审查的着眼点：正确性 / 边界（是否触碰了范围外的文件）/ 测试的妥当性 / 可 revert 性

## L1-4 lane 状态 — 封闭的五状态词汇表

lane 的状态通过在对应 Issue 上打标签评论来宣告。**lane 状态的正本是 Issue**（挂起中的 PR 指向该 Issue）：

`WIP / HOLD / MERGED / SUPERSEDED / ABANDONED`

- **WIP 是需要明确宣告的状态，而非默认值**
- `STUCK` **不是**第六个状态 — 它是触发条件，唯一合法的出口是有效的 HOLD（或上报给人类）
- 状态缺失、未知或格式不正确的 lane，视为**非活跃状态（相当于 HOLD 的姿态：不写入），等待状态修复**。在 GO 判定中不将该 lane 计为「空闲」— 可能与已宣告范围交叉的工作，在修复完成前一律串行（[FP-1](05-fail-posture.md)）。不得从不正确的输入捏造出有效的 HOLD 记录（HOLD 的必备字段无法从不正确的输入中生成）— 下一个接触该 lane 的 agent 的首要义务是**修复状态**，而不是写入（[FP-7](05-fail-posture.md)）
- **终止 / 阻塞声明的优先级高于继续推进的压力**。若同一次更新中出现阻塞声明，该次更新宣称的完成即为无效

## L1-5 HOLD 的必备字段

HOLD **可恢复、非终态**。只有具备以下全部字段才有效：

`owner / reason / review-by / lock disposition（锁在 review-by 前是保留还是释放）/ 剩余工作或后继者`

- **对锁的处理未作说明的 HOLD 无效** — 因为无论按幽灵锁还是双重写入去理解，都会成为冲突路径
- 超过 review-by 会产生**可见的审查义务**（在每周 ops probe 中会重新浮现）。不会自动释放，也不会自动变为 ABANDONED
- `retained until review-by` **并不等于**「到 review-by 就自动释放」— review-by 是审查义务产生的日期，锁会一直保留，直到经过明确处置（更新 HOLD / RELEASE / stale 化后的 TAKEOVER 流程）为止

## L1-6 重试次数有限

重试次数有限。用完后需宣告**附带证据的 HOLD / ABANDONED** — 用完重试次数本身不能算作成功（若打算继续则用 HOLD，若要终止则用 ABANDONED。经由 STUCK 触发的出口，按 L1-4 所述，仍是有效的 HOLD 或上报给人类）。

> 脚注（不在契约正文内，属于可调整的候选政策）：「同一失败连续两次（同一审查指摘或同一 CI 签名）⇒ STUCK」这一具体触发条件是单个审查者的提案，不包含在本契约中。默认值交由维护者裁定或按仓库各自选择。

## L1-7 完成证据合并闸门

只有当 PR 正文中存在满足以下条件的**完成记录**（[模板](../templates/issue-template.md)）时，才可以 merge：

1. **将 Done when 的所有项对应到 `PASS` / `FAIL` / 附理由的 `N/A`** — 命令「跑过了」不等于 PASS。必需项的 FAIL、以及没有理由的 N/A 都会阻塞 merge
2. 每一项都要有**带终态结果的永久性证据**（命令或手动步骤 + 观测结果 + 日期）。**以内联摘录为正**——仅凭记录本身即可读出终态结果。指向 CI 或外部日志的 URL 只是便利性指针，仅有链接的证据不合格
3. 明确写出**候选 commit SHA** — 须与审查时点的 PR head 一致（若在 merge 前发生变化，需按 L1-8 补充替换记录）
4. 核对已宣告的文件集合与 `git diff --stat origin/main...<候选SHA>`（diff 中存在但清单中没有的文件为 blocking — [L0-6](03-git-protocol.md)）
5. 关联实现者与审查者的身份，且**模型或 agent 必须不同**（L1-3）

**证据先于主张而存在。** 只在本地取得成功的状态不算完成。

## L1-8 订正以 superseding record 的方式进行

完成记录的订正，需要**新发布一份完整的替换记录，并重新打开审查**。不允许静默编辑。

## L1-9 上游异构审查 — 禁止 self-approve 原则向上游的扩展

- **Epic、架构变更、需求定义**（[L2-1](01-milestone-loop.md) 中较重的一侧）需要在**着手实现之前**通过异构交叉审查（L1-10 的席位、L1-11 的席位数量）。时机为「可以在 EPIC Issue 起票之后完成，最迟不晚于第一个子 Issue 着手实现之前」这一个时点（与 [E-6①](06-epic-lane.md) 使用同一时钟 — 不允许「起票前」与「着手实现前」两种解读并存）。由于最初方向的偏差会波及下游全部内容，因此越上游审查越要厚重
- 仅适用于较重的一侧：单个 Issue（bug fix、单一功能）不要求上游审查 — 依旧只走实现审查（L1-3 / L1-11）即可。若把这一要求扩大，会让 per-Issue 的审查等待重新出现，与追求速度的目的（[docs/06](06-epic-lane.md)）相矛盾
- **若上游审查的实施无法验证，则不得着手实现**（fail-closed — 与停止写入同一方向。记录须从 EPIC Issue 中链接 — 参见[模板](../templates/epic-template.md)的 kickoff 小节）

## L1-10 审查席位的异构性 — 最高位原则

- 审查席位须从**彼此不同的模型**中选取，且须与**实现的 writer 不同的模型**（「异构N席」指N个席位彼此互异；同一模型的不同 agent 组成的N个席位不算异构N席）
- **设计或实现了被审对象的人不计入席位**（含 orchestrator。让自己审查自己的设计这一席位，违背了 L1-3 / FP-8 的宗旨）。同一模型、不同 agent 的处理方式按 L1-3 作为 merge 的最低条件是有效的，但不计入 L1-11 的席位数量（唯一例外是 L1-11 的降级流程）
- 席位应配置**该团队能够启动的最高级别模型**。执行方式：各团队须在本地配置（CLAUDE.md / AGENTS.md 等）中维护**审查席位适格模型名单**，手册要求：①存在该名单 ②不将名单外的模型安排到席位上 ③名单的更新是可见的。至于哪些模型应列入名单（具体名称），手册不作规定 — 因为模型会更替，不应让正本随 PR 追着变
- 审查记录中必须留存 **requested / actual model**（可审计性 — 证据先于主张而存在）

## L1-11 席位数量规模

本表所定的席位数量适用于**推动 merge 的实现审查**与**上游审查（L1-9）**（L1-3 是 identity 的最低条件，席位数量由本表决定 — 二者并不矛盾）。Epic 内部子 Issue → epic 的关卡，也**按子 Issue 的重量**引用本表（[E-6②](06-epic-lane.md)：触及高风险领域的子 Issue 优先适用五席）。

| 对象 | 席位数 |
|---|---|
| S / M（局部、单一功能） | 异构 2 席 |
| L / H（多模块、边界变更、新功能） | 异构 3 席 |
| **高风险领域**（定义见 [docs/06 开头](06-epic-lane.md)，单一定义，优先于规模判定） | 异构 5 席 |
| Epic、架构、需求定义的**上游审查**（L1-9） | 着手实现前采用 L/H 体制（若涉及高风险领域则为 5 席） |

- 缺席时以**另一个异构席位**补充
- 无法物理上凑齐异构席位的团队（可启动的模型系列数量少于席位数）可采用**降级流程**：同一模型、不同 agent 组成的席位 + **owner（人类）的明确批准** + 在审查记录中注明降级。未经批准的降级视同席位数量不足
- 即使经过补充或降级仍未达标，则以 **SEAT-WAIT** 停止（这是审查启动前的等待状态。与 L1-4 的 lane 状态 HOLD 是不同的词汇，不适用 L1-5 的必备五字段 — 这样区分是为了避免每周 probe 将其误判为 HOLD）。SEAT-WAIT 须通过在对应 Issue 上评论使其可见，并写明 **owner / 缺少的席位 / 重试期限**三项（缺少这三项的 SEAT-WAIT 视为无效）。SEAT-WAIT 评论计入 [L0-3](03-git-protocol.md) 所定的活动更新 — 因为对席位不足的 lane 做 stale → TAKEOVER 并不能增加席位，所以此处的目的是让根本原因可见，而不是推进时钟
- 席位数量的数字调整只能通过手册的 PR 进行（与 [L0-3](03-git-protocol.md) 的 72h 规则同等对待）

## 完成的定义

- 测试、lint 均已通过
- 附带 L1-7 完成记录的 PR 已 merge，Issue 已 close
- **线上仓库已成为最新的正本**（不会以只在本地取得成果的状态结束）
- 若跨越多个 session，后续的入口（接下来要做的事）须留在 Issue 评论或 handoff 中
