# L1 Issue 循环 — 完成单个任务的层级

每条规则都附有稳定的 rule ID（`L1-1` 至 `L1-11`）。摘要侧（[docs/04](04-adoption.md)）引用这些 ID。无法验证时的姿态见 [docs/05](05-fail-posture.md)。

## L1-1 Issue-first 原则

仓库内的代码变更**以 GitHub Issue 为起点**。不进行没有 Issue 的实现（例外情况是 typo 等一行修复、非代码的 md/json/yaml、git 管理外的临时草稿）。

理由：Issue 正文 + PR diff 是**跨会话、跨 Agent 交接的 SoT（真相来源）**。无论哪个 Agent 中途接手，只要读 Issue 就能继续工作。

## L1-2 Issue 正文的必备三要素

使用[模板](../templates/issue-template.md)。

1. **目的 Why** — 为什么要做。背景，以及不做会带来什么困扰
2. **完成条件 Done when** — 复选框形式。用「测试 green」「实机确认」等可机器判定、可实机判定的形式表达
3. **预计涉及的文件 / 模块** — L2 并行 GO 判定的输入。着手时通过 WIP 评论重新宣告确定版本

## 实现 → 评审 → 合并的流程

```
Issue 起票 → WIP宣言（L0-1）→ worktree で実装 → テスト/lint green
→ クロスレビュー → 指摘対応 → PR（完了記録 = L1-7 を本文に）
→ merge → Issue close → 安定点で git tag
```

## L1-3 交叉评审的原则

- **禁止 self-approve** — 不能仅凭实现者本人的批准就 merge
- **通过 merge 的评审，评审者的模型或 Agent 必须与实现者不同**（例：Claude 实现 → GPT/GLM 评审，Codex 实现 → Claude 评审）。即使是同一模型，只要是**不同的 Agent**，merge 就有效。同一模型、同一 Agent，即便是不同会话也不足以支撑 merge——不同会话只能满足 merge 以外的检查点
- 默认由 Round-1 评审者担任全程评审者。如需更换，需明确宣告，替换的评审者必须**重新评审当前候选的全部内容**（不允许拼接部分评审来 merge）
- 在 blocking 指出的问题归零之前，反复循环 implementer → reviewer
- 评审的关注点：正确性 / 边界（是否触碰了范围外的文件）/ 测试的有效性 / 可 revert 性

## L1-4 通道状态 — 封闭的 5 种状态词汇

通道状态通过在对应 Issue 上打标签的评论来宣告。**通道状态的正本是 Issue**（挂起的 PR 指向 Issue）：

`WIP / HOLD / MERGED / SUPERSEDED / ABANDONED`

- **WIP 是需要显式宣告的状态，而不是默认值**
- `STUCK` **不是**第六种状态——它是一个触发条件，唯一合法的出口是有效的 HOLD（或上报给人类）
- 状态缺失、未知或格式不正确的通道，一律**视为非活跃（按 HOLD 等同的姿态处理：不写入）等待状态修复**。在 GO 判定中不将此通道计为「空闲」——可能与宣告范围交叉的工作在修复完成前一律串行（[FP-1](05-fail-posture.md)）。不得从不正确的输入伪造出有效的 HOLD 记录（HOLD 的必备字段无法从不正确的输入中构造出来）——下一个接触该通道的 Agent 的首要义务是**修复状态**，而不是写入（[FP-7](05-fail-posture.md)）
- **终止 / 阻塞声明优先于继续推进的压力**。同一次更新中如果存在阻塞项，该次更新的完成主张即无效

## L1-5 HOLD 的必备字段

HOLD 是**可恢复、非终态**的。只有同时具备以下全部要素时才有效：

`owner / reason / review-by / lock disposition（锁在 review-by 之前保留还是释放）/ 剩余工作或后续方案`

- **对锁的处理方式不明确的 HOLD 无效**——无论读作幽灵锁还是双重写入，都会成为冲突路径
- review-by 超期会产生**可见的评审义务**（在每周 ops probe 中重新浮出）。不会自动释放、也不会自动变为 ABANDONED
- `retained until review-by` **不等于**「到 review-by 自动释放」——review-by 是评审义务产生的日期，锁会一直保留，直到有明确的处置（HOLD 更新 / RELEASE / stale 化后的 TAKEOVER 流程）

## L1-6 重试次数有限

重试次数有限。用尽后应**附带证据宣告 HOLD / ABANDONED**——用尽重试次数本身不能算作成功（若打算继续则用 HOLD，若打算中止则用 ABANDONED。经由 STUCK 触发的出口，按 L1-4 的规定仍是有效的 HOLD 或上报给人类）。

> 脚注（契约正文之外、可调整的候选策略）：「同一失败连续 2 次（同一评审指出的问题或同一 CI 特征）⇒ STUCK」这一具体触发条件，是单个评审者提出的建议，不包含在本契约中。默认值交由维护者裁定或各仓库自行选择。

## L1-7 完成证据合并门槛

只有 PR 正文中包含满足以下条件的**完成记录**（[模板](../templates/issue-template.md)）时，才能 merge：

1. **将 Done when 的所有项目对应到 `PASS` / `FAIL` / 附理由的 `N/A`**——命令「跑过了」不等于 PASS。必需项目的 FAIL、或没有理由的 N/A，都会阻塞 merge
2. 每个项目都要有**附带终态结果的可追溯证据**（命令或手动步骤 + 观测结果 + 日期）。**以内联摘录为准**——仅凭记录本身就能读出终态结果。指向 CI 或外部日志的 URL 只是便利性的指针，仅有链接的证据不合格
3. 明确写出**候选 commit SHA**——必须与评审时的 PR head 一致（若在 merge 前发生变化，按 L1-8 进行替换记录）
4. 将宣告的文件集合与 `git diff --stat origin/main...<候选SHA>` 进行核对（diff 中存在但清单中没有的文件属于 blocking——[L0-6](03-git-protocol.md)）
5. 关联实现者与评审者的身份，且**模型或 Agent 必须不同**（L1-3）
6. **记载 CI 状态**——不得在红色状态下 merge。已知且无关的红这一唯一例外条件见 [T-4](10-test-ci-baseline.md)

**证据先于主张而存在。** 仅在本地取得成功不算完成。

## L1-8 修正以 superseding record 的方式进行

对完成记录的修正，需要**新发布一份完整的替换记录，并重新开启评审**。不允许悄悄编辑。

## L1-9 上游异构评审 —— 禁止 self-approve 原则向上游的延伸

- **规模为 L / H / Epic**（即 [L2-1](01-milestone-loop.md) 规模判定标准中较重的一侧。架构变更、需求定义也包含在内）需要在**开始实现之前**通过异构交叉评审（席位见 L1-10、席位数见 L1-11）。规模定义以 L2-1 为正本——此处不重复照抄。对于 Epic，评审时机为「可以在 EPIC Issue 起票之后进行，最晚不超过第一个子 Issue 开始实现之前」，只需进行一次（[E-6①](06-epic-lane.md) 的同一时钟——不允许「起票前」和「开始实现前」两种解读并存）。由于最初方向一旦偏移，下游全部都会随之偏移，所以评审应当越靠上游越充分
- 该要求**仅**适用于较重的一侧：规模为 S / M 的单发 Issue（bug fix、单一功能）不需要上游评审——依然只需通常的实现评审（L1-3 / L1-11）。如果把这个范围扩大，per-Issue 的评审等待会卷土重来，与追求速度的目的（[docs/06](06-epic-lane.md)）相矛盾
- 若**无法验证**上游评审是否已实施，则不得开始实现（fail-closed——与停止写入同向。记录需从 EPIC Issue 链接——见[模板](../templates/epic-template.md)的 kickoff 小节。单发的 L / H 则从对应的 Issue 链接）

## L1-10 评审席位的异构性 —— 最高优先原则

- 评审席位需从**互不相同的模型**中选取，且必须与**实现方的 writer 使用不同的模型**（「异构 N 席」指 N 个席位彼此互异；同一模型的 N 个不同 Agent 不算异构 N 席）
- **对审查对象进行设计或实现的人不计入席位**（包括 orchestrator 在内。让某人评审自己设计的内容，这个席位违背了 L1-3 / FP-8 的宗旨）。同一模型、不同 Agent 的处理方式按 L1-3 的规定，作为 merge 的最低条件是有效的，但不计入 L1-11 的席位数（唯一例外是 L1-11 的降级流程）
- 席位应配置为**该团队可调用的最高级别模型**。执行方式：各团队应在本地配置（CLAUDE.md / AGENTS.md 等）中维护一份**评审席位合格模型名单**，手册要求：①名单必须存在 ②不得将名单之外的模型安排到席位上 ③名单的更新必须可见。至于名单里具体列哪些模型（实名），手册不作规定——因为模型会更替，不应让正本靠追踪 PR 来维护
- **实名目录条款**：家族共享的**实名模型目录属于数据层**，放在手册之外（这是前一条「实名不写进手册」的必然结果——分离不是被许可的形态，而是唯一合法的形态）。目录为**非规范**（成员可附上记录在案的理由加以覆盖；无记录的偏离即为不合规）——「**目录既不能把法所禁止的席位合法化，也不能让成员无法确认存活的模型变为可用。eligibility 由成员配置决定，席位数与约束由手册决定。**」目录不点名任何面板，也不携带可用性字段。共享目录的存在，不削弱本条的名单要求、席位规则、记录要求中的任何一项，也不削弱 L1-11 的席位数、降级流程、SEAT-WAIT 词汇
- **席位的系统（lineage）与 correlated-seats**：本条的「异构」要求的是**不同的模型**，而不是不同的系统——系统的处理由本项规定。**在机器选择席位的路径（抽签、替补）上，必须两两异系（pairwise-distinct lineage）或有记录在案的例外**。owner 点名固定的面板中出现同系席位，仅在有**记录在案的 correlated-seats 标志**时合法。机器路径的「记录在案的例外」与点名面板的 correlated-seats 标志是**同一个例外记录**，携带 `scope / pair / reason / approved_by / date / writer 条件` 6 个字段（缺字段的标志无效）。例外仅在记录的 `scope` 范围内有效。存放位置为各团队的本地配置（因含实名，不写进手册）。**应用了 correlated-seats 的评审记录必须明确注明——未注明的同系入席视同席位数不足。**另外，本项与 L1-11 的降级流程（同一模型、不同 Agent + owner 批准）是两回事——那边处理的是席位不足，这边处理的是系统重叠
- 评审记录中必须留下 **requested / actual model**（可审计性——证据先于主张而存在）

## L1-11 席位数量的分级

本表所定的席位数适用于**通过 merge 的实现评审**以及**上游评审（L1-9）**（L1-3 是身份方面的最低条件，席位数量由本表决定——两者并不矛盾）。Epic 内部子 Issue → epic 的关卡，也**按子 Issue 的重量级**套用本表（[E-6②](06-epic-lane.md)——涉及高风险领域的子 Issue 优先适用 5 席）。

| 对象 | 席位数 |
|---|---|
| S / M（局部、单一功能） | 异构 3 席（按成员（团队）逐个生效——见下） |
| L / H（多模块、边界变更、新功能） | 异构 3 席 |
| **高风险领域**（定义见 [docs/06 开头](06-epic-lane.md)，单一定义，优先于规模判定） | 异构 5 席 |
| 规模为 L / H / Epic 的**上游评审**（L1-9） | 开始实现前需具备 L/H 体制（若涉及高风险领域则为 5 席） |

- **S/M=3 席的生效按成员（团队）逐个进行**（per-member）：生效数据（3 个字段：`owner / 生效日 or 建立完成条件 / LC-1 触发器`）由**各团队的手册正本仓库（fork 的情况下为 fork 侧）中每团队一条的 pinned Issue** 持有。未到生效日的团队按旧下限（异构 2 席）即为合规——施行间隙作为「日程」而非「违规」处理（不要以即时全员生效的方式发布一部许多团队从第一天就无法满足的法——[R-6](09-rejection-rubric.md)：一部所有人从第一天就在违反的法，无法晋升为 fail-closed 的 check）。「建立完成」的证据是**可观测的事件**（一次记录在案的 fresh-context / read-only 真实评审，附 requested/actual model），而非主观判断。**没有 3 字段 pinned Issue、或字段缺失的团队，不得主张「生效前」状态**（[FP-7](05-fail-posture.md)——记录的缺失一律向权限收缩的方向解释）＝适用表中的下限（异构 3 席）（旧下限 2 席是仅在能指出记录在案的生效数据时方可主张的宽限）
- 缺席由**另一个异构席位**补充
- 物理上无法凑齐异构席位的团队（可调用的模型系列数量少于席位数）可使用**降级流程**：以同一模型、不同 Agent 的席位 + **owner（人类）的明确批准** + 在评审记录中注明降级。未经批准的降级视同席位数不足
- 即便经过补充、降级仍未达标，则以 **SEAT-WAIT** 停止（评审启动前的等待状态。与 L1-4 的通道状态 HOLD 属于不同的词汇，不适用 L1-5 的必备 5 字段——这样区分是为了避免每周 probe 将其误判为 HOLD）。SEAT-WAIT 需通过对应 Issue 的评论使其可见，必须写明 **owner / 缺少的席位 / 重试期限**三项（缺少这三项的 SEAT-WAIT 无效）。SEAT-WAIT 评论计入 [L0-3](03-git-protocol.md) 所定的活动更新——即便把席位不足的通道 stale 化后进行 TAKEOVER，席位也不会因此增加，因此重点是让根本原因可见，而不是推进时钟
- **SEAT-WAIT 只适用于车道（lane）**：不得对成员（团队）本身施加无期限的 SEAT-WAIT——没有对应 Issue、没有重试期限的等待无法满足上述三项要求，会脱离可见性。团队层面的「尚无法满足」通过上面的按成员生效数据来表达
- 席位数字的调整只能通过手册的 PR 进行（与 [L0-3](03-git-protocol.md) 的 72h 规定同等对待）

## 完成的定义

- 测试、lint 均已通过（唯一的明文例外见 [T-4](10-test-ci-baseline.md)）
- 带有 L1-7 完成记录的 PR 已 merge，Issue 已关闭
- **在线仓库已成为最新的正本**（不能以仅在本地取得成果的状态结束）
- 若跨越多个会话，续接的入口（接下来要做什么）需留在 Issue 评论或 handoff 中
