# L1 Issue 循环 — 完成单个工作的层级

每条规则都带有稳定的 rule ID（`L1-1`〜`L1-11`）。摘要一侧（[docs/04](04-adoption.md)）会引用这些 ID。无法验证时的处理姿态见 [docs/05](05-fail-posture.md)。

## L1-1 Issue-first 原则

仓库内的代码变更**以 GitHub Issue 为起点**。没有 Issue 就不进行实现（例外情况是 typo 等的单行修复、非代码的 md/json/yaml、以及不受 git 管理的草稿）。

理由：Issue 正文 + PR diff 是**跨 session、跨 agent 的交接 SoT（真相源）**。无论哪个 agent 从中途接手，只要读了 Issue 就能继续工作。

## L1-2 Issue 正文必须包含的3点

使用[模板](../templates/issue-template.md)。

1. **目的 Why** — 为什么要做。背景，以及不做会带来什么问题
2. **完成条件 Done when** — checkbox 形式。用「测试 green」「实机确认」等可机械判定、可实机判定的形式表述
3. **将触及的文件 / 模块预测** — L2 并行 GO 判定的输入。着手时通过 WIP 评论重新宣告确定版本

## 实现 → 评审 → 合并的流程

```
Issue 起票 → WIP宣言（L0-1）→ worktree で実装 → テスト/lint green
→ クロスレビュー → 指摘対応 → PR（完了記録 = L1-7 を本文に）
→ merge → Issue close → 安定点で git tag
```

## L1-3 交叉评审的原则

- **禁止 self-approve** — 不能只凭实现者本人的批准就 merge
- **能放行 merge 的评审，必须与实现者的模型或 agent 不同**（例如：Claude 实现 → GPT/GLM 评审，Codex 实现 → Claude 评审）。即使是同一模型，只要是**不同的 agent**，也可以有效放行 merge。同一模型、同一 agent，即便是不同的 session 也不足以放行 merge —— 不同 session 只能满足 merge 以外的检查点
- 默认以 Round-1 评审者作为完整走完全程的评审者。如需更换，须明确宣告，且更换后的评审者需**重新评审当前候选的全部内容**（不允许拼接部分评审来放行 merge）
- implementer → reviewer 的循环要持续，直到 blocking 指摘归零为止
- 评审的关注点：正确性 / 边界（是否触及了范围外的文件）/ 测试的有效性 / 是否可 revert

## L1-4 lane 状态 — 封闭的5种状态词汇

lane 的状态通过在对应 Issue 上打标签的评论来宣告。**lane 状态的真相源是 Issue**（挂起中的 PR 指向 Issue）：

`WIP / HOLD / MERGED / SUPERSEDED / ABANDONED`

- **WIP 是需要明确宣告的状态,而不是默认值**
- `STUCK` **不是**第6种状态 —— 它是一个触发条件，唯一合法的出口是有效的 HOLD（或上报给人类）
- 状态缺失、未知或格式不正确的 lane，将被**视为非活跃状态（相当于 HOLD 的姿态：不写入），等待状态修复**。在 GO 判定中不将此类 lane 计为「空闲」——可能与其宣告范围交叉的工作，在修复完成前一律串行处理（[FP-1](05-fail-posture.md)）。不得从非法输入伪造出有效的 HOLD 记录（HOLD 的必须字段无法从非法输入中生成）—— 下一个接触该 lane 的 agent，其首要义务是**修复状态**，而不是写入（[FP-7](05-fail-posture.md)）
- **结束 / 阻塞声明优先于持续施压**。如果同一次更新中出现了阻塞声明，该次更新中的完成主张即无效

## L1-5 HOLD 的必须字段

HOLD 是**可恢复、非终态**的。只有具备以下全部要素时才有效：

`owner / reason / review-by / lock disposition（锁在 review-by 之前保留还是释放）/ 剩余工作或后继安排`

- **对锁的处置保持沉默的 HOLD 无效** —— 因为无论按「幽灵锁」还是「双重写入」来解读，都会形成冲突路径
- 超过 review-by 会产生**可见的评审义务**（在每周的 ops probe 中会重新浮现）。不会自动释放，也不会自动变为 ABANDONED
- `retained until review-by` **不等于**「到 review-by 就自动释放」—— review-by 是评审义务产生的日期，锁会一直保留，直到明确的处置动作（更新 HOLD / RELEASE / stale 化后的 TAKEOVER 流程）为止

## L1-6 重试次数有限

重试次数是有限的。用尽后要宣告**附带证据的 HOLD / ABANDONED** —— 用尽重试次数本身不会转化为成功（若打算继续则用 HOLD，若要终止则用 ABANDONED。经由 STUCK 触发条件产生的出口，依 L1-4 所述，仍然是有效的 HOLD 或上报给人类）。

> 脚注（不属于契约正文，属于可调整的候选策略）：「同一失败连续出现2次（同一评审指摘或同一 CI 签名）⇒ STUCK」这一具体触发条件，是单个评审者提出的方案，不包含在本契约中。默认值交由 maintainer 裁定或各仓库自行选择。

## L1-7 完成证据合并门槛

只有当 PR 正文中包含满足以下条件的**完成记录**（[模板](../templates/issue-template.md)）时，才能 merge 该 PR：

1. **将 Done when 的全部条目对应到 `PASS` / `FAIL` / 附理由的 `N/A`** —— 命令「跑过了」不等于 PASS。必须项目的 FAIL、以及没有理由的 N/A，都会阻塞 merge
2. 每个条目都要有**带终态结果的持久证据**（命令或人工步骤 + 观测结果 + 日期）。**以内联摘录为准** —— 记录本身单独就能读出终态结果。指向 CI 或外部日志的 URL 只是便利性指针，仅有链接的证据不合格
3. 明确写出**候选 commit SHA** —— 需要与评审时的 PR head 一致（如果在 merge 前发生变化，需按 L1-8 出具替换记录）
4. 将宣告的文件集合与 `git diff --stat origin/main...<候选SHA>` 进行核对（diff 中存在但清单中没有的文件属于 blocking —— [L0-6](03-git-protocol.md)）
5. 关联实现者与评审者的身份，且**模型或 agent 必须不同**（L1-3）

**证据必须先于主张存在。** 只在本地取得成功的状态不算完成。

## L1-8 更正要用 superseding record

对完成记录的更正，需要**新公开一份完整的替换记录，并重新开启评审**。不允许悄悄编辑。

## L1-9 上游异构评审 —— self-approve 禁令向上游的延伸

- **规模为 L / H / Epic**（= [L2-1](01-milestone-loop.md) 规模判别标准中偏重的一侧。架构变更、需求定义也包含在内）的工作，需要在**着手实现之前**完成一轮异构交叉评审（席位见 L1-10，席位数见 L1-11）。规模定义的正本是 L2-1 —— 此处不重复照抄。Epic 场景下的时机为「可在 EPIC Issue 起票之后，最迟不晚于第一个子 Issue 着手实现之前」进行一次（[E-6①](06-epic-lane.md) 采用相同的时钟 —— 不并存「起票前」与「着手实现前」这两种解读）。因为最初方向一旦偏移，下游全部都会跟着偏移，所以越是上游，评审就要越厚重
- 适用范围**仅限**偏重的一侧：规模为 S / M 的单个 Issue（bug fix、单一功能）不需要上游评审 —— 仍旧只走照旧的实现评审（L1-3 / L1-11）。若将此范围扩大，会让 per-Issue 的评审等待重新出现，与速度目标（[docs/06](06-epic-lane.md)）相矛盾
- 若上游评审**是否已实施无法验证，则不得着手实现**（fail-closed —— 与停止写入是同一方向。记录需从 EPIC Issue 中链接过去 —— 见[模板](../templates/epic-template.md)的 kickoff 小节。单个的 L / H 场景则从对应 Issue 中链接)

## L1-10 评审席位的异构性 —— 最高优先原则

- 评审席位需从**彼此不同的模型**、且**与实现 writer 不同的模型**中选取（「异构N席」= N个席位彼此互不相同。同一模型的不同 agent 组成的N个席位，不算异构N席）
- **设计或实现受审对象的人不计入席位**（包括 orchestrator）。自己评审自己的设计，这样的席位违背了 L1-3 / FP-8 的宗旨。同一模型、不同 agent 的处理方式，按 L1-3 所述，作为 merge 的最低条件是有效的，但不计入 L1-11 的席位数（唯一例外是 L1-11 的降级流程）
- 席位应配备**该家中可启动的最高级别模型**。执行方式：各家需在本地配置（CLAUDE.md / AGENTS.md 等）中维护一份**评审席位合格模型名单**，handbook 要求做到：①存在该名单 ②不将名单之外的模型安排上席位 ③名单的更新是可见的。至于名单上具体列哪些模型（实名），handbook 不作规定 —— 因为模型会不断更替，不应让 PR 去追逐这份正本
- 评审记录中必须留存 **requested / actual model**（可审计性 —— 证据必须先于主张存在)

## L1-11 席位数量的规模化

本表中的席位数适用于**放行 merge 的实现评审**，以及**上游评审（L1-9）**（L1-3 是身份方面的最低条件，席位数量由本表决定 —— 两者并不矛盾）。Epic 内部的子→epic 关卡，也按**子级的重量**参照本表（[E-6②](06-epic-lane.md)——涉及高风险领域的子级优先适用5席）。

| 对象 | 席位数 |
|---|---|
| S / M（局部・单一功能） | 异构2席 |
| L / H（多模块・边界变更・新功能） | 异构3席 |
| **高风险领域**（定义见 [docs/06 开头](06-epic-lane.md)，单一定义，优先于规模判定） | 异构5席 |
| Epic・架构・需求定义的**上游评审**（L1-9） | 着手实现前采用 L/H 体制（包含高风险领域时为5席） |

- 缺席时用**另一个异构席位**补充
- 对于物理上无法凑齐异构席位的家（可启动的模型系列数量不足席位数），可使用**降级流程**：同一模型・不同 agent 的席位 + **owner（人类）的明确批准** + 在评审记录中注明降级。未经批准的降级视为席位数不足
- 补充、降级之后仍未达标的，则以 **SEAT-WAIT** 状态停下（这是评审启动前的等待状态，与 L1-4 的 lane 状态 HOLD 是不同的词汇 —— L1-5 的5个必须字段不适用于它，这一区分是为了避免每周的 probe 将其误判为 HOLD）。SEAT-WAIT 需通过在对应 Issue 上评论使其可见，并写明 **owner / 缺少的席位 / 重试期限**这3点（缺少这3点的 SEAT-WAIT 无效）。SEAT-WAIT 评论计入 [L0-3](03-git-protocol.md) 所说的活动更新 —— 因为对席位不足的 lane 做 stale → TAKEOVER 并不会增加席位，所以此举的目的不是推进时钟，而是让根本原因可见
- 席位数字的调整只能通过 handbook 的 PR 进行（与 [L0-3](03-git-protocol.md) 的72小时规则同等对待）

## 完成的定义

- 测试、lint 均已通过
- 带有 L1-7 完成记录的 PR 已经 merge，Issue 已经 close
- **线上仓库已成为最新的正本**（不能以成果只存在于本地的状态收尾）
- 若工作跨越多个 session，后续入口（接下来要做什么）已留在 Issue 评论或 handoff 中
