# LC 工作空间生命周期 — 把放置的物品的退出变成契约的层

L 层（L2 / L1 / L0）是"如何推进工作"的契约，与之相对，LC 层规定的是**物品从持续积累的地方（共享存储、工作目录、交接场所）中，何时、以何种方式退出**的契约。每条规则都附有稳定的 rule ID（`LC-1`〜`LC-5`），并在每条规则中用〔 〕明确标注适用对象。摘要一侧（[docs/04](04-adoption.md)）会引用这些 ID。无法验证时的姿态见 [docs/05](05-fail-posture.md)。

背景：即便只规定了写入一侧的规矩（Issue-first、写在哪里），**没有退出触发条件的东西必然会滞留**。与"如何放置"的规则相对应地，统一规定"如何退出"，这就是 LC 层。各阶段的名称以角色词为准，英文标签作为括号内的辅助标注。

## LC-1 期限触发原则〔所有引入方〕

**在放置物品时，必须同时确定退出触发条件（期限 or 完成条件）。**

按"没有触发条件的东西会变成永久保留"这一前提来处理。触发条件的形式既可以是期限（日期、天数），也可以是完成条件（合并后・分类后・汇总后）。如果放置场所的规约（命名、期限元数据）无法表达，就在放置时的 Issue 或声明中留一行说明。

## LC-2 单向生命周期〔拥有持续领域的家〕

**git branch / worktree 不在本章的适用范围内 — 清理的正本是 [L0-4 / L0-8](03-git-protocol.md)（合并后删除）。**

放置在持续领域中的物品，按**接收（intake）→ 在用（active）→ 完成（complete）→ 归档（archive）**的方向单向流动，不允许逆流。

- 归档（archive）是**不可变**的 — 进入的东西不改写、不删除
- 需要恢复时，不要从 archive 中删除，而是**作为新副本恢复到在用一侧**
- 在归档目的地要附上记录（manifest），说明"移动了什么・何时・为什么，如何恢复"

## LC-3 明文规定退出条件〔拥有持续工作空间 / 共享存储的家〕

针对以下**3种类型**，**在本地配置中明文规定带数值的退出条件**：

1. **大体积二进制文件** — 超过一定大小的非文本放置物（例：超过 1MB 则归档）
2. **明确的旧版本** — 以能看出是旧版本的名称・位置放置的物品（例：`旧〜/`・`.bak` 一经检测到就归档）
3. **定期物品的汇总** — 定期产生的原始文件汇总后的原件（例：生成月度摘要后，原始文件归档）

**数值的正本在本地配置一侧，本章正文中出现的数字（天数、大小等）均为"示例"，不计入契约**（MUST）。框架（3种类型都要有退出条件）是本章的契约，实际数值由本地持有 —— 这与把合格模型名单放在本地配置中的 [L1-10](02-issue-loop.md) 是同一种方式。

## LC-4 追加型存储的退出三件套〔仅限声明为追加型的存储，MUST〕

**追加型存储**＝声明为不对既有内容进行改写・删除的运营方式的保存场所。**本条仅对声明存储为追加型的家作为 MUST 适用。没有相应存储的家为 N/A** —— 不将此前提强加给所有引入方。

从追加型存储中退出（移动到归档）是追加型原则唯一的明文例外，必须按以下**三件套**进行：

1. **备份** — 在移动之前，对存储做快照
2. **移动** — 移动到归档目的地（不是保留原件的复制，而是移动）
3. **保留指针** — 在原位置留下指向"移到了哪里・何时・为什么"的指针

**退出的实际操作始终由人 / agent 手动进行。** 不要在这条路径上放置自动化的移动・删除（→ LC-5）。

## LC-5 检查仅限于警告〔所有引入方〕

**检查・lint 不移动文件。** 允许做的止步于检测 → 定期报告 → 由人（或负责人）判断。不进行自动退出。

lint 的信息管道是 fail-open（[FP-4](05-fail-posture.md)）—— "检查故障不会阻止工作"（FP-4）与"检查不移动文件"（本条）是一对，检查始终应倾向于只读。
