# LC 工作区生命周期 — 把放置之物的退场变成契约的层

L 层（L2 / L1 / L0）是"如何推进工作"的契约，与之相对，LC 层规定的是**物品持续堆积的场所（共享存储・工作目录・交接场所）中，放置之物何时、以何种方式退场**的契约。每条规则附有稳定的 rule ID（`LC-1`〜`LC-5`），并在各条款处以〔 〕明确适用对象。摘要侧（[docs/04](04-adoption.md)）引用这些 ID。无法验证时的姿态见 [docs/05](05-fail-posture.md)。

背景: 仅规定写入侧的规范（Issue-first・写在哪里）是不够的，**没有退场触发器的东西必定会滞留**。与放置规则成对的"如何退出"，由 LC 层统一规定。阶段名称以角色语为正式表述，英文标签作为括号内的辅助标注。

## LC-1 期限触发器原则〔全部导入对象〕

**放置物品时，必须同时确定退场触发器（期限 or 完成条件）。**

按照"没有触发器的东西会变成永久保留"的前提来处理。触发器的形式可以是期限（日期・天数），也可以是完成条件（合并后・分类后・汇总后）。当存放位置的规约（命名・期限元数据）无法表达时，需在放置时的 Issue 或声明中留下一行说明。

## LC-2 单向生命周期〔拥有持久领域的家〕

**git branch / worktree 不在本章讨论范围内 — 清理的正本见 [L0-4 / L0-8](03-git-protocol.md)。**

放置在持久领域中的物品，按照**接收（intake）→ 现役（active）→ 完成（complete）→ 退藏（archive）**的单向流程流动。不允许逆流。

- 退藏（archive）是**不可变**的 — 进入其中的物品不得改写、不得删除
- 需要恢复时，不从 archive 中删除，而是**作为新副本回到现役侧**
- 退藏目的地需附带记录（manifest），说明"移动了什么・何时・为何移动，如何恢复"

## LC-3 明确退场条件〔拥有持久工作区 / 共享存储的家〕

针对以下**3种类型**，需在本地设置中**明确写出带数值的退场条件**:

1. **大体积二进制文件** — 超过一定大小的非文本放置物（例: 超过 1MB 移入退藏）
2. **明确的旧版本** — 以可辨识为旧版本的名称・位置放置的物品（例: `旧〜/`・`.bak` 一经检测即移入退藏）
3. **定期文件的汇总** — 定期产生的原始文件在汇总后的原件（例: 生成月度摘要后，原始文件移入退藏）

**数值的正本存在于本地设置侧，本章正文中出现的数字（天数・大小等）均为"示例"，不计入契约**（MUST）。框架（3种类型均须具备退场条件）是本章的契约，实际数值由本地方持有 — 这与将合格模型名单置于本地设置的 [L1-10](02-issue-loop.md) 采用相同方式。

## LC-4 追加型存储的退场三件套〔仅限声明为追加型的存储，为 MUST〕

**追加型存储**＝声明为不对既有内容进行改写・删除的运营方式的保存场所。**本条款仅对将存储声明为追加型的家作为 MUST 适用。没有相应存储的家为 N/A** — 不将此前提强加于全部导入对象。

从追加型存储中退场（移入退藏）是追加型原则唯一的明文例外，必须按以下**三件套**进行:

1. **备份** — 在移动之前，对存储进行快照
2. **移动** — 移至退藏目的地（不是保留原件的复制，而是移动）
3. **留下指针** — 在原位置留下指向"移到何处・何时・为何移动"的指针

**退场的实际操作始终由人 / agent 手动执行**。不在此路径中放置自动化的移动・删除（→ LC-5）。

## LC-5 检查仅限警告〔全部导入对象〕

**检查・lint 不移动文件。** 允许做的仅限于: 检测 → 定期报告 → 由人（或负责人）判断，到此为止。不进行自动退场。

lint 的信息管道遵循 fail-open（[FP-4](05-fail-posture.md)）—"检查故障不阻断工作"（FP-4）与"检查不移动文件"（本条）是一对关系，检查始终倾向于只读。
