# Epic 车道 — 将人工确认收拢到 Epic 层级

在较大的工作中，如果每个 Issue 都要人工负责人确认，人就会成为瓶颈。这一层**完全不放松**代理之间的关卡（交叉审查、证据、声明范围），只将人工确认收拢到 Epic 的三个位置：入口（启动）、事先约定的停止点、出口（集成确认）。
每条规则都附有稳定的 rule ID（`E-1`〜`E-10`）。摘要一侧（[docs/04](04-adoption.md)）会引用这些 ID。审查席位的规定见 [L1-9〜L1-11](02-issue-loop.md)，无法验证时的姿态见 [docs/05](05-fail-posture.md)（尤其是 FP-9）。

## 高风险领域的定义（E-3 与 L1-11 共同引用的单一定义）

触及以下内容的工作称为**高风险领域**：

**对外公开、面向个人的发送 / 计费、支出 / 不可逆操作（数据删除、migration、共享历史的改写）/ 权限、认证、secret 的边界 / 公开前关卡**

对高风险领域的应对有两项：作为人工检查点必须停止（E-3）、将审查席位增加到 5 席（[L1-11](02-issue-loop.md)）。不要分别维护两份列表——正本只在这一处。**这一定义适用范围不限于 Epic 车道**（L1-11 的席位数判定在所有规模、所有车道中都引用本节——即便未采用 Epic 车道的引入方，也只需阅读本节）。

## E-1 Epic 化的标准与成立

- 权重判定直接沿用 [L2-1](01-milestone-loop.md)（不发明新的判定标准）。本节只是入口声明：「在 L2-1 中被判定为符合 EPIC Issue 的工作，其运作方式属于这一层」
- **Epic 在负责人（人类）的启动批准下成立**——批准对象是 EPIC Issue 正文（含 E-3 的检查点表，见[模板](../templates/epic-template.md)）。批准通过负责人对 EPIC Issue 的评论进行，该评论即成立的证据
- 批准前的 Epic 不是 Epic：E-4 的集成分支和 E-5 的自由权都**不产生**（维持普通 Issue 运作方式——[FP-9](05-fail-posture.md)）。Epic 化 ＝ 自由权的赋予 ＝ 人类的明确判断，不能打破这一对应关系

## E-2 轴的分离 — 功能轴 Epic × 模块轴子 Issue

- **Epic ＝ 功能轴**（用人类的语言写出价值。例如：「让通话应答更快」）。**子 Issue ＝ 模块轴**（1 个子 Issue ＝ 1 个模块或 1 个仓库。gateway 侧的子 Issue 与 App 侧的子 Issue 分开）
- 触及模块边界接口的 Epic，需**先行设立契约冻结的第 0 号子 Issue**（[L2-2](01-milestone-loop.md) 在 Epic 内的应用。只在这一号中先确定双方都会触及的契约，例如 API schema、协议等）
- **在第 0 号合并到 epic 分支之前，其他子 Issue 不得开始实现**（Epic 内的串行区间——与 L2-2 中「直到边界 PR merge 为止停止新并行」同一思路）。第 0 号合并后，所有子分支需先 rebase 再继续实现
- 契约冻结之后，声明文件集合互不交叉的子 Issue 可以并行（直接适用 [L2-4](01-milestone-loop.md)）
- 跨仓库的 Epic，在各仓库中放置子 Issue，以 EPIC Issue 作为枢纽。子 Issue 之间的依赖关系用 `Blocked-by` / 后继链接来声明（采用[docs/05 附属](05-fail-posture.md)中保留事项 6a。**仅采纳声明义务这部分**——「直到终结前都不设为 MERGED」（6b）依然处于保留状态，子 Issue 在自身终结时可以照常设为 MERGED）

## E-3 人工检查点表

EPIC Issue 的**必需章节**（[模板](../templates/epic-template.md)）。每一行 ＝「在哪里停下 / 展示什么 / 为什么需要人类判断」。

- 负责人在启动时批准该表（与 E-1 是同一事件）→ 此后**只在表中列出的点停止**，其余部分一路完成
- **表中必须列出的强制触发项**：开头定义的**所有高风险领域项目** ＋ **契约级偏离**。是否属于契约级，用三项检查机械判定：「是否触及 **E-2 中第 0 号所冻结的成果物、EPIC Issue 的 Done when、外部接口描述**中的任意一项」。未设第 0 号的 Epic，将 Done when 和外部 IF 描述视为冻结成果物——不能从空集合推导出关卡判定（[FP-6](05-fail-posture.md)）
- 检查点的**通过批准需负责人的明确评论**（与 E-1 的启动批准同一形式，模板的状态栏留下批准评论的 URL）。仅改写表格状态栏不构成批准（[FP-8](05-fail-posture.md)）
- **内部实现判断的偏离不触发停止**：不涉及契约、外部 IF、Done when 的设计变更，无需停止，记录在 Epic 日志（E-7）中，在集成确认时一并审查。若把这里也纳入停止对象，就会让 per-Issue 的人工确认死灰复燃，使这一层的目的自相矛盾而崩溃
- 出现未预见的「需要人类判断的事项」时，**作为临时检查点停止**（fail-closed）
- **表的修订是非对称的**：行的**新增**可由代理单独完成，即时生效。行的**删除、放宽、附加条件化**视为 [L1-8](02-issue-loop.md) 的替换记录，**在负责人明确批准评论出现之前，旧表继续有效**（[FP-8](05-fail-posture.md)——正文的自我编辑不产生批准效力）。判定不看形式而看**效果**：即使采取新增的形式，若内容缩小了既有行的适用范围（例如新增「第 5 号子 Issue 之后不再需要本行停止」这样的行），也视为放宽，在负责人重新批准之前不生效（tighten-only——与 [docs/04](04-adoption.md) 同一方向）
- **没有表格、缺少强制触发行、格式不当、未获批准**的 Epic 尚未按 E-1 成立发起。在此状态下如果需要做检查点判定，应**停止并上报给人类**（[FP-9](05-fail-posture.md)）。**Epic 运行中**表格失效时也保持同样的姿态停止，但要维持拓扑结构——停止的是 E-5 的自由权和检查点通过，而不是把子车道恢复为直接推向 main 的普通 Issue 运作（那样会绕过 E-6③ 的集成关卡）

## E-4 Epic 集成分支与拓扑

- 创建 `epic/<EPIC Issue 编号>` 分支 ＋ **集成专用** worktree。默认为 Epic 完成时**合并到 main 一次**（L0-5 / [L0-7](03-git-protocol.md) 原样适用于 epic→main）
- **写入者分配**（与 [L0-4](03-git-protocol.md) 保持一致）：
  - 子车道照常保持 **1 个子 Issue ＝ 1 个 branch ＝ 1 个 worktree**，在各自的 worktree 中工作，并在各自的子 Issue 上发出 WIP 声明（[L0-1](03-git-protocol.md) 4 个字段）。**子分支从 epic 分支分出**（[L0-4](03-git-protocol.md) 命令示例中的 `origin/main` 是 Epic 外车道的默认值——在 Epic 内部要替换为 `epic/<编号>`。若从 main 分出，子→epic PR 会混入与 main 的全部差异，破坏 E-6② 的 diff 核对）
  - epic worktree **专用**于集成工作（合并、冲突解决、纳入 main），写入者**只有一位**——即在 EPIC Issue 上发出 WIP 声明的人（Files to touch 仅限集成工作对象）。子车道不在 epic worktree 中工作
  - 交叉判定分两层进行：(a) Epic 内部子 Issue 之间（准用 L2-4）(b) 与 Epic 外车道之间（E-10）。default-deny（[L0-2](03-git-protocol.md)）的判定基准是**子 Issue 的声明集合**
- **子→epic 的合并手段固定为「以 epic 分支为 base 的 PR」**（diff 核对与审查记录留存在 GitHub 上）。合并一次一个——相邻子 Issue 合并进 epic 后，排队等待的子 Issue 负有 rebase＋重新验证的义务（准用 L0-7）
- **main 的定期纳入**：当 Epic 外车道合并进 main 后，epic 分支应尽快纳入 main 并重新验证（L0-7 rebase 义务的 epic 版本，纳入操作由 epic worktree 的写入者执行）。长寿命分支的 rebase 地狱（[L0-8](03-git-protocol.md)）通过这种定期纳入与 E-8 的期限来应对
- **中间合并（epic→main 途中的合并）属于例外**，仅当：①在 E-3 中事先记载为检查点 ②每次都对该次合并施加 E-6③ 的集成关卡（完整 [L1-7](02-issue-loop.md)）时才被允许。不满足这两个条件的中途合并即为违反 E-4

## E-5 沙箱自由权

Epic 成立后（E-1），子车道的 worktree / 子分支内在声明范围内是自由的：commit 粒度、重做、重构、子分支运作方式、对**自身分支未合并历史**的改写（含 force-push）。

**「自身分支」＝ 自己的子 Issue 分支中尚未合并进 epic 的历史**。除此以外的都不算自身分支。

**不可变的禁止事项**（这份列表就是自由权的边界。摘要时不得改说成「除破坏性行为外皆自由」之类而放宽）：

1. 直接 push 到 main（[L0-5](03-git-protocol.md)）
2. 写入声明范围之外（[L0-2](03-git-protocol.md) default-deny——基准是子 Issue 的声明集合）
3. 删除、改动其他车道、其他 worktree
4. **改写 epic 集成分支的历史（force-push、reset）**——epic 相当于该 Epic 内部的 main。若想替换已合并进 epic 的内容，需按 [L1-8](02-issue-loop.md) 的替换记录＋重新审查执行（不能悄悄重新合并）
5. 向外部发送机密信息
6. 未经批准执行 E-3 检查点事项

## E-6 沙漏审查 — 三处、单位各不相同

审查席位的异质性、席位数量的定义见 [L1-10 / L1-11](02-issue-loop.md)。

1. **设计审查 ＝ 以 Epic 为单位进行一次（在开始实现之前——可以在 EPIC Issue 起草之后，最迟不晚于第一个子 Issue 开始实现之前。与 [L1-9](02-issue-loop.md) 是同一时钟）**：体制为 L/H（3 个异质席位）。**仅当 Epic 包含高风险领域时才为 5 席**（L1-11）。不对子 Issue 递归进行完整设计会议
2. **实现审查 ＝ 以子 Issue 为单位每次进行（子→epic 的轻量关卡）**：席位数按**该子 Issue 本身的权重**参照 [L1-11](02-issue-loop.md) 的表格（不按 Epic 的权重判定——如果对所有子 Issue 都套用厚重审查，速度会被拖垮）。**但若子 Issue 触及高风险领域（本文开头定义），则 L1-11 的 5 席优先，席位数不可减少**。**能减轻的只有席位数与记录形式，证据的存在性不能减轻**。子→epic PR 的必需记录：**测试 green 的终结结果内联摘录 / 异质交叉审查（[L1-3](02-issue-loop.md)，含 identity check）/ 候选 commit SHA / 声明文件集合 vs `git diff --stat` 核对（[L0-6](03-git-protocol.md)——diff 中有而声明中没有的文件属于 blocking）**。候选 SHA 必须**与合并时刻的 PR head 一致**——若审查后发生变化则需重新审查（准用 [L1-8](02-issue-loop.md)。E-5 的 force-push 自由权**不包括替换已审查 SHA**）。可以省略的只有对应 Done when 的表格形式记录（用要点文字即可，但仍需维持 L1-7「仅凭记录本身即可读懂终结结果」的原则——仅有链接的证据不合格）
3. **集成审查 ＝ epic→main 时进行一次**：对整体集成 diff，采用**与 Epic 权重相符的体制 ＋ 完整 [L1-7](02-issue-loop.md) 完成记录**。负责人的最终确认也在此处进行（E-7）

## E-7 Epic 日志与摘要

- 每当一个子 Issue 终结时，在 EPIC Issue 下发一条评论：**完成了什么 / 证据（子→epic PR 链接＋要点）/ Done when 未达成事项、妥协事项（如没有则明确写「无」）/ 下一步**。未达成、妥协事项的列举不可省略——防止摘要变成一味粉饰的总结
- 负责人的最终确认，通过**日志摘要 ＋ 集成 diff ＋ 可运行成果物的确认**来进行（若是可执行物则用演示，若是文档则读作 render、检查链接是否失效）
- 已在 E-3 检查点获得批准的范围，在最终确认时**只呈现从批准点起的差异**（让检查点批准具备累积效力，不把人类确认总量在最后一次性搬移过来）

## E-8 期限 — 分开阅读两个时钟

- **分支寿命（执行对象）**：epic 分支应在 **1〜2 周内**（起点 ＝ E-1 启动批准评论的日期）合并进 main。预计超期时，可考虑拆分 Epic，或设置中途合并的检查点（E-4 的例外程序）。这个数字的调整只能通过 handbook 的 PR 进行（与 [L0-3](03-git-protocol.md) 的 72h 同样对待）。「数个子 Issue」这种规模感只是参考（非规范性）
- **staleness（锁的时钟）**：EPIC Issue 的 WIP 同样直接适用 [L0-3](03-git-protocol.md)（默认 72h）。Epic 可能预期有较长的沉默期，必要时可使用 L0-3 的**例外声明路径**（在 WIP 声明中附理由明示较长的窗口）。「1〜2 周」是分支寿命，**不是** staleness 窗口——既不能因为在寿命之内就把沉默 5 天的 epic 当作非 stale，也意味着未声明窗口而超过 72h 的 epic 应照常视为 stale，这两层含义都成立

## E-9 Epic 的终结 — 完成、中断、交接

- EPIC Issue 的车道状态同样适用 [L1-4](02-issue-loop.md) 的 5 个词汇（WIP / HOLD / MERGED / SUPERSEDED / ABANDONED）
- **完成** ＝ epic→main 通过 E-6③ 并被合并，所有子 Issue 均已终结，epic 分支与 worktree 已清理完毕的状态
- **中断、废弃（ABANDONED / SUPERSEDED）**不能仅凭声明就结束。终结评论中必须记载：①**epic 分支的处置**——废弃（删除），或将有价值的部分做**救援 PR**（epic→main 的部分合并，需通过 E-6③ 的集成关卡——不能因为是救援就放宽）②已合并、未合并的**子 Issue 状态收敛**（SUPERSEDED / ABANDONED / 拆分为独立 Issue）③worktree 的清理。但是**不能从 epic 一侧单方面终结持有存活 WIP 锁的子车道**——收敛只能通过通知锁的持有者＋持有者本人的终结声明，或经 stale 化后的 TAKEOVER（[L0-3](03-git-protocol.md)）来完成
- **交接**：epic 车道的接手通过对 **EPIC Issue 的 TAKEOVER**（[L0-3](03-git-protocol.md)）＋重启检查清单（[L0-9](03-git-protocol.md)）进行。若存在存活中的子车道，接手者应先重新阅读子车道的 WIP 群，不在存活锁之上进行集成工作（L0-2 乐观重读的 epic 版本）

## E-10 多个 Epic 并行

- Epic 的**实际声明集合 ＝ 子 Issue 声明文件集合的并集 ∪ EPIC Issue 的 WIP 声明集合**（epic worktree 的集成工作对象——E-4——也纳入交叉判定。汇总记载于 EPIC Issue 正文，随子 Issue 的增减更新）
- Epic 之间、Epic 与单发车道之间的并行 GO 判定，按此实际声明集合准用 [L2-4](01-milestone-loop.md)（仅非交叉才 GO，无法验证则串行——[FP-1](05-fail-posture.md)）
- 触及仓库大范围的 Epic 按 [L2-5](01-milestone-loop.md) **单独执行**
- epic→main 的合并按 [L0-7](03-git-protocol.md) 一次一个。相邻的 Epic（或单发车道）合并进 main 后，正在运行的 Epic 负有纳入 main 并重新验证的义务（E-4 的定期纳入）
