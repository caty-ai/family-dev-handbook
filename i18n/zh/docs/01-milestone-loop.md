# L2 里程碑循环 — 决定能否并行的层级

置于 Issue 循环（L1）**上层**的层级。将"要做什么"转换为"谁触碰哪里"，在这一层判定并行作业是否可行，再下沉到 L1。
每条规则附有稳定的 rule ID（`L2-1`〜`L2-6`）。摘要侧（[docs/04](04-adoption.md)）引用这些 ID。

## 为什么需要这一层

分工安全的条件只有一个 — **在着手前就能知道要触碰的文件集合不会交叉**。
worktree 和 Issue 锁（L0）是用来压低冲突发生时损失的装置，真正防止冲突本身的是"边界的事前共识"。跳过这一层去并行,同一个热点（巨型文件）被两条线同时触碰,必然冲突。

## 循环的步骤

### L2-1 目标共识

- 先通过对话把需求确定下来再着手（deep-interview / 计划会议等，使用各 agent 手头已有的方法）
- 对让设计变复杂的需求先质疑一次（提问方式参见 [为什么要做得简单](why-simple-systems.md)）。删除、收窄的判断需在委托方同意的基础上进行，未经同意不得稀释 Done when。质疑之后仍然接受的复杂度,要把理由留在 Issue 的 Why 里
- **重量判定（规模判别）**: 着手前先把工作规模定为 **S / M / L / H / Epic** 之一（判定标准见下）。规模是审查席位数（[L1-11](02-issue-loop.md)）、实施着手前是否需要上游异构审查（[L1-9](02-issue-loop.md)）、Epic 入口（[E-1](06-epic-lane.md)）的输入
- 判定为 **Epic** 的工作要做成 **EPIC Issue + 子 Issue 分解 + 关联 GitHub Milestone**。运作方式（集成分支、人类检查点、沙漏审查）参见 [docs/06 Epic 车道](06-epic-lane.md)（E-1〜E-10）

#### 规模判别标准

| 规模 | 定义 |
|---|---|
| **S** | 局部、低风险 — 约1个文件、对现有行为的小修改 |
| **M** | 单次 bug fix、单一功能 — 在1个模块内完结,不涉及边界变动 |
| **L** | 触碰多个模块、包含模块边界的变更 |
| **H** | 新功能、架构变更、安全、migration、直接关联客户 / 对外的变更 |
| **Epic** | 会被分解为多个 Issue 的一束工作（成立条件是拥有者的启动批准 = [E-1](06-epic-lane.md)） |

判定按以下三条轴来看。**触及多条轴的混合情形,以较重的那条轴为准**（例如："单一功能但直接关联对外" = H，"局部但涉及 migration" = H）:

1. **影响范围** — 触碰的文件 / 模块数量。跨越或移动模块边界则为 L 以上
2. **不可逆性** — 若包含 migration、对外公开、删除等难以复原的操作则为 H
3. **周期、人数** — 若可能跨越多个 session / 多个 agent 则为 Epic 候选

作为辅助的第四条轴,有**高风险领域**（正本是 [docs/06](06-epic-lane.md) 的单一定义，不在此处照抄）。这是**独立于规模、单独上调审查席位数的一条轴**,一旦命中,席位数会优先于规模而增加（[L1-11](02-issue-loop.md)）。规模表中的 H 与高风险领域应作为两回事对待。

- **终止规则：拿不准就按重的算**。三条轴都判不出来、或信息不足时,按重一档的规模处理

### L2-2 架构影响判定

着手前必须先问一句："**这项工作是否会移动模块边界？**"

- **不移动** → 直接进入 Issue 分解
- **会移动**（模块拆分、目录重组、共享接口变更等）→ **先单独放行一个边界 PR**
  - 在边界 PR 被 merge 之前,该仓库**停止一切新的并行着手**（串行区间）
  - 边界 PR 本身要保持最小 — 不要把边界变更和功能变更混在一起
  - 在 Epic 内部,**契约冻结的第0号子 Issue** 相当于边界 PR（[E-2](06-epic-lane.md)）

### L2-3 Issue 分解 — 必须预测要触碰的文件

切分子 Issue 时，各 Issue 正文中必须写明以下内容（[模板](../templates/issue-template.md)）:

- **目的 Why**
- **完成条件 Done when**
- **要触碰的文件 / 模块预测** ← 作为并行 GO 判定的输入。无法预测时明确写"无法预测"（= 该 Issue 不可并行）

### L2-4 并行 GO 判定

只有在**声明的文件集合不交叉时**,才可以让两个 Issue 同时运行。

- 有交叉 → 按顺序串行
- 无法预测 → 按顺序串行,或先做调查性 spike 使其可预测
- **无法验证是否交叉**（未声明、格式不正确、`UNKNOWN`）→ 串行（fail-closed — [FP-1](05-fail-posture.md)）
- 无论如何都想并行 → 先单独通过一个**边界分离 Issue**（把冲突部分切出来的重构）

### L2-5 广域 Issue 的隔离

全面重构 / 设计全面翻新 / 批量格式化 / 依赖的一次性升级等，**触碰仓库大范围的 Issue 需单独执行**。运行期间全面停止该仓库的并行。

顺序原则：**先消化常规功能的 Issue → 广域 Issue 放到最后统一单独处理**。

### L2-6 对热点的投资

多种职责混杂在一起的巨型文件（例如：2500 行的 View + 手势 + 引擎调用）是并行开发最大的敌人。

- 在各仓库的 `ARCHITECTURE.md` 中放置一份"**并行安全地图**",记录模块边界与热点（[模板](../templates/architecture-parallel-map.md)）
- 把热点的拆分重构作为"**对并行可能性的投资**",以独立 Issue 的形式优先立项 — 拆分之后,该区域的并行在结构上就会变得安全
