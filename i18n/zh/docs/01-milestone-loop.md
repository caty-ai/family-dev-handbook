# L2 里程碑循环 — 决定并行可行性的层级

置于 Issue 循环（L1）**上层**的层级。将"要做什么"转换为"谁来触碰哪里"，在这一层先判断能否并行作业，然后再下沉到 L1。
为每条规则赋予稳定的 rule ID（`L2-1`〜`L2-6`）。摘要侧（[docs/04](04-adoption.md)）会引用这些 ID。

## 为什么需要这一层

分工能够安全进行的条件只有一个 — **在着手前就能确定要触碰的文件集合不会交叉**。
worktree 或 Issue 锁（L0）是用来压制冲突发生后损失的装置，而真正防止冲突本身发生的是"边界的事先协商"。如果跳过这一层直接并行，两路同时触碰同一个热点（巨型文件）时必然会发生冲突。

## 循环的步骤

### L2-1 目标协商

- 先通过对话固化需求再着手（deep-interview / 计划会话等，使用各 agent 手头已有的方法）
- 对使设计变复杂的需求要先质疑一次（提问方式参考 [为什么要简单地构建](why-simple-systems.md)）。删减、收窄的判断需在委托方同意的基础上进行，未经协商不得削弱 Done when。质疑之后仍接受的复杂性，需将理由留在 Issue 的 Why 中
- **重量判定**: 单次 bug fix / 单一功能 = 1 个 Issue。新功能 / 架构变更 / 多模块 = **EPIC Issue + 子 Issue 拆解 + 关联 GitHub Milestone**
- 迷惑时倾向于选择更重的一侧。判断依据是"**是否可能跨越多个 session / 多个 agent？**"
- 归类为 EPIC Issue 的工作的运作方式（集成分支・人工检查点・沙漏式审查）参见 [docs/06 Epic 通道](06-epic-lane.md)（E-1〜E-10）

### L2-2 架构影响判定

着手前必须提问: "**这项工作是否会改动模块边界？**"

- **不改动** → 直接进入 Issue 拆解
- **改动**（模块拆分、目录重组、共享接口变更等）→ **先行推进一个单独的边界 PR**
  - 在边界 PR 被 merge 之前，该仓库**停止一切新的并行着手**（串行区间）
  - 边界 PR 本身要保持最小 — 不要把边界变更和功能变更混在一起
  - 在 Epic 内部，**契约冻结的第 0 号子 Issue** 相当于边界 PR（[E-2](06-epic-lane.md)）

### L2-3 Issue 拆解 — 必须预测所触碰的文件

在切分子 Issue 时，每个 Issue 正文中必须写明以下内容（[模板](../templates/issue-template.md)）:

- **目的 Why**
- **完成条件 Done when**
- **将触碰的文件 / 模块预测** ← 作为并行 GO 判定的输入。若无法预测，需明确写出"无法预测"（= 该 Issue 不可并行）

### L2-4 并行 GO 判定

只有当**声明的文件集合不交叉时**，才可以同时运行两个 Issue。

- 交叉 → 按顺序串行
- 无法预测 → 按顺序串行，或先做调查性 spike 使其变得可预测
- **无法验证是否交叉**（未声明・格式不正确・`UNKNOWN`）→ 串行（fail-closed — [FP-1](05-fail-posture.md)）
- 无论如何都想并行 → 先通过一个**边界分离 Issue**（把冲突部分切分出来的重构）

### L2-5 广域 Issue 的隔离

全面重构 / 设计全面翻新 / 批量格式化 / 依赖的一次性升级等，**触碰仓库大范围的 Issue 应单独执行**。运行期间完全停止该仓库的并行。

常用顺序: **先消化常规功能的 Issue → 广域 Issue 放到最后统一单独进行**。

### L2-6 对热点的投资

多种职责集于一身的巨型文件（例如: 2500 行的 View + 手势 + 引擎调用）是并行开发的最大敌人。

- 在各仓库的 `ARCHITECTURE.md` 中放置"**并行安全地图**"，记录模块边界与热点（[模板](../templates/architecture-parallel-map.md)）
- 将热点的拆分重构作为"**对并行可能性的投资**"，以独立 Issue 的形式优先立项 — 拆分后该区域的并行在结构上就变得安全
