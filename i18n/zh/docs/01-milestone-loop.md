# L2 里程碑循环 — 决定是否可并行的层级

置于 Issue 循环（L1）**上层**的层级。把"要做什么"转化为"谁触碰哪里"，在这一层先决定是否可以并行作业，再下放到 L1。
为每条规则赋予稳定的 rule ID（`L2-1`〜`L2-6`）。摘要侧（[docs/04](04-adoption.md)）会引用这些 ID。

## 为什么需要这一层

分工安全的条件只有一个 — **在着手前就能知道要触碰的文件集合不会交叉**。
worktree 和 Issue 锁（L0）是用来压低冲突发生后损失的装置，真正防止冲突本身的是"边界的事前协商"。跳过这一层直接并行的话，两条同时触碰同一热点（巨大文件）的工作线必然会冲突。

## 循环的流程

### L2-1 目标共识

- 先通过对话把需求确定下来，再着手（可用各 agent 手头的方法，比如 deep-interview / 计划会议等）
- 对让设计变复杂的需求先质疑一遍（提问方式参见 [为什么要简单地构建](why-simple-systems.md)）。删除、缩小范围的判断需在委托方同意的前提下进行，未经同意不得稀释 Done when。质疑之后仍决定接受的复杂度，要把理由写进 Issue 的 Why 里
- **重量判定（规模判别）**: 着手前先把工作规模定为 **S / M / L / H / Epic** 之一（判定基准见下）。规模会作为 review 席位数（[L1-11](02-issue-loop.md)）、实现着手前是否需要上游异构 review（[L1-9](02-issue-loop.md)）、Epic 入口（[E-1](06-epic-lane.md)）的输入
- 被判定为 **Epic** 的工作 **拆分为 EPIC Issue + 子 Issue，并关联到 GitHub Milestone**。运作方式（集成分支、人工检查点、沙漏式 review）参见 [docs/06 Epic 车道](06-epic-lane.md)（E-1〜E-10）

#### 规模判别基准

| 规模 | 定义 |
|---|---|
| **S** | 局部 — 大约1个文件 · 对既有行为的小修改 |
| **M** | 单次 bug fix · 既有功能内的单次变更 — 在单个模块内闭环，不改动边界 |
| **L** | 触及多个模块 · 包含模块边界的变更 |
| **H** | 新功能（作为用户价值新建立起来的东西）· 架构变更 · 安全 · migration · 与客户 / 对外直接相关的变更 |
| **Epic** | 拆分为多个 Issue 的一束（成立需经负责人的启动批准 = [E-1](06-epic-lane.md)） |

判定沿以下三个轴来看。**触及多个轴的混合情况，以更重的那个轴为准**（例：「单一功能但直接对外」= H，「局部但涉及 migration」= H）：

1. **影响范围** — 触碰的文件 / 模块数量。若跨越或移动模块边界则为 L 以上
2. **不可逆性** — 若包含 migration、对外发布、删除等难以撤回的操作，则为 H
3. **周期 · 人数** — 若可能跨越多个 session / 多个 agent，则为 Epic 候选

作为辅助的第四个轴，还有**高风险领域**（正本是 [docs/06](06-epic-lane.md) 中的单一定义，此处不重复摘抄）。这是**独立于规模、专门用于提高 review 席位数的轴**，一旦命中，席位数会优先于规模而增加（[L1-11](02-issue-loop.md)）。规模表中的 H 与高风险领域应作为不同的东西对待（内容有重叠的变更可能同时命中两个轴 — 规模决定基础席位数，高风险命中决定追加数量）。

- **终结规则：拿不准就往重了判**。若某个轴无法判定、或信息不足，在 **S〜H 的范围内**按重一级来处理。向 Epic 的升级不走这个梯子，只由是否需要拆分为多个 Issue（第3轴 · [E-1](06-epic-lane.md)）来决定

### L2-2 架构影响判定

着手前必须提出这个问题：「**这项工作会移动模块边界吗？**」

- **不会移动** → 直接进入 Issue 拆分
- **会移动**（模块拆分、目录重组、共享接口变更等）→ **先行发出一个边界 PR**
  - 在该边界 PR 被 merge 之前，该仓库的**新并行着手一律暂停**（串行区间）
  - 边界 PR 本身要保持最小 — 不要把边界变更和功能变更混在一起
  - 在 Epic 内部，**契约冻结的第0号子 Issue** 相当于边界 PR（[E-2](06-epic-lane.md)）

### L2-3 Issue 拆分 — 强制预测所触碰的文件

拆分子 Issue 时，每个 Issue 正文必须写明以下内容（[模板](../templates/issue-template.md)）：

- **目的 Why**
- **完成条件 Done when**
- **预测触碰的文件 / 模块** ← 这是并行 GO 判定的输入。若无法预测，需明确写「无法预测」（= 该 Issue 不可并行）

### L2-4 并行 GO 判定

两个 Issue 只有在**声明的文件集合不交叉的情况下**才可以同时进行。

- 有交叉 → 串行、按顺序进行
- 无法预测 → 串行进行，或先做调查性 spike 使其可预测
- **无法验证是否交叉**（没有声明 · 格式不正确 · `UNKNOWN`）→ 串行（fail-closed — [FP-1](05-fail-posture.md)）
- 无论如何都想并行 → 先通过一个**边界分离 Issue**（把冲突部分切出来做重构）

### L2-5 广域 Issue 的隔离

全面重构 / 设计全面翻新 / 批量格式化 / 依赖的一并更新等，**触碰仓库大范围的 Issue 单独执行**。运行期间该仓库的并行全部暂停。

顺序的定式：**先消化普通功能的 Issue → 广域 Issue 放到最后统一单独进行**。

### L2-6 对热点的投资

多个职责混杂在一起的巨型文件（例：2500行的 View + 手势 + 引擎调用）是并行开发最大的敌人。

- 在各仓库的 `ARCHITECTURE.md` 中设置一份「**并行安全地图**」，记录模块边界和热点（[模板](../templates/architecture-parallel-map.md)）
- 把针对热点的拆分重构作为「**对并行可能性的投资**」，作为独立 Issue 优先立项 — 拆分之后，该区域的并行在结构上就会变得安全
