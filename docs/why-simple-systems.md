# なぜシンプルに作るのか — 複雑さは設計で解くより、要件で消す

> このページは条文ではありません。条文の本文は [docs/01](01-milestone-loop.md)〜[docs/03](03-git-protocol.md) と [docs/05](05-fail-posture.md)〜[docs/08](08-lifecycle.md) にあります。
> ここに書いてあるのは、それらの条文が**前提にしている考え方**です。

## 目指しているもの

このハンドブックの条文（L2 / L1 / L0）は「どう作るか・どう並行するか」を守る仕組みです。ただ、その手前 — **何を作ることにするか**の段階で、すでに決まってしまうものがあります。壊れやすさと、メンテナンスの重さです。

目指す状態は4つです。

- **シンプルで壊れにくい** — 部品が少ないほど、壊れる場所も少ない
- **放置に耐える** — 次にメンテナンスが必要になるまでのリードタイムが長い。動かし続けるのに人の注意が要らない
- **誰でも構造を理解できる** — 数ヶ月後の自分や、初めて入るエージェントが、説明なしで読んで追える。「作った本人にしか分からない」「後から解読に時間がかかる」は、それ自体を欠陥として扱う
- **責務の数だけのモジュール構成** — 責務より多くも少なくも切らない（測り方は [なぜモジュールを小さく切るのか](why-small-modules.md) の「責務の数」と同じ）

## 設計でハマったら、要件を疑う

作っている途中で、こうなることがあります。

- ロジックがあまりにも難解になってきた
- モジュールの組み合わせで解決できず、特別な仕掛けが要りそうだ
- 設計そのものでハマっている

このとき最初に取る手は、「もっと賢い設計を探す」ことではありません。**要件自体を疑うこと**です。

難しさの多くは、設計ではなく要件が連れてきます。要件を1つ消せると、その要件が要求していた設計の難所が、実装ごと・テストごと・将来のメンテナンスごと、まるごと消えます。設計の工夫は難しさを**薄める**ことしかできませんが、要件の見直しは難しさを**消す**ことができます。

## 疑うときの質問

順番に問います。どれも「要件を削れないか」ではなく「**前提を消して、問題そのものを消せないか**」を探す質問です。

1. **本当に誰が使うのか？** — 想定ユーザーを広く取るほど、認証・権限・エラー処理・サポートが厚くなります。実際の利用者を確かめると、その厚みの大半が不要だと分かることがあります
2. **本当にオンラインである必要があるか？** — ローカル実行や閉じたネットワーク（VPN 等）で足りるなら、公開のためのログイン設計・攻撃対策・可用性設計は、最初から問題として存在しません
3. **用途を縛れば、難所を消せないか？** — 「何でも扱える」をやめて入力や使い方を限定すると、難解だった分岐がごっそり消えることがあります
4. **その要件は、誰かが本当に頼んだのか？** — 「あったほうがよさそう」で足された要件が、いちばん高くつきます。答えは依頼した人に確かめます — Issue に残っている要件は過去の合意の記録なので、「誰も頼んでいない」とエージェントが単独で判定して消す対象ではありません

### 例: 「社内向けの SaaS を作ってほしい」

依頼どおりに受け取ると、安全に公開するための設計が始まります。ログイン、パスワードリセット、セッション管理、権限テーブル — どれも難しく、どれも壊れやすく、どれも保守が続きます。

そこで質問1に戻ります。「誰が使いますか？」— 答えが「自分たちのチームだけ」なら、そもそも公開する必要がありません。ローカルで動かすか、閉じたネットワークに置けば、**ログインという問題自体が消えます**。作る前に1つ質問しただけで、いちばん壊れやすい部分がまるごと不要になりました。

これが「前提を消して解決する」ということです。

> **注意:** これは「作る前に、利用者範囲という要件を確かめる」例であって、公開前提のシステムから認証を外す話ではありません。認証・権限・公開範囲という境界に触れる判断は — 作る前でも、動いているシステムなら特に — **高リスク領域**（[docs/06](06-epic-lane.md) の単一定義）に当たるため、人間の決裁対象です。

## 疑うのは自由、消す決定は依頼者のもの

ここが一番大事な線引きです。**疑いの出力は、要件の削除ではなく、ゴール合意（[`L2-1`](01-milestone-loop.md)）へ戻す「問い」と「提案」です。**

- エージェントは代替案を出すところまで。**何を捨てるかを最終的に決めるのは、依頼した人**です
- 合意済みの要件・完了条件（Done when）を、エージェント単独で書き換えたり薄めたりしない。「疑った結果、不要と判断した」を理由に完了条件を N/A にしない
- 途中で要件を落としたくなったら: 実装を進めたまま Done when を書き換えず、**Issue 上で依頼者に確認**する。合意できたら Why / Done when を更新してから再開する
- 行き詰まりの出口の**代わりにしない**。実装で詰まったときの正規の出口は [`L1-4`](02-issue-loop.md) / [`L1-6`](02-issue-loop.md) の HOLD か人間へのエスカレーションであって、「要件を疑う」ではありません。**「できなかった」と「要らなくなった」は別のことで、別々に記録します**
- 要件を消して仕事が軽くなった場合でも、それはレビューの重さ（[`L1-9`](02-issue-loop.md) / 席数）を**回避する手段ではありません**。消す合意そのものが要件変更として、重い側の仕事では上流レビューの対象です
- 重い仕事ではこの線はすでに条文が引いています — 要件定義は実装着手前の異種レビュー対象（[`L1-9`](02-issue-loop.md)）、Epic 内の Done when は凍結成果物で、変更は人間チェックポイントの停止対象（[`E-3`](06-epic-lane.md)）。このページはそれを緩めません

## 全部がこうできるわけではない

要件が本物で、複雑さが避けられないこともあります。規制対応・監査記録・個人情報の保護・課金のように、**消す自由がそもそも自分たちに無い要件**もあります — これらは疑う対象ではなく、確かめて満たす対象です。このページは「複雑なものを作るな」ではなく、「**複雑さを受け入れる前に、一度は要件を疑え**」です。

疑った上で受け入れるなら、それでかまいません。ただし**なぜ受け入れたのかを Issue の目的（Why）に1行残します**（Why の書き方は [`L1-2`](02-issue-loop.md)）。残っていれば、数ヶ月後に「この複雑さは要るのか？」と誰かが問い直せます。残っていなければ、複雑さは既成事実になります。

## 並行ルールとの関係

この前提は、条文の世界とつながっています。

- 要件を消すと、触るファイルが減ります。触るファイルが減ると、**触るファイル予測**（[`L2-3`](01-milestone-loop.md)）が書きやすくなり、並行GO（[`L2-4`](01-milestone-loop.md)）が出やすくなります。シンプルなシステムは、並行開発にも強いシステムです
- 「責務の数だけのモジュール構成」は、[分割は並行可能性への投資](why-small-modules.md) と同じ判断軸です。責務が同居していたら分ける（あちらの話）、責務がないのに部品を増やさない（このページの話）— 向きが違うだけで、目安はどちらも**責務の数**です
- [`L2-1`](01-milestone-loop.md) の「迷ったら重い側」は**プロセス**（Epic 化・レビューの厚み）の判定であり、機能を増やす話ではありません。「要件は軽く、プロセスは重く」は両立します
- 誰でも構造を理解できることは、引き継ぎの正本を Issue に置く（[Issue-first](why-issue-first.md)）のと同じ動機です。**記憶ゼロで入ってくる次の読み手**を基準にします

## よくある疑問

**エージェントが「要件を疑う」を口実に、勝手に要件を削りませんか？**

このページの読み方として、それは禁止です。疑う＝問いを立てて提案するまで。消す・狭める決定は依頼者にあります（上の「疑うのは自由、消す決定は依頼者のもの」）。合意なく Done when を薄める行為は、完了記録（[`L1-7`](02-issue-loop.md)）の突き合わせで露見する種類の逸脱として扱ってください。

**要件を疑うのは、依頼した人に失礼では？**

疑うのは依頼した人ではなく、要件と設計の間の変換です。「誰が使いますか？」という質問は、依頼を値切る交渉ではなく、依頼の本当の目的を確かめる作業です。目的が満たせるなら、作る量は少ないほど依頼した人の得になります。

**シンプルに作ると、あとで拡張できなくなりませんか？**

逆のことが多いです。将来の拡張に備えて先に入れた仕掛けは、たいてい予想と違う方向の拡張が来て使われず、読み手の理解だけを妨げます。構造が小さく理解しやすいことが、いちばん潰しの効く拡張性です。

**いつ要件を疑えばいいですか？**

2回あります。1回目は着手前 — ゴール合意（[`L2-1`](01-milestone-loop.md)）で要件を固めるとき。ここは依頼者との対話の場なので、その場で問えば足ります。2回目は途中 — 設計が難解になってきた・ハマったと感じたとき。こちらは依頼者がその場にいないので、上の線引きどおり「問いを Issue に書いて確認」までがエージェントの仕事です。ハマると人もエージェントも「もっと複雑な解決策」へ向かいがちです。その足を止めるためのページです。
