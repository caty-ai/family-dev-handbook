# Epic レーン — 人間確認を Epic 単位に束ねる層

大きめの仕事で人間オーナーの確認が Issue ごとに挟まると、人間がボトルネックになる。この層は、エージェント間のゲート（クロスレビュー・証拠・宣言スコープ）は**一切緩めずに**、人間の確認だけを Epic の入口（キックオフ）・事前合意した停止点・出口（統合確認）の3箇所に束ねる。
各ルールに安定 rule ID（`E-1`〜`E-10`）を付す。要約側（[docs/04](04-adoption.md)）はこの ID を参照する。レビュー席の規定は [L1-9〜L1-11](02-issue-loop.md)、検証できない時の姿勢は [docs/05](05-fail-posture.md)（特に FP-9）。

## 高リスク領域の定義（E-3 と L1-11 が共に参照する単一定義）

以下を触る作業を**高リスク領域**と呼ぶ:

**対外公開・対人送信 / 課金・支出 / 不可逆操作（データ削除・migration・共有履歴の書き換え）/ 権限・認証・secret の境界 / 公開前ゲート**

高リスク領域への応答は2つ: 人間チェックポイントとして必ず停止する（E-3）・レビュー席を5席に増やす（[L1-11](02-issue-loop.md)）。2つのリストを別々に持たない — 正本はこの1箇所。**この定義は Epic レーンに限らず適用される**（L1-11 の席数判定は全サイズ・全レーンでこの定義を参照する — Epic レーンを採用しない導入先も本節だけは読む）。

## E-1 Epic 化の基準と成立

- 重さ判定は [L2-1](01-milestone-loop.md) をそのまま使う（新しい判定基準を発明しない）。本節は「L2-1 で EPIC Issue に該当した仕事の運用がこの層」という入口の宣言のみ
- **Epic はオーナー（人間）のキックオフ承認をもって成立する** — 承認対象は EPIC Issue 本文（E-3 のチェックポイント表を含む・[テンプレ](../templates/epic-template.md)）。承認は EPIC Issue へのオーナーのコメントで行い、そのコメントが成立の証跡
- 承認前の Epic は Epic ではない: E-4 の統合ブランチも E-5 の自由権も**発生しない**（通常の Issue 運用のまま — [FP-9](05-fail-posture.md)）。Epic 化 ＝ 自由権の付与 ＝ 人間の明示的判断、という対応を崩さない

## E-2 軸の分離 — 機能軸 Epic × モジュール軸子 Issue

- **Epic ＝ 機能軸**（人間の言葉で価値を書く。例:「通話の応答を速くする」）。**子 Issue ＝ モジュール軸**（1子 Issue ＝ 1モジュール or 1リポ。gateway 側の子・アプリ側の子、と分かれる）
- モジュール境界のインターフェースに触る Epic は、**契約凍結の子 Issue を第0号として先行**させる（[L2-2](01-milestone-loop.md) の Epic 内適用。API スキーマ・プロトコル等、両側が触る契約だけを最初に1本で確定する）
- **第0号が epic ブランチにマージされるまで、他の子 Issue の実装着手は不可**（Epic 内直列区間 — L2-2 の「境界PR merge まで新規並行停止」と同じ趣旨）。第0号マージ後、全子ブランチは rebase してから実装を続行する
- 契約凍結後、宣言ファイル集合が非交差の子 Issue は並行可（[L2-4](01-milestone-loop.md) にそのまま乗る）
- リポ跨ぎ Epic は各リポに子 Issue を置き、EPIC Issue をハブとする。子 Issue 間の依存は `Blocked-by` / 後継リンクで宣言する（[docs/05 附属](05-fail-posture.md)・保留項目 6a の採用。**採用は宣言義務の部分のみ** — 「終端まで MERGED にしない」（6b）は引き続き保留であり、子 Issue は自分の終端で通常どおり MERGED にしてよい）

## E-3 人間チェックポイント表

EPIC Issue の**必須セクション**（[テンプレ](../templates/epic-template.md)）。各行 ＝「どこで止まるか / 何を見せるか / なぜ人間判断か」。

- キックオフ時にオーナーが表を承認（E-1 と同一イベント）→ 以降は**表にある地点でのみ停止**し、それ以外は完走する
- **表に必ず載せる必須トリガー**: 冒頭の**高リスク領域の全項目**＋**契約級の逸脱**。契約級かどうかは3項検査で機械的に判定する: 「**E-2 の第0号で凍結した成果物・EPIC Issue の Done when・外部インターフェース記述**のいずれかに触るか」。第0号を設けない Epic では Done when と外部IF 記述が凍結成果物とみなされる — 空集合からゲート判定を導出しない（[FP-6](05-fail-posture.md)）
- チェックポイントの**通過承認はオーナーの明示コメント**で行う（E-1 のキックオフ承認と同形式・テンプレの状態欄に承認コメント URL を残す）。表の状態欄の書き換えだけでは承認にならない（[FP-8](05-fail-posture.md)）
- **内部実装判断の逸脱は停止しない**: 契約・外部IF・Done when を動かさない設計変更は、停止せず Epic ログ（E-7）に記録し、統合確認で一括レビューする。ここを停止対象にすると per-Issue の人間確認が復活し、この層の目的が自己矛盾で潰れる
- 予見外の「人間判断が必要な事項」が発生したら、**臨時チェックポイントとして停止**する（fail-closed）
- **表の改訂は非対称**: 行の**追加**はエージェント単独で可・即時有効。行の**削除・緩和・条件付き化**は [L1-8](02-issue-loop.md) の差し替え記録扱いとし、**オーナーの明示承認コメントがあるまで旧表が有効**（[FP-8](05-fail-posture.md) — 本文の自己編集は承認を生まない）。判定は形式ではなく**効果**で行う: 追加の形をとっていても、既存行の適用範囲を狭める内容（例:「子#5 以降は本行の停止を要しない」という行の追加）は緩和とみなし、オーナー再承認まで効力を持たない（tighten-only — [docs/04](04-adoption.md) と同じ向き）
- **表が無い・必須トリガー行を欠く・形式不正・未承認**の Epic は Epic として発足していない（E-1）。この状態でチェックポイント判定が必要になったら**停止して人間へエスカレーション**（[FP-9](05-fail-posture.md)）。**Epic 走行中**に表が不正化した場合も同じ姿勢で停止するが、トポロジは維持する — 停止するのは E-5 の自由権とチェックポイント通過であって、子レーンを main 直行の通常 Issue 運用に戻すことではない（それは E-6③ の統合ゲートの迂回になる）

## E-4 Epic 統合ブランチとトポロジ

- `epic/<EPIC Issue 番号>` ブランチ＋**統合専用** worktree を作る。main へのマージは **Epic 完了時の1回が既定**（L0-5 / [L0-7](03-git-protocol.md) は epic→main にそのまま適用）
- **書き手の割り当て**（[L0-4](03-git-protocol.md) との整合）:
  - 子レーンは従来どおり **1子 Issue ＝ 1 branch ＝ 1 worktree** で、自分の worktree で作業し、自分の子 Issue に WIP 宣言（[L0-1](03-git-protocol.md) 4フィールド）を出す。**子ブランチは epic ブランチから分岐**する（[L0-4](03-git-protocol.md) のコマンド例にある `origin/main` は Epic 外レーンの既定 — Epic 内では `epic/<番号>` に読み替える。main から分岐すると子→epic PR に main との差分が丸ごと混入し、E-6② の diff 照合が壊れる）
  - epic worktree は統合作業（マージ・conflict 解消・main 取り込み）**専用**であり、書き手は **EPIC Issue に WIP 宣言した1名だけ**（Files to touch は統合作業の対象のみ）。子レーンは epic worktree では作業しない
  - 交差判定は2層で行う: (a) Epic 内の子同士（L2-4 準用）(b) Epic 外のレーンと（E-10）。default-deny（[L0-2](03-git-protocol.md)）の基準は**子 Issue の宣言集合**
- **子→epic のマージ手段は「epic ブランチを base とする PR」に固定**する（diff 照合とレビュー記録が GitHub 上に残る）。マージは1本ずつ・隣接の子が epic へマージされたら、キューで待つ子は rebase＋再検証の義務を負う（L0-7 準用）
- **main の周期取り込み**: Epic 外のレーンが main へマージされたら、epic ブランチは速やかに main を取り込み再検証する（L0-7 の rebase 義務の epic 版。取り込みは epic worktree の書き手が行う）。長生きブランチの rebase 地獄（[L0-8](03-git-protocol.md)）への対処はこの周期取り込みと E-8 の時限
- **中間マージ（epic→main の途中マージ）は例外**であり: ①E-3 のチェックポイントとして事前記載され ②各回に E-6③ の統合ゲート（フル [L1-7](02-issue-loop.md)）を課すときだけ許される。この2条件を満たさない途中マージは E-4 違反

## E-5 サンドボックス自由権

Epic 成立後（E-1）、子レーンの worktree / 子ブランチ内は宣言スコープ内で自由: コミット粒度・作り直し・リファクタ・子ブランチ運用・**自ブランチの未マージ履歴**の書き換え（force-push 含む）。

**「自ブランチ」＝ 自分の子 Issue ブランチの、まだ epic にマージされていない履歴**。それ以外は自ブランチではない。

**不変の禁止**（この列挙が自由の輪郭。要約時に「破壊行為以外自由」等と言い換えて緩めない）:

1. main への直接 push（[L0-5](03-git-protocol.md)）
2. 宣言スコープ外への書き込み（[L0-2](03-git-protocol.md) default-deny — 基準は子 Issue の宣言集合）
3. 他レーン・他 worktree の削除・改変
4. **epic 統合ブランチの履歴書き換え（force-push・reset）** — epic は当該 Epic 内での main 相当。epic にマージ済みの内容を差し替えたい場合は [L1-8](02-issue-loop.md) の差し替え記録＋再レビュー（黙った再マージをしない）
5. 秘密情報の外部送信
6. E-3 チェックポイント事項の無承認実行

## E-6 砂時計レビュー — 3箇所・単位が違う

レビュー席の異種性・席数の定義は [L1-10 / L1-11](02-issue-loop.md)。

1. **設計レビュー ＝ Epic 単位で1回（実装着手前 — EPIC Issue の起票後でも可・遅くとも最初の子 Issue の実装着手前。[L1-9](02-issue-loop.md) と同じ時計）**: 体制は L/H（異種3席）。**高リスク領域を含む Epic のみ5席**（L1-11）。子 Issue にフル設計会議を再帰させない
2. **実装レビュー ＝ 子 Issue 単位で毎回（子→epic のライトゲート）**: 席数は**その子 Issue 自体の重さ**で [L1-11](02-issue-loop.md) の表を引く（Epic の重さで判定しない — 全子に厚いレビューを付けると速度が死ぬ）。**ただし子 Issue が高リスク領域（冒頭定義）を触る場合は L1-11 の5席が優先し、席数は落とせない**。**軽くできるのは席数と記録形式だけで、証拠の存在性は軽くしない**。子→epic PR の必須記録: **テスト green の終端結果インライン抜粋 / 異種クロスレビュー（[L1-3](02-issue-loop.md)・identity check 込み）/ 候補 commit SHA / 宣言ファイル集合 vs `git diff --stat` 照合（[L0-6](03-git-protocol.md) — diff にあって宣言にないファイルは blocking）**。候補 SHA は**マージ時点の PR head と一致**していること — レビュー後に変わったら再レビュー（[L1-8](02-issue-loop.md) 準用。E-5 の force-push 自由権は**レビュー済み SHA の差し替えを含まない**）。省略してよいのは Done when 対応の表形式のみ（要点の文章でよい。ただし L1-7 の「記録単体で終端結果が読めること」の原則は維持 — リンクだけの証拠は不適合）
3. **統合レビュー ＝ epic→main で1回**: 統合 diff 全体に **Epic の重さの体制＋フル [L1-7](02-issue-loop.md) 完了記録**。オーナーの最終確認もここ（E-7）

## E-7 Epic ログとダイジェスト

- 子 Issue が終端するごとに、EPIC Issue へ1コメント: **何ができた / 証拠（子→epic PR へのリンク＋要点）/ Done when 未達・妥協事項（無ければ「なし」と明記）/ 次**。未達・妥協の列挙は省略不可 — ダイジェストがバラ色の要約になるのを防ぐ
- オーナーの最終確認は **ログのダイジェスト＋統合 diff＋動く成果物の確認**（実行可能物ならデモ、docs なら render・リンク切れ確認、に読み替える）で行う
- E-3 のチェックポイントで承認済みの範囲は、最終確認では**承認地点からの差分のみ**提示する（チェックポイント承認に累積効力を持たせる。人間の確認総量を最後に丸ごと移動させない）

## E-8 時限 — 2つの時計を分けて読む

- **ブランチ寿命（執行対象）**: epic ブランチは **1〜2週間**（起点 ＝ E-1 のキックオフ承認コメントの日付）で main へ。超過見込みは Epic 分割か、中間マージのチェックポイント設定（E-4 の例外手続き）。この数字の調整はハンドブックの PR でのみ行う（[L0-3](03-git-protocol.md) 72h と同じ扱い）。「子 Issue 数本」という規模感は目安（非規範）
- **staleness（ロックの時計）**: EPIC Issue の WIP にも [L0-3](03-git-protocol.md) がそのまま適用される（既定 72h）。Epic は長い沈黙が予定されうるので、必要なら L0-3 の**例外宣言経路**（WIP 宣言に理由つきで長い窓を明示）を使う。「1〜2週間」はブランチ寿命であって staleness 窓では**ない** — 5日沈黙の epic を寿命内だからと stale 扱いしないこと、逆に窓を宣言せず 72h 超過した epic は通常どおり stale であること、の両方を意味する

## E-9 Epic の終端 — 完了・中断・引き継ぎ

- EPIC Issue のレーン状態にも [L1-4](02-issue-loop.md) の5語彙（WIP / HOLD / MERGED / SUPERSEDED / ABANDONED）を適用する
- **完了** ＝ epic→main が E-6③ を通過して merge され、全子 Issue が終端し、epic ブランチ・worktree が掃除された状態
- **中断・破棄（ABANDONED / SUPERSEDED）**は宣言だけで終わらせない。終端コメントに必ず記載: ①**epic ブランチの処分** — 破棄（削除）か、価値ある部分の**救出 PR**（epic→main の部分マージ。E-6③ の統合ゲートを通す — 救出だからと緩めない）②マージ済み・未マージの**子 Issue の状態収束**（SUPERSEDED / ABANDONED / 独立 Issue への切り出し）③worktree の掃除。ただし**生きた WIP ロックを持つ子レーンを epic 側から一方的に終端しない** — 収束はロック所有者への通知＋所有者自身の終端宣言、または stale 化後の TAKEOVER（[L0-3](03-git-protocol.md)）経由でのみ行う
- **引き継ぎ**: epic レーンの引き取りは **EPIC Issue への TAKEOVER**（[L0-3](03-git-protocol.md)）＋再開チェックリスト（[L0-9](03-git-protocol.md)）。生存中の子レーンがある場合、引き取り者はまず子の WIP 群を読み直し、生きたロックの上で統合作業をしない（L0-2 楽観的再読の epic 版）

## E-10 複数 Epic の並走

- Epic の**実効宣言集合 ＝ 子 Issue の宣言ファイル集合の和集合 ∪ EPIC Issue の WIP 宣言集合**（epic worktree の統合作業対象 — E-4 — も交差判定に含める。EPIC Issue 本文に集約して記載・子の増減で更新）
- Epic 同士・Epic と単発レーンの並行 GO 判定は、この実効宣言集合で [L2-4](01-milestone-loop.md) を準用する（非交差のみ GO・検証不能なら直列 — [FP-1](05-fail-posture.md)）
- リポの広範囲を触る Epic は [L2-5](01-milestone-loop.md) どおり**単独実行**
- epic→main のマージは [L0-7](03-git-protocol.md) どおり1本ずつ。隣接 Epic（または単発レーン）が main へマージされたら、走行中の Epic は main を取り込み再検証する義務を負う（E-4 の周期取り込み）
