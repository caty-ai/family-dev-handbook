# Issue-first とは — なぜ会話ではなく Issue から始めるのか

> このページは条文ではありません。条文の本文は [docs/01](01-milestone-loop.md)〜[docs/03](03-git-protocol.md) と [docs/05](05-fail-posture.md)〜[docs/08](08-lifecycle.md) にあります。
> ここに書いてあるのは、それらの条文が**前提にしている考え方**です。ルールを覚える前に、なぜそうなっているのかを知りたい人向けです。

## 会話で指示すると、何が起きるか

AI エージェントに「あのバグ直しておいて」と頼む。直る。翌日、別のセッションを開く。

エージェントは昨日のことを何も覚えていません。何を直したのか、なぜその直し方にしたのか、どこまで確かめたのかは、閉じたターミナルと一緒に消えています。残っているのはコードの変更だけで、そこに至った判断は残っていません。

人間同士でも似たことは起きます。チャットで決めたことはスクロールの彼方へ流れていきます。違うのは、AI の場合は「思い出してもらう」ことすらできない点です。**毎回、記憶ゼロから始まります。**

そして今は、そのエージェントが1体とは限りません。2体が同時に動けば、お互いが何をしているかを知る手段がないまま同じファイルを触ります。

## Issue-first とは

やることは1つだけです。

**コードを触る前に、GitHub の Issue を1本立てる。**

それだけです。特別なツールも、追加のサービスも要りません。実装は Issue が立ってから始めます。Issue のない実装はしません。

## なぜそれで効くのか

Issue を立てると、**引き継ぎの正本が1か所に固定されます。**

作業が終わったとき、そこには2つのものが残ります。Issue の本文（何をやろうとしたか・どうなったら終わりか）と、Pull Request の差分（実際に何が変わったか）です。この2つが揃っていれば、途中から入ってきた誰か — 別の人でも、別のエージェントでも、記憶を失った明日の自分でも — は、Issue を読むだけで続きができます。

会話の履歴は消えます。エージェントの記憶も消えます。**Issue と PR は消えません。** だから、そこを唯一の正本にします。

これは信頼の問題ではなく、置き場所の問題です。誰かが忘れっぽいから Issue を書くのではなく、**忘れることを前提にした置き場所を1つ決めておく**ということです。

## Issue に何を書くのか

必須は3つだけです（条文では [`L1-2`](02-issue-loop.md)）。様式の正本は [templates/issue-template.md](../templates/issue-template.md) にあります。

**1. 目的（Why）** — なぜやるのか。やらないと何が困るのか。

数日後の自分と、明日入ってくる別のエージェントのために書きます。「やる」と決めた理由が残っていないと、途中で判断が分かれたときに戻る場所がなくなります。

**2. 完了条件（Done when）** — どうなったら終わりなのか。

チェックボックスで書き、**機械か実機で判定できる形**にします。「ちゃんと動く」ではなく「テストが通る」「実機で表示される」と書きます。これが「できました」を検証可能にする唯一の方法です。この項目があるから、マージのときに1つずつ PASS / FAIL を突き合わせられます（[`L1-7`](02-issue-loop.md)）。

**3. 触るファイル / モジュールの予測** — どのファイルを触るつもりか。

これは自分のためではなく、**他の作業のため**の項目です。2つの作業が触るファイルの集合が交差しないと着手前に分かれば、並行して進められます。分からなければ、並行しません（[`L2-3`](01-milestone-loop.md) / [`L2-4`](01-milestone-loop.md)）。予測なので外れても構いません。着手時に確定版を宣言し直します。

## Issue が要らない場合

全部に Issue を立てるわけではありません。次は対象外です（[`L1-1`](02-issue-loop.md)）。

- typo の1行修正
- コードではないファイル（md / json / yaml など）
- git 管理外のスクラッチ
- 探索・読解・対話（何も変更しない作業）

迷ったら、こう考えてください。**数セッションにまたがりそうなら Issue を立てる。** その場で終わるなら要りません。

## AI と組むと、何が変わるか

Issue-first は AI のために生まれた考え方ではありません。ソフトウェア開発では以前から使われてきたやり方です。ただ、AI エージェントと組むと、3つの理由でその価値が跳ね上がります。

- **記憶がゼロから始まる** — 人間なら「そういえば先週」がありますが、エージェントにはありません。Issue が唯一の記憶になります
- **同時に何体も動く** — 誰が何を触っているかを宣言しないと、衝突は運任せになります
- **「できました」を自己申告する** — 検証しない完了報告を防ぐには、着手前に完了条件を書いておくしかありません

## よくある疑問

**小さい修正でも毎回 Issue を立てるんですか？**

いいえ。上の「Issue が要らない場合」のとおりです。判断の目安は、数セッションにまたがるかどうかです。

**Issue が増えすぎませんか？**

増えます。ただし増えて困るのは「開きっぱなしの Issue」であって、閉じた Issue は記録として役に立ちます。レーンの状態を5つの言葉（WIP / HOLD / MERGED / SUPERSEDED / ABANDONED）だけで表すのは、開いているものと終わったものを一目で分けるためです（[`L1-4`](02-issue-loop.md)）。

**1人で開発していても意味がありますか？**

エージェントを使うなら、あります。1人であっても、セッションをまたぐ瞬間に引き継ぎが発生するからです。逆に、1セッションで完結する作業しかしないなら、Issue-first の効果はほとんどありません。

**Issue を書く時間がもったいないのでは？**

書くのは3項目です。これを書かずに始めると、後から「何を確かめたんだっけ」「どこまでやったんだっけ」を再構成する時間がかかります。どちらが得かは作業の長さ次第で、短い作業ほど Issue は要りません。だから「要らない場合」を先に決めてあります。
