# L1 Issueループ — 1つの作業を完遂する層

各ルールに安定 rule ID（`L1-1`〜`L1-11`）を付す。要約側（[docs/04](04-adoption.md)）はこの ID を参照する。検証できない時の姿勢は [docs/05](05-fail-posture.md)。

## L1-1 Issue-first の原則

リポジトリ内のコード変更は **GitHub Issue 起点**。Issue のない実装は行わない（例外は typo 等の1行修正・非コードの md/json/yaml・git 管理外のスクラッチ）。

理由: Issue 本文 + PR diff が**セッション間・エージェント間の引き継ぎ SoT** になる。どのエージェントが途中から入っても、Issue を読めば続きができる状態を保つ。

## L1-2 Issue 本文の必須3点

[テンプレ](../templates/issue-template.md) を使う。

1. **目的 Why** — なぜやるのか。背景と、やらないと何が困るか
2. **完了条件 Done when** — チェックボックス形式。「テスト green」「実機確認」など機械判定・実機判定できる形で
3. **触るファイル / モジュール予測** — L2 の並行GO判定の入力。着手時に WIP コメントで確定版を再宣言する

## 実装 → レビュー → マージの流れ

```
Issue 起票 → WIP宣言（L0-1）→ worktree で実装 → テスト/lint green
→ クロスレビュー → 指摘対応 → PR（完了記録 = L1-7 を本文に）
→ merge → Issue close → 安定点で git tag
```

## L1-3 クロスレビューの原則

- **self-approve 禁止** — 実装した本人だけの承認で merge しない
- **merge を通すレビューは、実装者とモデルまたはエージェントが異なること**（例: Claude 実装 → GPT/GLM レビュー、Codex 実装 → Claude レビュー）。同一モデルでも**別エージェント**なら merge 有効。同一モデル・同一エージェントは、別セッションであっても merge には不十分 — 別セッションで足りるのは merge 以外のチェックポイントだけ
- Round-1 レビュアーを完走レビュアーとするのが既定。交代する場合は宣言し、交代レビュアーは**現候補の全体を再レビュー**する（部分レビューの継ぎ足しで merge しない）
- blocking 指摘が 0 になるまで implementer → reviewer のループを回す
- レビューの観点: 正しさ / 境界（スコープ外ファイルを触っていないか）/ テスト妥当性 / revert 可能性

## L1-4 レーン状態 — 閉じた5状態語彙

レーンの状態は担当 Issue へのラベル付きコメントで宣言する。**レーン状態の正本は Issue**（保留 PR は Issue を指す）:

`WIP / HOLD / MERGED / SUPERSEDED / ABANDONED`

- **WIP は明示的に宣言する状態であって、既定値ではない**
- `STUCK` は6番目の状態では**ない** — トリガー条件であり、唯一の合法な出口は有効な HOLD（または人間へのエスカレーション）
- 状態が欠落・未知・不正な形式のレーンは、**非アクティブ扱い（HOLD 相当の姿勢: 書き込みなし）で状態修復待ち**。GO 判定でこのレーンを「空き」として数えない — 宣言スコープと交差し得る作業は修復まで直列（[FP-1](05-fail-posture.md)）。不正な入力から有効な HOLD レコードを捏造しない（HOLD の必須フィールドは不正な入力からは作れない）— 次に触るエージェントの最初の義務は**状態の修復**であって書き込みではない（[FP-7](05-fail-posture.md)）
- **終了 / ブロッカー宣言は継続圧より優先**。同じ更新の中にブロッカーがあれば、その更新の完了主張は無効

## L1-5 HOLD の必須フィールド

HOLD は**再開可能・非終端**。有効なのは以下を全部備えるときだけ:

`owner / reason / review-by / lock disposition（ロックを review-by まで保持 or 解放）/ 残作業 or 後継`

- **ロックの扱いに無言な HOLD は無効** — 幽霊ロック / 二重書き込みのどちらの読みも衝突経路になるため
- review-by 超過は**可視のレビュー義務**を発生させる（週次 ops probe で再浮上）。自動解放・自動 ABANDONED はしない
- `retained until review-by` は「review-by で自動解放」では**ない** — review-by はレビュー義務が発生する日付であり、ロックは明示的な処置（HOLD 更新 / RELEASE / stale 化後の TAKEOVER 手続）まで保持されたまま

## L1-6 リトライは有限

リトライは有限回。使い切ったら**証拠付きの HOLD / ABANDONED** を宣言する — 使い切りが成功になることはない（継続を意図するなら HOLD、打ち切るなら ABANDONED。STUCK トリガー経由の出口は L1-4 どおり有効な HOLD または人間へのエスカレーション）。

> 脚注（契約本文外・調整可能なポリシー候補）: 「同一失敗2連続（同一レビュー指摘 or 同一 CI シグネチャ）⇒ STUCK」という具体的トリガーは単一レビュアー提案であり、本契約には含めない。既定値はメンテナ裁定またはリポごとの選択に委ねる。

## L1-7 完了証拠マージゲート

PR を merge してよいのは、以下を満たす**完了記録**（[テンプレ](../templates/issue-template.md)）が PR 本文にあるときだけ:

1. **Done when の全項目を `PASS` / `FAIL` / 理由付き `N/A` に対応付ける** — コマンドが「走った」ことは PASS ではない。必須項目の FAIL・理由なき N/A は merge をブロック
2. 各項目に**終端結果つきの永続的な証拠**（コマンド or 手動手順 + 観測結果 + 日付）。**インライン抜粋が正** — 記録単体で終端結果が読めること。CI や外部ログへの URL は便宜ポインタであり、リンクだけの証拠は不適合
3. **候補 commit SHA** を明記する — レビュー時点の PR head と一致していること（merge までに変わったら L1-8 の差し替え記録）
4. 宣言ファイル集合と `git diff --stat origin/main...<候補SHA>` の照合（diff にあって一覧にないファイルは blocking — [L0-6](03-git-protocol.md)）
5. 実装者とレビュアーの身元をリンクし、**モデルまたはエージェントが異なる**こと（L1-3）
6. **CI 状態を記載する** — 赤のまま merge しない。既知・無関係の赤の例外条件（唯一の例外）は [T-4](10-test-ci-baseline.md)

**証拠は主張より先に存在する。** ローカルにしか成功がない状態は完了ではない。

## L1-8 訂正は superseding record で

完了記録の訂正は、**完全な差し替え記録を新たに公開し、レビューを再オープン**する。黙った編集はしない。

## L1-9 上流異種レビュー — self-approve 禁止の上流拡張

- **サイズ L / H / Epic**（= [L2-1](01-milestone-loop.md) サイズ判別基準の重い側。アーキテクチャ変更・要件定義はここに含まれる）は、**実装着手前**に異種クロスレビュー（L1-10 の席・L1-11 の席数）を通す。サイズ定義の正本は L2-1 — ここに書き写さない。Epic でのタイミングは「EPIC Issue の起票後でも可・遅くとも最初の子 Issue の実装着手前」で1本（[E-6①](06-epic-lane.md) と同じ時計 — 「起票前」と「実装着手前」の2つの読みを併存させない）。最初の方向がブレると下流全部がブレるため、レビューは上流ほど厚くする
- 適用は重い側**のみ**: サイズ S / M の単発 Issue（bug fix・単機能）に上流レビューは課さない — 従来どおり実装レビュー（L1-3 / L1-11）だけ。ここを広げると per-Issue のレビュー待ちが復活し、速度目的（[docs/06](06-epic-lane.md)）と矛盾する
- 上流レビューの**実施が検証不能なら実装に着手しない**（fail-closed — 書き込み停止と同じ向き。記録は EPIC Issue からリンクする — [テンプレ](../templates/epic-template.md)のキックオフ節。単発の L / H では担当 Issue からリンクする）

## L1-10 レビュー席の異種・最上位原則

- レビュー席は**互いに異なるモデル**、かつ**実装 writer と異なるモデル**から選ぶ（「異種N席」＝ N席が相互に異種。同一モデルの別エージェントN個は異種N席ではない）
- **審査対象を設計・実装した者は席に数えない**（オーケストレーター含む。自分の設計を自分でレビューする席は L1-3 / FP-8 の趣旨に反する）。同一モデル・別エージェントの扱いは L1-3 のとおり merge の最低条件としては有効だが、L1-11 の席数カウントには入らない（例外は L1-11 の降格手続きのみ）
- 席には**その家で起動可能な最上位クラスのモデル**を当てる。執行方法: 各家はローカル設定（CLAUDE.md / AGENTS.md 等）に**レビュー席適格モデル名簿**を維持し、①名簿があること ②名簿外を席に据えないこと ③名簿の更新が可視であること、をハンドブックが要求する。どのモデルを名簿に載せるか（実名）はハンドブックに書かない — モデルは入れ替わるため、正本を PR で追いかけさせない
- レビュー記録には **requested / actual model** を必ず残す（監査可能性 — 証拠は主張より先に存在する）

## L1-11 席数スケール

本表の席数は**マージを通す実装レビュー**と**上流レビュー（L1-9）**に適用する（L1-3 は identity の最低条件であり、席の数はこの表が定める — 両者は矛盾しない）。Epic 内の子→epic ゲートも**子の重さ**で本表を引く（[E-6②](06-epic-lane.md)・高リスク領域を触る子は5席が優先）。

| 対象 | 席数 |
|---|---|
| S / M（局所・単機能） | 異種2席 |
| L / H（複数モジュール・境界変更・新機能） | 異種3席 |
| **高リスク領域**（定義は [docs/06 冒頭](06-epic-lane.md)・単一定義。サイズ判定より優先） | 異種5席 |
| サイズ L / H / Epic の**上流レビュー**（L1-9） | 実装着手前に L/H 体制（高リスク領域を含むなら5席） |

- 欠席は**別の異種席**で補充する
- 異種席が物理的に確保できない家（起動可能なモデル系統が席数未満）は**降格手続き**を使える: 同一モデル・別エージェントの席＋**オーナー（人間）の明示承認**＋レビュー記録への降格の明記。無承認の降格は席数未達と同じ
- 補充・降格でも未達なら **SEAT-WAIT** で停止する（レビュー起動前の待機状態。L1-4 のレーン状態 HOLD とは別語であり、L1-5 の必須5フィールドは適用しない — 週次 probe が HOLD として誤検知しないための区別）。SEAT-WAIT は担当 Issue へのコメントで可視化し、**owner / 不足席 / 再試行期日**の3点を書く（3点を欠く SEAT-WAIT は無効）。SEAT-WAIT コメントは [L0-3](03-git-protocol.md) の活動更新として数える — 席不足のレーンを stale → TAKEOVER しても席は増えないため、時計を進めるのではなく根本原因を可視化する
- 席数の数字の調整はハンドブックの PR でのみ行う（[L0-3](03-git-protocol.md) 72h と同じ扱い）

## 完了の定義

- テスト・lint が通っている（唯一の明文例外は [T-4](10-test-ci-baseline.md)）
- L1-7 の完了記録つき PR が merge され、Issue が close されている
- **オンラインリポが最新の正**になっている（ローカルにだけ成果がある状態で終わらない）
- 数セッションにまたがる場合、続きの入口（次にやること）が Issue コメントか handoff に残っている
