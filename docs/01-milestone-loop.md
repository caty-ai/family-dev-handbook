# L2 マイルストーンループ — 並行の可否を決める層

Issue ループ（L1）の**上位**に置く層。「何を作るか」を「誰がどこを触るか」に変換し、並行作業の可否をここで決めてから L1 に降ろす。
各ルールに安定 rule ID（`L2-1`〜`L2-6`）を付す。要約側（[docs/04](04-adoption.md)）はこの ID を参照する。

## なぜこの層が要るのか

分業が安全な条件はただ1つ — **触るファイル集合が交差しないことが着手前にわかる**こと。
worktree や Issue ロック（L0）は衝突が起きた時の被害を抑える装置であって、衝突そのものを防ぐのは「境界の事前合意」。この層を飛ばして並行すると、同じホットスポット（巨大ファイル）を触る2本が確実に衝突する。

## ループの手順

### L2-1 ゴール合意

- 要件を対話で固めてから着手する（deep-interview / 計画セッション等、各エージェントの手持ちの手法で）
- 設計を難しくしている要件は一度疑う（問いの立て方は [なぜシンプルに作るのか](why-simple-systems.md)）。消す・狭める判断は依頼者の合意の上で行い、合意なく Done when を薄めない。疑った上で受け入れる複雑さは、理由を Issue の Why に残す
- **重さ判定（サイズ判別）**: 仕事のサイズを **S / M / L / H / Epic** のいずれかに決めてから着手する（基準は下記）。サイズはレビュー席数（[L1-11](02-issue-loop.md)）・実装着手前の上流異種レビュー要否（[L1-9](02-issue-loop.md)）・Epic 入口（[E-1](06-epic-lane.md)）の入力になる
- **Epic** と判定した仕事は **EPIC Issue + 子 Issue 分解 + GitHub Milestone 紐付け**。運用（統合ブランチ・人間チェックポイント・砂時計レビュー）は [docs/06 Epic レーン](06-epic-lane.md)（E-1〜E-10）

#### サイズ判別基準

| サイズ | 定義 |
|---|---|
| **S** | 局所 — 1ファイル程度・既存挙動の小さな修正 |
| **M** | 単発の bug fix・既存機能内の単発変更 — 1モジュール内で完結し、境界を動かさない |
| **L** | 複数モジュールに触れる・モジュール境界の変更を含む |
| **H** | 新機能（ユーザー価値として新規に立つもの）・アーキテクチャ変更・セキュリティ・migration・顧客 / 対外に直結する変更 |
| **Epic** | 複数 Issue に分解される束（成立はオーナーのキックオフ承認 = [E-1](06-epic-lane.md)） |

判定は次の3軸で見る。**複数の軸に触れる混合ケースは、重い側の軸が勝つ**（例:「単機能だが対外に直結」= H、「局所だが migration」= H）:

1. **影響範囲** — 触るファイル / モジュールの数。モジュール境界を越える・動かすなら L 以上
2. **不可逆性** — migration・対外公開・削除など、戻しにくい操作を含むなら H
3. **期間・人数** — 数セッション / 複数エージェントをまたぐ可能性があるなら Epic 候補

補助の1軸として**高リスク領域**（正本は [docs/06](06-epic-lane.md) の単一定義・ここに書き写さない）がある。これは**サイズとは独立にレビュー席数を引き上げる軸**で、該当すれば席数がサイズより優先で増える（[L1-11](02-issue-loop.md)）。サイズ表の H と高リスク領域は別物として扱う（内容が重なる変更は両軸に該当し得る — サイズが基本の席数を決め、高リスク該当が上乗せを決める）。

- **終端規則: 迷ったら重い側**。軸で判定しきれない・情報が足りない時は、**S〜H の範囲で**1段重いサイズとして扱う。Epic への昇格はこの梯子では行わず、複数 Issue への分解が必要かどうか（軸3・[E-1](06-epic-lane.md)）でのみ決める

### L2-2 アーキ影響判定

着手前に必ず問う: 「**この作業はモジュール境界を動かすか？**」

- **動かさない** → そのまま Issue 分解へ
- **動かす**（モジュール分割、ディレクトリ再編、共有インターフェース変更など）→ **境界PRを1本だけ先行**させる
  - 境界PRが merge されるまで、そのリポの**新規並行着手は停止**（直列区間）
  - 境界PR自体は最小に保つ — 境界の変更と機能の変更を混ぜない
  - Epic 内では**契約凍結の第0号子 Issue** が境界PRに相当する（[E-2](06-epic-lane.md)）

### L2-3 Issue 分解 — 触るファイル予測の必須化

子 Issue を切る時、各 Issue 本文に以下を必ず書く（[テンプレ](../templates/issue-template.md)）:

- **目的 Why**
- **完了条件 Done when**
- **触るファイル / モジュール予測** ← 並行GO判定の入力になる。予測できない場合は「予測不能」と明記（= その Issue は並行不可）

### L2-4 並行GO判定

2つの Issue を同時に走らせてよいのは、**宣言ファイル集合が交差しない場合のみ**。

- 交差する → 直列で順番に
- 予測不能 → 直列で順番に、または先に調査 spike で予測可能にする
- **交差が検証できない**（宣言がない・不正な形式・`UNKNOWN`）→ 直列（fail-closed — [FP-1](05-fail-posture.md)）
- どうしても並行したい → **境界分離 Issue**（衝突部分を切り出すリファクタ）を先に1本通す

### L2-5 広域 Issue の隔離

全面リファクタ / デザイン全面刷新 / 一括フォーマット / 依存の一斉更新など、**リポの広範囲を触る Issue は単独実行**。走行中は同リポの並行を全停止する。

順序の定石: **通常機能の Issue を先に消化 → 広域 Issue は最後にまとめて単独で**。

### L2-6 ホットスポットへの投資

多責務が同居する巨大ファイル（例: 2,500行の View + ジェスチャー + エンジン呼び出し）は並行開発の最大の敵。

- 各リポの `ARCHITECTURE.md` に「**並行安全マップ**」を置き、モジュール境界とホットスポットを記録する（[テンプレ](../templates/architecture-parallel-map.md)）
- ホットスポットの分割リファクタを「**並行可能性への投資**」として独立 Issue で優先起票する — 分割後はそのエリアの並行が構造的に安全になる
