# R 却下ルーブリック — 何を受け入れ、何を断るかの層

L 層（L2 / L1 / L0）が「どう進めるか」、B 層が「どう頼むか」の契約であるのに対し、R 層は**何がマージされ、何が断られるか**という意図の契約を定める。使い方は2つ:

1. **作る側のために** — 貢献（エージェント発の提案・タスク・PR を含む）が的に向かって狙いを定められるように
2. **一次判定のために** — 人間の判断なしに閉じてよいのはいつか、そして同じくらい重要な「いつ閉じてはいけないか」のガイダンスとして

規範性は条ごとに異なる: **R-1 / R-4 / R-5 / R-6 は契約**、**R-2 / R-3 は受け入れ判断の基準リスト**であり、R-2 / R-3 を根拠とする却下の執行は常に R-1 の権限規律（価値判断はオーナー専決）を経由する。

各ルールに安定 rule ID（`R-1`〜`R-6`）を付し、箇条は ①②③… で参照する（[E-6](06-epic-lane.md)① と同形式）。要約側（[docs/04](04-adoption.md)）はこの ID を参照する。検証できない時の姿勢は [docs/05](05-fail-posture.md)。

出典: この章は NousResearch/hermes-agent の AGENTS.md 「Contribution Rubric」（MIT）の翻案である。

## R-1 自動却下の3理由 — 価値判断はオーナー専決

**適用対象は記録された提案（Issue・PR・記録として提出されたタスク提案）**。人間の判断なしにこれらを却下してよいのは、**機械的に白黒がつく3理由のみ**。各理由は成立条件と証拠を伴って初めて成立する:

1. **既に main にある**（implemented on main）— 該当の振る舞いが現在の main に存在することを、commit または行で指させること。「機能的に似ているものがある」は本理由に含まれない（それは価値判断 = オーナー専決）
2. **再現できない**（cannot reproduce）— **バグ報告に限る**。現在の main に対する再現試行の記録（コマンド / 手順・観測結果・日付）を残すこと。情報不足は却下理由ではない — 照会して保留する
3. **内容が存在しない**（incoherent）— 矛盾・空欄・スパム等、実質的な主張が読み取れない場合に限り、**1回の照会を経てなお読み取れない**ときのみ。読むのに手間がかかるだけの提案は該当しない

- 「要らない・方針と違う・スコープ外」等の**価値判断による却下はオーナー（人間）専決**。エージェントは推奨と根拠を添えて上げるところまで（R-2 / R-3 を根拠とする却下も同じ — 3理由には含まれない）
- **迷ったら閉じない** — 「閉じる」は権限行使であり、検証不能なら権限が縮む方向（開けたままオーナーへ）に倒す（[FP-7](05-fail-posture.md) の向き）。一次判定の仕事は、設計意図を読んで**正当な貢献を誤って閉じないこと**
- **記録**: レーンが立っていた提案（WIP 宣言済み）の終端は [L1-4](02-issue-loop.md) の5語彙による。**レーンが立つ前に却下される提案にはレーン語彙を使わず**、クローズ理由（3理由のどれか+上記の証拠、またはオーナー裁定へのリンク）だけを記録する
- **再オープンは非対称**: 3理由によるクローズは、新しい証拠が出たらオーナー承認なしで再オープンしてよい（開け直すのは権限が縮む方向）
- R-4 の4パターンに触れる提案は、3理由での自動クローズが**安全でない**典型 — 人間へ
- Epic 走行中の却下判断は、レーンを止めず**非同期でオーナーへ回す**（[E-3](06-epic-lane.md) の停止点を増やさない）

## R-2 歓迎する貢献 — 6箇条

1. **実際のバグを、クラス全体で直す** — 現在の main で症状を再現し、現れる行を指差し、報告された1箇所だけでなく兄弟の呼び出し経路まで直す（R-4 の合言葉と対）
2. **端は拡張・腰は保守** — 端（各製品・各家の機能）を広げる貢献は歓迎。抑制が向くのは腰（家族共有の基盤・全員が恒久コストを払う場所）だけ。「フットプリント最小」は腰への配線の話であって、製品が成長してよいかの話ではない
3. **宣言されたリファクタは diff が大きくても歓迎** — 「全行が依頼に遡れること」の検査は機能変更に適用するもので、リファクタと宣言された変更の依頼は抽出そのもの（ホットスポット分割 = [L2-6](01-milestone-loop.md) の投資）。**緩和されるのは diff の大きさに対する疑いだけである** — 宣言ファイル集合（[L0-2](03-git-protocol.md) default-deny）と [L1-7](02-issue-loop.md)④ の diff 照合はリファクタでも一切緩まない（リファクタは触るファイル予測を広く宣言して通すのであって、宣言を省いて通すのではない）。広域リファクタの単独実行（[L2-5](01-milestone-loop.md)）・マージ手順（[L0-7](03-git-protocol.md)）もそのまま適用される
4. **複製せず拡張** — 新しいモジュール・マネージャ・フックを足す前に、既存の道具が用を足さないか確認する（置き場所は R-5）
5. **テストは不変条件を主張する** — 「2つのデータがどう関係すべきか」を検査し、現在値（一覧・件数・バージョン直書き）を凍結する変更検出テストを書かない
6. **境界・伝播・I/O は実経路で検証する** — 解決チェーン・設定の伝播・権限境界・外部 I/O に触れる変更は、実際の経路を動かした E2E の証拠を出す。モックだけの green を完成にしない。**本号は証拠の選び方の指針であり、merge ゲートの要件の正本は [L1-7](02-issue-loop.md) のまま**（要件を増やさない）

## R-3 よくできていても断るもの — 7箇条

品質のバーではなく**構造の判断**として断るもの。よくできていても、断る理由が消えるわけではない。**本条を根拠とする却下は R-1 の3理由に含まれない — 執行は常にオーナー専決**であり、エージェントは該当の疑いを指摘して上げるところまで:

1. **投機的なインフラ** — 具体的な使い手のいないフック・コールバック・拡張ポイント。表明された実ユースケースがあるなら投機ではない（使い手が別リポでも可）
2. **秘密でない設定のための環境変数の追加** — 秘密の置き場（.env 等）は秘密専用。挙動設定（タイムアウト・閾値・フラグ・表示）は設定ファイルへ
3. **既存の道具で足りるのに新設される skill・hook・常駐システム** — R-5 のはしごを最小の段から検討した記録がない新設は断る
4. **全部読むべきものへの怠け読みの逃げ道** — エージェントが完全に読むべきコンテンツ（スキル・プロンプト・手順書）のローダにページ送り・抜粋オプションを付けない。1ページ目だけ読んで残りを飛ばすようになる
5. **守ったはずの機能を壊す「修正」** — 機能の目的を殺す緩和策は間違った緩和策。挙動を制限する前に元のコミットの意図を読む（`git log -p -S`）
6. **証明なしの配線・無断の非秘密テレメトリ** — E2E 証明なしで配線されるコード・実行時に一度も通らない分岐・オプトインのゲートなしの外向きテレメトリ / 識別子付与（**非秘密の利用情報を含む**）。秘密情報の外部送信は本号の対象ではなく **[E-5](06-epic-lane.md) および各家の秘密規律に従う — 本条は E-5 の閉じた禁止列挙の輪郭を変更しない**
7. **外部ツール・他人の製品のコアツリーへの抱え込み** — 保守負担が恒久的にこちらへかかる。wrapper・隔離された置き場（例: 退避用の隔離ディレクトリ・外部管理の別リポ — 例示は非規範）に置き、コアには入れない。これは結合と保守の判断であり、品質が高くてもクローズはクローズ

## R-4 前提検証 — バグと呼ぶ前に

合言葉: **「バグが現れる行を指させないなら、前提は未検証」**

よくできた変更が断られる最大の理由は品質ではなく、**間違った前提**の上に建っているか、**意図的な設計を欠陥扱い**していること。次の4パターンは両方向に働く — レビュー席には「どこを精査するか」を、一次判定には「閉じてはいけないのはいつか」を教える:

1. **意図的な設計であって、欠陥ではない** — 見落としに見える制限はしばしば意図的。直す前に「その隔離こそが設計では?」と問い、元のコミットの意図を読む
2. **前提が実際の動き方に照らして成立しない** — 言い分を受け入れる前に実コード・実行時の動きをトレースする。修正がどの行の挙動を変えるか示せないなら未検証
3. **不在が荷重を支えていた** — 「明らかに欠けている」ピースの追加が、その省略が守っていたものを壊すことがある
4. **やりすぎ・通り過ぎた方針の復活** — 合意済みのベースを超える拡張や、意図的に閉じた方向の蒸し返しは、動いていても断る。変更は合意された狭い部分に留め、残りはフォローアップとして提案する

通奏低音: **主張と意図の両方を、書く前・マージ前にコードベースへ照らして検証する**。確認済みの再現 + 行レベルの説明は、もっともらしい理屈にいつでも勝つ。意図に迷ったら、設計と喧嘩する修正を出すより尋ねる方が安い。

（実例は各家の事故記録で差し替えてよい — 本文の例示は非規範。レビューを委譲するときは、この4パターンを [B-4](07-delegation-brief.md) の「最悪の失敗形の名指し」の観点として前積みできる）

## R-5 置き場所のはしご — 恒久表面積は最小の段で

新しい能力を作る時、下の段ほど恒久的な表面積（全員が払い続けるコスト）が増える。**問題を正しく解ける、いちばん番号の小さい段を選ぶ**:

1. **既存コードの拡張** — 既にあるものの変種なら、新しい表面はゼロ
2. **スクリプト / skill** — シェルで表現できる操作。常駐しない・呼ばれた時だけ動く
3. **条件ゲート付き hook** — 前提条件が設定された時だけ現れる自動化
4. **既存リポへの機能追加** — 置き場所が既にあるなら、そこへ
5. **MCP サーバー・別リポへの分離** — 本当に独立した能力なら、コアの外で
6. **新リポ・新常駐システム** — 最終手段。**オーナー（人間）の承認が要る**。Epic 走行中に該当が生じた場合は **[E-3](06-epic-lane.md) の臨時チェックポイントとして停止**する（E-3 の表側には追記しない）

- 迷ったら上の段（表面積最小）へ。「下の段が楽だから」は理由にならない
- **段を選んだら、置く物の退場トリガーも同時に決める**（[LC-1](08-lifecycle.md) — はしごは置き場所を決め、LC-1 は出て行き方を決める。対で使う）
- **同種3つ目で共通受け口** — 同じカテゴリの統合が3つ集まったら、1本ずつ入れずに共通インターフェースを設計し、既存実装を最初のプロバイダとしてラップする。受け口の設計は境界変更なので [L2-2](01-milestone-loop.md) の境界PR先行に乗る

## R-6 方針は check で強制する

**破られては困る方針を「お願い」のままにしない。** 受け身のルール（.gitignore・文書・口約束）は「うっかり」しか止めない — 強制したい方針は、破られたら赤になる check に昇格させる。

- **昇格トリガー**: 同じ方針が2回破られたら、check 化を Issue で起票する。**破られの記録は Issue または各家の事故記録に残し、2件目の記録時に起票する**（計数が後から検証できる形にする）
- check は**実体で検知**する（ディレクトリ名や拡張子の綴りではなく中身・パターンの本質でマッチさせる — 綴り違いにすり抜けられた実例が出典にある）
- check の姿勢は既存条文と揃える: **マージを止めるゲートは fail-closed**（[FP-3](05-fail-posture.md) の向き）、**報告・合成・通知の配管は fail-open**（[FP-4](05-fail-posture.md)）。check はファイルを動かさない（[LC-5](08-lifecycle.md) — 検知して止めるだけ・自動修理や自動退場をしない）
- 承認系の check（人間のラベル等）は、**承認の実在を検証する** — 本文やラベルの存在だけで通さない（[FP-8](05-fail-posture.md) の向き）。承認の検証には限界がありうる（identity 共有環境等）— その場合、限界を check の説明に明記し、「検証済み」を装わない（[FP-5](05-fail-posture.md)）
- 型の正本は本リポの `templates/ci/`（#18 で整備）
