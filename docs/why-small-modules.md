# なぜモジュールを小さく切るのか — 分割は「並行可能性への投資」

> このページは条文ではありません。条文の本文は [docs/01](01-milestone-loop.md)〜[docs/06](06-epic-lane.md) にあります。
> ここに書いてあるのは、それらの条文が**前提にしている考え方**です。

## 並行できるかどうかは、着手する前に決まっている

このハンドブックの並行判定はシンプルです。**2つの作業が触るファイルの集合が交差しなければ、並行してよい**（[`L2-4`](01-milestone-loop.md)）。

ところが、たとえば2,500行の画面ファイルの中に、レイアウトも、ジェスチャー処理も、エンジンの呼び出しも同居していたらどうなるでしょうか。そのエリアで何をしようとしても、必ずそのファイルを触ります。**何をやっても交差するので、いつも直列になります。**

このとき問題なのは判定ではありません。**切り方が、判定を通せない形になっている**のです。

つまり「並行できるかどうか」は、やる気や段取りではなく、着手するずっと前に決まっています。**コードの形が、並行可能性の上限を決めています。**

## 分割は「整理」ではなく「投資」

ふつう、分割リファクタは「読みやすくする」「きれいにする」という品質の話として扱われ、機能開発より後回しにされます。

このハンドブックでは扱いが違います。多責務が同居した巨大ファイル（**ホットスポット**）の分割は、**並行可能性への投資**として、独立した Issue で優先的に起票します（[`L2-6`](01-milestone-loop.md)）。

投資と呼ぶのは、返ってくるものが3つあるからです。

**1. 並行できるようになる**

分割したあと、そのエリアを触る Issue 同士がお互いに交差しなくなります。**分割した瞬間から、そのエリアの並行が構造的に安全になります**（[`L2-6`](01-milestone-loop.md)）。1回の分割が、それ以降のすべての作業に効き続けます。

**2. エージェントが目の前の仕事に集中できる**

責務が1つだけのファイルなら、エージェントが読むのはその1つだけです。**読む量が減るほど注意が散らず、目の前の仕事だけに向かえます。** どのモデルを使っていても、見る範囲が狭いほうが最後まで走り切りやすくなります。

逆に、2,500行の中に3つの責務が同居していると、そのうち1つを直したいだけでも全部を読むことになります。関係のない2つの責務が、毎回コンテキストを埋めます。

> **メモ:** これは条文が定める要件ではなく、設計の意図です。どれだけ効くのかを測った数字は持っていません。

**3. ブロックのように、後から差し替えられる**

責務ごとに切ってあれば、壊れたときに壊れた1つだけを外して直せます。ブロックをつけ外しする感覚に近く、周りに手を入れずに済みます。

このハンドブックが merge レビューの観点に「**revert 可能性**」を入れているのも（[`L1-3`](02-issue-loop.md)）、[`L2-2`](01-milestone-loop.md) が「境界の変更と機能の変更を混ぜない」と言っているのも、同じ理由です。混ざっていると、片方だけを戻すことができなくなります。

だから分割は「後でやる整理」ではなく「先にやる投資」です。

## 「小さい」は行数ではなく、責務の数

小さいモジュールを行数の話だと思うと、判断を間違えます。見るのは**同居している責務の数**です。

300行でも3つの責務が同居していれば、3種類の Issue がそこで交差します。1,000行でも責務が1つなら、交差するのは同じ種類の Issue だけです。

だから並行安全マップ（[templates/architecture-parallel-map.md](../templates/architecture-parallel-map.md)）のホットスポット表には、行数の目安だけでなく「**同居している責務**」を書く欄があります。行数は目印であって、判断の材料ではありません。

## 境界を動かす時は、それだけをやる

モジュールの切り方を変える作業 — 境界を動かす作業 — は、他のすべての作業に影響します。だから扱いを分けます（[`L2-2`](01-milestone-loop.md)）。

- 境界を動かす PR は**1本だけ先に通す**
- それが merge されるまで、そのリポジトリの新規並行着手は停止する（直列区間）
- **境界PR自体は最小に保つ。境界の変更と機能の変更を混ぜない**

最後の1行が実務では効きます。境界の変更と機能の変更が1つの PR に混ざると、レビューする側は「この差分は境界の都合か、機能の都合か」を判別できなくなります。あとで問題が出ても、境界だけを戻すことができません。

## どこに書いておくのか

各リポジトリの `ARCHITECTURE.md` に「並行安全マップ」を置きます（[`L2-6`](01-milestone-loop.md)・テンプレートは [templates/architecture-parallel-map.md](../templates/architecture-parallel-map.md)）。書くのは2つの表です。

- **モジュール境界の表** — どのパスがどの責務を持つか
- **ホットスポットの表** — どのファイルが多責務で、どの Issue で分割する予定か

境界を動かす PR を merge したら、**同じ PR でこのマップも更新します**。マップが実態からずれた瞬間、並行GO 判定の材料が嘘になるからです。

## 自分で設計する必要はない

ここまで読んで「モジュール設計を自分でやらないといけないのか」と思われたかもしれません。そうではありません。

**このハンドブックをエージェントに渡しておけば、分割すべき場所は向こうから Issue として上がってきます。** 仕組みは3つです。

- **Issue を切るたびに、触るファイルを予測して書く**（[`L2-3`](01-milestone-loop.md)）。範囲が広すぎて予測できない作業は、その時点で並行不可として扱われます。どこが詰まっているのかが、作業のたびに表に出ます
- **巨大ファイルにぶつかったときの手順が決まっている**（[`L2-6`](01-milestone-loop.md)）。「分割 Issue を先に起票する」と書いてあるので、エージェントはその手順を取ります。毎回ゼロから判断しません
- **新しく作るときは1子 Issue = 1モジュール**（[`E-2`](06-epic-lane.md)）。最初から責務が混ざりにくくなります

ただし、**分割の作業そのものは発生します**。読み込ませれば勝手にコードが整うわけではありません。変わるのは、分割が「いつかやる整理」ではなく「並行したくなったときに必ず通る道」になることです。**後回しにされなくなる**、という言い方が正確です。

## このハンドブック自身の切り方

このリポジトリも同じ原則で作られています。

- **条文は層ごとに1ファイル** — L2 = [docs/01](01-milestone-loop.md)、L1 = [docs/02](02-issue-loop.md)、L0 = [docs/03](03-git-protocol.md)、失敗時姿勢 = [docs/05](05-fail-posture.md)、Epic = [docs/06](06-epic-lane.md)。いちばん長いものでも100行強です
- **条文と様式を混ぜない** — コメントの書式やテンプレートは [templates/](../templates/issue-template.md) に分けてあります
- **参照は安定 rule ID で行う** — ファイル同士は `L2-4` のような ID で指し合います。ファイルを動かしても参照が壊れません
- **同じ定義を2箇所に置かない** — 高リスク領域の定義は [docs/06](06-epic-lane.md) だけ、配布用の要約ブロックは [docs/04](04-adoption.md) だけです

最後の1つはとくに効きます。定義が2箇所にあると、片方だけ直った瞬間に、どちらが正しいのか誰にも分からなくなります。だから先に「正本は1箇所」と決めて、他は参照だけにします。README がロードマップを持たず Issue 一覧へ渡しているのも、同じ理由です。

## よくある疑問

**最初から完璧に切れないのですが。**

切れません。だから「投資」という言い方をしています。いまの切り方で交差してしまうなら、それを分割 Issue として起票し、順番に返していきます。着手前にすべてを整える必要はありません。

**小さく切りすぎるとどうなりますか？**

ファイル数が増え、1つの変更が複数ファイルに散ります。今度は「交差はしないが、あちこち触る」状態になり、レビューが追いにくくなります。判断の目安は責務の数なので、**責務が1つなら分けません**。

**既存の巨大ファイルはどうすればいいですか？**

いますぐ触らなくて構いません。並行安全マップのホットスポット表に記録しておき、そのエリアで並行したくなった時に、分割 Issue を先に通します。記録しておくこと自体が、次に判断する人への引き継ぎになります。

**そもそも1人で開発していても関係ありますか？**

あります。AI エージェントを2体走らせた時点で、それは並行開発です。加えて、責務が分かれているほど1つの Issue の「触るファイル予測」が書きやすくなるので、[Issue-first](why-issue-first.md) の3項目目のコストも下がります。
