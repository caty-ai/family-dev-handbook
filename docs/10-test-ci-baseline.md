# T テスト & CI 基準 — 正しさの証明を機械に蓄積する層

L 層（L2 / L1 / L0）が「作業をどう進めるか」、R 層が「何を受け入れるか」の契約であるのに対し、T 層は**リポジトリが自分の正しさをテストと CI で証明し続けるための最低限 — 初期整備・回帰テストの蓄積・委譲様式への焼き込み・赤のまま merge しない**を契約にする。各ルールに安定 rule ID（`T-1`〜`T-4`）を付し、条ごとに適用対象を〔 〕で明記する。要約側（[docs/04](04-adoption.md)）はこの ID を参照する。ゲートを check として強制する一般原則は [R-6](09-rejection-rubric.md)、検証できない時の姿勢は [docs/05](05-fail-posture.md)。

背景: 公開リポジトリの信頼性は「テストがあるか・CI が緑か」で外部から即座に判定される。merge の証拠ゲート（[L1-7](02-issue-loop.md)）と check 強制（[R-6](09-rejection-rubric.md)）の思想は既にあるが、**テストと CI の初期整備・蓄積を義務づける層が無かった**。テストの蓄積は CI の機能ではなく運用ルールでしか作れない。一方でこのプロトコルの実装は委譲ブリーフ（[B 層](07-delegation-brief.md)）を通るので、様式に焼き込めばほぼ自動で徹底できる — 人間チームより定着コストが低い。

## T-1 初期整備 — 枠を先に張る〔新規リポ = MUST / 既存リポ = 触った時〕

**新規リポジトリは作成時に、テストランナーと CI workflow（typecheck + test を gate）を整備する。テストが0本でも枠を先に張る。**

理由: 後からの導入は「テスト文化が無いリポ」を既成事実化する。枠さえあれば、以後のテストは T-2 / T-3 が自動的に積み上げる。CI の型は [templates/ci/](../templates/ci/README.md) を使ってよい（任意 — 自前の workflow でも条を満たす）。

既存リポジトリへの遡及は **opportunistic** — 次にコードを触るレーンで、その Issue に1行加えて T-1 を同時に整備する。棚卸し専用のレーンは立てない（使われていないリポに工数を先払いしない — [シンプル原則](why-simple-systems.md)）。

## T-2 回帰テスト既定〔サイズ M 以上のバグ修正〕

**サイズ M 以上（[L2-1](01-milestone-loop.md) の重さ判定）のバグ修正 PR は、当該バグの再現テスト（fix 前に赤・fix 後に緑）を同梱するのが既定。**

サイズ S（typo・局所1ファイル程度）は免除する。免除狙いの過小申告は、サイズ判定側の「迷ったら重い側」（L2-1）が押さえる。

同梱できない場合は、**列挙式の理由**を PR に明記する:

1. **環境依存** — 実機・実端末・特定 OS でしか再現しない
2. **外部サービス依存** — 外部 API・外部システムの実応答が必要
3. **再現コスト過大** — 構築コストが修正価値に見合わない（オーナーが認めた場合のみ）

列挙にするのは、自由記述の「書けない理由」が言い訳として無限に増殖するのを防ぐため。列挙に無い事情はオーナー判断で通す（その判断を PR に1行残す）。

## T-3 ブリーフ接続 — 蓄積を様式に焼き込む〔実質的委譲 = B-1 適用対象〕

**実装を伴う委譲ブリーフの「実装チェック（Self-verification）」に、「追加・変更したテストと、その実行結果」を標準項目として含める**（様式の正本: [templates/brief-template.md](../templates/brief-template.md)）。

テストを追加しなかった委譲は、納品報告に「追加なし + 理由」を含める（T-2 の列挙式に準じる）。

理由: テストの蓄積は、委譲の様式に焼き込んだ時だけ自動化される。委譲先は fresh context なので、ブリーフに無い期待は存在しないのと同じ（[B-4](07-delegation-brief.md) と同じ向き）。

## T-4 fail-closed merge — 赤のまま merge しない〔全リポ〕

**CI が赤のままの merge を禁止する。**

例外は1つだけ: **既知かつ当該 PR と無関係な赤**（例: main 側の既存バグによる赤）は、該当 Issue への参照を完了記録（[L1-7](02-issue-loop.md)）に添えることで merge できる。判断は**オーナー専決**。

「無関係」の主張には Issue 参照が**必須** — 参照できる Issue が無いなら、先に立てる。参照の無い赤は例外にならない（fail-open は「通過」を意味しない — [docs/05](05-fail-posture.md)）。

## 付録（非規範） — 推奨ランナー早見表

条文が求めるのは「ランナー + CI を整備する」まで。ツールの選定は実装者の裁量で、この表は**非規範の参考**である。表の更新は条文改訂に数えない。

| 言語 / ランタイム | 推奨ランナー | 補足 |
|---|---|---|
| TypeScript / JavaScript (Node) | vitest | 標準ライブラリで足りるなら `node:test` でも可 |
| Python | pytest | — |
| Shell | bats-core | — |
| Go | `go test` | 言語標準 |
| Rust | `cargo test` | 言語標準 |
| Swift / iOS | XCTest（`xcodebuild test`） | — |
| CI 実行環境 | GitHub Actions | リポジトリが GitHub にある場合の既定 |
