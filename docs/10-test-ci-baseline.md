# T テスト & CI 基準 — 正しさの証明を機械に蓄積する層

L 層（L2 / L1 / L0）が「作業をどう進めるか」、R 層が「何を受け入れるか」の契約であるのに対し、T 層は**リポジトリが自分の正しさをテストと CI で証明し続けるための最低限 — 初期整備・回帰テストの蓄積・委譲様式への焼き込み・赤のまま merge しない・出荷をタグで終える・テスト出力契約・バッジと数字の正直さ**を契約にする。各ルールに安定 rule ID（`T-1`〜`T-7`）を付し、条ごとに適用対象を〔 〕で明記する。要約側（[docs/04](04-adoption.md)）はこの ID を参照する。ゲートを check として強制する一般原則は [R-6](09-rejection-rubric.md)、検証できない時の姿勢は [docs/05](05-fail-posture.md)。

背景: 公開リポジトリの信頼性は「テストがあるか・CI が緑か」で外部から即座に判定される。merge の証拠ゲート（[L1-7](02-issue-loop.md)）と check 強制（[R-6](09-rejection-rubric.md)）の思想は既にあるが、**テストと CI の初期整備・蓄積を義務づける層が無かった**。テストの蓄積は CI の機能ではなく運用ルールでしか作れない。一方でこのプロトコルの実装は委譲ブリーフ（[B 層](07-delegation-brief.md)）を通るので、様式に焼き込めば徹底できる。

## T-1 初期整備 — 枠を先に張る〔コードを含む新規リポ = MUST / 既存リポ = 次にコードを触るレーン / 非コードリポ = 理由付き N/A〕

**コードを含む新規リポジトリは作成時に、テストランナーと CI workflow を整備する。gate の必須は test で、型検査を持つ言語では typecheck も同じ gate に含める。テストが0本でも枠を先に張る。**

理由: 後からの導入は「テスト文化が無いリポ」を既成事実化する。枠さえあれば、以後のテストは T-2 / T-3 が自動的に積み上げる。CI の型は [templates/ci/](../templates/ci/README.md) が既定（自前の workflow でも条を満たす）。整備した CI は required status checks に登録して機械確認する（templates/ci の展開手順5-6。branch protection を張れない環境では運用で守る）。

既存リポジトリへの遡及は **opportunistic** — 次にコードを触るレーンで、その Issue に1行加えて T-1 を同時に整備する。棚卸し専用のレーンは立てない（使われていないリポに工数を先払いしない — [シンプル原則](why-simple-systems.md)）。

文書・素材・設定だけの**非コードリポは理由付き N/A**（[L1-7](02-issue-loop.md) と同じ語彙）— 判断を作成時の Issue に1行残す。中身の無いダミーテストで枠を埋めない（「対象0件で緑」を自作しない — [templates/ci/](../templates/ci/README.md) の落とし穴）。

## T-2 回帰テスト既定〔サイズ M / L / H のバグ修正。Epic 内の子 Issue は子の重さで判定〕

**サイズ M / L / H（[L2-1](01-milestone-loop.md) の重さ判定。Epic 内の子 Issue は [E-6](06-epic-lane.md) と同じく子の重さで引く）のバグ修正 PR は、当該バグの再現テスト（fix 前に赤・fix 後に緑）を同梱するのが既定。**

サイズ S（typo・局所1ファイル程度）は免除する。免除狙いの過小申告は、サイズ判定側の「迷ったら重い側」（L2-1）が押さえる。機能追加のテスト義務は本条の対象外 — [T-3](#t-3) と各 Issue の Done when が受け持つ。

同梱できない場合の理由は**2段構成**で書く:

1. **既定の3類型**（閉じた列挙 — 機械判定できる）:
   - **環境依存** — 実機・実端末・特定 OS でしか再現しない
   - **外部サービス依存** — 外部 API・外部システムの実応答が必要
   - **再現コスト過大** — 構築コストが修正価値に見合わない（オーナーが認めた場合のみ）
2. **3類型に当たらない事情はオーナー専決** — 専決の事実と理由を PR に1行残す。自由記述の理由はオーナー専決の場合に限る

列挙にするのは、自由記述の「書けない理由」が言い訳として無限に増殖するのを防ぐため。

## T-3 ブリーフ接続 — 蓄積を様式に焼き込む〔コード変更を含む委譲 = B-1 適用対象のうちリポジトリのコードを変更するもの〕

**コード変更を含む委譲ブリーフの「実装チェック（Self-verification）」に、「追加・変更したテストと、その実行結果」を標準項目として含める**（様式の正本: [templates/brief-template.md](../templates/brief-template.md)）。

テストを追加しなかった委譲は、納品報告に「追加なし + 理由」を含める。理由は**閉じた列挙**で書く:

1. **T-2 の免除に該当**（サイズ S） — その旨の1行で足りる
2. **変更にテスト対象がない**（設定・宣言のみ等）
3. **既存テストが当該変更を担保している** — そのテストを指せること
4. **T-2 の3類型のいずれか**（環境依存 / 外部サービス依存 / 再現コスト過大 = オーナー承認）
5. **T-2 第2段のオーナー専決に該当** — その専決記録を指せること

理由: テストの蓄積は、委譲の様式に焼き込んだ時だけ自動化される。委譲先は fresh context なので、ブリーフに無い期待は存在しないのと同じ（[B-4](07-delegation-brief.md) と同じ向き）。

## T-4 fail-closed merge — 赤のまま merge しない〔全リポ = MUST〕

**CI が赤のままの merge を禁止する。** 本条は [docs/02](02-issue-loop.md)「完了の定義」の「テスト・lint が通っている」に対する**唯一の明文例外**を定め、CI 状態は完了記録（L1-7）に記載する。

例外は1つだけ: **既知かつ当該 PR と無関係な赤**（例: main 側の既存バグによる赤）。成立条件は**すべて必須**:

1. **無関係の立証** — base（当該 PR の変更を含まない状態）で同一の赤が再現する記録を完了記録にインラインで添える（主張ではなく証拠 — L1-7②）
2. **赤の identity の束縛** — 失敗した check 名 + workflow run 識別子 + 観測日付を候補 SHA と対応づけて書く
3. **該当 Issue への参照** — 参照できる Issue が無いなら先に立てる。Issue には [LC-1](08-lifecycle.md) の退場トリガー（期限 or 完了条件）を必ず付け、トリガー失効後はこの例外も失効する
4. **オーナー専決の実在検証** — オーナー本人のアカウントによる PR コメント等、**第三者が実在を確認できる形**で残す。完了記録本文の記述だけでは例外は成立しない（[FP-8](05-fail-posture.md) / [R-6](09-rejection-rubric.md)）

境界の明文化:

- **間欠的な赤（flaky）は「既知かつ無関係」に含めない** — 含めたい場合は上記4条件に加えて、その都度オーナーが専決し記録する
- **CI が無い状態を green と書いてはならない** — CI 未整備のリポでコードを触るレーンは、同レーンで T-1 を満たすまで merge しない（緊急修正等で間に合わない場合はオーナー専決で猶予でき、T-1 整備の Issue を LC-1 退場トリガー付きで残す。この専決も条件4と同じ、実在を検証できる形で残す）
- **`CI: N/A` は、CI が当該変更を検査しない場合に限る**（理由 = 検査対象外である根拠を書く）。CI が走る変更は、非コードでも N/A にしない
- required status checks が張られたリポでは、例外の行使を **required の解除で行わない** — オーナーの明示操作として記録する

参照の無い赤・検証できない例外は例外にならない（fail-open は「通過」を意味しない — [docs/05](05-fail-posture.md)）。

## T-5 リリース既定 — 出荷をタグで終える〔出荷相当の変更を含む merge = MUST / それ以外 = 理由付き N/A〕

**すべての完了記録（[L1-7](02-issue-loop.md)）に release 欄を置く。** 値は次の3つの閉じた語彙のいずれかで、**出荷相当の変更**（利用者が動かす挙動・公開 API・配布物・利用者が従う規範が変わる merge）を main に入れるレーンは `N/A` を選べない。**判定に迷う merge は出荷相当として扱う**（[L2-1](01-milestone-loop.md)「迷ったら重い側」と同じ向き — 迷いを軽い側（N/A）に逃がさない）:

1. **`release: vX.Y.Z`** — この merge の安定点としてタグを切る宣言。タグは **annotated + SemVer** 必須で、**当該 merge が main に残したコミット**（squash / rebase merge なら main 上の新 SHA）に切る。記録時点でタグは未作成 — 欄に書くのは宣言であり、**タグを切って MERGED コメント（[L1-4 終端](../templates/issue-template.md)）に tag URL を載せるまで、レーンは MERGED を宣言できない**。この tag URL 義務は **GitHub Releases 上の Release 実在まで含めて履行**とする（素のタグでも `/releases/tag/<名前>` の URL は 200 を返す — URL の存在は Release の存在を意味しない）。release-sync キャリアー（[templates/ci/](../templates/ci/README.md)）を持つリポでは通常タグ push の **green run** で満たされるが、履行の確認はレーンの義務のまま — **run の不発・赤・キャリアー不在は履行を意味しない**。未履行のレーンは**終端しないまま WIP として残る**ため [L0-3](03-git-protocol.md) の stale 時計に乗り、次のレーンが来ないリポでも切り忘れが可視のまま残る（tag URL または Release 実在を欠く MERGED は**不正形式**であり終端は成立しない = [L1-4](02-issue-loop.md) の非アクティブ扱い）。この履行報告の追記は宣言の履行であって [L1-8](02-issue-loop.md) の訂正には当たらない。タグ名は**宣言した識別子と同名が原則** — レビュー後にスコープが動いて版が変わった場合に**限り**別名で切ってよく、その差異と理由を MERGED コメントに1行書く（黙って別の版を切らない）。宣言そのものを `deferred` へ変える場合は L1-8 の差し替え記録による（黙った書き換えはしない）。レーン自身にタグを切る権限が無い運用では、owner をタグ権限者にした **HOLD**（[L1-5](02-issue-loop.md) の5フィールド）が合法な出口
2. **`release: deferred`** — 今は切らない宣言。**理由 + 退場トリガー（期限 or 完了条件 = [LC-1](08-lifecycle.md)）付きの Issue への参照**を併記する — 参照できる Issue が無いなら先に立てる（**T-4**③と同型。merge 済み PR 本文は誰の視界にも戻らないため、再浮上する面 = Issue に置く）。Issue 参照 or トリガーを欠く deferred は無効（= 欄なしと同じ blocking）。**トリガーが失効した deferred は「切らない特権」を失う** — 当該レーンの MERGED は有効なままで、**次の出荷相当の merge は `deferred` を選べない（`vX.Y.Z` 必須）**。失効それ自体は次の完了記録を止めない（止めると、宣言済みの識別子も対象コミットも持たない未履行を解除する手段が無くなる — **T-4**③が特権の失効にとどめているのと同じ理由）。期限を過ぎた deferred の可視化は参照先の Issue が担う。deferred は**後続の出荷相当 merge が `vX.Y.Z` を履行した時点で解消**し、参照先 Issue を close する（残件があれば新しいトリガーで再宣言する）
3. **`release: N/A`** — 出荷相当でない merge に限る。理由は**閉じた列挙**で書く: ①利用者が従う規範を含まない docs のみ ②挙動・公開 API・配布物のいずれも変えない内部整理 ③CI・開発環境の配線のみ ④main 未到達の中間 merge（Epic の子→epic ゲート = [E-6](06-epic-lane.md)②）。**類型外はオーナー専決** — 専決の事実と理由を1行残す（**T-2** と同型）。理由の無い N/A は無効（= 欄なしと同じ blocking）。規範を配るリポ（本ハンドブック等）では docs の変更こそ出荷相当 — 「docs-only」を N/A の口実にしない

**欄そのものが無い・値が空欄・未編集のプレースホルダ・3語彙以外の値は、いずれも未記入扱いとして blocking**（**T-4** の CI 欄と同じ強度）。「忘れないようにする」ではなく「忘れると完了記録が通らない」形にする — T 層の思想（様式に焼き込めば徹底できる）の適用であり、CI は T-1〜T-4 で層になったのにリリースだけ層が無かった穴を塞ぐ。

タグの中身と署名:

- リリースノート（タグメッセージ or Releases）に**検証可能な証拠へのポインタを1つ以上**引用する（CI run・完了記録つき PR 等）— 検証できない数字を置かない原則（[R 層](09-rejection-rubric.md)）との整合。完了記録本体の証拠規律（[L1-7](02-issue-loop.md)②「リンクだけの証拠は不適合」）とは別文脈 — 記録はインラインが正・タグはポインタで足りる
- **署名検証機構を持つリポ（updater 等・タグ署名を機械が検証するもの）は署名タグ必須・鍵は per-repo**。署名必須リポでは MERGED の履行報告に署名の有無を1語含める（記録面から署名の欠落が見えるように）。それ以外は annotated で足り、署名は SHOULD
- バージョンの上げ幅（MAJOR / MINOR / PATCH）は SemVer の一般則に従い、本条は縛らない

境界の明文化:

- **deferred の乱用防止** — 同一リポで出荷相当の merge の deferred が2回続いたら、3回目の出荷相当の merge では deferred を選べない（タグを切る）。連続は**出荷相当の merge の列**で数え（N/A の merge は列に入らない）、**`vX.Y.Z` の履行でリセット**する。計数を後から検証できるように、**すべての完了記録**に同一リポの直前の出荷相当 merge の release 値と履行状態を1行併記する（`previous release` 欄）。回数は直前レーンの `previous release` を**1段たどれば確定する** — 直前が deferred で、その直前も deferred なら今回は `vX.Y.Z` 必須（[R-6](09-rejection-rubric.md)「計数が後から検証できる形にする」と同じ向きのエスカレーション）
- **履行の配線** — 完了記録は自分の release 欄に加えて、**同一リポの直前の出荷相当 merge の release 宣言が履行済みであること**を確認する（[L1-7](02-issue-loop.md)⑦）。**「履行済み」の判定は次で閉じる**: `vX.Y.Z` = タグが切られ MERGED に URL があり Release が実在する（**タグ・URL・Release 実在のいずれを欠いても未履行 = blocking**）/ `deferred` = トリガーが生きている間は履行待ちであり阻害しない・失効しても blocking にはせず上記2のとおり次の選択肢を狭める / `N/A` = 出荷相当の列に入らないため対象外。release 欄は**タグ運用の代替ではない** — 欄は判断の記録であり、履行されていない `vX.Y.Z` 宣言は MERGED 不能（上記1）と次レーン blocking の両面で塞ぐ
- **適用強度は全リポ一律** — 出荷相当が無いリポでは全 merge が自然に N/A になるため、私有スクラッチに実質負荷はない。公開/私有で強度を変える一般論は別途の棚卸しで扱い、結論が出たら本条の〔 〕を追随させる
- **Epic の子→epic ゲート（[E-6](06-epic-lane.md)②）はタグ義務の対象外** — 欄そのものは全記録と同じく必須で、値は上記3の類型④（`N/A（epic 統合前）`）。タグを求めるのは epic→main の統合 merge（E-6③ フル L1-7）
- 過去の未タグ分への遡及は本条の対象外（本条は「これからの merge」に効く。過去分は各リポのオーナー判断）
- record-vs-reality の PR-side check と scheduled drift sweep は [Issue #106](https://github.com/caty-ai/family-dev-handbook/issues/106) で追う（LC-1 の退場トリガー付き follow-up）

## T-6 テスト出力契約 — 実行の事実を機械が読める1行にする〔コードを含む新規リポ = MUST / 既存リポ = 次にコード・テスト・CI test job のいずれかを触るレーンで同一 Issue 内に整備（T-1 と同じ opportunistic）/ ランナーを持たない非コードリポ = 理由付き N/A〕

**テストランナーは、機械が「何が走り・何が走らず・なぜか」を判定できる出力契約を満たす。** 成立条件は5点:

1. **サマリ行（契約の本体）** — ランナーは出力に次の1行を出す。書式の正本はこの正規表現そのもの:

   ```
   suites: declared=([0-9]+) executed=([0-9]+) skipped=([0-9]+)
   ```

   意味の定義: `declared` = 登録されたスイート総数 / `executed` = PASS または FAIL まで実走した数 / `skipped` = SKIP を正直に申告した数。**不変条件 `declared = executed + skipped`**。破れは欠け落ち（silent drop）= 赤。数値はランナーが動的に集計する — **固定値の埋め込み（echo 等での定数出力）は本条違反**（機械は導出を検証できないため、導入レビューの検査項目とする）。行は出力中に最低1回・複数回出た場合は**最後の一致が正**。スイートを declared から外す（登録解除する）判断は、それを行うレーンの Issue に1行記録する — 記録の無い登録解除は欠け落ちと同じ扱い
2. **結果語彙** — **家族が書いたランナー・ラッパーの結果表示**は `PASS` / `FAIL` / `SKIP` の3語彙で出す。pytest / unittest / vitest 等**フレームワーク固有の素の出力はこの制約の対象外**（機械のゲートが読むのはサマリ行と exit code であり、フレームワーク出力はそのまま流してよい）
3. **exit code の閉集合** — `0` = FAIL なし / `1` = FAIL あり / `2` = 使い方・入力エラー / `127` = **必須依存の欠落**（プリフライトで検知し、stderr に `missing-dep: <名前>` の形で原因を名指ししてから落ちる — 依存欠落をテスト失敗や入力エラーとして誤報しない）。任意環境の欠落（実機なし等）は 127 ではなく **SKIP**（サマリ行の skipped に計上）
4. **異常終了でもサマリを出す** — ランナーが途中で死んでもサマリ行が出る構造にする（bash なら `trap finish EXIT` — 非規範の例示。Python の atexit・Makefile の合成等、同等機構は全て可）。サマリの欠落 = 判定不能 = 赤（[FP-6](05-fail-posture.md)）— ただしこの赤が実際に発火するのは下記5の配線後
5. **CI 照合の配線（採用の完了条件）** — 本条の「整備済み」は、CI 側の照合ゲート（[templates/ci/](../templates/ci/README.md) の test-lint。reusable の `require_suite_reconciliation: true`）が**有効になった時点**で成立する。サマリ行を出すだけ・条文を引用するだけでは整備済みを名乗れない（「置いただけ」= [FP-5](05-fail-posture.md)）。適用範囲外のリポはその旨を Issue に明示の N/A で残す — 沈黙は N/A にならない。skipped 形（3値サマリ）での配線は、照合ゲート側の skipped 対応（#80 delta）が main に入った後に行う — 順序が逆だと正直な SKIP が赤になる

**SKIP 率上限** — `skipped × 5 > declared`（= 20% 超・declared > 0）は赤。上限を変えるリポは、**値の正本を CI caller の入力（機械が読む場所）に置き**、変更の根拠を PR 1行 or [LC-1](08-lifecycle.md) トリガー付き Issue で記録する（[LC-3](08-lifecycle.md) と同じ「数値はローカル設定・記録必須」型）。記録の無い変更は無効 = 既定 20% で判定する。この式は declared ≤ 4 のリポで「SKIP 0 が既定」になる — 意図的である（小さいリポほど全部走らせられる。恒常 SKIP が要るなら上限値を宣言して変える）。SKIP は「環境が無い」の正直な申告であって恒常的な逃げ道ではない — 上限超過の赤は「環境を直すか、対象から外す判断を記録する」への催促

理由: テストの「実行された」は自己申告になりやすい。declared / executed / skipped の3値と不変条件は、「走ったことにする」経路（スイートの黙った脱落・SKIP の executed への混入・登録解除による分母操作・依存欠落の誤報）を1行の機械検査に還元する。書式を正規表現で固定するのは、CI 側の照合（W0-3 reusable test-lint）が全リポ共通の1実装で済むようにするため。

境界の明文化:

- 本条は**出力契約**であり、テストの中身・粒度・フレームワーク選定は縛らない（推奨ランナーは付録参照）
- スイート単位で足りる（テストケース単位まで求めない — 粒度はリポの裁量。スイート内 SKIP の可視化はスイート分割で表現する）
- テスト0本の新規リポ（T-1 の枠だけ状態）は、サマリ行を出さない（配線前なので赤にならない）か `declared=0 executed=0 skipped=0` を出す（executed=0 で赤 = 「対象0件で緑」を自作しない側に倒れる）— どちらでもよいが後者が推奨
- 本ハンドブック自身のランナーは本条の**最初の適用対象**（条文を出すレーンが自リポの make test を契約準拠にしてから merge する — パイロット原則）

## T-7 バッジと数字の正直さ — 緑は機械が塗った色だけ〔README を持つ公開リポ = MUST / それ以外のリポ = 数字・バッジを置くなら同じ規律（置かない私有スクラッチは自然に N/A）〕

**README・docs に置く「検証済みらしさ」の表示は、機械の検査結果に接続されたものに限る。** 成立条件は3点:

1. **CI 状態の明示（無バッジで「無検査」を隠さない）** — README を持つ公開リポは、CI の状態を次の**どちらか**で必ず表示する: ①**T-1 のテストゲートを実行する workflow** の live バッジ（GitHub Actions の badge.svg またはその workflow を指す同等の live エンドポイント。**テストを走らせない別 workflow のバッジは緑でも本条を満たさない**）②CI 未整備なら `CI: not yet`（灰）の静的バッジ。表示しない・別 workflow の緑で代用する、はどちらも違反
2. **色の閉集合** — 静的バッジに使ってよい色は **`lightgrey` / `blue`（言語・ライセンス等の事実表示系を含む）のみ**（閉じた列挙）。`green` / `brightgreen` / `success` / `passing` 系、および同等の緑系 hex 指定は静的バッジに使えない（検査は綴りでなく実体で — [R-6](09-rejection-rubric.md)）。緑を名乗れるのは機械が塗った live バッジだけ
3. **実測数字と Project status 節** — 実測と読める数字（テスト数・カバレッジ・性能値）を README / docs に書く場合は、**その実測の run URL と実測日**を添える。添えられない数字は書かない（検証できない数字を置かない — [R 層](09-rejection-rubric.md)）。当該 workflow のより新しい run の**実測値と異なる**数字は stale — 更新するか消す（値が変わっていない限り、run が進むだけでは stale にしない）。設計値・目標値は「目標」と明記すれば書けるが、実測を装う表示（run URL の無い「passed」等）にはできない。README に状態節を置く場合の標準形は次のとおり（**この様式が正本** — 外部リポを参照モデルにしない):

   ```markdown
   ## Project status

   [live バッジ（T-1 テスト workflow の badge.svg）または CI: not yet（灰）]

   - CI: <test-lint ゲートの有無と接続先 workflow 名>
   - 検証済み環境: <実測した OS / ランタイム>
   - maturity: <stable / beta / reference 等>
   - 既知の制約: <列挙。無ければ「なし」と明示>
   ```

理由: 外部は「バッジが緑か」でリポの信頼性を即断する。手書きの緑は機械の緑と見分けが付かず、1個の手書き緑が**家族全リポの緑の証拠能力を毀損する**。逆に、バッジを置かないことで「無検査」を隠すのは同じ嘘の裏面（実測: 手書き緑9個と、CI 無しの無表示リポの併存）。表示を機械接続に限定し、緑 = 検査が走った / 灰 = 検査が無い、を全リポで同じ意味にする。

境界の明文化:

- 対象は「検査結果を装い得る表示」— 事実表示系バッジ（言語・ライセンス・バージョン。blue 系）は自由
- **数字を書かない自由は常にある**（本条は「書くなら正直に」+「CI 状態だけは公開リポの義務」）
- README を持たない・公開もしない私有スクラッチは自然に N/A。**公開しているのに README が無い**リポは、README を整備するレーン（B8 等）で本条の適用対象に入る — README 不在は本条からの恒久免除にならない
- 本条の check 化（静的緑バッジの検知・stale 数字の検知等）は [R-6](09-rejection-rubric.md) に従い Issue で追う
